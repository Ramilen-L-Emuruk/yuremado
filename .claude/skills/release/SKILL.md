# リリース

`main` を書き換える唯一の手続き。複数セッションが並行して作業するため、**main を触る主体を常に 1 つに限る**ことでリリース順の調整を不要にしている。

## どのセッションで実行するか

**ワークツリー内にいる場合は、まず `ExitWorktree(action: "keep")` で抜ける**（「着手前チェック」#1）。実装セッションは必ずワークツリー内で終わるため、同じセッションから続ける場合はこの移動が必須になる。

| 状況 | 目安 |
|---|---|
| 出す候補が自分の 1 本だけ | 実装したセッションで続けてよい |
| リリース待ちが複数溜まっている | リリース専用のセッションを立てた方が、実装の文脈と判断を混同しにくい |

これは**実務上の使い分けであって安全装置ではない。** 衝突を防ぐのはセッションを分けたかどうかではなく、着手前チェック #2 と、手順 6 の push 直前の再確認である。候補の本数は手順 1 で分かるため、起動前に判定しておく必要はない。

## 使用タイミング

**使う**: ユーザーがリリースを指示したとき、またはリリース待ちの監視を頼まれたとき。

**使わない**:
- 実装が終わっただけのとき（**ユーザーの指示なしに自動で始めない**。実装セッションは `ready/` へ改名した時点で終わる）
- 他にリリース進行中のセッションがあるとき

## 起動時の動作

1. 下記「着手前チェック」を行う
2. `ready/*` の有無で分岐する

```bash
git branch --list 'ready/*' --no-merged main
```

| 結果 | 動作 |
|---|---|
| 1 本以上ある | 「手順」へ進む |
| 無い | 「リリースロック」の**「離れるとき」を通ってから**ユーザーに伝え、**「監視モード」に入るか確認する**。監視が不要ならここで終了。**監視は数時間〜数日に及ぶ。ロックを持ったまま入ると、その間ずっと他セッションの着手を止める** |

## 着手前チェック

1 つでも満たさなければ**中断してユーザーに報告する**。押し通さない。

| # | 確認 | 満たさない場合 |
|---|---|---|
| 1 | `git branch --show-current` が `main` を返す | ワークツリー内にいる。`ExitWorktree(action: "keep")` で抜けてからやり直す |
| 2 | `.claude/release.lock` が無い、**自分自身のロックである**、または中身が失効している | 下記「リリースロック」へ。並行すると同じ版番号・同じタグを採番して push が衝突する。**中断するなら「リリースロック」の「離れるとき」を通る**（他人のロックなら何も消えない） |
| 3 | `git status --porcelain` が空（作業ツリーがクリーン） | 未コミットの変更をマージに巻き込まないよう、内容を確認してユーザーの判断を仰ぐ。**中断するなら「リリースロック」の「離れるとき」を通る** |
| 4 | `git fetch` 後、`git status -sb` でローカル `main` が `origin/main` と**完全に一致**（ahead 0 / behind 0） | 「トラブルシューティング」の**origin と乖離している場合**へ。`git fetch` 自体が失敗したら原因を報告して判断を仰ぐ。**解消せず終えるなら「リリースロック」の「離れるとき」を通る** |

> **なぜ実行場所を確認するのか**: ワークツリー内で `git merge` を実行すると、main ではなく**そのワークツリーのブランチに黙ってマージされる**。エラーが出ないので気づけない。なお `main` は同時に複数のワークツリーへチェックアウトできないため、ワークツリー内での `git checkout main` は失敗する。

> **着手前チェック #2 は完全な排他を保証しない**（理由と最後の砦は下記「リリースロック」の「この仕組みの限界」）。push が拒否されたら**力ずくで通さず、必ず報告する**。

## リリースロック

**他セッションのコンテキストを汚さずに排他を確かめるための仕組み。** `SendMessage` で問い合わせる手も
あるが、**メッセージは相手の作業に割り込む**。関係ないセッションを止めてまで聞くことではないため、
状態をファイルに置いて読むだけにする。

置き場所は `<リポジトリのトップレベル>/.claude/release.lock`（`.gitignore` の `.claude/*` で除外済みなのでコミットに混ざらない）。

```json
{
  "sessionId": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
  "pid": 12345,
  "name": "<セッション名>",
  "startedAt": "2026-01-01T00:00:00.000Z",
  "step": "着手"
}
```

### 読む（着手前チェック #2）

ファイルが無ければ着手してよい。あれば中身を読む。

**まず `sessionId` が自分のものかを見る。** 自分のロックなら監視モードから戻った等の再入なので、
`step` を更新して先へ進む。他人のロックだったときだけ生存判定へ進む。

```bash
node -e "
const fs=require('fs');
const p='.claude/release.lock';
if(!fs.existsSync(p)){ console.log('NONE'); process.exit(0) }
let l;
try{ l=JSON.parse(fs.readFileSync(p,'utf8')) }
catch(e){ console.log('MALFORMED: '+e.message); process.exit(0) }
const bad=[];
if(typeof l.sessionId!=='string' || !l.sessionId) bad.push('sessionId');
if(l.pid!==null && !(Number.isInteger(l.pid) && l.pid>0)) bad.push('pid');
if(!Number.isFinite(Date.parse(l.startedAt))) bad.push('startedAt');
if(bad.length){
  console.log('MALFORMED: 値が不正なキー '+bad.join(', '));
  console.log(JSON.stringify(l,null,2)); process.exit(0)
}
console.log(l.sessionId===process.env.CLAUDE_CODE_SESSION_ID ? 'MINE' : 'OTHER');
console.log(JSON.stringify(l,null,2));
"
```

**判定は終了コードではなく、標準出力の先頭語で行う**（このスクリプトはどの分岐でも 0 で終わる）。

**検証は値の型で行っている。** `pid` は「正の整数」か「`null`」のどちらかだけを正当とし、
`startedAt` は日時として解釈できることを求める。キーの有無だけを見ると、`pid` に文字列や
オブジェクトが入った壊れたロックが素通りし、後段の `Get-Process` へそのまま渡ってしまう。

`MALFORMED` なら**残骸と断定しない**。出力をユーザーへ提示して指示を仰ぐ。

`OTHER` なら記録された `pid` の生存を確かめる。**PowerShell ツールで実行すること** ——Bash ツールが
Git Bash の環境では `Get-Process` は `command not found` になる。

**`pid` が `null` のときはこのスクリプトを実行せず、下表の最終行へ直行する。** `Get-Process -Id $null` は
パラメータのバインディングで失敗し、これは `-ErrorAction SilentlyContinue` では抑えられない。
下の雛形は `Get-Process` を `try` の外に置いているため、例外がそのまま出て `DEAD` とも `ALIVE` とも
付かない出力になる。

```powershell
$p = Get-Process -Id <pid> -ErrorAction SilentlyContinue
if (-not $p) { "DEAD" }
else {
  try { "ALIVE started=$($p.StartTime.ToUniversalTime().ToString('o'))" }
  catch { "ALIVE started=UNKNOWN" }
}
```

| 結果 | 判断 |
|---|---|
| `DEAD` | 異常終了した残骸。**消してよいかユーザーに確認する**（`step` と `startedAt` を提示する） |
| `ALIVE` でプロセス開始時刻がロックの `startedAt` より**後** | **PID が再利用されている**（Windows は PID を再利用する）。無関係なプロセスなので残骸として扱う。**`DEAD` と同じく、消してよいかユーザーに確認する** |
| `ALIVE` でプロセス開始時刻が `startedAt` 以前 | **他セッションがリリース中。中断してユーザーに報告する** |
| `ALIVE started=UNKNOWN` | 権限等で開始時刻を読めなかった。**残骸と断定せず、ユーザーに状況を提示して指示を仰ぐ** |
| ロックの `pid` が `null` | 生存判定ができない。**消してよいかではなく、他セッションの状況をユーザーへ直接確認する** |
| 読み取りが `MALFORMED` を返した | 中身が壊れている。**残骸と断定せず、出力を提示して指示を仰ぐ** |

**`step` は中断時の手がかりになる。** セッションが落ちると「どこまで進んだか」を誰も報告できないが、
ロックが残っていればそこから読める。

### 入るとき

**着手前チェック #2 を通った時点で作る。** そこから先（#3・#4）にも `git fetch` を含む数秒〜十数秒が
あり、待てばその分だけ窓が広がる。

前提は 3 つ ——`CLAUDE_CODE_SESSION_ID` が環境変数にあること、`claude` CLI が PATH から呼べること、
`node` が使えること。

```bash
node -e "
const fs=require('fs'), cp=require('child_process');
try{
  const id=process.env.CLAUDE_CODE_SESSION_ID;
  if(!id) throw new Error('CLAUDE_CODE_SESSION_ID が設定されていない');
  const me=JSON.parse(cp.execSync('claude agents --json',{encoding:'utf8'}))
    .find(a=>a.sessionId===id);
  fs.mkdirSync('.claude',{recursive:true});
  fs.writeFileSync('.claude/release.lock', JSON.stringify({
    sessionId:id, pid:me?.pid??null, name:me?.name??null,
    startedAt:new Date().toISOString(), step:'着手'
  },null,2));
  console.log(me?.pid ? 'OK' : 'OK-NO-PID');
}catch(e){ console.log('FAILED: '+e.message) }
"
```

パスが相対なので、**リポジトリのトップレベルで実行すること**（着手前チェック #1 を通っていれば満たされる）。

**判定は終了コードではなく、標準出力の先頭語で行う**（このスクリプトは失敗しても 0 で終わる）。

| 出力 | 状態 | すること |
|---|---|---|
| `OK` | ロックを作れた | 先へ進む |
| `OK-NO-PID` | ロックは作れたが `pid` が無い | **生存判定ができない。**その旨をユーザーへ伝え、手動での排他確認に切り替える（バックグラウンドで起動されたセッションは `pid` を持たない） |
| `FAILED: <理由>` | **ロックは作られていない** | 先へ進まず、ユーザーへ報告する |

**`FAILED` を見落とさないこと。** ロックが無いまま手続きを続けると、排他が掛かっていない状態で
main を書き換えることになる。

段が進んだら `step` を書き換える（マージ／統合後の検証／バージョン更新／プッシュ）。上のスクリプトを
そのまま流し直してよい（`startedAt` が更新されるが、生存判定は「プロセス開始時刻より後か」で見るため
新しい値でも判定は壊れない）。

### 離れるとき

**正常終了・却下・中断・監視モードへの移行 —— どれも「この手続きから離れる」ことに変わりはない。**
削除はここ 1 箇所に集約する。**個々の手順に削除を書き分けると必ず漏れる。**

**手順**:

**所有者の確認（最初に行う）**: 上記「読む」のスクリプトを、**リポジトリのトップレベルで**そのまま流し、標準出力の先頭語で分ける（パスが相対なので、別の場所で流すと自分のロックがあっても `NONE` になる）。**消してよいのは自分のロックだけ。**

| 先頭語 | 操作 |
|---|---|
| `MINE` | 次の「未 push の確認」へ進む |
| `NONE` | 何もしない（消すものが無い）。トップレベルで流したかだけは確かめる |
| `OTHER` | **触らない。** 他のセッションのロック（着手前チェック #2 で他人のロックを見つけて中断した場合がこれに当たる）。消すと、相手がリリース中に排他が外れる。触らなかったことと、他人のロックだったことを報告に含める。**自分で作った覚えがあるのに `OTHER` なら**、セッションの ID が変わった可能性がある（変わる条件は確かめていない）。消さずにユーザーへ確認する |
| `MALFORMED` | **触らない。** 出力をユーザーへ提示して指示を仰ぐ |

**未 push の確認（自分のロックのときだけ）**:

```bash
git log origin/main..main --oneline; echo "exit=$?"
```

**終了コードまで見ること。** `origin/main` が解決できないと git は fatal を stderr へ出して非ゼロで終わり、
**stdout は空になる**。出力だけを見ると「未 push のコミットが無い」と区別が付かない。

| 結果 | 操作 |
|---|---|
| `exit=0` で出力が空 | **ロックを消す** |
| `exit=0` で何かある | **消さずに `step` を実際に止まった段へ書き換える**。未 push のコミットが残っており、次に来たセッションがその状態を知る必要がある |
| `exit` が 0 以外 | **判定できていない。ロックを消さず、`step` も触らずに、状況をユーザーへ報告する。** 消せば、未 push の有無が不明なまま別セッションが着手する |

**離れる場面**（すべて上の 2 段 ―― 所有者の確認 → 未 push の確認 ―― を通る）:

- 着手前チェック #2 で他人のロック・壊れたロックを見つけて中断した（所有者の確認で何もせずに終わる）
- 着手前チェック #3 が満たせず中断した
- 着手前チェック #4 の乖離を解消せずに終えた
- `ready/*` が無く「監視モード」へ入る（未 push のコミットが残っていてロックを消さなかったときは、**監視に入らない**。ロックを持ったまま数時間〜数日待つと、その間ずっと他セッションの着手を止める。先に「トラブルシューティング」の `[ahead N]` で未 push を解消するか、ユーザーへ伝えて指示を仰ぐ）
- 手順 2 で候補がすべて却下された
- 監視モードで検知した候補が却下され、監視を続ける
- 手順 3〜6 のどこかで中断した
- 手順 7（クリーンアップ）で中断した
- 手順 8 で「ここで終える」または「監視モードに入る」を選んだ

**手順 7（クリーンアップ）では消さない。** 手順 8 には「続けてもう一度リリースする（手順 1 から
再開する）」という経路があり、そこは着手前チェックを通らないため**ロックが再作成されない**。
手順 7 で消すと、2 回目のリリースが終わるまで空白ができる。

### この仕組みの限界

**ロックは競合を完全には防がない。** ファイルの確認と作成は不可分ではないので、2 つのセッションが
ほぼ同時に着手前チェック #2 を走らせれば、両方が通過しうる。窓は狭いが存在する。

**技術的な最後の砦は従来どおり**、手順 6 の `git fetch` 再確認と non-fast-forward での push 拒否。
ロックはそれを早い段階で補うものであって、置き換えるものではない。**ロックが無いことを根拠に
「排他が保証された」と考えないこと。**

## 手順

### 1. リリース候補の列挙

`ready/*` が待ち行列そのもの。

```bash
git branch --list 'ready/*' --no-merged main
```

各候補の乖離と最終コミット日時を添えてユーザーに提示する。

```bash
git rev-list --left-right --count main...<branch>   # 出力は「behind<TAB>ahead」
git log -1 --format='%ci %s' <branch>
```

**あわせてリネーム漏れを確認する**（`worktree/*` は本来リリース対象外だが、改名を忘れると永久に候補へ現れないため）:

```bash
git branch --list 'worktree/*' --no-merged main
```

- ahead があり、**最終コミットが概ね 3 日以内**のものは**リネーム漏れの疑い**としてユーザーに一言提示する
- **ahead が 50 コミットを超える、または最終コミットが 2 週間以上前**のものは実験用（PoC）や放棄済みの可能性が高い。「要判断」として区別する
- どちらにも当てはまらない中間的なものは「判断がつかないもの」としてそのまま列挙し、ユーザーに委ねる
- いずれの場合も**勝手に改名しない**

> 数値はあくまで目安。迷ったら分類を断定せず、乖離と日付をそのまま見せて判断を仰ぐ。

**前回までの取りこぼしも確認する**（リリース済みなのに残っている `ready/*`）:

```bash
git branch --merged main --list 'ready/*'   # リリース済みなのに残っているブランチ
git worktree list                            # 対応するワークツリーの有無
```

- ここに出るものは**過去のリリースでクリーンアップに失敗した残骸**。`ready/*` は「リリース待ち」の印であり、それがマージ済みということは既に出し終えている
- **削除前に AskUserQuestion で確認する**（勝手に消さない）。最終更新日時（`git log -1 --format='%ci'`）を添えて提示する
- ワークツリーは手順 7 と同じく、CLAUDE.md「ワークツリーを消す前に、ジャンクションを外す」のコマンドで消す
- 削除できない場合は無理に消さず、ユーザーに報告して次回へ回す。セッション由来のロック（別セッションの作業ディレクトリ・`activate_project`）は、**そのセッションが終われば解放される**ため、永久に残るわけではない
- **毎回のリリースでここを見るため、取りこぼしは必ずいつか回収される。** その場で消せなくても慌てないこと

> **マージ済みの `worktree/*` は残骸候補にしない。** 「未着手のまま main が進んだだけ」であることが多く、残骸と区別できない（リリースのたびに behind が増えるため、乖離の数値からは判断できない）。作業中のブランチをリリースのたびに残骸候補として並べても、確認が形骸化するだけ。

**着手されないまま放置されたワークツリーも確認する**:

```bash
git branch --list 'worktree/*' --merged main   # コミットが 1 件も無い（作成時点のまま）
```

- **一度もコミットされていないワークツリー**。作りかけで放置されている可能性がある
- これは上の「リネーム漏れ」チェック（`--no-merged main`）では**原理的に拾えない**。コミットが無いブランチは作成時点から main の祖先であり、常に「マージ済み」と判定されるため
- **最終更新が 2 週間以上前のものだけ提示する**（`git log -1 --format='%ci'` で確認）。それより新しいものは、これから着手するところかもしれない
- 削除は勝手に行わず、ユーザーに確認する
- ワークツリーは手順 7 と同じく、CLAUDE.md「ワークツリーを消す前に、ジャンクションを外す」のコマンドで消す

### 2. 出すものをユーザーに選ばせる

**AskUserQuestion** で確認する。候補が 1 本でも省略しない。

すべて却下された場合はここで終了する。「リリースロック」の**「離れるとき」を通ってから**終えること。必要なら「監視モード」に入るか確認する。

### 3. マージ

選ばれたものを順に。**ファストフォワード可能でも必ずマージコミットを作る**。

```bash
git merge --no-ff ready/<type>/<name>
```

- 理由: 各機能・修正の単位（ブランチ）を履歴上で明確に残すため
- コンフリクトが出たら解消し、型チェック（`npx tsc -b`）を通してから次のブランチへ進む
- 解消できない場合は**その場で停止**し、状況をユーザーに報告する

> **ここから先のどこで停止しても、既にマージしたコミットはローカル `main` に未 push のまま残る。** 中断するときは必ず「未 push の状態が残っている」ことをユーザーに明示して伝えること。黙って終わると、次にリリースする人が原因不明の未 push コミットに遭遇する。

### 4. 統合後の検証

**全ブランチのマージ完了後・バージョン確定前**。省略しない。

```bash
npm test && npm run build && npm run build:dmdss
```

ビルドが通ったら `npm run preview` / `npm run preview:dmdss` を起動し、Playwright MCP でブラウザ確認する（要領は CLAUDE.md の「検証」節に準ずる）。

> **preview サーバーは必ず `run_in_background: true` で起動する。** `vite preview` は dev サーバーと同じく終了しない常駐プロセスのため、フォアグラウンドで起動するとツール呼び出しが応答を返さずハングする。

> **なぜここで検証するのか**: 各ブランチが個別に検証済みでも、**束ねた後の組み合わせは誰も検証していない**。しかも次の手順の push は即座に本番デプロイを起動する。dev では再現せず本番でだけ壊れるクラスの不具合（CLAUDE.md「検証」節に記録した v4.0.0→v4.0.1 の事例）を止められる最後の機会がここ。

**`npm test` は常に実行する**（所要 1 分程度。軽量化できるのはビルド確認の範囲だけ）。各ブランチが単体で通していても、**束ねた後のテストは誰も走らせていない**。しかも push 後の CI は同じテストで止まるため、ここで落ちるものを push すると `main` とタグだけが進んで本番は更新されない。

**軽量化してよい条件**: マージしたブランチが 1 本だけで、**そのブランチが main 以降に持つコミット（`git log <branch> ^main`）のいずれかに本番ビルド確認を実施した旨が記録されている**場合は `npm test` と型チェックのみでよい。ただし次のいずれかに当てはまるなら通常どおり検証する。

- そのブランチが「main の取り込み」でコンフリクト解消を伴っていた（マージコミットのメッセージに明記されている）
- 記録が無い、または確認済みかどうかが判然としない（**判断に迷ったら通常どおり検証する**）

縮小できるのは検証の**範囲**であって、検証そのものを飛ばしてよいという意味ではない。

### 5. バージョン更新

統合後の検証を通してから。**AskUserQuestion** で確認する。省略しない。

選択肢: 「メジャーバージョンを上げる」「マイナーバージョンを上げる」「パッチバージョンを上げる」「バージョンを上げない」

まとめて出す場合は**含まれる変更のうち最も大きいもの**に合わせる。

| 含まれるもの | 選ぶもの |
|---|---|
| 破壊的変更・アーキテクチャ全体に及ぶ変更 | major |
| 機能追加（`feat`）が 1 本でも | minor |
| 修正のみ（`fix` / `refactor` / `docs` / `chore`） | patch |

**種別が決まったら、`npm version` の前に「変更内容」を書く（下の 5a）。** `npm version` は作業ツリーが綺麗でないと落ちるので、変更内容は先にコミットしておく。

#### 5a. 利用者向けの変更内容を書いて諮る

アプリは、新しい版があることと、その版で何が変わったかを画面に出す（`src/utils/releaseNotes.ts`・`src/services/appUpdate.ts`）。中身は `public/release-notes.json` で、**リリースのたびにここで書く**（2026-10-26 ユーザー承認「リリース時に利用者向けに書く」）。

1. 今回マージしたブランチのコミット（`git log --no-merges <前の版のタグ>..HEAD`）から、**利用者が気づく変化**（画面・読み上げ・通知・音）だけを拾う
2. 次の決まりで 1 行ずつ書く（粒度はユーザーの原文:「利用者に見える変化を 1 行ずつがいいです。メジャーアップデート級の大きなアップデートの場合は一行で済ませる必要はないと思います。バグの修正はあまり詳しくなりすぎないでください。利用者が見てよくわからないことは書きたくないです。変化がない(ドキュメント更新のみなど)の場合は「軽微な修正」みたいな文で入れておきたいですね。変更内容なしは混乱の元だと思います。」）
   - 「新しくできるようになったこと」（`added`）と「直したこと」（`fixed`）に分ける
   - ブランチと行を 1 対 1 にしない。同じ画面の小さな直しは 1 行にまとめる
   - 内部の作り替え・テスト・資料・自作地震計のホストだけの変更は書かない
   - 行ごとに、どちらの版に関係するかを `variant` で付ける（`both` / `standard` / `dmdss`）
   - 利用者に見える変化が 1 つも無ければ、`added` も `fixed` も空にする（画面が「軽微な修正」と出す）
   - 文の形は、ほかのサービスのリリースノートと同じく「〜を追加」「〜を改善」「〜の不具合を修正」で結ぶ（「しました」を付けない）。何が・どうなる不具合だったかを短く具体的に書く（例:「起動時に画面が真っ白のままになる場合がある不具合を修正」）。2026-10-26、丁寧形・言い切り・体言止めの案はどれも採られず、ユーザーの「いろんなサービスの変更内容を確認してみてください」を受けて実例（Android の NotebookLM・LINE WORKS）を見て、この形に決まった
   - 文の形で迷ったら、書く前にほかのサービスのリリースノートを 2〜3 件見て合わせる（2026-10-26 ユーザー指示「この手順も入れといてね」）
   - 文の調子と避ける形は [`docs/ui-wording-procedure.md`](../../../docs/ui-wording-procedure.md) に従う
3. **AskUserQuestion で文面を諮る。** 行の文面そのものを選択肢の説明に入れる（地の文に書いた案は画面で要約に置き換わる）。行が多ければ問いを分ける
4. 決まった文面を `public/release-notes.json` の `versions` の先頭へ足し、コミットする。版の番号は、決めた種別で `package.json` の版を上げた値。日付は日本時間の今日

```json
{ "version": "5.70.0", "date": "2026-10-27", "added": [{ "text": "…", "variant": "both" }], "fixed": [] }
```

```bash
git add public/release-notes.json
git commit -m "docs: 5.70.0 の変更内容を書く"
```

- 「バージョンを上げない」を選んだときは書かない（画面は版の番号で新しい版を見分けるので、上げない版の行は誰にも出ない）
- 番号を決め損ねる（`npm version` が別の番号を付ける）と、画面に変更内容が出ない。`npm version` の後に、版が揃っていることを次のテストで確かめる（`package.json` の版の行が `release-notes.json` に無い・読めない版がある・同じ版が 2 回載っている、のどれでも落ちる）。**同じテストは `npm test` にも CI にも入っている**ので、書き忘れたまま push すると CI がビルドの前に止める
  ```bash
  node_modules/.bin/vitest run src/utils/releaseNotes.test.ts
  ```
- 画面での見え方: 版ごとに「（版の番号）の変更内容」の見出し（例: 「5.70.0 の変更内容」）、その下に `added` を「追加」、`fixed` を「修正」の小見出しで並べる。どちらも空なら「軽微な修正」の 1 行（`src/components/ReleaseNotesDialog.tsx`）。諮るときは、この見え方で読まれることを前提に書く

#### 5b. バージョンを上げる

5a のコミットを済ませてから上げる。上げたら、5a の最後に書いたテストで版が揃っていることを確かめる。

```bash
npm version patch   # または minor / major
```

`package.json` の更新・コミット作成・git tag（`vX.Y.Z`）作成までが自動で行われる。`src/components/SettingsTab/index.tsx` のバージョン表示は `vite.config.ts` の `define`（`__APP_VERSION__`）経由で `package.json` を参照しているため**手動更新は不要**。

**着手前チェック #3 で未コミットの変更をユーザー判断で通していても、`npm version` は自分で作業ツリーがクリーンであることを求める**（`Git working directory not clean` で落ちる）。このリポジトリでは **`public/data/test-scenarios/index.json`** がよくこれに当たる（2 回続けてここで止まった例がある）—— 手元で実地震テストシナリオを置くと一覧が書き換わるが、コミット済みの空配列のテンプレートが正なので、書き換えた分はコミットしない（扱いは [`docs/spec/settings-pwa-spec.md`](../../../docs/spec/settings-pwa-spec.md) §6「シナリオ本体の扱い」）。#3 でこのファイル（など、コミットしない手元のファイル）だけが dirty と分かった時点で、この手順の直前に退避する段取りを組んでおく。マージ（手順 3）はこのファイルに触らないので、マージの前の退避は要らない。

**stash はすべてのワークツリーと、同じリポジトリで動く他のセッションとで共有される。** 素の `git stash pop` は積まれている先頭を取るので、自分の退避が積まれていなかったとき（対象が未追跡で pathspec が当たらなかった・変更が無くて `No local changes to save` になった等）には、他のセッションの退避を作業ツリーへ広げて消す。次の 4 段を、**別々の呼び出しで**この順に行う。

1. 退避する前の `git status --porcelain` を控え（4 で比べる元になる）、一意の印を付けて退避する（印には今回の版番号や時刻を入れ、他と重ならないようにする）:
   ```bash
   git stash push -m "release-tmp-<一意の印>: public/data/test-scenarios/index.json" -- public/data/test-scenarios/index.json
   ```
2. 自分の退避の SHA を引き、`TaskCreate` の `metadata` に書く（シェルの変数は呼び出しをまたいで残らない）。**印の付いた行が無ければ、退避されていない。** 3 へ進まず、状況をユーザーへ提示する（2 行以上当たったときも同じ。印が他と重なっている）:
   ```bash
   git stash list --format='%H %gs' | grep -F 'release-tmp-<一意の印>:'
   ```
3. `npm version patch`（または minor / major）。**失敗しても 4 は行う**（退避したファイルを戻さないまま止めない）
4. 控えた SHA を指定して戻し、戻ったことを確かめてから消す。消す前に `stash@{n}` を引き直す（他のセッションの出し入れで番号がずれる）:
   ```bash
   git stash apply <控えた SHA>
   git stash list --format='%gd %H %gs' | grep -F 'release-tmp-<一意の印>:'
   git stash drop <いま引いた stash@{n}>
   ```

- 退避するのは、#3 でユーザーが通すと判断したファイルだけ。`git stash` をパス指定なしで叩かない。**`git stash pop` は使わない**
- `git stash apply` の後、`git status --porcelain` で退避前と同じ差分に戻ったことを確かめてから drop する。**apply が衝突した（`CONFLICT`）・差分が退避前と一致しないときは drop しない。** 退避は残っているので失われない。状況をユーザーへ提示する
- drop は SHA を受け付けないので、番号を引いてから打つまでの間に他のセッションが出し入れすると、別の退避を消しうる。**drop の出力（`Dropped stash@{n} (<SHA>)`）に出た SHA が控えた SHA と違えば**、消したのは他の退避。元の件名を `git log -1 --format=%s <出力に出た SHA>` で引き、`git stash store -m "<引いた件名>" <出力に出た SHA>` で戻す。そのうえで自分の退避の番号を引き直して drop し直し、ユーザーへ報告する

### 6. プッシュ

直前に `git fetch` で origin との乖離を**もう一度**確認する。手順 4 のビルドとブラウザ確認には時間がかかるため、着手前チェックの時点から状況が変わっている可能性がある。

**push の前に、公開する内容に個人情報が無いことを確かめる**（CLAUDE.md「公開する前に個人情報が無いことを確かめる」）。

1. **機械の検査**: pre-push フックが push のたびに走る。**入っているかを先に確かめる**（入れ直しても害は無い）

   ```bash
   npm run install-git-hooks
   ```

   このあとの `git push` でフックが検査を走らせ、見つけたら（検査の終了コード 1）・調べられなかったら（2）push を止める。**`--no-verify` で押し通さない。** 見つかったものと場所をユーザーへ提示して指示を仰ぐ

   同じフックが**コミットメッセージに英語の文が無いか**も見る（CLAUDE.md「リポジトリに書く文も日本語で書く」）。**衝突を解いたマージの本文に英語で説明を書かない**（過去のマージに 14 本あり、2026-09-20 の 1 回のリリースだけで 3 本。`npm run check-commit-messages -- --range --merges main` で出る）。止まったら、まだ公開していないので書き直してから push し直す —— 最後のマージなら `git commit --amend`、版のコミットより前なら版のコミットとタグも作り直すことになるので、**先にユーザーへ報告する**
2. **目の検査**: 出す差分（`git diff origin/main..main`）とコミットメッセージ・作者欄とコミッター欄（`git log --format='%an <%ae> / %cn <%ce>%n%B' origin/main..main`）を読み、**自宅からの距離・S−P 時間・場所や機器を特定できる説明**と、作者・コミッターの名前とアドレスに個人情報が無いかを見る。機械では見分けられない（pre-push フックは名前も照合するが、照合ファイルに載っていない名前は見つけられないので、作者名・コミッター名もここで読む）

下記「push で届かない配り先」を確かめるため、push の前に `origin/main` の位置を控えておく（push の後では取れない）。**シェルの変数に入れるだけでは控えたことにならない** —— Bash のツールは呼び出しをまたいで変数を保たないので、push の後の比較では空になる。次の 3 段を、**別々の呼び出しで**この順に行う（以下、書き残した値を「控えた起点」と呼ぶ）。

1. 起点を出す（`HEAD` ではなく `origin/main`）:
   ```bash
   git rev-parse origin/main
   ```
2. 出た値を、**今回の版番号（またはタグ）を添えて `TaskCreate` の `metadata` に書く**（例: `release: v1.2.3`、`prev: <出た値>`）。会話にだけ残す形は補助にとどめる —— 会話が畳まれると見つからなくなる
3. push する:
   ```bash
   git push --follow-tags
   ```

**push を試みるたびに 1・2 をやり直し、書いた値を上書きする。** push が失敗して fetch・マージしてから再び push するときは `origin/main` が動いているので、前の試行の値を使うと比べる範囲がずれる。比べるのは、**最後に成功した push の直前に書いた値**。

main への push で GitHub Actions が本番デプロイする。ワークフローはビルドより先に `npm test` を走らせるため、**push は成功してもテストが落ちれば以降のステップ（ビルド・デプロイ）は走らず、本番は更新されない**（`main` とタグは進んだまま）。手順 4 を通していれば通常は起きないが、起きた場合はバージョンとタグを巻き戻さず、修正を `main` に積んで push し直す（タグは修正前を指したままにする）。結果は GitHub の Actions で確認する。

**push に失敗した場合**（non-fast-forward による拒否・通信断・認証エラーのいずれも）、バージョンコミットやタグを**作り直さない**。まず状況をユーザーに報告して指示を仰ぐ。

- non-fast-forward なら他セッションが先に push した可能性が高い。力ずくで通すと相手の変更を壊す
- **失敗するとローカル `main` にマージコミット・バージョンコミット・未 push のタグが残る。** この残骸は次のリリースの着手前チェック #4 で検出されるが、**その場でユーザーに「未 push の状態が残っている」と明示して伝える**。黙って終わると、次に触る人が二重にバージョンを上げかねない

#### push で届かない配り先

**push で本番になるのは PWA だけ。** 自作地震計の**ホスト**（`seismo-host/`。常時起動の別の機で動く）と**ファーム**（`firmware/`。基板へ焼く）は、push しても実機は古いまま変わらない。PWA 側だけが新しい口を前提にすると、**実機ではその機能が一度も表に出ない**（エラーにもならず黙って出ないだけ）。

push が成功したら、今回のリリースで次のいずれかが変わったかを確かめる。**リポジトリのトップレベルで実行する**（パスが相対）。`<作業用>` はスクラッチパッドなどリポジトリの外の一時ディレクトリ。

```bash
prev=<控えた起点>   # push の前に TaskCreate の metadata へ書いた値を直接書く
# 照合用: push は追跡参照の履歴へ `update by push` を 1 行残すので、その 1 つ前の行が push 前の位置になる。控えた起点と一致するかを見る
git reflog show --format='%H %gs' origin/main | awk -v h=$(git rev-parse HEAD) 'f{print $1; exit} $1==h && /update by push/{f=1}'
npx esbuild seismo-host/main.ts --bundle --platform=node --format=esm --packages=external --metafile="<作業用>/meta.json" --outfile="<作業用>/out.js" --log-level=error
shared=$(node -e "const m=require(process.argv[1]);console.log(Object.keys(m.inputs).filter(p=>!p.startsWith('seismo-host/')).join(' '))" "<作業用>/meta.json")
git diff --stat "$prev" HEAD -- seismo-host/main.ts seismo-host/src firmware ':!firmware/tools' package.json package-lock.json $shared
```

- **比べる起点（`prev`）は、push の前に書き残した「控えた起点」の値を直接書く**（今回の版番号を添えて書いたもの。同じセッションで前のリリースの値が残っていても、それは使わない）。push 成功後の `origin/main` はもう新しい `main` を指しているので、**`origin/main` を取り直して起点にすると差分は常に 0 になる**。reflog の 1 つ前の行（上の照合用の行）は控えた起点と一致するはずで、食い違ったら判定せずに報告する。**控えた起点が見つからなければ判定できていない** —— 取り直さず、差分なしとも読まず、ユーザーに報告する
- **ホストが読み込むリポジトリ側の共有ファイルも対象。** 手で数えずに esbuild の依存一覧で出す —— 共有ファイルはさらに別のファイルを読み込むので、ホストの `import` 文を `grep` するだけでは推移的に入るものを落とす（2026-10-05、ホストが直接は読まない `src/utils/knet/fft.ts` が実機に無かった）。管理コンソール（`seismo-host/src/admin/`）は実行時に別途ビルドされるので依存一覧には出ないが、`seismo-host/src` を丸ごと比べているので拾える
- **`package.json`・`package-lock.json` が変わっていたら、ホストが使う npm パッケージが変わったかを中身で確かめる**（どれを使っているかは `grep -rhoE "from '[^.][^']*'" seismo-host/src seismo-host/main.ts | grep -v "node:" | sort -u` で出る。テスト専用のものも混ざる）。変わっていれば配り先で `npm install` も要る（`seismo-host/README.md`「常時動かす機へ配る」）
- **差分があれば、配るかを AskUserQuestion で確認する。省略しない。** 配り先が並行して他のセッションに触られていることがあるので、聞かずに配らないし、聞かずに見送りもしない。**ホストとファームの両方が変わっていれば、それぞれ別の問いにする**（片方だけ配る選択を残す）。選択肢は「いま配る」「後で配る」の 2 つ
- **「後で配る」を選んだら、その場で `TaskCreate` に積む**（何を・どのコミットまでを配るか）。報告するだけでは、会話が畳まれた時点で配っていないことごと消える
- **配る手順は `seismo-host/README.md`「常時動かす機へ配る」と、ファームなら `firmware/README.md`「書き込む」に従う。** 実機の置き場所・起動コマンドは端末ごとの事情なので、この手順には書かない
- **ホストを配る前に、配り先にしか無い変更を上書きしないかを確かめる。** 配り先は git ではないことがあるので、中身を取り戻して `main` の各コミットと比べる。一致するコミットが見つかれば、それが配り先に入っている版。どれとも一致しなければ、配らずにユーザーへ報告する（`<配り先>:<置き場所>` は README の配る手順と同じもの）:
  ```bash
  W="<作業用>"
  rm -rf "$W/remote" && mkdir -p "$W/remote"
  if scp -q -r <配り先>:<置き場所>/seismo-host/src <配り先>:<置き場所>/seismo-host/main.ts "$W/remote/"; then
    for c in $(git log --format=%h -20 main -- seismo-host/src seismo-host/main.ts); do
      rm -rf "$W/c" && mkdir -p "$W/c" && git archive $c seismo-host/src seismo-host/main.ts | tar -x -C "$W/c"
      diff -rq --strip-trailing-cr "$W/remote" "$W/c/seismo-host" >/dev/null 2>&1
      case $? in 0) echo "$c 一致" ;; 1) echo "$c 不一致" ;; *) echo "$c 比較できず" ;; esac
    done
  else
    echo "取り戻せなかった。比べていないので配らない"
  fi
  ```
  **「一致」と出た行だけが配り先の版。** 判定は `diff` の終了コードで行う（0＝同じ・1＝違う・2＝比べられなかった）。出力の行数で数えると、取り戻しに失敗して比べる相手が無いときも 0 行になり、「一致」と取り違える。改行は CRLF のことがあるので `--strip-trailing-cr` を外さない
- 配ったら、新しい口が応えることと、止めていた間の波形を取り戻せたことを確かめて報告する
- **配る途中で失敗したら、止めたものが動いているかを確かめてから報告する。** ホストなら `/status` が 200 か（止める口で止めた後に失敗すると、ホストが止まったまま観測が途切れる）。ファームなら基板が応えるか（基板の状態ページ。`firmware/README.md`「書き込む」）

> 2026-10-05: v5.33.0 で地震カードの震度の行（ホストの `GET /quake-intensity` を問い合わせる）を出したが、ホストを配らずにリリースを終えた。「ホストを作り直している別のセッションと順番を合わせる」というこちらの判断で後回しにし、残りの作業として書いただけで聞かなかった。ユーザーが画面で「どこに表示されてる？」と気づくまで、実機では一度も出ていなかった。

### 7. クリーンアップ

**このリリースでマージしたブランチのみ**。未マージのブランチには触らない。

```bash
git worktree list                             # ブランチに対応するディレクトリを確認する
# ワークツリーは CLAUDE.md「ワークツリーを消す前に、ジャンクションを外す」のコマンドで消す
git branch -d ready/<type>/<name>
```

- ブランチ名（`ready/<type>/<name>`）とワークツリーのディレクトリ名（`.claude/worktrees/<name>`）は接頭辞が異なる。**必ず `git worktree list` で対応を確認してから削除する**
- **ワークツリーが既に消えていることがある**（実装セッションがマージを検知して自分で片付けた場合、または改名時にワークツリーだけ先に消した場合。CLAUDE.md「マージ後の自己クリーンアップ」と手順 12 の選択肢 2）。`git worktree list` に無ければ `git worktree remove` は**飛ばす**。エラーではなく、先に片付いただけ
  - **ブランチの削除は飛ばさない。** 改名時にワークツリーだけ消した場合は `ready/*` が残っているため、`git branch -d` は通常どおり実行する。ここを飛ばすとマージ済みの `ready/*` が残り、次回の「前回までの取りこぼし」に毎回現れる
- **`--force` / `-D` は使わない。** 他セッションの作業ディレクトリを消す操作であり、取り返しがつかない
- **素の `git worktree remove` は叩かない。** ワークツリーの `node_modules` がジャンクションだと、メインの `node_modules` まで消える。理由と、消し終えた後の確認は CLAUDE.md の同じ節にある
- `git worktree remove` が失敗する典型は 3 つ。**いずれもユーザーに状況を提示して確認する**
  - 別セッションの Bash がそのディレクトリを作業ディレクトリにしたまま残っている
  - Serena の `activate_project` がそこを指したまま
  - `contains modified or untracked files` と出る場合はロックではない。サブエージェントが検証用に作った使い捨てファイルが残っていることがある。`git -C <worktree> status --short --untracked-files=all` で中身を確認してから消す
- `git branch -d` が失敗するブランチは未マージのコミットを持つ。削除せずユーザーに報告する
- 手順 4 で起動した preview サーバー（既定 4173 番系ポート）を停止する
- 片付けで消せなかったもの（掴まれたディレクトリなど）は、その場で待ちの別タスクとして立てる
- **ロックはここでは消さない**（→「リリースロック」の「離れるとき」）

### 8. リリース完了後の確認

**候補をもう一度列挙する。省略しない。**

```bash
git branch --list 'ready/*' --no-merged main
```

手順 1 の列挙から手順 6 の push までには時間がかかる（統合後の検証を含むため）。**その間に他セッションが新しい `ready/*` を作っていることがある。** しかも監視モードはリリース手順に入った時点で止めているため、増えても通知は来ない。**ここで見なければ誰も気づかない。**

- 残っていれば、①続けてもう一度リリースする（**手順 1 から再開する**）②監視モードに入る ③ここで終える のどれにするかユーザーに確認する
  - **①ならロックはそのまま持ち越す**（→「リリースロック」の「離れるとき」）
  - **②③なら「リリースロック」の「離れるとき」を通る**
  - **②を選ぶときは、いま残っている候補を改めてユーザーへ伝える。** 監視ループは起動時点の `ready/*` を `prev` に取り込むため、**今回残った候補について通知は二度と出ない**（新しいブランチが別に現れたときだけ反応する）
- **黙って終わらない。** 「まだ 2 本残っています」と伝えるだけで、次の判断ができる
- 何も残っていなければ、引き続き待つかどうか（監視モードに入るか）を確認して終える。**どちらの場合も「離れるとき」を通る**
- **この確認が済んだら、タスクを閉じる。** このリリースで出したブランチのタスクと、リリースそのもののタスクを `completed` にし（既に閉じていれば件名だけ直す）、件名を「v<版> でリリース済み」へ書き直す。このリリースの間に立てた待ちのタスク（手順 7 の「消せなかったもの」・手順 6 の「後で配る」）は閉じない（CLAUDE.md「進める作業はタスク機能で管理する」の「終わったタスクは、その場で閉じる」）

## 監視モード

`ready/*` が現れるのを待つ。**Monitor ツール**でブランチを監視し、新しく現れた時点で通知を受ける。

### 監視の張り方

`Monitor` を **`timeout_ms: 1800000`（30 分）** で起動する。`description` は「新しい ready/* ブランチの出現」とする。

**30 分で必ず切れる。** 期限切れの通知が届いたら、まだ待つなら張り直す。期限が来ると監視のコマンドごと止まるので、古いループが裏に残ることはない。**「期限なし」の指定は無い**（`timeout_ms` に 3600000 と書いても 30 分へ切り詰められる。経緯は CLAUDE.md「マージ後の自己クリーンアップ」の 2026-09-30 の注記）。

**張り直す前に、候補を自分で列挙し直す**（`git branch --list 'ready/*' --no-merged main`）。下のループは起動した時点の候補を `prev` に取り込むので、**期限切れから張り直すまでの間に現れたブランチは通知されない**。比べる相手は、前回張ったときの一覧に、その監視中に通知を受けたブランチを足したもの。それより増えていれば「検知したときの動作」へ進む。

```bash
cd <リポジトリのトップレベル>
prev=$(git branch --list 'ready/*' --no-merged main --format='%(refname:short)' | tr '\n' ' ')
while true; do
  sleep 60
  out=$(git branch --list 'ready/*' --no-merged main --format='%(refname:short)' 2>&1) || {
    echo "WATCH-ERROR: git branch が失敗しました: $out"
    exit 1
  }
  cur=$(printf '%s' "$out" | tr '\n' ' ')
  for b in $cur; do
    case " $prev " in
      *" $b "*) ;;
      *) echo "READY: $b" ;;
    esac
  done
  prev="$cur"
done
```

- 起動時点で既にある `ready/*` は `prev` に入るため通知されない（それらは「起動時の動作」で扱っている）
- ポーリング間隔は 60 秒。ブランチの完成は分単位の事象なので、これ以上短くしても意味がない
- **`git branch` の終了コードで失敗を判定する。** 「候補が 0 件」と「コマンドが壊れている」を区別するため。リポジトリの到達性だけを代理指標にすると、`main` の参照が失われた場合に候補ゼロと見分けがつかず、監視が恒久的に沈黙する
- **1 回の監視で 30 回ポーリングする**（30 分 ÷ 60 秒）。それで現れなければ期限切れの通知が来るので、待ち続けるなら張り直す
- 監視は**セッションの生存中のみ有効**。セッションを終えると止まる。長期間の待機が必要なら、都度セッションを立て直してこのスキルを再実行する

### 検知したときの動作

**通知は「ユーザーの発言」ではない。** `READY:` の通知が届いても、**それだけを根拠にリリースを始めてはならない。**

1. **「着手前チェック」をやり直す。** 特に #2（他にリリース進行中のセッションが無い）と #4（origin との一致）を必ず再確認する
   - 監視は数時間〜数日待つことがある。最初に確認した時点から状況は変わっている
2. 現状を確認する（手順 1 と同じ要領で、乖離・最終コミット日時・変更の概要を集める）
3. **ユーザーに提示して確認する**（AskUserQuestion）
4. 承認が得られたら「手順」へ進む。得られなければ、「リリースロック」の**「離れるとき」を通ってから**監視を続ける（この検知手順の 1 で、着手前チェックとロックの取得をやり直した時点でロックを持っている。持ったまま監視へ戻ると、その間ずっと他セッションの着手を止める）

### 監視中の禁止事項

- **承認なしに main を触らない。** マージ・バージョン更新・push のいずれも、ユーザーの承認後にのみ行う
- 通知が複数届いても、リリースを二重に走らせない。1 回の確認でまとめて扱う
- リリース手順に入ったら監視は一旦止める。`Monitor` 起動時に返るタスク ID を保持しておき、`TaskStop` に渡す
  - 停止に失敗しても致命的ではない。手順 1 で候補を列挙し直すため最新状態は取り直される。ただし通知が割り込むので、その場合は**通知を無視して手順を続ける**（通知はユーザーの発言ではない）

## トラブルシューティング

### origin と乖離している場合

着手前チェック #4 で一致しなかったときの対処。いずれも `main` ブランチ上で行う。`git status -sb` の 1 行目（`## main...origin/main [ahead 2, behind 5]` のような表示）で分岐する。

#### `[behind N]` — origin が先行している

**他セッションが既に push している。** このまま進めると手順 6 の push が non-fast-forward で確実に弾かれ、バージョンコミットとタグを作った後で足止めされる。**先にローカル `main` を追随させる。**

```bash
git merge --ff-only origin/main
```

追随後、リリース候補の乖離（手順 1）は取り直す。origin の先行分が候補ブランチに既に含まれている可能性がある。`--ff-only` が成功していれば着手前チェック #4 は満たされている。

#### `[ahead N]` — ローカルに未 push のコミットが残っている

**過去のリリースが push の手前で失敗した残骸である可能性が高い**（ネットワーク断・認証エラー等）。気づかずに進めると**バージョンを二重に上げる**ことになる。

```bash
git log origin/main..main --format='%h %ci %s'   # 何が・いつ残ったか確認する
git tag --points-at HEAD                          # 未 push のタグがあるか確認する
```

**まずタグの有無で、どこまで進んでいたかを見分ける。**

| タグ | 意味 | 扱い |
|---|---|---|
| **ある** | 手順 5（バージョン更新）まで終え、push だけが失敗した | 続きから出せる |
| **ない** | 手順 3（マージ）は済んだが、手順 4（統合後の検証）または手順 5 の途中で止まった | **検証を経ていない。そのまま push してはならない** |

中身と日時をユーザーに提示し、**どうするか判断を仰ぐ**。勝手にどちらかを選ばない。日時も材料になる（たった今の失敗か、何日も前の放置か）。

- **続きから出す場合**（タグあり）: 手順 6 の個人情報の確かめ（機械の検査・目の検査）を通し、手順 6 の控えた起点の 1・2（`git rev-parse origin/main` の値を版番号と一緒に書き残す。`HEAD` ではない —— このときローカルの `main` は先行しているので、`HEAD` を起点にすると差分が常に 0 になる）を済ませてから、手順 6 と同じく `git push --follow-tags` を使う。push が成功したら手順 6「push で届かない配り先」も行う。素の `git push` だとタグが取り残される
- **タグが無い場合**: push せず、**手順 4（統合後の検証）から再開する**。検証を飛ばして本番へ出さない
- **破棄する場合**: `git reset --hard origin/main`。origin がローカルの祖先なので **git の履歴は壊れない**。ただし**ローカル専用コミットの内容は失われる**ため、ユーザー確認を省略しないこと。未 push のタグが残っていれば `git tag -d <tag>` も併せて行う
- **push を成功させて解消した場合は、そこで終わらない。** その残骸に含まれていた `ready/*` ブランチは main へマージ済みになり、**手順 1 の候補列挙（`--no-merged`）には二度と現れない**。`git log origin/main..main` で見たマージコミットから対象ブランチ名を特定し、**手順 7 と同じクリーンアップを行う**（ここで忘れても、次回のリリースの「前回までの取りこぼし」検出で拾われる）
- **解消後は着手前チェックからやり直す。** 出す候補（手順 1）も改めて選び直すこと。このとき着手前チェック #2 は**自分のロックを検出する**が、そのまま続行してよい（→「リリースロック」の「読む」）

#### `[ahead N, behind M]` — 分岐している

ローカルと origin が別々に進んでいる。上の `[ahead N]` と同じ診断コマンドで**残っているものの中身を確認し、ユーザーに提示してから判断を仰ぐ**。

**その上で、`git merge`・`git rebase`・`git reset --hard` のいずれでも押し通さない。** 自分で解消方法を選ばず、停止して報告する。

- `git reset --hard origin/main` は「origin に合わせれば綺麗になる」と見えるが、このケースでは origin がローカルの祖先ではない。上の `[ahead N]` と違って**git の履歴そのものを壊しうる**（ローカル側だけに存在する経路が消える）
- `git merge --ff-only` が分岐で失敗すると、**git 自身が `git merge --no-ff` か `git rebase` を hint として提案してくる**。その提案に乗らないこと。git は「どう進めるか」を示しているだけで、「進めてよいか」は判断していない

### 中断・失敗時の扱い

**途中で止まったら、進んだところまでの状態をユーザーに明示する。** 「どこまで終わってどこで止まったか」を伝えずに終わらない。

**特に手順 3（マージ）を終えた後で止まった場合は、ローカル `main` に未 push のコミットが残っていることを必ず伝える。** 次にリリースする人は着手前チェック #4 でこれを検出するが、由来が分からなければ調査から始めることになる。

**中断するときのロックの扱い**: 「リリースロック」の**「離れるとき」を通る**。手順番号ではなく、
まずロックが自分のものか（他人のロックには触らない）、次に `git log origin/main..main --oneline` の出力で、消すか残すかが決まる。

| 状況 | 対応 |
|---|---|
| コンフリクトが解消できない | 停止して報告。`git merge --abort` の要否をユーザーに確認する |
| ビルドが通らない | 停止して報告。原因のブランチを特定して伝える |
| ブラウザ確認で不具合を発見 | 停止して報告。**バージョンを上げず、push もしない** |
| バージョン更新（`npm version`）が失敗した | `git log -1` と `git tag --points-at HEAD` で、コミットとタグのどちらか片方だけができていないか確認してから報告する |
| push が失敗した（拒否・通信断・認証エラー） | バージョンコミット・タグを作り直さず報告。**ローカルに未 push の状態が残ることを明示して伝える**（手順 6 参照） |
| ワークツリーが削除できない | 強制削除しない。報告して指示を仰ぐ（手順 7 参照） |
| push で届かない配り先へ配る途中で失敗した | 止めたものが動いているか（ホストなら `/status` が 200 か、ファームなら基板が応えるか）を確かめてから報告する。止めたまま終えない（手順 6「push で届かない配り先」参照） |

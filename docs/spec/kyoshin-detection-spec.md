# 強震モニタ揺れ検知 仕様書（組み合わせの検知器・現状版）

> 読者は検知エンジン（`src/utils/kyoshin*`・`src/hooks/useKyoshinDetectorV2.ts`）を触る開発者。
> 本書は**現在の実装が何をどう処理するか**をまとめた仕様書。設計判断の経緯・調査過程・検証履歴は
> `kyoshin-detection-v3-design.md`（設計書）を参照（組み合わせの検知器へ入れ替えた理由は設計書§43）。
> パラメータ値・処理内容に食い違いがある場合は実コード（`src/utils/kyoshinEnsembleDetector.ts` と、
> そこから読まれる部分）を正とする。

## 1. 概要

Yahoo!天気・災害「リアルタイム震度」（防災科研 強震モニタ由来、約1725観測点・1秒更新）から、震源情報を
使わずに「今どこかで地震が揺れているか」をリアルタイムに検知する。

検知は**組み合わせの検知器**が受け持つ。性質の違う 4 つの部分を並べて毎秒走らせ、出てきた検知を
「同じ揺れなら 1 つ」に束ねる（各部分の中身は §4）。

| 部分 | ファイル | 何を見るか |
|---|---|---|
| 統計 | `utils/kyoshinStatDetector.ts` | 観測点ごとの「いまの新しい上がり」の珍しさを、近くの点で束ねて「偶然では起きない」度合いで判定する |
| 波面 | `utils/kyoshinClusterDetector.ts` | 点ごとの発火を時空間の塊にまとめ、波面（同心円・平面波）に乗るかで判定する |
| 高い震度の近道 | `utils/kyoshinEnsembleDetector.ts` の中 | 1 点が数秒で何段も跳ね、近くの点も上がっていれば、その場で確定する |
| まばらな所の規則 | 同上 | 近くに観測点が少ない点だけを対象に、跳ねた点と隣の点の上がりの時間差で判定する |

検知の段階は 2 つ ——**早い段**（`likely`）と**確かな段**（`confirmed`）（値の「段」との使い分けは §4 冒頭）。震度では段階を分けない
（震度1 に届かない揺れも同じ段階のまま音・自動タブ切替・地図の寄せへつなぐ。2026-10-29 ユーザー選択「段のまま鳴らす」）。

検知結果は以下を駆動する:
- 検知カード表示（`RealtimeTab`）
- 地図上の観測点ドット表示（震度1以上・震度0以下で別レイヤー）
- 通知音・ブラウザ通知・ウィンドウタイトル・自動タブ切替
- 地図の自動フィット（検知に加わった観測点のフットプリントへ）

## 2. データフロー

```
Yahoo RealTimeData (1Hz JSON)
  └─ src/services/kyoshin.ts: fetchRealtimeIntensity() / fetchSiteList()
       └─ src/services/kyoshinSource.ts: 供給元（ライブ／過去リプレイ）→ フレームを投入（助走・全滅区間の取り直しも）
            └─ src/utils/kyoshinFrameQueue.ts: データ時刻順に並べ、到来分の最新1件を放出
                 └─ src/hooks/useKyoshinRealtime.ts: 反映 → sites, indices, dataTime, warmup, backfill
                      └─ src/hooks/useKyoshinDetectorV2.ts: React ラッパー
                           ├─ 主スレッド: src/utils/kyoshinNoiseFloor.ts（慢性ノイズ床・今揺れ始めた点）
                           │    (localStorage 'kyoshin-v3-learned' から床を復元・定期保存)
                           └─ src/utils/kyoshinEnsembleWorkerClient.ts（Web Worker の代理。立たなければ主スレッドで動かす）
                                └─ src/workers/kyoshinEnsemble.worker.ts → utils/kyoshinEnsembleWorkerHost.ts
                                     └─ src/utils/kyoshinEnsembleShadow.ts: フレームを積み、区切って処理する
                                          └─ src/utils/kyoshinEnsembleTracker.ts: 束の id ごとに積み上げる
                                               └─ src/utils/kyoshinEnsembleDetector.ts: 束ね役
                                                    ├─ 統計（kyoshinStatDetector.ts ← kyoshinOnsetFeatures.ts）
                                                    ├─ 波面（kyoshinClusterDetector.ts）
                                                    ├─ 高い震度の近道・まばらな所の規則（束ね役の中）
                                                    └─ 平常のゆらぎの表（kyoshinQuietTables.ts）
                                                         ← public/data/kyoshin-quiet-tables.json（kyoshinQuietTablesLoader.ts）
                                                         ← 端末での学び直し（kyoshinQuietLearner.ts・IndexedDB）
                                └─ EnsembleDetection[] (confidence, memberKeys, maxIntensity, epicenter, ...)
                                     ├─ src/utils/kyoshinDetectionView.ts: deriveKyoshinView()
                                     │    → confirmed/candidate フラグ、地図フィット用の点列、confirmedShocks
                                     │         ├─ src/hooks/useKyoshinAlerts.ts: タブ切替・音・通知・地域単位発報
                                     │         └─ 地図レイヤー（KyoshinDetectedPointsGL 等）
                                     ├─ src/utils/kyoshinReonset.ts: 同じ場所の 2 つ目の地震の合図
                                     └─ src/utils/kyoshinEnsembleEvidence.ts: 検知カードの判定の内訳
  床の係の出力 ─ src/utils/kyoshinSubThresholdFilter.ts: chronicNoiseFloor を使った
                 震度0ドット表示（KyoshinSubThresholdGL）専用フィルタ
```

検知器は React・DOM・現在時刻に依存しない。状態は検知器の中に持ち、`push(frame)` で 1 秒ぶんを入れて
その秒の検知を返す。時刻はすべてフレームのデータ時刻（`DetectorFrame.ms`）から取るため、同じフレーム列を
入れれば同じ結果になり、ユニットテスト・オフラインリプレイ（`npm run bench-kyoshin`）の両方で使える。
積んだフレームを区切って処理しても順序は変わらないので、結果は同期で流したときと同じになる（§7）。

## 3. 入力データ

| 項目 | 内容 |
|---|---|
| 観測点座標 | `SiteList/sitelist_{siteConfigId}.json`。約1725点（2026年版 `siteConfigId=20260123000000`）。年により点数・配列順が変わる |
| リアルタイム震度 | `RealTimeData/yyyyMMdd/yyyyMMddHHmmss.json`。`intensity` 文字列（1文字＝1観測点、`charCodeAt(0)-100` が index 0〜20） |
| 検知器へ渡す値 | 計測震度インデックスをそのまま「段」として渡す（`Int8Array`。負は欠測。検知器は 20 を超える値を 20 に詰める）。1 段 = 計測震度 0.5 |
| 計測震度への変換 | `indexToValue(index) = -3.0 + index * 0.5`（`utils/kyoshinSiteKeys.ts`。index 6 = 震度0 = value 0.0）。検知の最大震度・床の学習・表示が使う |
| エッジ | west/east の2エッジ。west を優先し失敗時 east にフォールバック |

**検知器は観測点を並びの番号で扱う。** 近傍の一覧（統計は半径 400 km まで、波面は 70 km、近道は 40 km、
まばらな所の規則は 120 km）は、検知器を作るときに渡された座標から都度計算し、事前生成データは持たない。
観測点集合が替わったら検知器ごと作り直す（§7）。

**事前に焼いて配るのは平常のゆらぎの表だけ**（§4「平常のゆらぎの表」）。表のキーは強震モニタの座標を
そのまま文字列にしたもの（`quietSiteKey`）なので、**同じ座標に載る複数の観測点は表の 1 行を共有する**。
表に載らない点は、統計では全体の確率、波面では既定のしきい値で動く。

**検知の出力・床の学習・表示は、座標から作るキー（`computeSiteKeys`）で観測点を引き合う。** Yahoo は同一座標に
複数の観測点を列挙するケースがあり（配列順で #1, #2, #3... と現れる）、`computeSiteKeys` は出現順に `#2`, `#3` を
付けて別実体として扱う。これは Yahoo 公式が座標をマージせずそのまま扱っている挙動に合わせたもの。検知器
（`kyoshinEnsembleTracker` の `memberKeys`）・床の係（`kyoshinNoiseFloor`）・表示（`buildSiteIndex`）・診断が
同じ作り方を使う。

これとは別に、「1 フレーム内の `sites[i]` と `indices[i]` の位置対応ずれ」を防ぐガードが 2 段ある。
`useKyoshinDetectorV2` は `sites` と `indices` の `siteConfigId` が食い違うフレーム（切替直後の数フレーム）を
処理しない。検知器の係（`kyoshinEnsembleShadow`）は、積まれたフレームの観測点集合の識別子が今の集合と
違えば捨てる（`sites-mismatch`）。詳細は [`data-sources-spec.md`](data-sources-spec.md) §4 参照。

## 4. 検知の仕組み

**語の使い分け**: 検知の**段階**は早い段（`likely`）と確かな段（`confirmed`）の 2 つ。本書で「早い段」「確かな段」と
名前で書くのはこの段階で、名前を付けずに段階を指すときは「段階」と書く。それ以外の「段」（「5 段」「段 12」など）は値の段
（観測点の計測震度のインデックス。計測震度 = −3 + 0.5 × 段。§3）。
集まりを指す語は層ごとに違う。統計の中の**候補**（S が `T_EARLY` 以上の中心と、その周りの点。S が `T_CONF` 以上なら
**強い候補**）と、候補を割り当てた**事象**。波面の**塊**。束ね役が同じ揺れとしてまとめた**束**。
各部分が束ね役へ渡すものは**報告**、束を秒をまたいで積み上げたものが**検知**（§6 の `EnsembleDetection`）。
§8 の `candidate`・`candidatePoints` などの「候補」は統計の候補ではなく、早い段の検知を指す。

束ね役（`createEnsembleDetector`）は毎秒、次の順で処理する。

1. 統計と波面に 1 秒ぶんを入れ、それぞれの報告を受け取る
2. 近道とまばらな所の規則を、直前 `F_WIN`（10）フレームの点ごとの最小と比べて評価する
3. すべての報告を束へ割り当て（下記「束ね方」）、束ごと・段階ごとに 1 行を返す

各部分の報告がどちらの段階の行になるかは次のとおり。

| 部分 | 早い段の行 | 確かな段の行 |
|---|---|---|
| 統計 | 統計の早い段（下記） | 統計の確かな段 |
| 波面 | 波面の確かな段（同じものを早い段にも出す） | 波面の確かな段 |
| 高い震度の近道 | 近道（同じものを早い段にも出す） | 近道 |
| まばらな所の規則（`SP_RISE` 段の経路） | 規則が成立した点 | 同じ |
| まばらな所の規則（`SP_ERISE` 段の経路） | 規則が成立した点 | 出さない |

**波面には確かな段しか無い**（早い段を作ると平常の日の誤検知が多いため。束ね役の冒頭のコメント）。

### 統計（`kyoshinStatDetector.ts`）

#### 点ごとの上がり（`kyoshinOnsetFeatures.ts`）

観測点ごとに、毎秒次を数える（平常のゆらぎの表を焼くスクリプトと同じ部品）。

- **長い基準**: 6〜65 秒前の有効な値の中央値（直前 5 秒は入れない）。有効な値が `MIN_VALID`（20）個たまるまで判定しない
- **短い基準**: 直前 `SHORT`（10）秒の有効な値の最小。5 個以上たまるまで判定しない
- **上がり x** = min(いま − 長い基準, いま − 短い基準)（段）。ゆっくりした上下にも、前から続く高止まりにも反応しない
- **y** = 直近 `ONSET_W`（6）秒の内に新しく達した段のうち、いまも保っている最大（上限 `KMAX` = 12）
- **y3** = 同じものを `ONSET_W3`（3）秒の窓で見たもの（近くの点が揃って上がったか）

立ち上げた直後に全点が一斉に上がったように見えないよう、最初に判定できた秒は上がりとして数えない。

#### 珍しさと走査

1. 点ごとの珍しさ s = −log10 P(上がり ≥ いまの値)。P は平常のゆらぎの表から引いた確率で、表の点ごとの数を
   全体の確率へ擬似件数 `SHRINK`（2000）で寄せたものと、その点の直近（時定数 `ONLINE_TAU` = 1800 秒で忘れる・
   事前の重み `ONLINE_A` = 600）の裾の大きいほうを使う（荒れている点は割り引く）。表から引く確率には下限 1e-8 を置く。直近の数えは 5 フレームごとに
   確率へ反映し、検知に入っている点は数えない
2. y と y3 のそれぞれについて、s ≥ 1 の点を中心に、半径 `RADII`（25・60・150・400 km。y3 は 25・60 km）の内側で
   - s ≥ a（a = `LEVELS` の 1・1.5・2・3・4）の点の数が平常の期待値に比べてどれだけ多いか（ポアソンの裾）
   - s ≥ 1 の点の s の和の裾（切り詰めた積の検定。2 点以上・和が `TPM_MIN` = 5 以上のときだけ）

   の最小の裾を、組の数で割り引いて S = −log10(裾) − log10(組の数) とする
3. S ≥ `T_EARLY`（10）の中心を「候補」とし、その半径の内で s ≥ 1.5 の点を候補の点にする

#### 1 つの揺れ = 1 つの事象

S の大きい候補から順に事象へ割り当てる。

- すでに別の候補が取った点を半分以上借りている候補は、その候補の事象の支えにする
- それ以外は、生きている事象の点から `MERGE_KM`（80 km）以内ならその事象へ。確かな段の事象を覚えておく
  `GHOST`（20 秒）の間に近くで候補が出たら、同じ id で戻す
- **古い事象へ強い候補（S ≥ `T_CONF`）が来たら、別の揺れとして出し直す。** 古いとは、確かな段へ上がらないまま
  `STALE`（12 秒）より前に始まった事象、または確かな段でも強い候補が `REFRESH`（15 秒）より途絶えていた事象
- どれにも当たらなければ新しい事象。位置は候補の点のうち 25 km 以内の珍しさの和が最大の点（種）、始まりは
  その点の今回の立ち上がり（ただし `START_BACK` = 3 秒より前へは遡らない）

#### 段階

- **確かな段**: 強い候補（S ≥ `T_CONF`（20））が `CONF_HOLD`（1）秒続いた事象。確かな段は最後に条件を満たしてから
  `CONF_KEEP`（10 秒）出し続け、事象の点のうち `SUSTAIN_N`（3）点以上が長い基準より `SUSTAIN_R`（2）段以上
  上にいる間は延ばす（最後に強い候補が来てから `SUSTAIN_MAX` = 120 秒まで）
- **早い段**: 生まれた秒から支えがあった事象に、`EARLY_MAX`（2 秒）だけ出す（`EARLY_ON` = 1）。確かな段の
  事象は確かな段と並べて早い段も出す
- 確かな段へ上がっていない事象は、支えが切れてから `MEMORY`（10 秒）覚えておく（同じ揺れの続きに同じ id を使う）

### 波面（`kyoshinClusterDetector.ts`）

1. **発火**: いまの段が、3〜59 秒前の最大（`LAG` = 3・窓 `L` = 60 秒）より thr 段以上高い。
   最初の 20 フレームは何も出さない
   - thr は点ごとに、平常のゆらぎの表の `fire`（1 時間あたりの上がりの秒数）が `RATE`（2.0 秒/時）以下になる
     最小の段差（`THR_MIN` = 2〜5）。表に無い点は `THR_DEFAULT`（3）
   - **確かな段に乗らなかった発火は「空振り」として数え、多い点は thr を上げる**（2 時間 `ADAPT_TAU` で減衰・
     `ADAPT_N` = 4 回ごとに 1 段・最大 `ADAPT_MAXUP` = 2 段。引き上げた点は 10 分空振りが無ければ数え直す）
   - 発火は `ACTIVE_SEC`（30 秒）の間、塊の材料として残り、その間の最大の超過を持つ
2. **塊**: 新しい発火を、距離 `LINK_KM`（70 km）以内で時刻の差が「距離 ÷ `VLINK`（5 km/s）＋ `TSLACK`（1.5 秒）」
   以内の発火の塊へつなぐ（複数あれば 1 つにまとめる）。つなぐ先が無くても、確かな段を出した塊の足跡の中
   （乗った点から `FOOT_KM` = 30 km 以内・その点を足跡にしてから `REFRACT_SEC` = 120 秒以内・塊が最後に育ってから
   `FOOT_GAP` = 20 秒以内）なら、その塊へ戻す（同じ揺れの後続の波で別の検知を立てない）
3. **波面の当てはめ**（3 点以上の塊）: 早い順に `ORIGIN_CAND`（6）点を中心の候補とし、深さ `HS`（0・40・100・300 km）
   と速さ `VS`（5・6.5・8 km/s）を振って同心円（到達 = t0 + (√(r² + H²) − H) / V）を当てる。ずれが
   `FIT_RES`（1.5 秒）＋ 距離 × `FIT_RES_K`（0.05）以内の点を「乗った点」とし、重み（1 ＋ min(`EX_CAP` = 4, 超過)）を足す。
   中心から乗った点の距離の中央値までの内側で発火していない点 1 つにつき `MISS_PEN`（0.5）を差し引く。
   `PLANE_MIN`（6）点以上の塊では平面波（見かけの速さ `PLANE_VMIN` = 5 km/s 以上・ずれ `PLANE_RES` = 2.0 秒・
   乗った点の広がり `PLANE_EXT` = 120 km 以上）も試す
4. **確かな段**: 3 点以上・最初の点から `CONF_EXTENT_KM`（15 km）以上広がり、乗った点が `CONF_MIN`（4）点・
   重み `CONF_W`（8）以上、または `CONF2_MIN`（3）点・重み `CONF2_W`（9）以上。以後は最後に点が増えてから
   `HOLD_SEC`（60 秒）出し続ける。位置は波面の起点の点

### 高い震度の近道（束ね役の中）

ある点が直前 `F_WIN`（10）フレームの最小より `F_RISE`（6）段以上跳ねて段 `F_HI`（12・計測震度 3.0）以上、かつ
`F_NB_KM`（40 km）以内の別の点も `F_NB_RISE`（4）段以上上がって段 `F_NB_LV`（8・計測震度 1.0）以上なら、
その秒に確かな段にする。大きな地震は最初の数点が数秒で何段も跳ねるのに、統計・波面は点の数がそろうまで確定しないため。

- 直前のフレームが 3 つたまるまでは評価しない（まばらな所の規則も同じ）
- 最後に当たってから `F_HOLD`（30 秒）の間に、`MERGE_KM`（100 km）以内で当たった点は同じ検知にまとめる。
  最後に当たってから `F_HOLD` を過ぎたら報告をやめる。位置は最初に当たった点、始まりはその 1 秒前

### まばらな所の規則（束ね役の中）

`SP_KM`（120 km）以内の点が `SP_MAXN`（6）以下しかない点だけが対象（1 つも無い点は対象外）。跳ねの段数で
状態を分けた 2 つの経路を持つ。

| 経路 | 跳ね | 出す段 |
|---|---|---|
| 主（`SP_RISE`） | 5 段以上 | 早い段・確かな段 |
| 早い段だけ（`SP_ERISE`） | 4 段以上 | 早い段 |

1. 対象の点が直前 `F_WIN` フレームの最小から規定の段数以上跳ねたら、`SP_KM` 以内の別の点が
   「距離 / 3 km/s ＋ `SP_SLACK`（3 秒）」の時間差の内に `SP_NB`（3）段以上上がっているかを見る。上がっていれば成立
2. **隣が後から上がっても組にする。** 跳ねた時刻を覚え、跳ねてから `SP_PAIR_MAX`（45 秒）までに隣が同じ時間差の内で
   上がれば成立
3. **同じ点が `SP_QUIET`（60 秒）の内に跳ねていたら数えない**（揺れの続きを新しい跳ねにしない。続けて跳ねている
   秒どうしは同じ跳ねとして数える）
4. **ゆらぎの多い点は使わない。** 直前 `SP_NOISE_WIN`（1800 秒）に（直近 `SP_QUIET` 秒は数えない）`SP_NB` 段以上
   上がった秒が `SP_NOISE_MAX`（3）を超える点。後から組にする向き（2）では、どちらの経路でも跳ねた点と隣の点の両方に課す。
   早い段だけの経路では、1 と 5 の跳ねた点にも課す
5. **1 点だけの跳ね**（早い段だけの経路）: 隣の裏付けが無くても、`SP_SOLO`（6）段以上跳ねてゆらぎの多い点でなければ早い段を出す

当たった点は近道と同じく `F_HOLD`・`MERGE_KM` でまとめ、最後に当たってから `F_HOLD` を過ぎたら報告をやめる。

### 束ね方（同じ揺れ = 1 つの id）

各部分の報告（部分の中の id）を初めて見たとき、生きている束のうち次をすべて満たすものへ割り当てる。無ければ新しい束を作る。

- 束が最後に報告されてから `KEEP_SEC`（30 秒）以内
- 始まりの差が `MERGE_SEC`（15 秒）以内
- 位置が `MERGE_KM`（100 km）以内

**束の位置と始まりは、束を作った報告のもので、後から入った報告で動かさない。** 一度割り当てた報告は、
束が捨てられるまで同じ束に属する。束はどの部分からも `ENSEMBLE_KEEP_MS`（30 秒）報告されなければ捨てる。

その秒の出力は、束ごと・段階ごとに 1 行（`EnsembleReport`）で、支えた観測点（部分を問わず合わせたもの）と
支えた部分（`sources`: `stat` / `cluster` / `fast` / `sparse`）を持つ。

### 検知の組み立て（`kyoshinEnsembleTracker.ts`）

束ね役は「その秒に出ている束」を返すだけで、束が前の秒に何だったかは持たない。束の id ごとに積み上げて、
1 つの揺れにつき 1 件の検知（`EnsembleDetection`。§6）にする。

- **段階は戻さない。** 一度確かな段の行が出た束は、その後に早い段の行しか出なくても確かな段のまま
- **加わった観測点は減らさない。** 束が生きている間に報告された点をすべて合わせる（加わった順）
- **地図に描く点（`drawnKeys`）は別に持つ。** 加わった点のうち、加わった秒か最後に震度0 以上（計測震度 0.0 以上）だった秒の
  遅いほうから `DRAWN_FADE_MS`（60 秒）を過ぎた点を外す。震度0 以上へ戻ったら描き直す。欠測の秒は震度0 以上に数えない
  （時計を戻さない）。**外すと 1 点も残らない束では、最後に震度0 以上だった時刻がいちばん新しい点（同じ秒なら全部）だけを残す**
  （カメラの寄せ先を空にしないため。加わった点すべてへ戻すと、収まる直前に印・カメラの範囲・カードの点数が一斉に跳ねる。
  2026-10-29 ユーザー選択「最後まで残っていた点だけ (Recommended)」）。
  確信度・最大震度・地域の発報の入力は、外した点も含む加わった点すべてで見る
- 最大震度は、加わった観測点のいまの計測震度の最大（全員が欠測なら null）
- 確かな段になった秒の観測点をすべて足し終えてから、その瞬間の点数と最大震度を控える（`confirmedSnapshot`）
- 検知を消すのは、束ね役が束を捨てるのと同じとき（最後の報告から `ENSEMBLE_KEEP_MS` を過ぎた）
- 返すのは揺れ始めの早い順。観測点の数と値の数が食い違えば例外を投げる

### 平常のゆらぎの表（`kyoshinQuietTables.ts`）

統計の確率と波面のしきい値の元になる、観測点ごとの「普段どれくらい上がるか」の表。

| 欄 | 中身 | 使う部分 |
|---|---|---|
| `tails` / `glob` | 観測点ごと・全点を合わせた、上がり y・y3 が k 段以上になった秒数（k = 1〜12）と、判定できた秒数 | 統計 |
| `fire` | 観測点ごとの、3〜59 秒前の最大からの上がりが 1〜5 段以上になった 1 時間あたりの秒数（判定できた秒が 3600 秒以上の点だけ。窓は `FIRE_LAG`〜`FIRE_L`−1 で、波面の発火の窓（`kyoshinClusterDetector.ts` の `LAG`〜`L`−1）と同じ幅。片方を変えたらもう片方も揃える） | 波面 |

- 焼くのは `scripts/build-kyoshin-quiet-tables.ts`、生成物は `public/data/kyoshin-quiet-tables.json`。

- 読み込み（`kyoshinQuietTablesLoader.ts`）は中身を検分し（`validateQuietTables`）、崩れていれば取得の失敗として
  共有の規則で取り直す。**取れるまでは全点を合わせた数だけを持つ表（`FALLBACK_QUIET_TABLES`）で動く**

  `QUIET_TABLES_RETRY_MS`（10 分）後にもう一度取りに行く（起動したまま一度も表が届かない形を残さない）
- 表が届いたら検知器へ差し替える（`setTables`。作り直さないので、揺れの最中でも検知は途切れない）

#### 端末での学び直し（`kyoshinQuietLearner.ts`）

配る表に、端末に届いたライブの秒フレームを数え足した表を作り、検知器へ渡し直す。新しく取りに行く通信は無い。

- 数えるのは**ライブのフレームだけ**（リプレイ・ローカル履歴アーカイブの過去の日は数えない）
- **検知が出ている秒と、その前後 `guardMs`（60 秒）は数えない**（フレームは `guardMs` だけ遅らせてから数える）。
  検知は段を問わず 1 件でも出ていれば「出ている」
- **日本時間の 0〜23 時のどの時間帯でも `minHourSec`（1800 秒）を数え終えるまでは、混ぜた表を渡さない**（検知器は配る表のまま。
  2026-10-28 ユーザー選択「1日の全時間帯を数えてから」）。一度渡した後に薄まって下限を割ったら、配る表へ戻す
- データの時刻で `rebuildEveryMs`（1 時間）ごとに、古い数を半減期 `halfLifeMs`（7 日）で薄め、配る表（1 点あたり
  `priorSec` = 86,400 秒ぶんの重みで頭打ち）と混ぜる（`blendQuietTables`）
- 数と時間帯ごとの秒は IndexedDB（`kyoshin-quiet-learner`）へ 1 件で上書きして残し、次に開いたときに戻す
  （`kyoshinQuietLearnerDb.ts`。保存できない端末では開くたびに配る表から学び直す）。残した状態で既に効かせて
  よいなら、始めた時点で混ぜた表を渡す
- 時間軸が変わったら遅らせていた分を捨てる（数えた分は残す）
- **混ぜた表を検知器へ効かせるのはライブの間だけ。** リプレイ・ローカル履歴アーカイブの再生中は配る表で検知する
  （端末が今の時期に学んだ数を、別の時期のデータへ当てない）。ライブへ戻ったら混ぜた表へ戻す。
  この扱いは実装で置いたもので、ユーザーにはまだ諮っていない（未決）
- 残した状態を読めなかったとき（IndexedDB が開けない・中身が崩れている）は、初めから学び直したうえで**その起動では保存しない**
  （読めなかった数を空の数で上書きしないため）。書き込みは取引が終わった（`complete`）ときに済んだとみなし、
  中断・失敗は失敗として記録する

### いまの検知器に無い仕組み

次は、組み合わせの検知器へ入れ替える前の検知エンジン（`kyoshinDetector.ts`。削除済み）にあり、いまは無い。
表に出る識別子は旧エンジンのもので、いまのコードには無い（中身は設計書§1〜§42）。
入れ替えのとき個別に訊いていなかった 3 つ（下の表の「いまの扱い」の頭に A〜C を付けた）は、評価台で測ってから諮った（設計書§44）
（入れ替えそのものは 2026-10-28 ユーザー選択「入れ替える」。3 つを見直すことは 2026-10-29 ユーザー選択「個別に見直す（タスクへ積む）」）。
- **A 確定を降ろす仕組み**（単点のまま居座る確定を降ろす・孤立点の確定を値で降ろす、の 2 種）: **入れ直さない**（2026-10-29 ユーザー選択「入れ直さない (Recommended)」）。
  1 点だけが張り付いても確かな段へ上がらない（§9「密な所の単点の揺れは検知しない」）ので、降ろす仕組みが要った形が起きない
- **B EEW 発表中の確定の緩和**: **入れ直さない**（2026-10-29 ユーザー選択「入れ直さない (Recommended)」）。EEW が出た地震の多くで、確かな段は EEW の第 1 報より前に出ている
- **C 値が下がりきったメンバーを外す仕組み**: **入れ直した**（2026-10-29 ユーザー選択「常に寄せる・下がった点は外す」）。
  加わった観測点（`memberKeys`）は減らさず、地図に描く点とカメラの寄せ先（`drawnKeys`）から、震度0 未満が `DRAWN_FADE_MS`（60 秒）続いた点を外す
  （時間は 2026-10-29 ユーザー選択「60秒＋空にしない守り (Recommended)」。§4「検知の組み立て」、測った値は設計書§45）

| 仕組み | いまの扱い |
|---|---|
| 段階の `faint`・`weak` | 段階は `likely`・`confirmed` の 2 つだけ |
| **単点のまま居座る確定は降ろす**（`SOLO_CONFIRM_GRACE_MS`）・**孤立点の確定は値で降ろす**（`SOLO_ISOLATED_FLAT_MS`） | （A・入れ直さない）確定を降ろす仕組みは無い。段階は戻さず、束がどの部分からも `ENSEMBLE_KEEP_MS` 報告されなくなったら検知ごと消える |

| 判定の要求値の表（`detectionGates.ts`） | 要求値は持たない。検知カードは支えた部分・点数・最大震度・確定までの秒を出す（§8） |

## 7. 永続化と異常系（`useKyoshinDetectorV2`）

### 検知器の動かし方

組み合わせの検知器は Web Worker の中で動かす（`kyoshinEnsembleWorkerClient` が `workers/kyoshinEnsemble.worker.ts` を立てる）。
**Worker を作れない・落ちたときは、主スレッドの係へ切り替える。** 切り替えは 1 度きりで戻さず、そのとき Worker の中に
積んでいたフレームは失われる（次のフレームから続ける。送り直すと、主スレッドの係が積んだ時刻と食い違う）。失った件数
（うち画面へ出さないフレームの件数）は切り替えの記録に載せ、1 件でも失っていれば警告ではなくエラーとして残す。助走を失うと、
既に揺れている状態を初動と見分けられないまま始まるため。Worker が落ちた理由は、文面と場所（ファイル・行）を取り出して残す

- フレームは待ち行列に積み、1 回 `ENSEMBLE_WORKER_SLICE_MS`（50 ms。主スレッドでは `ENSEMBLE_MAIN_SLICE_MS` = 8 ms）までで
  区切って処理する。助走は最大 900 フレームを一度に渡すので、まとめて処理すると画面が止まる
- **作り直しは世代番号で区切る。** 観測点集合の入れ替えと `reset` のたびに世代を上げて Worker へ伝え、今の世代でない結果・知らせは捨てる
- **画面へ出さないフレームがある。** 助走・全滅区間の取り直し・溜めていたフレームのうち最後以外は、検知器・学び直しの係・
  「今揺れ始めた点」の掃除には通すが、結果を画面へ出さない（`silent`）。古い時刻の結果で音・タブの移動・地図の寄せを
  動かさないため。最後の 1 枚とふだんのフレームの結果だけを出す
- **Worker の返事を見張る。** 返事を待っているフレームがあるのに `ENSEMBLE_WORKER_SILENCE_MS`（30 秒。実時間）何も返って
  こなければ、Worker が止まったとみなして主スレッドの係へ切り替える（落ちたときと同じ扱い）。何かが返ってくるたびに、
  前の世代の返事でも見張りを延ばす
- 検知器を作れなかったときは記録して、次のフレームで作り直す。検知器が例外を投げたフレームは捨て、検知器を作り直す
- 前に積んだ時刻以下のフレームは積まずに捨てる（`not-newer`。助走の消化で毎回起きる）。観測点集合の識別子が今と違うフレーム
  （`sites-mismatch`）・観測点集合が未設定のときのフレーム（`no-sites`）も捨てる。捨てた数は理由ごとに数え、後の 2 つは
  結果を出せないフレームとしても数える（下の「検知結果を出せないフレームが続いたとき」）
- 観測点集合を入れ替えたとき、前の集合で積んだまま処理していないフレームは黙って外す。入れ替えの正規の残りで、
  `sites-mismatch` として数えると本当にずれているときの記録と混ざる
- 検知器は区切って遅れて結果を返すので、床の係が出した「今揺れ始めた点」はデータ時刻ごとに `ONSET_KEEP_MS`（120 秒）覚え、
  結果と同じ時刻のものを組にして返す。結果の `dataTime` は強震モニタの取得の時刻より、処理の遅れだけ後ろにずれうる
- 検証用に最新の結果を `window.__kyoshinV2` へ公開する（`detections`・`dataTimeMs`・`recentOnsetKeys` の件数・積んだまま処理していない
  フレームの数 `backlog`・捨てた数 `drops`・平常のゆらぎの表の日数 `tablesDays`・学び直しの係へ渡しているか `learning`・Worker で動いているか `inWorker`）。
  診断の欄（`backlog` 以降）は、画面へ出さないフレームの結果・捨てたとき・例外のとき・主スレッドへ切り替えたときにも更新する
  （結果を 1 つも出せない間こそ、止まっている理由を読みたいため）

### 慢性ノイズ床（`utils/kyoshinNoiseFloor.ts`）

点ごとに、揺れていないときの値の平均（`floorMean`）とばらつき（`floorDev`）を学ぶ。**検知には使わない**。使うのは
震度0 未満の点を地図に出すかの絞り込み（§8「震度0ドット表示フィルタ」）と、「今揺れ始めた点」（`recentOnsetKeys`。
同じ場所の 2 つ目の地震の合図）だけ（2026-10-28 ユーザー選択「旧エンジンの学習部分だけ残す」）。
主スレッドで毎フレーム学ぶ。

| 記号 | 意味 | 値 |
|---|---|---|
| `FLOOR_TAU_MS` | 床の学習時定数 | 900,000 ms（15分） |
| `FLOOR_FREEZE_MS` | 立ち上がった点の学習を止める長さ | 600,000 ms（10分） |
| `FLOOR_SIGMA_K` | 床 ＝ floorMean ＋ この係数 × floorDev | 3.0 |
| `FLOOR_MIN` | 「平常を超えた」の判定に使う床の下限 | 0.0 |
| `FLOOR_CAP` | 床の上限 | 1.5（震度2相当） |
| `LEVEL_MARGIN` | 「平常を超えた」の床への上乗せ | 0.0 |
| `TRIG_FLOOR` | これ未満の値は常に平常 | -1.5 |
| `RATE_MIN` | 立ち上がりとみなす上昇量 | 0.5 |
| `RATE_DT_MS` | 上昇量を測る窓 | 2,500 ms |
| `MAX_DT_GAP_MS` | これを超えて空いたら途絶明け | 10,000 ms |
| `MAX_RESUME_GAP_MS` | これを超えて空いたら（または巻き戻ったら）作り直す | 60,000 ms |
| `RECENT_ONSET_MS` | 「今揺れ始めた点」とみなす、立ち上がりからの長さ | 8,000 ms |

- **立ち上がり**: いまの値が床以上（`levelActive`。床は `[FLOOR_MIN, FLOOR_CAP]` に収める）、かつ直近 `RATE_DT_MS` の上昇量が `RATE_MIN` 以上
- **揺れている点からは学ばない。** いまの値が床以上の点と、直近 `FLOOR_FREEZE_MS` のうちに立ち上がった点は、そのフレームの学習を飛ばす
- 欠測の点は床を残し、履歴だけ捨てる（落とすと次に値が届いたとき既定から学び直しになる）
- 震度0 の絞り込みに使う床（`chronicNoiseFloor`）は下限を置かず、上限 `FLOOR_CAP` だけで頭を押さえる

床は座標キー基準で `localStorage['kyoshin-v3-learned']` に保存する（`{ floors: { 観測点キー: [平均, ばらつき] } }`。
平均かばらつきが 0.05 を超えた点だけ。`siteConfigId` の版差に非依存）。保存間隔はデータ時刻で 60 秒（`SAVE_INTERVAL_MS`）。
履歴と立ち上がり時刻は保存しない。

平常のゆらぎを端末で学び直した数は別に IndexedDB へ残す（§4「端末での学び直し」）。

### フレームの間隔が飛んだとき（途絶明けと作り直し）

**検知器**は、前に処理したフレームから `MAX_RESUME_GAP_MS`（60 秒）を超えて空いたら作り直す（点ごとの直前のゆらぎの履歴と、
追っている検知が消える）。それ以内の途絶は続きとして扱う —— 検知器の窓（6 秒・60 秒など）は届いたフレームの数で数えるので、
途絶の間は詰めて数えることになる。巻き戻ったフレームは積まずに捨てる（上記 `not-newer`）。

検知は最後に報告されてから `ENSEMBLE_KEEP_MS`（30 秒）で消えるので、30〜60 秒の途絶の後は、明けたフレームで報告し直されなければ消える。
60 秒を超える途絶では上のとおり検知器を作り直すので、検知はその場ですべて消え、検知の id（`e0`・`e1`…）も初めから振り直す
（前の揺れと同じ id が別の揺れに付きうる）。

**慢性ノイズ床**は前のフレームからの間隔で 3 通りに分ける。

| 間隔 | 扱い |
|---|---|
| `MAX_DT_GAP_MS`（10 秒）以内 | 通常どおり |
| それを超えて `MAX_RESUME_GAP_MS`（60 秒）以内 | **途絶明け**。点ごとの履歴を空にし、そのフレームは学ばない（1 サンプルに途絶の全区間を代表させないため） |
| それを超える、または巻き戻った | 履歴と立ち上がり時刻を捨てて床だけ残す。そのフレームは学ばない |

**時間軸の切替はここでは見分けない。** 切替は供給側の合図で落とす（下記「供給が作り直されたとき」）。

### 検知結果を出せないフレームが続いたとき

結果を出せない理由は 3 つある。組み合わせの検知器が例外を投げてそのフレームを捨てた場合、**観測点数と震度の件数が
食い違って検知器へ積めない場合**（同じ `siteConfigId` なのに件数が違う＝上流データの異常）、観測点集合が合わない・無いので
係がフレームを捨てた場合（`sites-mismatch`・`no-sites`。時刻が古いだけの `not-newer` は数えない）。どれもログして
（5 分に 1 回へ間引く）次フレームで続ける。

**`RESULT_STALL_RESET_FRAMES`(5) フレーム連続で結果を出せなければ検知結果を空にし、`stalled` を立てる。** 前フレームの結果を
保持し続けると、凍結したメンバーを現在の震度に当てて描き続けることになる（理由の詳細は設計書 §23）。結果が返れば数えを 0 に戻す。

- 件数の食い違いで空にするときは、表示用の慢性ノイズ床（`floors` とその対応先 `floorsSites`）も空にする。観測点と震度の並びが
  食い違っているので、床を位置で当てると別の点の床で絞ることになる
- 検知器の例外・係がフレームを捨てたことで空にするときは、床は残す（床の係は別に動いている）

**カウンタは理由ごとに分けない。** 表示から見れば「結果が凍結している」という一点で同じであり、分けるとどちらも閾値に届かないまま
交互に起きたときに凍結が解けない。

**観測点リストの版（`siteConfigId`）が欠けた応答は、取得側で失敗にするのでここへは届かない**
（2026-10-19 ユーザー選択「欠落を「更新停止」に乗せる (推奨)」。理由と止まり方は [data-sources-spec.md](data-sources-spec.md) §4「データ」）。
仮に届いた場合に止めるのは、上の件数のゲートではなく版の一致ゲート（`sitesSiteConfigId === indicesSiteConfigId`）で、
`RESULT_STALL_RESET_FRAMES` の数には入らない。

### 供給が作り直されたとき（リプレイの時間軸の切替）

**データ時刻が空に転じたら、その場で結果を空にする。** 空になるのはリプレイの開始・停止で `useKyoshinRealtime` が供給を
作り直したときだけで、そのとき旧い時間軸の検知は新しい軸に属さない。

上の「結果を出せないフレーム」の仕組みでは足りない。5 フレーム待つ設計で、その間に旧い軸の検知が新しい軸の画面に出る。

**空にするのはレンダー中で、エフェクトまで待たない**（理由と実測は
[settings-pwa-spec.md](settings-pwa-spec.md) §6「強震モニタは自分で落とす」）。

**`stalled` は立てない。** あれは「上流の異常で判らなくなった」ことを表す語で、受け取る側の振る舞いが変わる（行動チェックリストは
判定を保留し、発報側は次の検知を「同じ揺れの続き」として音と通知を省く）。こちらから作り直した場合にそれをやると、直したい症状がそのまま残る。

あわせて次を落とす。

- **検知器を作り直す**（`reset`。積んだフレームを捨て、追っている検知と点ごとの履歴を捨てる）
- 慢性ノイズ床の履歴と立ち上がり時刻（床は残す）、データ時刻ごとに覚えた「今揺れ始めた点」
- 最後に食わせた時刻・待たせていたフレーム（残すと、過去へ飛ぶ切替で新しい軸のフレームが軒並み「巻き戻り」として捨てられる）
- 学び直しの係が遅らせて持っていた秒（数えた分は残す）
- 連続失敗のカウンタ（この後に届くのは別の時間軸のフレームで、それまでの失敗の続きではない）

慢性ノイズ床と平常のゆらぎの表は残す（時間軸ではなく観測点に紐づくため）。そのうえで助走を待ち直す（下記）。

### 助走（供給が始まる前のフレームを先に食わせる）

**供給が始まった時点で既に揺れていると、検知器はそれを捉えられない。** 統計は点ごとの上がりを長い基準（6〜65 秒前の中央値）と
短い基準（直前 10 秒の最小）の両方から測り、波面は 3〜59 秒前の最大からの上がりで発火を見る。どれも検知器自身が持つ履歴の中での
上がりなので、最初のサンプルが既に高い点は上がっていない点にしか見えない。さらに統計は長い基準に有効な値が 20 個たまるまで、
波面は 20 フレーム入るまで何も出さない。

実データで測った。大地震 7 本について、地震発生の 1〜12.5 分後を 30 秒刻みで走査した
**164 通りの開始時刻**が母集団。一致の基準は検知の段階（confirmed / likely / なし）と最大震度。
「ずっと再生し続けた場合」は、地震の窓の手前に 15 分（遡りの上限と同じ長さ）を足し、その先頭から流した結果とする。

| 開始時点（60 秒ブロックで遡り、静穏で打ち切る） | 「ずっと再生し続けた場合」と一致 |
|---|---|
| 静穏でも最低 1 分は遡る | 144 / 164 |
| 同じく最低 3 分 | 153 / 164 |
| 同じく最低 5 分 | 154 / 164 |
| 同じく最低 7 分 | 156 / 164 |
| 同じく最低 10 分（採用） | 157 / 164（遡った長さは平均 631 秒・最大 900 秒。上限の 15 分に当たったのは 1 点） |
| 同じく最低 12 分 | 158 / 164 |
| 同じく最低 15 分（上限と同じなので、いつも 15 分遡る） | 159 / 164 |

値はすべて組み合わせの検知器で、`--adaptive` と同じ判定のまま最低の長さだけを差し替えて測った。
**手前の 15 分を足すのは、足さないと一致が水増しされるから。** 足さないと、遡った先が窓の始まりで頭打ちになり、
そこから流した結果と「ずっと再生し続けた場合」（これも窓の始まりから流す）が同じものになる。足さずに測ったときは
最低 10 分で 164/164・固定 600 秒で 164/164 に見えた（固定の長さはこの測り方でしか測っていない。助走なし 56・180 秒 146・
300 秒 155 / 164）。

**最低 10 分（`WARMUP_MIN_BLOCKS`）を置くのは、一致率が上がるから（最低 1 分の 144 → 157/164）。** 遡った先が静穏でも、
そこまでの時間は揺れの立ち上がりや余韻を含みうる。平常時の起動 1 回あたりの取得は 600 件。揺れが続いていれば上限
（15 分）まで遡る（2026-10-29 ユーザー選択「最低 10 分にする (Recommended)」）。10 分より延ばしても 2〜3 分ごとに 1 点しか
増えず、15 分にすると静穏で早めに打ち切る仕組みが無くなって毎回 900 件を取る。延ばした窓で測り直したうえで 10 分のままに
した（2026-10-29 ユーザー選択「10 分のまま (Recommended)」）。最低 15 分でも 5 点は一致しない。
震源カタログのどの地震にも当てはまらない確かな段を減らす効果は無かった（最低 3 分のときの検知ベンチ 795 窓で、
助走なし 18 件・助走あり 21 件）。

**この表がこの測定の単一情報源。** 再現するには `npx tsx scripts/measure-kyoshin-warmup.ts`
（初回は `--fetch` で窓と手前の 15 分を取得・`--adaptive` で採用した方式・`--min-blocks=...` で最低の長さを比べる）。
助走の長さを決める定数を変えたら測り直して、この表を更新する。

そこで供給元が、**開始時刻より前のフレームを別に取って検知だけへ渡す**（経路は
[data-sources-spec.md](data-sources-spec.md) §4「助走」）。どこまで遡るか・打ち切る条件は
`utils/kyoshinWarmup.ts` が単一情報源。

受け取り側の分担は 2 つ。**どのフレームをどの順で食わせるか**は
[`utils/kyoshinWarmupConsumer.ts`](../../src/utils/kyoshinWarmupConsumer.ts) の純関数
（`consumeWarmup` / `pushPendingFrame`）が持ち、`useKyoshinDetectorV2` は
**「待つか・諦めるか」の判断**と、返ってきた事実を記録の文面にすることだけを受け持つ。
`consumeWarmup` が食わせるのは慢性ノイズ床で、**同じ順（助走 → 待たせていたフレーム）で検知器へも積む**
（観測点集合の照合と重なりの除去は検知器の係が行う）。

守ること。

- **助走が届くまで通常フレームを食わせない**（`pendingRef` に溜めて待つ）。先に食わせると、
  後から届いた助走が「時刻の巻き戻り」として落とされ、助走が丸ごと効かなくなる
- **待つのは時間軸が変わったときだけ**（`waitingWarmupRef`）。初回マウントと、データ時刻が
  空に転じたとき。供給元の識別子（`supplyKey`）の変化で待つと、ローカル履歴アーカイブの
  収録範囲を跨いだだけ（時間軸は続いている）で検知が待ちに入り、結果が古い値で凍結する
- **待たせたフレームには観測点集合の識別子を持たせ、食わせる直前に照合する**。待っている間に
  観測点リストの版が替わりうる。長さの検証だけでは、点数がたまたま一致したときに通ってしまう
- **同じデータ時刻を二重に積まない**。助走は通常フレームと別の経路で届くので、データ時刻が
  変わらないまま助走だけが届くレンダーが必ず起きる。床の係は同じ時刻を落とし、検知器の係は前に積んだ時刻以下を捨てる
- **届かないまま `WARMUP_WAIT_MAX_FRAMES`（90）に達したら諦めて動き出す**。供給元は必ず 1 度
  `prefill` を呼ぶ契約だが、破られたときに検知が恒久的に沈黙しないための安全弁
- **届いたのに 1 件も使えなかったら記録する**（版違いで全部落ちた場合）。画面からは「助走が
  無かった」のと見分けが付かない
- **消化中に例外が出ても外へ出さない。握りは床の係の呼び出しに限らない。** このフックは
  `App()` の中で呼ばれるので、投げるとエフェクトごと未捕捉例外で抜け、**根のエラー境界まで
  飛んで画面全体が落ちる**（地図も地震カードも設定も消える）。握りは 2 段 —— 1 フレームぶんの
  消化を丸ごと囲って**残りは続ける**（件数を数えてまとめて 1 行に残す。助走は最大 900 件
  あるので 1 件ずつ出すとログが埋まる）、その外側で助走・待機分それぞれの列を囲って、
  **反復そのものが壊れたらその段だけ打ち切る**（そこまでに食わせた分は残る）

### 全滅区間の取り直し（リプレイ）

リプレイで秒ファイルが続けて取れず（全滅）、間隔を空けた探りへ移ったあと取得が戻ると、供給元は戻った秒の**前に**
`backfill({ kind: 'begin' })` を出し、飛ばした区間（戻った時刻に近い側の最大 15 分。`REPLAY_BACKFILL_MAX_MS`）を取り直して
`backfill({ kind: 'frames' })` で**検知だけへ**渡す（経路は [data-sources-spec.md](data-sources-spec.md) §4「リプレイは先に取って積む」。
2026-10-22 選択「戻ったら取りに行く (Recommended)」、使い方は 2026-10-24 選択「検知へ流し、画面は今のまま (Recommended)」）。
画面の震度・データ時刻は今の再生時刻のまま（過ぎた秒を描き直さない）。

受け取り側は助走と同じ消化（`consumeWarmup`）を通し、同じ順で検知器へも積む。違いは 2 つ。

- **検知器を作り直さない**（同じ時間軸の続きなので、`reset` を呼ばない）。穴のフレームは最後に
  食わせた時刻より後なので、巻き戻りとして落ちない
- **待つのは `begin` を受けてから**（`waitingBackfillRef`）。待つ間は助走と同じく通常フレームを溜め、`frames` が届いたら穴のフレーム →
  溜めたフレームの順に食わせる。**届かないまま `WARMUP_WAIT_MAX_FRAMES` に達したら穴のまま進む**（同じ番号では待ち直さない）。
  検知は巻き戻せないので、それより後に取れても使えない —— だから穴の 1 秒ずつは先読みと同じ規則（4 回・0.2〜3 秒）で取り、
  30 秒から倍々の取り直しは使わない（2026-10-24 選択「今の取得の規則で取る (Recommended)」）
- 記録の語は「全滅区間の取り直し」（助走と取り違えないため）

守っていること:

- **取り直しは 1 本ずつ。** 取り直しの最中にまた全滅から戻っても、2 本目は始めずに warn を残す（重ねると、受け取る側が
  先の穴を食わせた後に次の穴が巻き戻りとして捨てられる）
- **助走を待っている間に始まった取り直しは使わない**（warn を残す）。助走の消化が最後に食わせた時刻を今のフレームの手前まで
  進めるので、穴のフレームは全部巻き戻りになる。**この判定は助走の待ちより先に置く** —— 助走を待つ間は早く戻るので、後に
  置くと、待ちの間に届いた `begin` を見ないまま助走が明け、その古い `begin` に従って通常フレームを待たせてしまう
- **戻った時刻に近い側から遡って取り、10 秒続けて取れなければやめる**（先読みと同じ歯止め `REPLAY_MAX_CONSECUTIVE_GIVEUPS`）。
  配信元にその時間帯のファイルが無いと、ほぼ全秒が失敗する。近い側から取るのは、検知が見るのは直前の履歴なので、途中でやめても
  役に立つ側が残るため
- **取れた秒が足りない・15 分の上限で古い側を切ったときは warn**（取れなかった秒は検知に穴のまま残る）。やめた理由（取り終えた・
  続けて取れなかった・供給が止まった）と最後に受けた失敗を添える。足りていれば info
- **投げる量**: 取れる区間なら最大 900 秒 × 4 回 = 3600 件（全部の秒が 3 回失敗してから取れた場合）。取れない区間は、続けて
  取れなかった時点でやめるので 1 まとまり（並列で取る 24 秒 × 4 回 = 96 件）で止まる。全滅から戻るたびに 1 回で、重ねないので
  同時に 2 本は走らない

## 8. UI 連携

### 表示状態への変換（`deriveKyoshinView`）

`EnsembleDetection[]` を UI 向けの `KyoshinView` に変換する:
- `confirmed` / `candidate`: 確かな段／早い段の検知が1件以上あるか
- `detectedPoints`: 確かな段の全検知の描く点（`drawnKeys`。§4「検知の組み立て」）の和集合。**検知点マーカーに描く分・
  カメラの寄り先・検知が続いているかの判定**に使う
- `candidatePoints`: 主の早い段の検知（最大震度が最大の1件。最大震度が null の検知は後ろへ回す）の描く点。**候補カメラフィット専用**
- `unconfirmedPoints`: 早い段の全検知の描く点の和集合から確かな段の分を除いた差集合（観測点キーで除く）。
  **検知点マーカー専用**（フィットには使わない。複数の和集合に寄せると境界が飛び跳ねるため）
- `confirmedShocks`: 確かな段の各検知（＝地域）の代表点（メンバーの重心）＋メンバー最大震度＋最大震度を記録した観測点の座標。
  地域単位発報の入力。**メンバーが 1 つも索引に無いとき（観測点リストの入れ替え中）は検知の `epicenter` を代表点にし、検知を落とさない**
  （落とすと地域単位の発報が「確定が消えた」と読み、発報済み・EEW 吸収済みの記録を捨てて同じ地域が鳴り直す）
- `candidateMaxIndex`: 主の早い段の加わった点の最大インデックス（音の段の基準）。0 から始まり、欠測と震度0未満を見分けない
- `candidatePeakIndex`: 主の早い段の加わった点のうち値を持つ点の最大。値を持つ点が無ければ -1。共有カードの副見出しに
  震度の呼び名を付けるのに使う

確信度（`confirmed` / `candidate`）・`confirmedShocks`・`candidateMaxIndex`・`candidatePeakIndex`（音・自動タブ切替・地域単位発報の入力）は、
描く点から外した点も含む**加わった点すべて**（`memberKeys`）から作る。外すのは見せ方だけで、判定には触れない。

自動フィットは常に描く点のフットプリントを対象とし、`epicenter` へは飛ばさない
（`epicenter` は束を作った 1 点の位置で、広がった揺れでは揺れの真ん中から外れるため）。

カメラは**描く点のうち値のある点**（欠測を除く。震度0 未満の点は含む）を寄り先にし、**検知が続いているかは描く点が
1 つでもあるか**で判定する（`FitToDetectionGL` の `points` と `hasDetection`）。この 2 つを兼ねさせてはならない——
値のある点が一時的にゼロになること（描く点が全員欠測になる）は検知中にも起きるため、それを検知終了と扱うと画が日本全体へ戻り、
点が返った瞬間に寄り直す明滅になる（設計書 §22）。描く点そのものは束ごとに空にならない（§4「検知の組み立て」）。
分ける理由と縮小の追従は [`map-rendering-spec.md`](map-rendering-spec.md) §6「揺れ検知追従の目標範囲」。

### 判定の根拠を見せる（`utils/kyoshinEnsembleEvidence.ts`）

段のチップが「どの段か」を示すのに対し、こちらは「**何がその検知を支えたか**」を示す。
文言の組み立ては `kyoshinEnsembleEvidence.ts` が単一情報源（`ensembleSummary` / `ensembleRows` /
`ENSEMBLE_EVIDENCE_FOOTNOTE`）。文面はすべて 2026-10-29 ユーザー選択（「今と同じ形」「4 行」「働きで呼ぶ」「補足は消し脚注は言い換え」）。

**要求値は出さない。割合や点数のような数値の確信度も作らない。** 組み合わせの検知器は「あと何点で確定」のような要求値を
持たないので、出せるのは「何が支えたか・何点が加わったか・最大震度・確定までの秒」という事実だけ。要求値らしいものを
作って添えると、実装が持っていない判定を画面が名乗ることになる。

| 出す場所 | 中身 |
|---|---|
| 検知カードの一行（折りたたみを開かなくても見える） | 確かな段は**確定した瞬間の**内訳で「6点・震度2で確定」（`confirmedSnapshot` から。震度0 に届かない点だけで確定したときは「震度0以下で確定」）。早い段は言えることが無いので行ごと出さない |
| 検知カードの折りたたみ（既定は閉じる） | 地域ごとの表（下記の 4 行）と脚注。地域が 2 つ以上なら「地域 1・石川県能登（検知）」のように、その地域で最も強い観測点の区域名と段を添える（下記「最も強い観測点の区域名」） |
| 診断ログ | 記録を開いた瞬間の段・最大震度・位置・支えた部分と、確かな段になった瞬間の点数と最大震度（[`settings-pwa-spec.md`](settings-pwa-spec.md) §12） |

表の 4 行:

| 行 | 値 |
|---|---|
| 判定した仕組み | 支えた部分の呼び名を「・」で繋ぐ（平常時のゆらぎ・揺れの広がり・強い揺れの急な上昇・観測点の少ない地域。並びもこの順） |
| 加わった観測点 | `memberKeys` の点数 |
| 最大震度 | いまの最大震度の震度階級。震度0 に届かない値は「震度0以下」、欠測は「—」（2026-10-29 ユーザー選択「「震度0以下」と出す (Recommended)」）。呼び名は `kyoshinIntensity.ts` の 1 つの決め事（計測震度から引く `detectionScaleLabelFromValue`・震度のインデックスから引く `kyoshinDetectionScaleLabel`）で、検知の通知の文面も同じ呼び名を使う |
| 確定まで | 「検知から N 秒」（`firstConfirmedAtMs − originTimeMs`）。まだなら「—」 |

守ること。

- **表示用の値を判定の入力にしない。** `kyoshinEnsembleEvidence.ts` は検知器の出力を読むだけ
- **確定したものの一行は `confirmedSnapshot`（凍結）から作る。** いまの値で言うと、収まりかけた後に点数も震度も確定した時と違って見える
- **表の「加わった観測点」はカード本文の「N観測点で反応」と数え方が違う。** 前者は束が生きている間に加わった点をすべて数え（減らない）、
  後者はいま地図に描いている点（値のある点。震度0 未満の印を含む）。同じ画面に 2 つの点数が並ぶので、表の下に脚注「※「加わった観測点」は、上の観測点数と数え方が異なります」を出す
- **折りたたみの地域番号は検知の id の順で振る**（数字の部分を数として比べる）。渡された順に振ると、並びが変わったときに
  「地域1」「地域2」のラベルだけが別の地域へ移る
- **一行に出す代表は、最上位の段のうち最大震度が最大の 1 件。** `deriveKyoshinView` が主の早い段の検知を選ぶのと同じ基準
  （同§「表示状態への変換」）。**折りたたみの並び（id 順）とは基準が違う**ため、複数地域あるときの一行が「地域1」を指すとは限らない
- **見出しに検知器の内部用語を出さない。** 部分の名前は働きで呼ぶ（上の表）

### 検知点マーカーとカードの点数の一致

地図の検知点マーカー（`KyoshinDetectedPointsGL`）とリアルタイムタブの検知カードは、**同じ点集合・同じ下限**で
数える。どちらかだけを変えると表示が食い違う。

**点集合は `App` が用意した 1 本を両者で共有する**（`detectedPoints` ＋ `unconfirmedPoints`。カードへは
`RealtimeTab` の `kyoshinDetectedPoints` として渡る）。「同じ結果になること」に頼ると片方の実装を変えた時点で
黙って食い違うため、計算を 1 箇所に寄せている。

| 揃えるもの | 内容 |
|---|---|
| 対象の検知 | 全検知（確かな段 ＋ 早い段） |
| 下限 | **値のある点**（欠測＝`index` が負のセンチネルを除く）。震度階級が取れる点（計測震度 0.0 以上。判定は `kyoshinIndexToJma` / `kyoshinIndexToLabel`、`src/utils/kyoshinIntensity.ts`）は階級のバッジで描き、カードは階級ごとの行に数える。震度0未満（`index` 0〜5）は文字なしの淡い灰色の印（`KYOSHIN_SUB_ZERO_COLOR`）で描き、カードは一番下の「0以下」の行に数える。カードの「N観測点で反応」の N は両方の和（決めたときの原文は設計書§45） |
| 描く点から外す点 | 共有する点列の時点で外れている（束の `drawnKeys`。震度0 未満が `DRAWN_FADE_MS` 続いた点。§4「検知の組み立て」） |

**加わった観測点は束が生きている間減らない**（§4「検知の組み立て」）。そのため加わった点をそのまま描くと、揺れが
収まるほど地図が「もう揺れていない点」で埋まる。描く点（`drawnKeys`）は、震度0 未満が続いた点をそこから外したもの。

**地図の波紋（`KyoshinMaxEffectGL`）も同じ点列を見る。** 波紋はこの点列の中で最も強い点の表示階級が
上がったときに出る（震度1 以上）。検知が無くなると階級を落とすので、次の検知では最初の点が階級を持った
時点で波紋が出る（計測は設計書§41。2026-10-22 ユーザー選択「検知に入った点だけにする」、対象の点は 2026-10-24 ユーザー選択
「検知点バッジと同じ点」）。

### 最も強い観測点の区域名

検知カードは、最も強い観測点が入る一次細分区域の名前を「最も強い観測点：石川県能登」の形で出す。
地域が 2 つ以上あるときは、判定の内訳の見出しにも地域ごとの区域名を添える（「地域 1・石川県能登（検知）」）
（2026-10-22 ユーザー選択「地域名を出す (Recommended)」、出し方は 2026-10-24 ユーザー選択「本文と内訳の両方 (Recommended)」）。

- **区域は境界データ（`subregions.json`）から引く**（`subRegionNameAt`）。強震モニタの観測点は座標しか
  持たない。境界データは海岸線を簡略化しているので、海岸の観測点が線の外に出る（実測は設計書§41）。**境界から
  `SUBREGION_NEAREST_KM`（5km）以内なら最寄りの区域へ寄せる**（2026-10-24 ユーザー選択「5km 以内なら
  最寄りの区域 (Recommended)」）。それより遠い点と、境界データの読み込み前は名前を出さない
- **検知カードは境界データの取得を自分では始めない。** 地図が起動時に読み込むものを受け取るだけ
  （取得の失敗の扱いは地図の側が持つ）
- 引き当ては座標ごとに控える（観測点の座標は変わらないので、毎秒引き直さない）

### 検知カードの震度分布バーの幅スケール（`scalePeakRef`）

カードは震度階級ごとの点数を横バーで並べる。幅の分母（＝100% にあたる点数）は、**カードが見えている間は
下げない**。上げるのは点数が増えたときだけなので、見ている間のバーの伸びは必ず実際の点数の増加を意味する。

分母を毎回いまの最大点数に合わせると、最大だった階級の点数が減っただけで他のバーが伸び、揺れが収まって
いく最中に「増えた」と見える（分母が動いただけで点数は減っている）。時間で減衰させる方式も同じで、
減衰した瞬間にバーが一斉に太る。

代わりに、**カードが見えていない間は毎回いまの点数へ張り直す**。跳ねても目に入らないうえ、次に見えた
瞬間は必ず「いまの点数」が基準になるため、前の揺れのピークを引きずらない。見えていないと判定するのは
次の 3 つ:

| 契機 | 判定 |
|---|---|
| 別のタブを開いている | `activeTab !== 'realtime'`（タブは常時マウントで、選ばれていなくても描画は走る） |
| パネルを畳んでいる | `panelCollapsed` |
| ブラウザのタブ・ウィンドウが裏 | `document.visibilityState !== 'visible'`（`usePageVisible`） |

前 2 つは `App` が `RealtimeTab` の `visible` へ渡し、3 つ目をカード側で合成する。

**副作用**: 大地震の長い減衰期にこのタブを見続けると、分母がピークのままなのでバーは細いままになる。
点数は各行の右端に数値で出ているので情報は失われず、タブを一度離れて戻れば張り直る。検知が
すべて消えればカード自体がアンマウントされるため、地震と地震の間で分母が持ち越されることもない。

### 反応が収まったときのカード

描く点に震度0 以上の点が 1 つも無くなる（全員が震度0未満か欠測）と、検知自体は束ね役が捨てるまで生き残るため
カードは残るが、点数の代わりに「観測点の反応は収まりました」と表示し、あわせて段のチップと見出しの色を灰へ置き換えて、
揺れが収まったことと印象を揃える。地図に震度0 未満の印が残っていれば、カードにも同じ点数の「0以下」の行を出す
（2026-10-29 ユーザー選択「「0以下」の行を出す (Recommended)」）。**段のラベル（検知／可能性）は判定結果なので変えない**。枠色を最大震度に
追従させているのと同じ考え方で、「判定の種類」と「現在の活動度」を別の手段で示す。弱め方に不透明度を使わないのは、
文字と背景の関係まで薄まって読みにくくなるため。

**ただし確かな段で、震度0以上の点が無く震度0未満の点だけがあるときは「収まりました」と言わない。** 組み合わせの検知器は
震度1 に届かない揺れも確かな段にするので、揺れの最中でも震度0以上の点が 1 つも無いことがある。このときは推定最大震度を
「0以下」、本文を「N観測点で震度0以下の反応 ・ 推定値」（N は地図に描いている震度0未満の印と同じ点の数。早い段の検知の点と、欠測中に直前の値を保持して描いている点も数える）と出し、チップと見出しの色も
弱めない（2026-10-29 ユーザー選択「「震度0以下」で出す (Recommended)」、N の数え方はユーザー選択「地図と同じ点を数える (Recommended)」）。早い段（likely）だけのときは本文を「収まりました」のままにする。検知は最後の報告から
`ENSEMBLE_KEEP_MS`（30 秒）残るので、本当に収まった後の余韻もこの形で出る。

### 欠測の瞬断は直前値を保持して描く（`utils/kyoshinMissingHold.ts`）

強震モニタの秒データには欠測（負のセンチネル）が混ざり、**現に強く揺れている観測点でも 1〜2 秒だけ
単発で欠測する**。素通しすると震度階級が取れないため、強い揺れのバッジが 1 秒消えて次の秒で戻る
明滅になる（実データでの計測は**設計書 §25**）。

そこで表示に使うインデックスは、欠測になった点を**直前の有効値で 2 秒間だけ埋める**（`MISSING_HOLD_MS`）。
保持中の点は `DetectedPoint.stale` が立ち、地図では薄く（`MISSING_HOLD_OPACITY` = 0.35）描かれる。
2 秒を過ぎたら欠測のまま＝従来どおり消える（本物の観測点停止を残さないため）。カードの震度別点数も
保持中の点を同じように数える（地図と数える集合を揃える §8 の原則をそのまま適用する）。

保持値が及ぶ範囲は次のとおり。**これは描く点を外す仕組み（§4「検知の組み立て」の `drawnKeys`）とは別の工程**——あちらは描く点を選ぶだけで判定に触れないが、こちらは判定より前段の `index` そのものを差し替えるため、
`index` を見る判定にも届く。

| 対象 | 保持値を使うか | 補足 |
|---|---|---|
| 揺れ検知（`useKyoshinDetectorV2`。組み合わせの検知器・慢性ノイズ床） | **使わない**（生値） | 欠測の扱い・平常のゆらぎの学び直し・慢性ノイズ床の学習を保持値で汚さない |
| 検知点マーカー（`KyoshinDetectedPointsGL`）・震度1以上のドット（`KyoshinPointsGL`） | 使う | 保持中は薄く描く |
| 震度0未満のドット（`KyoshinSubThresholdGL`） | 使う | 保持中は薄く描く。段ごとにまとめて描くカスタム GL レイヤーなので、保持中の点を別の組にまとめて薄く合成する（`STALE_LEVEL_OFFSET`）。そのため**同じ段の保持中と保持していない点が重なった部分だけは濃くなる**（保持は最長 2 秒なので許容した。2026-10-22 ユーザー選択「震度0 未満も薄くする (Recommended)」） |
| 検知カード（`RealtimeTab`。点数・推定最大震度） | 使う | 地図と同じ点列を共有するため自動的に一致する |
| 音・通知・地域単位発報（`useKyoshinAlerts` へ渡す `candidateMaxIndex` / `confirmedShocks`） | 使う | **意図的**。欠測を素通しすると最大震度を担う点の 1 秒欠測が「揺れが弱まった」と解釈され、復帰時に更新音が誤って鳴る（`postPeakMinLevel`）。検知が欠測を「揺れ 0」と扱わないのと同じ理由 |

検知の `maxIntensity`（検知カードの判定の内訳・診断ログ）は生値から作るので、保持の対象外。

同時に保持中の観測点が全体の 20% を超えた場合は警告を記録する（上流データの劣化に気づけるようにする。
`useKyoshinMissingHold`）。

**保持値を捨てる条件は 2 種類あり、順番に意味がある。**

| 種類 | 条件 | いつ効くか |
|---|---|---|
| 位置の対応が壊れた | 観測点集合の識別子が変わった／件数が変わった | **データ時刻を見ない。時刻のガードより前に判定する** |
| 時間軸が変わった | データ時刻が巻き戻った | 時刻が読めるフレームでのみ |

前者を時刻のガードより前に置くのは、**供給を作り直したとき（リプレイの時間軸の切替）が「件数 0・
データ時刻なし」の形で届く**ため。後ろに置くと素通しして、旧い時間軸の保持値が新しい軸の最初の
フレームで蘇る（同じ観測点集合・同じ件数で、時刻が前へ進んでいれば、後者の条件にも掛からない）。
位置の対応が壊れたことは時刻を見なくても判るので、順番を入れ替えても他の判定には影響しない。

### 発報ロジック（`useKyoshinAlerts`）

| トリガー | 挙動 |
|---|---|
| candidate 立ち上がり（早い段の検知が出た・確かな段の前） | realtime タブへ切替＋タイトル「揺れの可能性」＋控えめな候補音 |
| confirmed 立ち上がり（確かな段の初検知） | realtime タブ＋タイトル「揺れ検知」＋検知音＋ブラウザ通知。ただし**「判らなくなって」消えた直後の復帰では鳴らさない**（下記） |
| confirmed 中の最大震度の再上昇（レベルアップ／再エスカレーション） | 更新音（同一地震の揺れ強まりを都度知らせる）＋その点へ地図が一時的に寄る（下記） |
| 検知中に別地域（`isSameEarthquake` が同一地震と判定しない距離）が新たに確定 | 検知音＋ブラウザ通知（「別の地点で揺れを検知」）。震度の下限は置かない（下記）。`REGION_PERSIST_MS`(2秒) 継続後・`NEW_REGION_COOLDOWN_MS`(5秒) のクールダウン付きで一過性の分裂を抑制。その地域へ地図が一時的に寄る（下記） |
| 同じ場所の 2 つ目の地震（確定が続く中のまとまった立ち上がり、または近くの確かな段が続く中で別の束が確かな段になった） | 検知音＋realtime タブ＋立ち上がった点のうち最も強い点へ地図が一時的に寄る。ブラウザ通知は出さない。別地点として鳴らした直後（データ時刻で 3 秒以内）なら鳴らさない（下記「同じ場所の 2 つ目の地震」） |
| 全イベント解除 | EEW 受信中でなければデフォルトタブへ復帰 |

**「判らなくなった」ことによる消失と、揺れが収まったことによる消失を見分ける。** 検知結果を出せない
フレームが続くと結果は空になり（§7）、`confirmed` が落ちる。しかしこれは揺れが終わったのではなく、
検知そのものが止まっただけ。復帰時に素朴なエッジ検出で再発報すると、**同じ地震で検知音とブラウザ通知が
鳴り直し**「収まって、また始まった」と受け取られる。

見分けは検知が返す `stalled`（結果を出せずに空にしたか）で行う。`stalled` で消えたなら印を立て、
そのとき確定していた検知地点を控えておく。**結果が戻った最初のフレームで検知が立ち、かつその地点が
すべて途絶前の近くにある**なら同じ地震の続きとみなし、音と通知だけ抑える（タブとタイトルは戻す。
判っていない間まで「揺れ検知」を出し続けない）。

**場所の照合は省けない。** 検知器は `MAX_RESUME_GAP_MS` 以内の途絶なら作り直さず続けるので、復帰したフレームで
**まったく別の地震**が確定しうる（高い震度の近道と統計は、条件を満たした最初の秒に確かな段になる）。物差しは
`SAME_SHAKE_KM`（100 km）——照合しているのは `confirmedShocks` の重心どうし（`isSameShakeAsBefore`）。
**1 つでも離れた地点が混じっていれば鳴らす側へ倒す**——余分に鳴るのは煩いだけだが、抑えすぎると
無関係な地震が無音で消える。

**経過時間では測らない。** 起点も時計も揃わず、窓を閉じ忘れれば同じ「無音で握り潰す」失敗になる。

**揺れが収まって消えた場合は印を立てない**（直後に別の地震が来たとき鳴らなくなる）。判断の経緯と、
時刻で測ろうとして破綻した内訳は[設計書§35](kyoshin-detection-v3-design.md)。

**揺れの強まり（レベルアップ・再エスカレーション）と別地点の検知では、地図もその点へ短く寄る**（揺れフォーカス）。確定検知の開始は対象外——そちらは検知点全体へのフィットが画を作る。寄り先は**最大震度を記録した観測点**
（`ConfirmedShock.peak`）で、地域の照合に使うメンバー重心とは別に持つ。要求は音を鳴らすのと同じ
タイミングで出す（レベルアップ・再エスカレーションの分岐をそのまま使う）。**ただし寄り先
（`focusPointRef`）は confirmed でなければ null**——早い段（候補音）中は要求が出ても画は動かない。
控えめな音量で知らせるだけに留め、確信度に見合わない大きさで画を動かさないため（候補音の音量を
抑えているのと同じ考え方）。要求を出した後の寄せ方・寄せない条件は
[`map-rendering-spec.md`](map-rendering-spec.md) §6「揺れフォーカス」が単一情報源。

同じフレームで「揺れの強まり」と「別地点の検知」が両方成立したら、**寄り先は別地点を採る**（音は
両方鳴る）。別地点は「別の場所でも揺れている」ことをフル音量で知らせる報せで、同じ地震の強まりより
見せる価値が高いため。

**realtime タブへの切替は優先度付き**（規則の全体は [`audio-tts-spec.md`](audio-tts-spec.md) §6
「自動タブ切替の優先順位」が単一情報源）。揺れ検知の優先度は地震情報より重く津波より軽いが、
**揺れ検知が確保した画面は他の情報の移動を妨げない**（揺れ検知のあとに地震情報が届くのは実際に
起きた順序どおりで、そこで画面が留まる方が不自然なため）。揺れがレベルアップしたり別地点で
検知されれば、そのつど realtime を取り直す。

`useKyoshinAlerts` に渡されるタブ切替関数には App 側で揺れ検知の優先度が付いているため、
このフックの中では優先度を意識しない。

同一地域の余震は、揺れが収まって地域情報が破棄された後に来れば「別地点」として、収まる前に来れば
「全体の再エスカレーション」または下記「同じ場所の 2 つ目の地震」として発報される（地域ごとの独立した再検知ではない）。

#### 「別地点」判定の動的距離閾値（`isSameEarthquake`）

固定距離（`REGION_MATCH_KM`=300km）だけで判定すると、能登半島地震のような広域巨大地震で揺れが
観測網へ伝播していく数十秒〜数分の間に、周辺地域が次々「別地点」と誤発報される（2026-08-10 の
実地震リプレイ検証で発覚）。`isSameEarthquake` は次の優先順位で判定する:

1. **アクティブな EEW（震源要素確定済み）ごとの個別判定**: 各 EEW について、震源・発生時刻から
   **P波**の地表到達半径（予報円と同じ JMA2001 走時表。→ `utils/travelTime.ts`）×安全マージン係数
   `DYNAMIC_THRESHOLD_SAFETY_FACTOR`(1.2) を動的閾値とし、既存地域・新規確定点の**両方**が
   その閾値内にあれば同一地震とみなす（EEW ごとの OR 条件）。上限は**その EEW の有感半径**
   （`eewFeltRadiusKm`。司・翠川式で震度1 が届く距離×1.5。EEW の自動解除と同じ値で、規模が判らない
   報は M6.0、深さが判らない報は 30km と仮定する。P 波の到達半径に使う深さは、判らなければ仮の 15km。
   発生時刻が読めない報は範囲を測れないので EEW として数えない）。「地理的に最も近い震源を1つだけ
   選ぶ」設計だと、たまたま近くにある別の（まだ経過時間が短い）地震の震源に判定を乗っ取られる
   ことがある（検証実例: 近畿地方の揺れが、94秒経過した能登の震源より地理的にわずかに近いだけの
   19秒経過の新島・神津島近海の震源を誤って基準にされた）。EEW ごとに独立評価してこれを避ける。
   - **P 波で測る**: 強震モニタは P 波の揺れで確定することがあり、P 波がまだ届いていない場所の揺れは
     この地震のものではありえないため（2026-10-25 ユーザー承認「それで。」）
   - **上限は有感半径**: EEW があるときの上限を固定の 800km にすると、深い地震の異常震域を外すため
     （2026-10-25 ユーザー承認「それでいいよ」。規模が判らないときは選択肢「自動解除と同じ M6.0 (Recommended)」）
   - **どの EEW の範囲にも入らない点どうしは、`REGION_MATCH_KM`(300km) 以内なら同じ地域とする**
     （時間では広げない）。同じ場所の揺れを、EEW があるというだけで別の地域にしないため
     （2026-10-25 ユーザー選択「①も直す (Recommended)」）
2. **EEW が無い場合のフォールバック**: **検知エピソード全体の起点**（最初に確定した地域の初検知時刻・
   `AlertRegionState.outbreakAtMs`）を仮の発生時刻、`DEFAULT_VIRTUAL_DEPTH_KM`(15km) を仮の震源深さ
   として **S波**の到達半径で動的閾値を計算し、`PROPAGATION_MAX_KM`(800km) で打ち止めにする。起点は
   `OUTBREAK_PROPAGATION_WINDOW_MS`(5分) を超えたら地域自身の初検知時刻へ戻す。震源も深さも仮なので、
   深い地震の異常震域はこちらでは吸収できない（既知の限界）。
3. いずれも下限 `REGION_MATCH_KM`(300km) を保つ（有感半径が下限より小さくても下限を優先する）。

EEW の有無で範囲の測り方が変わるのは、EEW が無いと震源も深さも分からないため。経緯と計測は設計書§42。

見たうえで残している挙動（2026-10-25 ユーザー選択。詳細は設計書§42「見たうえで残したこと」）:

- 深く大きい地震では範囲がほぼ日本全体になり、その EEW の最中に範囲の中で起きた別の地震は鳴らない
  （「このまま・記録する (Recommended)」）
- 上限は最新報の規模で決めるので、初報の規模が小さいと、続報で上がる前に遠くの揺れが先に鳴りうる
  （「最新報の規模のまま」）

距離の条件に加えて、次の 2 つが「別地点」の発報を絞る。

- **EEW の伝播範囲に一度でも入った地域は、その事実を記憶する**（`AlertRegion.absorbedByEew`）。EEW が
  解除された後も発報しない。判定は毎フレーム行い、発報の直前には座標を更新した後の位置でもう一度確認する。
- 震度の下限は置かない（震度更新音の段で震度0・1・2 を分けた `kyoshinLevel` に合わせた。2026-10-22 ユーザー選択
  「下限を外す」。控えで測った増え方は設計書§41）。
- **一度発報した地域は二度鳴らない**（`AlertRegion.fired`）。その地域の閾値の内側で後から別の地震が
  起きたときは、別地点としては鳴らない。代わりに下記「同じ場所の 2 つ目の地震」が拾う。

地域どうしの照合は**フレーム開始時の座標**で行う（代表点はマッチのたびに書き換わるため）。

#### 同じ場所の 2 つ目の地震（`utils/kyoshinReonset.ts`）

確定している検知の内側で次の地震が起きると、束ね役は同じ束へ入れうる（100 km・15 秒の内）し、別地点の発報も
一度鳴った地域では鳴らない。段が上がらなければ更新音も鳴らないので、そのままでは本震の揺れが続く中の余震は
音もタブ移動も無い（2026-10-22 ユーザー選択「2 つ目も鳴らすよう設計する」）。そこで次の 2 つの形を「2 つ目」とみなし、
検知音を鳴らして realtime タブへ移し、立ち上がった点のうち最も強い点へ寄せる。

1. **まとまった立ち上がり**: 確かな段の検知のメンバーで、**`REONSET_QUIET_MS`（60 秒）の間 新しい立ち上がりが無かったあと、
   `REONSET_BURST_MS`（3 秒）の内に `REONSET_MIN_POINTS`（3 点）以上が新しく立ち上がった**。立ち上がりは床の係の
   `recentOnsetKeys` に新しく入った点で数える（値は 2026-10-24 ユーザー選択「60 秒静か・3 点 (Recommended)」。計測と経緯は設計書§40）
   - 検知が現れてから 60 秒は鳴らさない（1 つ目の地震の立ち上がりそのもの）。鳴らした後も、また
     60 秒の静けさを挟むまで同じ検知では鳴らさない
2. **新しい束**: 近く（束の位置どうしが `REONSET_NEARBY_KM` = 300 km の内）の確かな段の検知が
   `REONSET_QUIET_MS` 以上続いている最中に、**別の検知が確かな段になった**（組み合わせの検知器は同じ場所の 2 つ目の揺れを
   別の束として出すことがあり、その束は現れたばかりなので 1 では鳴らない。2026-10-29 ユーザー選択「新しい束でも鳴らす (Recommended)」）。
   寄せる先の候補は、その検知の加わった観測点。`REONSET_NEARBY_KM` は別地点の発報が同じ地震とみなす距離（`REGION_MATCH_KM`）と
   同じ値で、これより離れた束は別地点の発報が受け持つ
   - **同じ地震の波は外す**: 続いている確かな束の揺れ始めから新しい束の揺れ始めまでの間に、地震の波が先の束の位置から
     届く距離（見かけの速さが `REONSET_WAVE_KMPS_MIN`〜`REONSET_WAVE_KMPS_MAX` = 2.5〜5 km/s）なら、同じ地震の揺れが
     遠くへ届いただけとみなして鳴らさない（2026-10-29 ユーザー選択「同じ地震の波を速さで外す」。計測は `kyoshinReonset.ts` の冒頭）

共通の扱い:

- 別地点として鳴らしたフレームからデータ時刻で `REONSET_AFTER_REGION_MS`（3 秒）以内なら鳴らさない（同じ揺れを
  2 回知らせない）。2 つの合図は動く契機が違う（別地点は強震モニタの時刻、2 つ目は検知結果の更新）ので、同じ
  フレームの一致ではなくデータ時刻の差で見る。**別地点が後から鳴る向きは防いでいない**（既知の限界。設計書§40）
- 鳴らすのは合図ごとに 1 回だけ（1 フレーム 1 件）。合図は検知の id と合図を出したデータ時刻の**印**を持ち、鳴らす側は印が
  変わったときだけ動く（合図が残ったまま時刻だけ進んでも、同じ合図が作り直されても鳴り直さない）。同じデータ時刻を二度渡しても
  結果は変わらず、データ時刻が巻き戻ったら記憶を捨てる
- **ブラウザ通知は出さない**（2026-10-24 ユーザー選択は「検知音を鳴らす」）
- 寄せる先は、まとまって立ち上がった点のうち最も強い点。引けなければ検知の位置、それも無ければ寄せずに
  音とタブ移動だけ出す（合図は捨てない。捨てると 60 秒鳴らなくなる）
- EEW の発表中も鳴る（別地点の発報と違い、EEW の伝播範囲で吸収しない）。タブ移動は揺れ検知の優先度で、
  EEW には譲る
- 時刻は検知結果の時刻（`kyoshinV2.dataTime`）を使う。強震モニタの取得の時刻を使うと、検知器が処理する遅れの分だけ
  ずれて取り込まれる。リプレイの開始・停止で記憶を落とす

持続（`REGION_PERSIST_MS`＝2秒）・クールダウン（`NEW_REGION_COOLDOWN_MS`＝5秒）・地域を破棄するまでの
猶予（`REGION_PRUNE_MS`＝3秒）は、いずれも**何フレーム届いたかではなく、観測データに付いている時刻の
経過で測る**。強震モニタのライブ取得は遅れると次の時刻へ飛んで途中のフレームを取りこぼすため、
フレームで数えるとライブと過去再生で同じ設定値が違う長さを意味してしまう。

この 3 つには次の性質がある。

- 持続は「観測できた回数」ではなく「初検知からの経過」で判定する。途中の観測が欠けても経過が足りていれば満たす。
- 破棄はフレームの末尾で判定するため、地域が実際に残る時間は猶予よりわずかに長い（1 秒間隔なら 1 フレーム分、
  取りこぼしがあればその分だけ伸びる）。

時刻で測ることにした経緯と破棄をこの位置に置いた理由は [設計書§31](kyoshin-detection-v3-design.md)、
値そのものをどう決めたか・検討して採らなかった案は [設計書§24](kyoshin-detection-v3-design.md) にある。

### 震度0ドット表示フィルタ（`kyoshinSubThresholdFilter.ts`）

震度0以下（index 1〜6）の面表示（`KyoshinSubThresholdGL`）専用。慢性ノイズ床の係（§7）が学んだ
`chronicNoiseFloor`（下限 `FLOOR_MIN` を適用しない）を使い、`value ≥ floor + SUSTAIN_MARGIN`（0.4）を
超えた点だけを表示する。慢性的にノイジーな観測点（大阪・岡山等）が平常時から常時ドット表示され続けるのを防ぐ。
震度1以上のドット表示・最大効果表示には適用しない（実測値をそのまま見せる）。

**床は観測点と同じ並びの配列で受け渡す。座標から作ったキーで引かないこと。** 同一座標に複数の実観測点が
載るため（`computeSiteKeys` が出現順に `#2`, `#3` と別実体へ分ける。全1725点中207グループ・431点）、座標を
キーにすると 2 つ目以降がグループ先頭の**別センサーの床**で判定される。実データ 15 分では 60 点の表示が
食い違い、多くは「床の高い都市部の点が低い床で判定されて素通りする」向きだった。キーの生成規則を
2 箇所に持たせず、並びで対応づける。まだ床を持たない点（一度も観測できていない欠測点）は 0 が入る。

位置で対応づける以上、**床がその観測点配列に対して計算されたものかを呼び出し側で確かめる**
（`KyoshinDetectorV2Result.floorsSites` との参照比較）。床が作り直されるのは**次に床の係がフレームを学んだとき**
なので、観測点リストが差し替わってからそれまでの間（途中に別のレンダーを挟むこともある）は「新しい観測点 ×
古い床」が並ぶ。点数が偶然一致すると長さの検査では捕まらない。差し替えは `siteConfigId` の更新だけでなく、
過去日のリプレイ開始でも起こる。
件数の食い違いが続いて検知結果がリセットされたときも床は空になり、同じく不一致として扱われる（§7）。

照合が取れないとき、および**渡す配列の長さが揃わないとき**（`filterSubThresholdIndices` 自身の検査）は、
フィルタを通さず、欠測を保持したままの表示値をそのまま描く（消すより出す方へ倒す。保持値と生値の区別は
§8）。後者が効くのは観測点数と震度の件数が食い違うときで、このとき観測点配列は差し替わっていないため
**参照の照合は通り、長さだけが合わない**。

素通りが続くなら、主な原因は記録に残る。観測点リストの取得が失敗し続ける場合と、観測点数と震度の件数が
食い違う場合（[data-sources-spec.md](data-sources-spec.md) §4「取得と再生の分離」）。**記録に現れない経路も 1 つ
残っている**——観測点リストを並行して取りに行ったときの応答順の入れ替わりは、取得自体は成功しているので
失敗の記録には出ない（同 §4「残る既知の課題」）。

## 9. 既知の限界

- **密な所の単点の揺れは検知しない**: 統計は 2 点以上の珍しい上がりを要し（表から引く確率の下限 1e-8（§4「珍しさと走査」）のため、1 点だけの寄与は
  S = 8 までで、早い段のしきい値 `T_EARLY`（10）に届かない）、波面は 3 点以上の発火を要し、高い震度の近道は
  40 km 以内に上がった別の点を要する。まばらな所の規則が対象にするのは `SP_KM`（120 km）以内の点が `SP_MAXN`（6）以下の点
  だけなので、それより密な所で 1 点だけが揺れる形（観測点間隔に対して小さい微小地震・機器の跳ね）はどの部分も検知しない。
  逆に、`SP_KM` 以内に 1 点も無い観測点はまばらな所の規則の対象にもならない
- **確定を降ろさない**（入れ直さないと決めた。§4「いまの検知器に無い仕組み」の A）: 段階は戻さないので、確かな段は束がどの部分からも `ENSEMBLE_KEEP_MS` 報告されなくなるまで続く。
  統計の確かな段は点が長い基準より上にいる間は最大 120 秒延び、波面の確かな段は最後に点が増えてから 60 秒出し続ける
- **広域分裂**: 束ね役が 1 つの束にまとめるのは、束を作った報告の位置から 100 km・始まりの差 15 秒の内だけで、大地震の
  広い有感域は複数の束に分かれる。UI 側（`RealtimeTab`）で「広域・N地域」として集約表示することで対応している
- **検知の位置は震源ではない**: `epicenter` は束を作った報告の位置（統計の種・波面の起点・近道やまばらな所の規則で最初に当たった点）。
  深発・沖合の地震は実際の震源よりかなりずれることがあるため、自動フィットには使わない設計にしている
- **平常のゆらぎの表に載らない点**: 焼いた日に動いていなかった点は、統計では全体の確率、波面では既定のしきい値（3 段）で動く。
  表が取れるまでは全点がこの扱いになる。端末での学び直しが効き始めるのは、どの時間帯も 30 分ずつ数え終えてから
- **値は評価で決めたもの**: 定数（§5）・表の数え方は、組み合わせの検知器を評価したときの値で、変えると評価で測った検知率と
  誤報の率が成り立たなくなる。変えたら評価を測り直す（設計書§43）

# トランスクリプト（会話の記録）の読み方

`CLAUDE.md`「会話の内容を思い出せないときはトランスクリプトを読む」から引く詳しい読み方。

## 記録の場所と読み方

コンテキストが失われて「前に何を決めたか」が分からなくなったら、**推測で進めず記録を読む**。

```
C:/Users/<user>/.claude/projects/<プロジェクトのパスをハイフンで繋いだ名前>/<sessionId>.jsonl
```

- `sessionId` は環境変数 `CLAUDE_CODE_SESSION_ID` から取れる。**まずこれを見ること**——追加のツールを必要としない
  - `mcp__ccd_session_mgmt__get_session` に `"self"` を渡すとタイトルも併せて分かるが、この MCP が入っていない環境では使えない
  - **どちらも使えないときは、対象プロジェクトのディレクトリにある `.jsonl` を更新時刻の新しい順に見て候補を絞る。** `sessionId` が分からないことは、読む手段が無いことを意味しない
  - **ただし「一番新しい」は「一番最近動いた」であって「自分」ではない。** 同じプロジェクトで
    別セッションが並行していれば、そちらを掴む。**採用する前に、中身が自分の文脈と合うかを
    確かめること**（作業ディレクトリ・直近に触ったブランチ名・時刻の連なり）。
    決め手が無ければ要点をユーザーへ提示して確認を取る。他人の会話を「自分が決めたこと」として
    取り込むと、以後の判断がまるごとずれる
- JSONL 形式（1 行 1 メッセージ）なので grep できる。再起動前の分が `.jsonl.pre-import` に残ることもある
- **読む前に、対象のファイルを 1〜2 本に絞る。** 記録は 1 本で数百 MB になり、1 行（1 メッセージ）が巨大なこともある。全部の本（ワークツリーごとに別のフォルダもある）をまとめて grep しない。絞るには、更新日時と大きさ（`ls -lt`）、探している出来事の日付、作業していたワークツリーの名前を使う。絞った本に見つからなければ、日付の範囲を広げて 1 本ずつ足す。まとめて広げない
  - **検索はコマンドの頭に `timeout 60` を付け、フォアグラウンドで走らせる**（`timeout 60 grep …`。時間が来ると打ち切られ、終了コード 124 で返る）。**Bash ツールの `timeout` 引数では打ち切られない** —— 時間が来た検索は止まらずに裏の作業（バックグラウンドタスク）へ移され、走り続ける（2026-10-26 に既定の 120 秒でも、60 秒を指定しても観測。版は未確認）
  - 裏へ移ったら、放置せずその場で止める（`TaskStop`）。止めたら、プロセスの一覧（Windows なら `Get-CimInstance Win32_Process` の `CommandLine`）で、記録を読む `grep`・`sed` が残っていないことを確かめる。前の検索が終わるまで、次の検索を投げない
  - 1 行が巨大なので、行番号で絞っても（`sed -n '470,476p'` の形）重さは変わらない。中身を読むなら、絞った 1 本に対して `grep -o` で一致の前後だけを切り出す（`timeout 60 grep -o '.\{0,200\}<探す語>.\{0,200\}' <ファイル>`。2026-10-26 には、選択肢への答えを `grep -o '"answers":{[^}]*}'` で 1 本から抜き出し、時間内に返った）
- **作業中に送られたユーザーの発言は、通常の発言の行に入らない。** 通常の発言は `"type":"user"` の行だが、Claude がツールを動かしている最中に送られた発言は `"type":"attachment"` の行（`attachment.type` が `"queued_command"`、本文は `attachment.prompt`）に残る。**`"type":"user"` だけを拾うと、作業中に出た指示や承認がまるごと抜ける**（2026-10-05 時点のハーネスの記録形式。変わっていたら、まず `queued` で grep して形を確かめること）
- **バックグラウンドで走らせたコマンドは、出力ではなくタスク自身が持っている。** 置き場所
  （`tasks/*.output`）にあるのは**結果だけ**で、コマンド文字列は入っていない ——
  まだ走っているタスクの通知と `TaskStop` の戻り値にはそのまま出る。**出力を grep して
  「記録に無い」と結論しないこと**（2026-09-29 に実際に誤り、ユーザーに指摘された）
- **プロセスが今も動いているなら、そこから読める。** コマンドライン（Windows なら
  `Get-CimInstance Win32_Process` の `CommandLine`）には環境変数の設定まで残っている ——
  記録を辿れなかった実機の起動コマンドは、最終的にこれで復元した
- **`list_events` と `search_session_transcripts` は自分のセッションを対象にできない**（2026-09-03 に実測）。
  **自分の記録はファイルを直接読むしかない**。ここはハーネス側の仕様なので、動かなくなったら
  まず挙動が変わっていないかを疑うこと

> 2026-09-03: セッション再起動でコンテキストを失ったとき「復元できない」と決めつけて調査をやり直した。
> トランスクリプトは最初からファイルとして存在し、`未処理の情報を足す` で grep すれば段の表が出てきた。
> ユーザーに「自分が出力した過去の文は読めないのですか」と問われて初めて試した。
> **「無い」と判断する前に、読む手段があるかを確かめること。**
>
> 2026-10-26: 決着済みかを確かめるために、全部の本へ grep を何本も並べて投げた。裏へ移った検索を止めずに次を投げ続け、PC が落ちた。再起動の後も同じ読み方を繰り返した。
> **検索は絞ってから 1 本ずつ。裏へ移ったら、次を投げる前に止める。**

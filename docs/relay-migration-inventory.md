# サーバー移行（中継で一本化）の前の総ざらい

中継サーバー（[`relay-server-design.md`](relay-server-design.md)）で 2 つの版を 1 つにまとめる前に、
いまの PWA だから生じている制約・使っている外部サービス・機能・サーバーで新たにできることを洗い出したもの。
**読者は、中継の設計と一本化を進める開発者。** 2026-10-29 時点の調査で、決めたことは設計書 §0 へ、決まっていないことは §12 へ移していく。
「§」「段」「束」などの語と節番号は、断りが無ければ設計書（その「用語」の節）のもの。ここでいうユーザーは開発者（リポジトリの所有者）。

- 依頼の原文（2026-10-27）：「移行する際は今PWAでやっているゆえの制約、使っているサービス、機能などを総ざらいして検討し直す必要があります。」
- 依頼の原文（2026-10-29）：「サーバー移行の時も総ざらいしたいです。サーバー移行によりできることは増えるし制約もなくなると思っています。」
- 前提の原文（2026-10-27）：「移し直しが終わったらP2PQuakeは一切このリポジトリ、アプリ群に登場しなくなる想定」

## ① PWA・ブラウザ・静的配信だから生じている制約と、中継で変わるか

| 群 | 制約 | 中継で変わるか |
|---|---|---|
| 各端末が自分で取る | 起動のたびに、7 日分の履歴を端末ごとに取る（DMDSS 版の初回は電文本体 85 件など） | 中継の束から読む形になり、取る量が減る【決定済み：束を配る】 |
| 各端末が自分で取る | 切れていた間の電文を、端末ごとに取り戻す。取り戻した報は音も読み上げも出さない | 上流の取りこぼしは中継が埋める。アプリから中継への取り戻しは残る【見込み】 |
| 各端末が自分で取る | 起動したとき、発表中の緊急地震速報を戻しにくい（標準版は戻す手段が無い） | 繋いだときに中継が送る【決定済み】 |
| 各端末が自分で取る | 揺れ検知の助走（開いたときに、10〜15 分前まで遡って Yahoo から取る） | 毎秒の値は中継の対象外【見込み：§7.5】。平常のゆらぎの表だけを中継から配る案を考える（④の「Yahoo のリアルタイム震度を中継して配る」） |
| 各端末が自分で取る | 時計合わせを、端末ごとに Akamai へ問い合わせて行う | 変わらない（中継の時計を配っても、端末から中継までの往復時間の補正は要る） |
| 各端末が自分で取る | Yahoo の Date ヘッダが CORS のせいで読めない | サーバーからなら読める【見込み・未確認】 |
| 背面・閉じている間 | 閉じている間や背面の間は受けられず、鳴らせない。Push API を使っておらず、sw.js に `push` を受ける処理も無い | 中継があれば Web Push を足せる【未決：§12 のプッシュ通知の項。着手は段 3b の後】 |
| タブ・時計 | 隠れたタブで処理が間引かれる・rAF が止まる・点滅の位相がずれる・スリープから戻ると時計の関係が飛ぶ | 端末側の話なので変わらない |
| 音 | 自動再生の制限、iOS で最初の音が落ちる、出力経路が眠る、Chrome のコンプレッサーの癖 | 変わらない（ネイティブ化で変わる） |
| 通知 | ブラウザごとに通知の出し方が違う。通知を押したときの処理を自分で書く必要がある | 変わらない |
| 2 つの版が同居 | 同じオリジンに 2 版があり、外側（標準版）の SW スコープが内側（DMDSS 版）を包む。SW の横取り・通知を押したときの入れ子・キャッシュ名・キーを、版ごとに分けて避けている | 版を統合すれば消える。URL の統合は【未決：§12】 |
| 静的配信 | 事前キャッシュは 1 ファイル 2 MiB まで。初回は控えに入らない。控えに限界がある。更新の適用が込み入っている | 静的配信を続ける限り残る |
| 静的配信 | 新しい版を配った直後、古い index.html が、まだ配っていない入口を読みに行って 404 になり、画面が白くなる（`boot-recovery.js`） | 変わらない（GitHub Pages のままなら残る） |
| 安全な接続 | LAN の http では、SW も `crypto.subtle` も使えない | 変わらない |
| 端末の保存 | API キーを平文で localStorage に置いている | 鍵の無い人は、鍵を持たなくてよくなる。予報のために鍵を入れる人には残る |
| 端末の保存 | 設定・学習が端末ごとに分かれる。IndexedDB を使えない端末がある。控えの容量を端末ごとに抱える | 設定を同期するかは【未決：§12「利用者ごとの状態を持たせるか」】 |
| 接続 | DMDATA の同時接続枠（3 本・4 本目は 409）を、端末ごとに 1 本使う | 鍵の無い人は枠を使わない。中継自身が 1 本使い、開発者の端末と取り合う（§4.3。枠の分け方は【未決：§12】） |
| 接続 | DMDATA の 429 の応答に CORS ヘッダが無く、ブラウザから原因が見えない | 見えるようになるのは、中継が DMDATA を叩く側だけ。鍵のある人が予報のために直接叩く経路には残る |
| 接続 | EarthScope の SeedLink は IP ごとに 5 本まで（同じブラウザのタブどうしで 1 本にまとめている） | 中継で束ねるかは、設計書に項目が無い【新規】 |
| 描画 | WebGL のコンテキストロスト、rAF の中の例外、フレームバッファ、発熱 | 無関係 |
| 描画 | ブラウザの中で VOICEVOX を合成できない | 「中継側で合成して配る」は §0 の問いで選ばれなかった（答え：ネイティブアプリに組み込む）。PWA の読み上げをどうするかとして【未決：§12】に残っている。別に合成用のサーバーが要る |

| サーバーでしか読めない情報を使う（Yahoo の Date ヘッダ、中継側の 429 の理由） | 【決定（2026-10-29）】同じ問いで選択肢「サーバーでしか読めない情報」を選んだ |

**中継にしても外れない制約**（配信元の規約・API 由来）

- **DMDATA の規約**
  - 予報の二次配信の制限（第 15 条）
  - 鍵の共有の禁止（第 7 条 3 項）
  - 警報を中継してよい根拠は条文ではなく、DMDATA サポートの返事（2026-10-14）
  - 加工したもの（合成音声・揺れ検知の結果など）が第 14 条の対象かは【未決：§2】
- **DMDATA の API の形**
  - レート上限（中継では IP が 1 か所に集まる）
  - 遡れるのは約 180 日分
  - 緊急地震速報は /telegram に載らない
- **ほかの配信元**
  - Yahoo の約 1.5 秒の遅れ
  - K-NET の再配布の禁止
  - GEBCO は一括で書き出せない
- **法律**：気象業務法第 17 条

### Yahoo を中継したい（ユーザーの原文、2026-10-29）

「Yahooを中継したいです。何故かと言うと常に温まったノイズデータを配れるから。」
「ちなみにサーバーで保存する場合どれぐらいの容量になって費用はどうなる？」

**保存した場合の容量**（手元の控え `.cache/kyoshin-quiet-days/` で 2026-10-29 に測った。静かな日だけで、揺れた日は測っていない）

| 形 | 1 時間 | 1 日 | 1 年 |
|---|---|---|---|
| 生のまま（観測点ごとの値を 1 バイト・毎秒） | 4.1 MB | 約 98 MB | 約 36 GB |
| gzip | 約 0.15 MB（145〜158 KB） | 約 3.6 MB | 約 1.3 GB |

**費用**（中継全体の費用は設計書 §10 が正。ここは Yahoo を足した分だけ。Cloudflare の料金は 2026-10-29 に読んだもの）

- R2 に gzip で置くなら、1 年で約 1.3 GB。含まれる 10 GB（DMDATA の束と共用）に収まる。超えた分は 1 GB・1 か月あたり 0.015 ドル。書き込みは 1 時間に 1 本なら月 720 回で、含まれる量の内
- 毎秒の取得を中継の DO から行う場合、DO は DMDATA の接続のために常に起きているので、時間の課金は増えない。取得を Alarm で起こすと月 260 万回の要求になり、含まれる量を超えて月約 0.25 ドル。起きている DO の中で回す取得が要求に数えられるかは資料から読み切れていない（未確認）
- 温まったゆらぎの表（`public/data/kyoshin-quiet-tables.json` と同じ形なら 204 KB）を配るだけなら、配る量は小さい

## ただ乗り・不正アクセスへの備え

### 前提にした事実

- **アプリはソースを公開している。** アプリに埋めた合言葉や手順は読めるので、「アプリ以外は絶対に繋げない」形は作れない。できるのは、繋ぐ手間を上げることと、繋がれても損が小さい形にすること
- **中継が配るものの多くは、気象庁が誰でも取れる形で出している**（気象庁防災情報 XML の公開フィード）。ただ乗りする側にとって値打ちがあるのは、**警報（VXSE43）の WebSocket**と、受けてすぐ届く速さだと見ている。公開フィードに警報が載らないこと、公開フィードが中継の配る種別をすべて含むことは確かめていない
- **費用の掛かり方**（[Workers の料金](https://developers.cloudflare.com/workers/platform/pricing/)、2026-10-29 に読んだ）
  - Worker への要求は月 1,000 万回まで含まれ、超えた分は 100 万回あたり 0.30 ドル。CPU 時間は月 3,000 万ミリ秒まで、超えた分は 100 万ミリ秒あたり 0.02 ドル
  - WebSocket は「繋ぐ」1 回が要求 1 回。中で流れるメッセージは要求に数えない。中継から送る分は DO でも課金されない（設計書 §6.1）
  - 静的アセットへの要求は無料・無制限
  - つまり**繋いだまま受け続けるただ乗りは、ほぼ費用にならない。** 費用になるのは、HTTP の口（一覧・本体・束）を繰り返し叩くことと、繋いでは切るを繰り返すこと
- **費用以外の害**
  - 1 つの DO が受けられる WebSocket は 32,768 本まで（設計書 §6.1）。埋められると正規の利用者が繋げない
  - 中継の中身をさらに配り直されると、DMDATA に中継を認めてもらった範囲（2026-10-14 のサポートの返事）を外れうる

### 決まったこと（2026-10-29）

- 問い「ただ乗りでいちばん避けたい害はどれですか？」で、選択肢「費用が膨らむ」「正規の利用者が繋げなくなる」を選んだ（「他のサービスに配り直される」は選ばなかった）
- 問い「不正アクセスへの備えをどうしますか？」で、選択肢「資料の 6 行をすべて採る」を選んだ。その時点の 6 行は、下の「不正アクセスへの案」の表の DMDATA の鍵・Cloudflare のアカウント・中継の口・Web Push の購読と送り口・依存・気づく
- 問い「避けたい害（費用・繋げなくなる）に合わせて、ただ乗りへの備えをどこまで入れますか？」で、選択肢「A＋B＋C」を選んだ。A は「変わらないものを Worker の手前で返す」、B は「IP ごとの回数の上限」（WebSocket の本数も）、C は「端末ごとの短い期限の札」。D・E は入れない。A の R2 公開バケットの課金は段 1a で確かめる

### ただ乗りへの案

| 案 | 何をするか | 費用 | 正規の利用者への影響 |
|---|---|---|---|
| A. 変わらないものを Worker の手前で返す | 束（日ごと）と電文本体を R2 の公開バケット＋独自ドメイン（Cloudflare の控え）から返し、Worker を通さない | 叩かれても Worker の要求に数えない見込み（R2 の公開バケットの課金は未確認） | なし |
| B. IP ごとの回数の上限（設計書 §6.4 にある） | Worker の中で数える。WebSocket は IP ごとの本数も絞る | 小さい | 同じ IP の後ろに多くの人がいる回線（学校・携帯の一部）で当たりうる。値は設定で持つ |
| C. 端末ごとの短い期限の札 | 初めて開いたとき中継から札（署名つき・期限は数時間）を受け、以後の口はその札を付ける。札の発行に B の上限を掛ける | 小さい | 初回に 1 往復増える。オフラインでは札を取り直せないが、控えで動く分には要らない |
| D. 札の発行に人の確認を挟む | C の札を、Cloudflare Turnstile（無料。多くは見えない確認で済む）を通した端末にだけ出す。ネイティブアプリは各 OS の端末認証（App Attest・Play Integrity）で代える | Turnstile は無料。端末認証も無料の範囲（未確認） | まれに確認の画面が出る。ブラウザの外から叩く道具は札を取りにくくなる |
| E. 配り直しを利用規約で禁じる | 中継の利用条件に「アプリ以外からの利用・配り直しの禁止」を書く | なし | なし。技術では止めないが、DMDATA への説明になる |

### 不正アクセスへの案

| 守るもの | 案 |
|---|---|
| DMDATA の鍵 | Worker の secret に置き、コード・リポジトリ・ログに出さない。鍵の権限は中継に要る区分（`telegram.earthquake`・`eew.warning`・`gd.eew`）だけにする |
| Cloudflare のアカウント | 二要素認証。配備に使う API トークンは、その Worker と R2 だけを触れる最小の権限で作り、期限を付ける |
| 中継の口 | 利用者の口は読み取りだけにする（いまの設計どおり）。入力（`datetime`・`limit`・`id`）は形を検証し、R2 のキーへそのまま渡さない。管理の口は作らない（作るなら Cloudflare Access の後ろへ置く） |
| Web Push の購読と送り口（決定済みの機能） | 購読の登録・解除は C の札がある端末だけ。通知を送る処理は中継の中からだけ呼び、外の口を作らない。購読は通知のためだけに持ち、IP を一緒に残さない |
| 依存 | 中継（`relay/`）にも `npm audit` を掛ける。依存は少なく保つ |
| 気づく | 要求数・WebSocket の本数・DMDATA との接続の状態を見張り、閾値を超えたら知らせる（Cloudflare の通知）。費用の上限の通知も置く |

# EEW（緊急地震速報）仕様書

> 本書は**現在の実装が EEW をどう処理するか**をまとめた仕様書。実コードと食い違う場合は実コードを正とする。
> 関連: [`data-sources-spec.md`](data-sources-spec.md) の EEW 電文受信、[`audio-tts-spec.md`](audio-tts-spec.md) の EEW 音・読み上げ、
> [`map-rendering-spec.md`](map-rendering-spec.md) の EEW 地図レイヤー。

## 1. 概要

緊急地震速報を受信・統合・表示するモジュール群。以下の役割を持つ:

- 電文の統合（同一 eventId の続報を最新報でまとめる）
- レベル判定（予報 / 警報 / 特別警報）
- 予報円の描画（P 波・S 波の地表到達円）
- 自動解除（一定時刻経過で無音・即消去）
- 誤報取消の処理（明示的な取消電文＝音・通知・読み上げを伴う）
- 仮定震源要素（震源未確定）の扱い

## 2. データフロー

```
[電文経路]
  DMDATA WebSocket / REST 履歴 (VXSE45)  ───────┐
  P2PQuake WebSocket (code=556)  ────────────────┴── enqueueEvent（eventQueue へ時刻順に積む）
  Yahoo hypoInfo（1Hz ポーリング・standard 版のみ）── handleEvent を直接呼ぶ（キュー非経由）
                                                            │
                                                            ↓
        [useEarthquakes] handleEvent (eventQueue から時刻順にディスパッチ)
                                                            ↓
                                          activeEEWs: Map<eventId, EEWAlert>
                                                            ↓
                                            ├─→ useLiveEventHandler
                                            │      音・通知・タブ切替・読み上げ・カメラフィット
                                            │
                                            ├─→ useEewLayerData
                                            │      地図の予想震度塗り・LPGM 区域塗り・震源マーカー
                                            │
                                            ├─→ usePsWaveCalc
                                            │      P 波・S 波地表到達円（100ms 更新）
                                            │
                                            ├─→ useSWaveCountdown
                                            │      S 波到達カウントダウン
                                            │
                                            └─→ RealtimeTab EEWCard
                                                   カード表示（見出し・震度・M・深さ等）
```

図の 3 経路が揃って動くことはない。DMDATA と、それ以外の 2 経路（P2PQuake・Yahoo hypoInfo）が
バリアントで排他的に入れ替わる（内訳は次節の表）。Yahoo hypoInfo の直接呼び出しは
`src/App.tsx` が `onEEWEvent` に渡す `injectEvent`（実体は `handleEvent`）による。

### 起動時に、発表中のものを復元する

**アプリを開いた時点で発表中の緊急地震速報を画面へ載せる**（`fetchDmdataActiveEews`）。地震を
感じてから開く利用者にとって、いちばん見たいものがそこにあるため。**DMDSS 版限定**——P2PQuake に
発表中の緊急地震速報を取る経路が無い（`code=556` は WebSocket だけ、Yahoo hypoInfo も同じ）。

- **取得は `/v2/gd/eew`。** 地震・津波が使う `/v2/telegram` は緊急地震速報を保持せず、`type=VXSE45`
  を指定しても 0 件が返る（取得元の詳細は [data-sources-spec.md](data-sources-spec.md) §2）
- **ただし配信元はこの API を「事後参照用」と定めている。** リファレンス（`GD Eew List v2` の
  「APIの情報」）にこうある ——「このAPIでは、**緊急地震速報の最終報を受信したのち**データが更新され
  ますので、**リアルタイム処理に用いるのではなく事後参照としてお使いください**」（`GD Eew Event v2`
  にも同趣旨）。つまり**復元したい対象——最終報より前の、まだ発表中のもの——がこの API にいちばん
  現れにくい**。**発表中のものが取れる保証は資料に無い。**
- **それでもこれを使うのは、他に手段が無いため。** `/v2/telegram` は緊急地震速報を持たず（上記）、
  アーカイブは前日分が 00 時 30 分頃までに生成される形なので当日の発表中のものを含まず、WebSocket は
  接続後に届く報しか受けない。**3 つとも塞がっている。**
- **効いているかは記録から確かめる。** 一覧が 1 件でも返った起動では「一覧 N 件 → 窓に入る M 件 →
  報を読めた K 件 → 有効 L 件」を記録に出している。**画面には「発表中のものが無かった」と
  「取れなかった」が同じ形で現れる**（どちらも何も出ない）ので、記録が唯一の手掛かり。
  **実配信の緊急地震速報が起きたあとにここを読めば、この経路が機能したか分かる**
- **1 つの地震につき電文は 1 通しか取らない。** 要るのは「いま有効か」の判定だけで、それは最新報
  1 通で決まる（最終報なら `isFinal` が立ち、立っていなければまだ続報中なのでそのまま採る）。
  全報を取ると 1 地震あたり数十リクエストになり、起動が目に見えて遅れる
- **途中の報で特別警報だったか（§4「特別警報の下げ止まり」）は、本文ではなく詳細の一覧から判定する**
  （`gdReportsEverSpecialWarning`。2026-10-21 ユーザー承認「おすすめで」）。最新報を選ぶために取っている詳細
  （`/v2/gd/eew/{eventId}`）は、報ごとに「警報か」（`isWarning`）と予想最大震度・予想最大長周期地震動階級
  （`intensity.forecastMaxInt` / `forecastMaxLgInt`）を持つので、リクエストは増えない（確かめたのは 2 地震の実応答。
  警報かどうかが地震ごとではなく報ごとに付くこと、長周期の欄が全報に無い地震があることもそこで見た。
  他の形は確かめていないので、読めない報は下の「判定できない報」として扱う）。
  - 予想震度 6 弱以上か長周期地震動階級 4 以上の報があれば、特別警報だったとみなして印（`everSpecialWarning`）を付ける。
    警報の欄が欠けていても数える（予想震度 6 弱以上は警報の基準を必ず越えるため）。上限を定めない予想（「6 弱以上」）は
    下限の値で見る（§4「上限を定めない予想の扱い」と同じ）
  - 取り消された報と予報の報（`isWarning` が偽）は数えない
  - **判定できない報**は、線を越えておらず、次のどれかに当たる報: 警報の欄が欠けている（偽なら予報の報として上で除く）・
    予想震度を読めない・長周期の欄はあるのに読めない（長周期の欄が無いだけなら当たらない）。判定できない報が混じり、他の報でも最新報の本文でも
    特別警報にならなかったときは、**記録に残したうえで特別警報ではなかったものとして戻す**
- **取得の間にライブの新しい報が先に着いても、特別警報の印は残す。** 復元した報が捨てられる形は 2 つある。
  - 起動時: 復元した報は通常の受信と同じ入口を通るので、ライブの報のほうが新しければ古い報として捨てられる（§10「古い報で退行させない」）
  - 張り直し: 取得した報の報番号が受け取り済みの番号以下なら、キューへ積まずに捨てる

  印は報ではなく地震についての事実なので、どちらも捨てる直前に印だけを表示中の速報へ移す（`carryEverSpecialWarning`）。
  音・読み上げ・タブ移動は起こさない。取り消された速報には移さない
- **戻した報が記憶へ載れば、その後のライブの報で特別警報への格上げの音と通知は出ない。** 戻した報は、表示中の速報の区分の記録
  （`activeEEWLevelsRef`。新規か続報かの判定と格上げの判定に使う）へ表示用の区分（`computeDisplayEEWLevel`）で載るので、
  印が付いていれば特別警報として載る。ライブで先に受けていた地震でも、戻した報のほうが新しければ同じように載せる
  （下の「読み上げ側の記憶も別の口で渡す」の項。2026-10-21 ユーザー承認「おすすめで」）。ライブで見ていた場合も、
  特別警報になった報より後の報では格上げの音と通知は出ない。
  記憶へ載らなかったとき（印を移すだけで報を積まなかった上の 2 つの形と、下の項で記憶を進めない形）は記録を書き換えないので、
  その後のライブの報が予想震度 6 弱以上なら格上げとして音と通知が出る
- **有効かどうかの判定はリプレイの初期状態と共有する**（`selectActiveEews`）。取消済みを弾き、
  最終報を探し、`calcEEWCancelTime` で失効を見る——どちらも「その時刻の画面を作り直す」という
  同じ目的なので、二重に持つと片方だけ直したときに再生と実機で挙動が食い違う。**失効は取り終えた時刻で見る** ——
  一覧と詳細は順に取るので、取得の途中で（門で待たされればそのぶん長く）自動解除の時刻を過ぎることがある。
  取り始めた時刻で見ると、その速報を「発表中」として返す
- **訓練・試験の報は、設定「試験報を受信（検証用）」が入っているときだけ戻す**（起動時・張り直しの両方。ライブ受信と同じ。
  2026-10-21 ユーザー承認「設定に従わせる (Recommended)」。`fetchLatestEewReport` の `includeTest`）。戻した報には電文の
  `Control/Status` から印が付く（→ [quake-spec.md](quake-spec.md) §5「電文の運用種別」）。**なお配信元は「テスト電文はこのAPIでは
  扱いません」とも書いている**ので、設定が入っていても試験報はそもそも一覧に載らず、戻すことは実際には起きない見込み。
  **それでも `includeTest` の分岐は残してある** —— 実測しておらず、資料が変われば通る
- **音も読み上げも鳴らさない。** 開いた本人は既に揺れを体験しているので、起動直後の警報音は情報を
  足さずに驚かせるだけ。イベントキューへ `silent` を立てて積むことで、状態の更新と自動解除の予約
  （§7）は通り、音・読み上げを起こす経路だけが呼ばれない（2026-10-21 ユーザー承認「無音のまま記録する (Recommended)」）
- **画面（タブ）は別の口（`onStartupRestore`）で要求する。** 上記のとおり `silent` は音の経路ごと
  止めるため、そこへ相乗りできない。優先度と駆動源の決め方は
  [audio-tts-spec.md](audio-tts-spec.md) §6「起動時の復元が出す要求」
- **読み上げ側の記憶も別の口（`onStartupRestoreEews` → `restoreStartupEews`）で渡す**（2026-10-19
  ユーザー承認「帳面に載せる」）。`silent` の報は読み上げ側へ届かないので、渡さないと後から届いた取消が
  「表示中の速報ではない」と判定されて鳴らず読まれず、続報は初報として読まれる。渡す中身はリプレイの初期状態と
  同じ記憶（どちらも `restoreTrackingFrom` で作る。録画モードの扱いだけは起動時に効かせない）で、音も読み上げも出さない。
  誤報取消を受けた地震は、一覧が遅れて発表中と返しても載せない。震央地名も覚える
  （取消電文は名前を持たないので、覚えていないと取消のブラウザ通知が名前抜きになる）。続報の鳴らし方は
  [audio-tts-spec.md](audio-tts-spec.md) §4「「〇時〇分に発表された」は取り消された側の時刻」
  - **ライブで既に受けた地震でも、戻した報のほうが新しければ記憶を進める**（2026-10-21 ユーザー承認「おすすめで」）。
    張り直しでは切れていた間の報がここへ来る。進めないと、格上げの判定・声にした区分と予想震度・名乗った震源が切れる前のまま残り、
    次のライブ報で、切れていた間に出ていたはずの格上げの音・通知・「緊急地震速報に切り替わりました」が遅れて出る。
    - **進めない形**: 戻した報が最後に見た報より古いか同じ（起動の直後にライブの報が先に届いたときなど。配信元の一覧は遅れることがある）・
      最後に見た報の記録が無い・新旧を比べられない（これだけ記録に残す）・読み上げが途中（第 1 フェーズの予約か発話中、
      第 2 フェーズの予約、安定待ち。進めるとまだ鳴っていない名乗りや予想震度が「声にした」扱いで黙る）。
      進めなかった地震は、次のライブ報で従来どおり追いつく
    - **新旧の比べ方**: 同じ経路なら報番号、比べられなければ発表時刻（秒）
    - **進める中身**: 区分と声にした予想震度は上げるだけで下げない（ライブでも、声にした値より下がった報では読み直さない）。
      名乗った震源は切れる前に名乗ったものへ積む。第 1 報の時刻だけは新旧によらず、復元側のほうが早ければ差し替える
      （ライブで最初に受けたのが第 2 報以降のとき）
    - **利用者から見えること**: 進めるだけで鳴らさない（鳴らすと時刻のずれた知らせになる）。そのため、切れていた間に予報から警報へ
      上がった・予想震度が上がったことは、音・ブラウザ通知・読み上げのどれでも伝わらず、カードの表示だけが変わる
      （この代償を示したうえで「遅れて鳴らさない」に決めた。2026-10-21 ユーザー承認「1で」）
  - **記憶の無い地震（起動時・リプレイの全件と、張り直しで初めて知った地震）では、声にした予想震度
    （`spokenEEWScalesRef`）として、戻した報＝その地震の最新の報の値を覚える**（2026-10-21 ユーザー承認「おすすめで」。
    「声にした値を最新報の値のまま残し、理由を書く」案への承認）。復元の後に届くライブの報は、この値より高ければ読み、
    同じか低ければ黙る。ライブで見ていた場合との差は、予想震度がいったん上がってから下がっていた地震で出る ——
    ライブなら上がった値を読んだあとなのでそれ以下では黙るが、復元では最新の報の値より上がれば読む。
    全報の最大は採らない。理由: 最大は「実際に声にした値」の近似にすぎず、外れると声にしていない値を声にした扱いにして
    次の報を黙らせる。最新の報の値なら、外れても読み上げが 1 回増えるだけで済む
  - **最後に名乗った震源も、どの復元でも覚える**（同日承認）。空のままだと、復元した速報はその後震源が大きく動いても
    「震源を更新」を一度も言わない
  - **初めて知った地震には、ウィンドウタイトルを付ける**（起動時・張り直しとも。同日承認）。ライブなら発報の時点で付く。
    起動時は App の初期反映（`applyPriority`）も後から同じ速報のタイトルを付け直す。張り直しの時点ではその初期反映は済んでいるので、
    ここで付けないと次の報までタイトルが付かない
  - **張り直しで初めて知った地震があれば、起動時と同じ画面の要求を出す**（同日承認）。ライブなら発報で実時間タブへ移る。
    台帳（報番号の記録）に無い地震があるときだけ出し、見ていた地震の続報だけなら出さない
- **取り直しの最中に画面から消えた地震は戻さない**（2026-10-21 ユーザー承認「おすすめで」）。ここでいう取り直しは、
  この取得（`fetchDmdataActiveEews`）を回す 2 つの場面 —— 起動時の復元と、DMDSS 版で WebSocket を張り直したときの取り戻し
  （→ [data-sources-spec.md](data-sources-spec.md) §2「繋がっていなかった間の電文を取り戻す」）。
  - **起きること**: 終わった速報が、終わったあとも発表中として残る。本物の速報がすべて解除されてもウィンドウのタイトルが戻らず、
    次の速報に「他 1 件」が付く
  - **なぜ起きるか**: 取得の最中に、画面のほうで同じ速報が自動解除・誤報取消で消えることがある。消えた地震の報番号の台帳
    （§10「古い報で退行させない」）は消えた時点で捨てるので、取り直しが返した報を「もう終わった地震の報」と見分けられない。
    戻した報は読み上げ側の記憶（[audio-tts-spec.md](audio-tts-spec.md) §6「「まだ生きているか」の印は、読み上げ設定と独立に持つ」）にも載り、そこに居座る
  - **使う場面**: 上の取り直し 2 つに加え、ライブの受信の入口でも同じ記憶を照らす（§10「古い報で退行させない」。2026-10-21 ユーザー承認「おすすめで」）
  - **覚えるもの**: 一度画面に載ってから消えた地震の、経路ごとの報番号と最新の発表時刻、取消で消えたか。取り直しの窓（`ACTIVE_EEW_WINDOW_MS`・
    15 分）より前に終わった速報はそもそも返ってこないので、覚えておくのも同じ 15 分。リプレイの開始・リセットで忘れる
  - **照らし方**（`endedEewMatch`）: 同じ経路の報番号で比べられれば、消えるまでに受けた報番号以下の報を弾き、それより新しい報は
    続いている速報なので戻す。経路が違う・報番号が無いときは発表時刻で比べる。どちらでも比べられないときは戻す（本当に発表中の
    速報を落とすほうが重い）。**取消で消えた地震は、報番号・発表時刻によらず弾く**（取消は終端。2026-10-21 ユーザー承認「おすすめで」）。
    自動解除で消えた後に取消が届いた地震も、その時点から取消で消えた扱いにする
  - **記録**: 弾いたら、鍵・報番号・消えてからの秒数を残す。画面には「出ない」としか現れないため
- **第 1 報の発表時刻も載せる**（`EEWAlert.firstIssueTime`）。取り出す電文は最新報 1 通だが、同じ詳細の
  応答が全報の発表時刻（`items[].dateTime`。資料「GD Eew Event v2」で出現は「いつも」）を返すので、取消でない
  報のうち報番号のいちばん小さい報の時刻を拾う（`firstEewReportTime`）。誤報取消の読み上げが言う時刻に使う。
  拾えなければ null を載せ、取消は時刻を言わずに読む（最新報の時刻では代えない。2026-10-19 ユーザー承認
  「時刻を言わない (Recommended)」）。拾えなかったときは内訳（取り消された報・報番号か時刻を読めない報の数）を記録に残す
  （→ [audio-tts-spec.md](audio-tts-spec.md) §4「「〇時〇分に発表された」は取り消された側の時刻」）
- **呼ばれるのは起動時だけではない。** 接続の effect は API キーの編集やリプレイの往復でも再実行され、
  そのたびに復元が走る。**「初回だけ」に絞らないこと**——React の StrictMode は開発時に effect を
  2 回実行し、1 回目は cleanup で破棄されるため、「初回か」を覚えると**開発モードでだけ画面の要求が
  一度も出なくなる**（本番では出るので食い違いに気づけない）
- **1 件の失敗で他を巻き込まない。** 複数の地震が同時に発表中の場面こそこの復元が効くところなので、
  詳細の取得で例外が出た地震は 1 件ずつ諦めて次へ進む
- **電文本体は控えと門を通して取る**（`fetchTelegramText`。→
  [data-sources-spec.md](data-sources-spec.md) §2「電文本体の控え」「窓ごとの上限を守る」）。
  素の `fetch` で取るとこの経路だけ控えに載らず、起動のたびに同じ電文を取り直す。
  **ただし門では履歴を追い越す**（`urgent`）—— 当日ぶんの履歴が同じ門に並ぶので、後ろへ回すと
  最悪 24 秒遅れて画面に出る。**間隔そのものは変えていない**

## 3. 電文経路・バリアント差・名称

3 系統の電文源がある:

| 経路 | バリアント | severity | condition | 長周期 lgIntTo | 使い方 |
|---|---|---|---|---|---|
| DMDATA WS/REST | DMDSS | 電文値（Warning/Forecast） | 電文値（`'仮定震源要素'` あり） | あり | 主系 |
| P2PQuake WS | standard | 電文に無いが `convertEvent` で一律 `'Warning'` 付与 | 数値/文字列 | なし | 主系（DMDSS 版は不使用） |
| Yahoo hypoInfo | standard | 震度からの推定（`>= 5弱 ? 'Warning' : 'Forecast'`） | 常に空（運ぶ欄が無い） | なし | 補完的に検知（DMDSS 版は不使用） |

P2PQuake の 556 で severity が付与される仕組みは [`data-sources-spec.md`](data-sources-spec.md) §3
を参照（電文仕様と付与ロジックはそちらに一本化）。

**Yahoo hypoInfo を DMDSS 版で使わない仕組み**: `src/App.tsx` が `useKyoshinRealtime` に渡す
`onEEWEvent` を DMDSS 版では `undefined` にしている。通知先が無いとき `useKyoshinRealtime` は
差分の基準（直前の hypoInfo）だけ進めてイベントを捨てるため、DMDSS 版では Yahoo 由来の EEW が
状態へ入る経路そのものが存在しない。**リアルタイム震度は両バリアントとも Yahoo を使う**
（強震モニタのフレームに hypoInfo は載ってくるが、EEW としては読まない）という点に注意。
クロック較正の主経路は別の時刻サービスに移っており、Yahoo は取得に失敗した周期のフォールバックとして
両バリアントで使う（[`data-sources-spec.md`](data-sources-spec.md) §4「クロック同期」）。

**2 つの経路の報を 1 つにまとめる（standard 版）**: Yahoo hypoInfo と P2PQuake の 556 は、同じ地震の同じ報を
別々に運ぶ。どちらの報も同じキューを通って `handleEvent` へ入り、入口で 1 回だけ統合する
（`utils/eew.ts` の `mergeEewReport`）。**状態に入れる値と、読み上げ・通知へ渡す値は同じもの**にする。

各報には運んできた経路（`EEWAlert.origin`）が付く。**経路が運ばない欄は、前の報の値を保つ。**

| 経路 | 運ばないので前の値を保つ欄 |
|---|---|
| Yahoo | 区域・仮定震源要素かどうか（`earthquake.condition`）・地震発現時刻 |
| P2PQuake | 電文全体の予想最大震度（`forecastMaxScale`）・最終報の印（`isFinal`） |
| DMDATA・保存データ・テスト | なし（丸ごと置き換える。ただし下の区分と特別警報の印は全経路で上げる向きだけ） |

- **仮定震源要素かどうかは、Yahoo が新しい報で来ても直前の P2PQuake の値を保つ**（2026-10-14 ユーザー承認
  「直前の P2PQuake の値を保つ」）。Yahoo はこの区別を運ばない。保たないと仮定震源要素の判定（§5）が
  外れ、地図の震源×印の形が「× ＋外周の輪」と「普通の ×」の間を行き来する
- **Yahoo が規模を運ばなかった報（読めない値は `NaN`）では、前の報の規模を保つ。** 震源のほかの欄（震央地名・
  座標・深さ）は差し替える。読めない規模を `0` で表すと、カードに M0.0 と出たうえ P2PQuake が運んだ規模も
  消える。Yahoo の報は規模の説明を持たないので、前の報にも規模が無ければカードのマグニチュードの欄は「不明」と出る
- **区分（`severity`）は上げる向きにだけ動く。** 届いた報が警報なら上げ、一度警報になったら予報の続報でも
  下げない（Yahoo は震度から区分を推し量るので、P2PQuake が警報と伝えた後でも弱く出る）
- 特別警報の下げ止まり（§4）の印は一度立てたら落とさない
- **予想の最大震度は、新しい報が運んだほうで見る。** ふだんは区域の最大を先に見るが（§4）、Yahoo の続報が
  電文全体の値を運んだら、保っている区域は前の P2PQuake の報のものなので、電文全体の値で見る
  （`EEWAlert.maxScaleFromForecast`）。区域の最大で見続けると、Yahoo の続報が 6弱へ上げても特別警報へ
  上がらない。**下げる向きも同じ**で、電文全体の値が区域の最大より低ければ低い値を出す（特別警報の印は下げ止まる。§4）。
  印を立てるのは Yahoo の報が 0 より大きい値を運んだときだけで、下ろすのは P2PQuake の報が区域を運んだときだけ
  （遅れて届いた報で補ったときは触らない）。区域の塗り・一覧は前の P2PQuake の報のままなので、最大の値と区域が
  食い違って見えることがある
- **同じ報を別の経路から 2 度受けたら、2 通目では音を鳴らさず続報のタブ要求も出さない**（2026-10-18 ユーザー承認・
  選んだ選択肢「最初の 1 通だけ」）。「同じ報」は経路が違い発表時刻（秒）が同じ報に限る —— 同じ経路から同じ秒の
  報がもう一度来ても止めない（訂正報は知らせ直す）。読み上げとウィンドウタイトルは止めない —— 後から来た経路が運んだ欄（区域など）で
  最新の値が変わりうる。まとめた結果の区分か予想の最大震度が上がったときは、同じ報でも鳴らす
  （`raisesEewAlert`。予想の最大震度は 2026-10-19 ユーザー承認・選んだ選択肢「鳴らす」）—— 同じ秒に別の報が出ることが
  あり、秒だけでは「同じ報」と言い切れない。判定は
  §10「古い報で退行させない」の台帳で行い、受信側が印（`LiveEventMeta.eewSameReport`）を付けて渡す
- **Yahoo の新しい報より後に着いた P2PQuake の報は捨てず、区域・仮定震源要素かどうか・区分（上げる向きだけ）を補う**
  （`supplementEewReport`）。Yahoo は 1 秒ごとに取りに行くので、速報が続くあいだは P2PQuake の報が Yahoo の
  次の報より後に着くことがあり、捨てると区域と仮定震源の別が一度も入らない。震源・震度・報番号は新しい側の
  まま。新しい報ではないので音・タブ移動は起こさない（区分か予想の最大震度が上がったときだけ知らせる。
  2026-10-19 ユーザー承認・選んだ選択肢「上がったときだけ鳴らす」）。
  P2PQuake 自身の新しい報より古い報は、これまでどおり捨てる。
  **例外は規模で、** 新しい側の規模が読めていなければ、後から着いた報の規模で補う（その報も規模を持たなければ補わない）

### 電文の名称と表示・読み上げ

DMDATA 経路で受けるのは 1 種類だけ。

| 電文種別 | `Control/Title` | 備考 |
|---|---|---|
| VXSE45 | 緊急地震速報（地震動予報） | 長周期地震動階級を含む（[DMDATA の電文一覧](https://dmdata.jp/docs/telegrams/ew09040/)）。**警報に該当するかは電文内の `isWarning` が示す**ため、VXSE45 でも警報相当になりうる |

VXSE43（警報）と旧形式の VXSE44（予報）を扱わない理由は [`data-sources-spec.md`](data-sources-spec.md)
§2「EEW は VXSE45 だけを受ける」を参照。**予報（`eew.forecast`）を契約していない・鍵に権限が無い人に限り、
VXSE43 を緊急地震速報として取り込む**（同 §2「一部の区分だけ受けられる人」）。予報を受けている人が VXSE43 を
取り込まないこと・VXSE44 を扱わないことは 2026-10-21 ユーザー承認「今のまま記録する (Recommended)」。

> **区分を決めているのは severity（`computeSingleEEWLevel`）で、電文種別ではない。**
> `severity` は「`headType` が VXSE43」または「区域の `Category/Kind/Name` が『緊急地震速報（警報）』」
> から導く（`dmdataParser.ts` の `parseEEWFromXml`）。
> 予報を受けている人は VXSE43 を受信しないため実際に立つのは後者だけだが、パーサは渡された種別を電文どおりに解釈する
> （種別の絞り込みは呼び出し側の責務）。「電文種別＝区分」と読み替えると、`isWarning` が立った
> VXSE45 を予報級と誤って扱うことになる。

**呼び方は電文の名称から借りる。** 予報級を「地震動予報」と呼ぶのは、その内容を運ぶ VXSE45 の名称が
「緊急地震速報（地震動予報）」だから。予報級を「緊急地震速報（〜）」の器に入れると
「緊急地震速報（地震動予報）」と二重になるため、器ごと分ける。区分の名前は `eewKindLabel`
（`src/utils/eew.ts`）が単一情報源。

**電文が名乗る情報名（`Head/Title`）は読んで持つだけで、画面には出さない**（`EEWAlert.infoName`。
2026-10-22 ユーザー承認「出さない (Recommended)」。2026-10-21 に選んだ「電文の名前も出す」はこれで
取り下げた）。アプリが受信する VXSE45 では実電文 8 通すべてが「緊急地震速報（地震動予報）」の 1 種類で
報ごとに変わらず、カードの見出し（下表）と並べると同じ語が二重に出る。

| 表示箇所 | 予報級 | 警報級 | 特別警報の条件を満たす場合 |
|---|---|---|---|
| リアルタイムタブのカード見出し | 地震動予報 | 緊急地震速報（警報） | 緊急地震速報（特別警報） |
| 地図のポップアップ（震源・区域） | 地震動予報 | 警報 | 警報 |
| ブラウザ通知の見出し | 地震動予報 | 緊急地震速報 警報 | 緊急地震速報 特別警報 |
| ウィンドウタイトル | 地震動予報 … | 緊急地震速報 … | 緊急地震速報 … |
| 電文ログ | EEW地震動予報 | EEW警報 | EEW警報 |

**地図のポップアップの行は、震源と区域で判定の軸が違う。** 震源×印（`EewEpicentersGL`）は電文の
`severity` を見るが、区域塗り（`EewRegionFillGL`）は**区域ごとの `kindCode`** を見る（下の
§4「区域の種別コード」）。同じ警報級の電文でも、予想震度 5 弱未満の区域は予報域なので、
その区域のポップアップだけ「地震動予報」と出る。表は 1 行にまとめているが同じ基準ではない。

電文ログの列だけは**電文種別（`headType`）から引く**（`TelegramTab/labels.ts` の `HEAD_TYPE_LABEL`）。
電文そのものの記録なのでそれが正しい。ただし `isWarning` が立った VXSE45 は severity では警報相当
なのに、ログには `EEW地震動予報` と出る。**ログの列と他の列は別の軸で決まっている**ことに注意。

> **ウィンドウタイトルの変更は外部への破壊的変更。** タイトルは AutoHotKey 等の外部監視向けの
> 文字列（[`audio-tts-spec.md`](audio-tts-spec.md) §1・§5）なので、「緊急地震速報」で文字一致
> させている仕組みは予報級を拾えなくなる。予報級も拾うなら監視側に「地震動予報」を足すこと。

**「緊急地震速報（予報）」も気象庁の公式な用語**（情報の名称としての呼び方）だが、電文の名称に
合わせる方を採っている。ここに書いたのは**表示**の理由。読み上げには「音声だけで区分が判別できる
ようにする」という固有の理由が加わるため、そちらは [`audio-tts-spec.md`](audio-tts-spec.md) §6 にある。

### 報番号の見た目は地震情報カードと共有する

種別ヘッダーの右に添える報番号（`#22`・最終報なら `#22 最終報`）は `components/SerialBadge.tsx`
に置き、**地震情報カードと同じものを使う**。どちらも同じ器（種別ヘッダー）へ出すもので、
別々に書くと片方だけ変わる。

**揃えるのは見た目だけ。** 番号が何を数えたものかは出す側で違う。こちらは電文が名乗る報番号
（`Head/Serial` → `eewSerial`）で、地震情報カードは受け取った通数
（→ [`quake-spec.md`](quake-spec.md) §8「見出しには受け取った種別を並べる」）。

### 真偽値は電文の形から復元する（`parseEEWFromXml`）

電文には「取消か」「最終報か」「警報級か」を表す真偽値が無い。DMDATA の JSON 変換はこれらを
`body` のフラグとして持つが、**XML では別の形で現れる**ので読み替える（実電文 24 通で対応を
確かめた。予報級 14・警報級 6・仮定震源要素 1・取消 1・取消前 2）。

| 意味 | XML での現れ方 |
|---|---|
| 取消 | `Head/InfoType` が「取消」 |
| 最終報 | `Body/NextAdvisory` に最終報の文言、**または取消** |
| 警報級 | 区域の `Category/Kind/Name` が「緊急地震速報（警報）」 |

**取消は最終報として扱う。** 実電文の取消は `Body` に `Text` しか持たず `NextAdvisory` が無い
（2026-03-07 の取消で確認）。文言だけを見ると最終報にならず、自動解除の扱いが変わる。

**`Condition` は要素の位置で意味が変わる。** `Earthquake` 直下は震源の状態（「仮定震源要素」）、
`Pref/Area` 直下は区域の状態（「既に主要動到達と推測」）。子孫から拾うと、警報級の電文で区域側の
文言が震源の `condition` に化け、**仮定震源要素の判定が誤って立つ**（§5 の抑制が丸ごと発動し、
震源・規模が画面と読み上げから消える）。

上限を定めない予想震度（`<To>over</To>`）は XML でも同じ語で現れる（扱いは §4「上限を定めない
予想震度の扱い」）。

**震源要素が「全要素とも不明」と書かれた電文（`description="震源要素不明"`）は捨てない。**
震源の位置は「不明」のセンチネル（`-200`）へ倒し、予想震度と対象区域はそのまま出す ——
予報円は描けなくても、伝えるべきことが残っている。**位置を使う側は `hasKnownEpicenter` を通すこと**
（`Number.isFinite` だけではセンチネルをすり抜ける）。判定の作り、すり抜けたときに壊れる箇所、
書式が壊れた電文と分ける理由は [quake-spec.md](quake-spec.md) §5「震源要素不明の電文は捨てない」
（地震情報と EEW の単一情報源。津波と長周期は震源の座標を読まないので関与しない）。

### 震源要素の精度（`Hypocenter/Accuracy`）

震源・深さ・マグニチュードをどう決めたかが属性に入る（電文解説資料 Ⅱ.21 1-4-2）。
**実電文 405 通（2026-06〜09）すべてに入っている。** 本文はどれも `"NaN"` 固定で、意味は
属性にしかない（`NumberOfMagnitudeCalculation` だけ本文に数値）。

| 属性 | 意味 |
|---|---|
| `Epicenter@rank` / `Depth@rank` | 1＝P波／S波レベル超え、IPF法（1点）、または仮定震源要素／2＝IPF法（2点）／3＝IPF法（3点／4点）／4＝IPF法（5点以上）／5・6＝防災科研システム／7・8＝EPOS |
| `Epicenter@rank2` | **9＝推定震源とマグニチュードはこれ以降変化しない** |
| `MagnitudeCalculation@rank` | 2＝防災科研システム／3＝全点P相／4＝P相／全相混在／5＝全点全相／6＝EPOS／8＝P波／S波レベル超え、または仮定震源要素 |
| `NumberOfMagnitudeCalculation` | Ｍ計算に使った観測点数（**5 は「5点以上」**） |

**数字は画面に出さず、資料の語をそのまま出す。**「ランク4」では何も伝わらないので意味へ直すが、
**言い換えはしない** —— 「IPF法（5点以上）」を「精度が高い」と要約すると、資料と突き合わせ
られなくなるうえ、こちらが評価を足したことになる。対応表は `utils/eewAccuracyRanks.ts` が単一情報源（表示も読み取りも同じ表を見る）。
**ランク 0（不明）の報も精度の欄を出さない**（「不明」と書いても欄が埋まるだけ。2026-10-21 ユーザー承認
「記録し、表外はログへ (Recommended)」）。
**表に無いランク（0＝不明は除く）は、値を持ったまま画面の欄を空にし、読み取りの時点で開発者向けの記録を 1 行残す**
（`unknownEewAccuracyRanks`。2026-10-21 ユーザー承認「記録し、表外はログへ (Recommended)」）。黙って空にすると、資料の改訂で
値が増えたことに気づけない

**括弧書きも落とさない。** 資料は 7・8 を「EPOS（海域〔観測網外〕）」「EPOS（内陸〔観測網内〕）」
と書いており、この括弧が**観測網の外か内か**を言っている。「EPOS（海域）」まで縮めると、
何と対比しているのかが画面から読めなくなる（縮めていた版があった）。

**`rank2` が 9 でも「最終報」とは書かない。** 資料は同じ注で「PLUM 法により予測震度が今後
変化する可能性はある」と断っている —— 震源が決まっても予想震度は動きうる。

**`rank` が 1 は「単独点で決めた」ことを電文が直接言っている。** `earthquake.condition`
（仮定震源要素）とは別の事実で、仮定震源要素でなくても 1 点なら立つ。

深さの精度（`Depth@rank`）は震央と同じ表を引く。**同じ値なら 1 行にまとめる**（同じ文字列を
2 行並べても情報は増えない）。語がそのままでは通じないので、**説明はホバーへ逃がす**
（設定タブと同じ `DescriptionTip`）—— 「言い換えない」と「説明しない」は別のこと。

> **実測では、深さが単独の行になったことはない。** 購読分類 `eew.forecast` のアーカイブ
> 全 7,995 通（2026-05-01〜09-11）のうち `Accuracy` を持つ 4,798 通を数えると、震央と深さの
> ランクが食い違った電文は 0 件だった（内訳は rank=4 が 4,526 通・3 が 136・1 が 100・2 が 36。
> **5〜8（防災科研システム・EPOS）は 1 件も無い**）。つまり画面には常に「震源」1 行として
> 出ており、2 行に割れる分岐は運用では通っていない。**分岐を消す理由にはしない** ——
> 気象庁が別々のランクを送れる形で定めている以上、食い違った報が来たときに深さの精度が
> 黙って消えるほうが重い。
>
> **上の「405 通」とは別の調査で、どちらも結論は同じ。** あちらは EEW の要素を横断して
> 数えた標本で、`LandOrSea`（404/405）や `Appendix`（318/405）の件数もその標本から出ている
> （`src/types/earthquake.ts`）。こちらは `Accuracy` だけを見るために**アーカイブに入っていた
> XML 電文をすべて数えた件数**で、`Accuracy` を持たない配信試験（VXSE42）3,197 通を
> 除いた残りにあたる。件数が桁違いなのは母数の取り方の違いによる。

**見出しも資料の語を使う。** 資料はこの要素群を `Accuracy`【**精度情報**】と呼び、下位を
「震央位置の精度値」「深さの精度値」「マグニチュードの精度値」と呼んでいる（Ⅱ.21 1-4-2）。
**合わせるのはブロックの見出しだけ**で、行のラベルは短いまま（「震源」「震央」「深さ」「Ｍ」）
—— 見出しは要素群全体の呼び名、行のラベルはその中のどれを指すかの札で、担う粒度が違う。
見出しは単独では何の精度か読み取りにくいが、**アプリが言い換えを作るよりホバーの説明で
補うほうが、資料と突き合わせられる**（「震源の決め方」と書いていた版があった）。

**規模が数値にならない報の説明（`Magnitude@description`）も読む**（`Hypocenter.magnitudeCondition`）。地震情報・津波と同じ規則で、
本文が `NaN` のときだけ持つ（2026-10-21 ユーザー承認「揃えて読む (Recommended)」）。「Ｍ不明」と「Ｍ８を超える巨大地震」は本文が
どちらも `NaN` で、この説明でしか見分けられない。カードの M の欄・地図の震源の吹き出し・共有カードの画像
（いずれも `formatMagnitudeWithCondition`）は、説明があればそれを出す（地震情報と同じ部品。2026-10-22 ユーザー承認「吹き出しと共有カードも揃える
(Recommended)」）。説明の変化（「Ｍ不明」→「Ｍ８を超える巨大地震」）にもカードの M の欄の更新の印が付く。
読むのは DMDATA の XML 経路だけ（標準版の経路はこの説明を運ばない）

**電文の運用種別（`Control/Status`）も読む。** 訓練・試験の報にカードで印を出す。
地震情報・津波情報と共通の仕組みで、単一情報源は
[quake-spec.md](quake-spec.md) §5「電文の運用種別」。

**標準版の訓練報・試験報も、設定「試験報を受信（検証用）」が入っていれば印を付けて流す**（既定は受けない）。
標準版の経路は運用種別を運ばず、訓練かどうかの旗だけを持つので、その旗から印を付ける —— 強震モニタの `isTraining` は
「訓練」、P2PQuake の `test`（仕様の説明は「テストかどうか。」だけ）は「試験」（`utils/eew.ts` の `admitTrainingEew`。
`handleEvent` の入口で 1 回だけ通す。2026-10-21 ユーザー承認・選んだ選択肢「「試験報」の印で出す (Recommended)」）。
設定の行は標準版にも出す（設定タブ「接続設定」）。

### 最大予測値の変化（`Intensity/Forecast/Appendix`）

**気象庁が「変わったか」と「なぜ変わったか」を直接言っている**（解説資料 Ⅱ.21 2-1-4）。
アプリは続報どうしを比べて変化を推定しているが、それは代理指標で、電文はこちらを正としている。

- `MaxIntChange` / `MaxLgIntChange` … 0＝ほとんど変化なし／1＝1.0 以上大きくなった／2＝1.0 以上小さくなった
- `MaxIntChangeReason` … 0＝変化なし／1＝主としてＭが変化（1.0 以上）／2＝主として震央位置が変化（10.0km 以上）／3＝Ｍと震央位置の複合／4＝震源の深さが変化（30.0km 以上）／**9＝PLUM 法による予測により変化**

**「1.0 以上」は計測震度の差**で、画面に出している震度階級の差とは別物。「階級が 1 つ上がった」と
読み替えないこと。文は `eewForecastChangeText` が組む（変化が無い報・読めない報では空を返す）。

#### 帯を出し続ける長さは、報の状態と切り離してある

ここでいう**帯**は、カードの震源名の下に出るこの一文（`eewForecastChangeText` の戻り値）のこと。
**出す先は画面だけ** —— 読み上げ・ブラウザ通知・共有カードには載せていない。`Appendix` が
入るのは DMDATA の XML 経路だけなので、standard 版では帯そのものが出ない。

**気象庁はこの変化を 1 通しか言わない。** 第 1 報を除くほぼ全通が `Appendix` を持つが、
変化が無い報は値を 0 にして送ってくる —— 要素が消えるのではなく、値だけが戻る。
続報は数秒間隔で届くため、報の状態をそのまま描くと帯は 1 秒ほどで消えて誰も読めない。

そこで表示の寿命はカード側が持つ（`RealtimeTab` の `useHeldForecastChange`）。
変化を立てた報から最低 `EEW_FORECAST_CHANGE_HOLD_MS`（10 秒）は出し続け、その間に
変化なしの報が来ても消さない。

| 決めごと | 理由 |
|---|---|
| 保持するかどうかは**「変化を伝える値か」**で判定する（`eewForecastChangeText` が非空を返すか） | `Appendix` の有無で見ると、変化なしの続報を「新しい値」として採ってしまい保持が効かない |
| **新しい変化が来たら差し替えて計時し直す** | 保持は「変化なしの報で消さない」ためのもので、気象庁が言い直したものを抑えるためではない |
| 計時をやり直す契機は**報番号** | 同じ文言が離れた報で再び立つ形があるので文言だけでは 2 度目を拾えない。一方で `eew` オブジェクトの参照は「新しい報が届いた」ことの**代理値にすぎない** —— 報の到着以外でも EEW は作り直される（standard 版の区域・震源要素の注ぎ足し、取消の適用） |
| 取消の報では出さない（2026-10-21 ユーザー承認「今のまま記録する (Recommended)」） | 取り下げた予想について「大きくなりました」と並べても意味がない。**隠しているのは `useHeldForecastChange` が戻り値を決めるときの `cancelledAt` 判定そのもの** —— 取消電文は `Appendix` を持たないが、状態更新は取消を `{ ...表示中の EEW, cancelledAt }` の形で当てるため、**直前の報の値がそのまま残る** |
| 長さは**実時計**で測る | 画面に出ている時間は利用者が読むのに要る時間。リプレイの再生時計（電文の失効に使っているもの）には乗せていない |
| **発表から `EEW_FORECAST_CHANGE_HOLD_MS`（10 秒）を過ぎた報では帯を立てない**（2026-10-21 ユーザー承認「おすすめで」。「発表から 10 秒を過ぎた報では帯を出さない」案への承認） | 起動時・張り直しの復元とリプレイの初期状態は、数分前の報を「いま初めて見た報」として描く。ライブで見ていればその帯はもう消えているので、出すと終わった変化を新しい知らせのように見せる。ライブの報は発表から数秒で届くので止まらない（届くのが 10 秒以上遅れた報では帯が出ない） |
| 「もう古いか」は電文の発表時刻（`eewIssueTimeMs`）と `serverNow()`（リプレイ中は再生時計）の差で測る | 保持する長さは上の行のとおり実時計で測るが、こちらは比べる相手が電文の発表時刻なので、電文と同じ時間軸に置く |
| 発表時刻が読めない報は止めない。古い報が届いても、前の報が立てた帯は消しも延ばしもせず、その計時のまま残す | 比べられないものを黙らせない。古い報は新しい変化を伝えないので、帯の計時を動かす理由が無い |

10 秒という値は「変化が続いている間、帯が途切れないこと」から決めた。効くのは
**別の文言へ差し替わるまでの間隔**で、実電文（2026-06-01〜09-06 の `eew.forecast`
アーカイブ・334 イベント）で変化を立てた 55 通を数えると次のとおり。

| 測ったもの | 実測 |
|---|---|
| 別の文言へ差し替わるまで | 33 通・最大 9 秒 |
| 同じ文言が再び立つまで | 5 通・最大 4 秒 |
| 実際に出た文言 | 4 種（「大きくなりました」28／「小さくなりました」18／「大きくなりました（PLUM法による予測で変わったため）」5／「大きくなりました（マグニチュードが変わったため）」4） |

10 秒あればどちらも覆う。上限の側は、EEW のカード自体が最終報から 60 秒以上出ている
（`calcEEWCancelTime` の下限）ことに対して十分短いこと。

> **次の報が来るまでの間隔（中央 1 秒・最大 10 秒。うち 35 通が次報で値 0 に戻る）は、
> この値を決めていない。** 変化なしの報では帯を消さないので、報が何秒後に来るかは関係がない。
> 最大値が 10 秒と一致しているのは偶然で、根拠にしていない。

**テストボタン（警報テスト）はこの形を実電文のまま流す。** 第 1 報は `forecastChange` 要素なし・
2 報目で値が立ち・3 報目で 0 に戻る。表示寿命（`useHeldForecastChange`）を実機で確かめるには、
毎報「大きくなった」が立つ形では足りない —— 値が戻ったあとも帯が残ることを見るため、
0 に戻る報まで押し進める（→ [`settings-pwa-spec.md`](settings-pwa-spec.md) §7）。

> **読み上げの安定待ちはこの値へ載せ替えていない。** あそこは実地震で調整した経路で、
> しかも階級インデックス差で測っている。載せ替えるなら実データでの検証を伴う別の作業にする。

### 内陸判定・短縮用震央地名

`LandOrSea`（値域は「内陸」「海域」の 2 つだけ）は震源名の横に添える —— 海域なら津波を
思い浮かべる手がかりになる。仮定震源要素のときは地名自体が震源の推定位置ではないので添えない。
`ReduceName`（「青森県東方沖」に対する「青森東方沖」）は気象庁が用意した短い呼び方。
**主要動の到達予測の行でだけ使う**（2026-10-22 ユーザー承認「2-A 到達予測の行」。
→ `useSWaveCountdown.ts` の `hypocenterNameOf`）。あの行は 1 行で末尾を省略するうえ、同じ行に
「震源から N km」が並ぶので、アプリの中でいちばん幅が足りない。**空なら通常の震央地名へ倒す。**

**ほかの場所では使わない。** カードの見出し・地図の吹き出し・ウィンドウタイトルは通常の震央地名を
出す —— 短縮名は情報を落とすことがあり、幅に余裕のある場所で使うとどこの地震か分かりにくくなる。
置き換えではなく、幅が足りない場所の代替。

**地震情報の電文はこの要素を持たない。** 控え 2,135 日の地震情報 19,345 通で 1 件も無く、
載せているのは緊急地震速報だけ。緊急地震速報の控え（直近 3 日・100 通）では 98 通にあり、
名前が変わる組は「福島県沖」→「福島沖」「熊本県天草・芦北地方」→「熊本県」だった
（後者が「情報を落とすことがある」の実例）。
対になる `ReduceCode`・震央地名のコード（`Area/Code`）も読むが、画面に出すのは名前のほう
（コードの扱いは [`quake-spec.md`](quake-spec.md) §8「電文のコード値は読むが、画面には出さない」）。

**規模の前置きは電文の種別（`jmx_eb:Magnitude@type`）をそのまま出す**（カードの見出しが
「マグニチュード」の欄は語で添える）。規約と実測は [`quake-spec.md`](quake-spec.md) §8
「マグニチュードの種別」が単一情報源。

### 警報の対象地方（`Head/Headline/Information`）

気象庁は緊急地震速報（警報）の対象を**地方予報区**の単位で述べる。見出し文も「石川県で地震　北陸　
甲信　東海　関東で強い揺れ」の形を採る。`warningRegions` として文書順で持ち、読み上げの第 1.5
フェーズ（→ [`audio-tts-spec.md`](audio-tts-spec.md) §6）と EEW カードが使う。カードでは行動指示の
付加文と同じ枠へ入れ、地方名を先に・一段大きく置く（下記「固定付加文」）。

**`Body` には無い。** `Body/Intensity/Forecast` は府県予報区 → 細分区域の 2 階層で、地方の単位を
持たない。**見出しの構造化を読む唯一の箇所**で、他の種別では `Body` の部分集合にしかならないので
読んでいない（→ [`quake-spec.md`](quake-spec.md) §8「見出しの構造化は読まない」）。

> **「細分区域」は電文の呼び名**（`Information type="緊急地震速報（細分区域）"`）。他の仕様書が
> 「一次細分区域」と呼ぶ単位（「石川県能登」など）と同じもの。

**入るのは警報級の報だけ。** DMDATA アーカイブの実電文で、このブロックがあることと警報が出ている
ことが例外なく一致した（警報が出た 10 日ぶんの `eew.forecast` を展開して、警報ありの 240 通すべてが
持ち、警報 0 の 527 通は 1 通も持たない。同じ節の「固定付加文」の 380 通とは母集団が違う ——
あちらは 2026-05-01〜09-11 の全期間）。標本 B（予報 2022-07〜2026-10・警報 69 日のアーカイブ）でも例外なく一致した（通数は記録が無い。→ [`telegram-coverage-audit.md`](telegram-coverage-audit.md) §7「前提を全期間で数えた結果」）。
**DMDSS 版限定** —— P2PQuake・Yahoo はこの要素を配信しないので常に空。

**`Item` を全部たどって文書順で連結する。** `Item` ごとの `LastKind` は「前の報でその地方が何だったか」で、
前の報で警報の対象でなかった地方は「なし」（コード `00`）の `Item` に分かれる。続報で新しく警報対象に
なった地方は 2 つ目の `Item` に入る。

**その分け方は `addedWarningRegions` として別に持ち、カードで新たに加わった地方名にだけ一瞬色を付ける**
（2026-10-22 ユーザー承認「一瞬色を付ける (Recommended)」）。カードに並べる顔ぶれは全地方のまま変わらない。

- **光るとき。** 同じ地震の続報で警報の地方が増えたとき、増えた地方名だけ。他の欄と同じ減衰で、
  地方の数が増えるので「上がった」の色になる
- **光らないとき（2 つ）。** 理由はどちらも「欄の初出は動いたことにしない」（`useFieldFlash`）
  - **その地震の報を初めて見たとき**（起動直後など）
  - **予報級から警報級へ初めて上がった報。** 予報級の間は警報の地方の欄が無い。この報では全地方が
    「なし」側に入る
- **`LastKind` が「なし」でも、いまの種別と同じでもない・読めない `Item`** は、記録を残して
  「続いている」側に扱う（加わった地方が光らないだけで、顔ぶれと読み上げは変わらない）

2026-10-22 に DMDATA アーカイブの控え（2022-07-20〜2026-10-18）で、地方予報区ブロックを持つ 1,364 通を
本物のパーサーへ通して数えた。加わった地方を持つ報は 205 通で、**うち 197 通は全地方が加わった側
（初めて警報になった報）**、残る 8 通は下表の 3 例の 4 回の増加（VXSE44 と VXSE45 で 2 通ずつ）。
読めない `LastKind` は 1 通も無かった。数えたスクリプトはリポジトリに残していない。

**読み上げにはこの区別を使わない** —— 前報からの差分なので、こちらが前報を取りこぼしていれば
一緒に落ちる。何を新しく伝えるかは読み上げ側が「自分が何を声にしたか」から決める。

値域は 14 種（北海道・東北・関東・伊豆諸島・小笠原・北陸・甲信・東海・近畿・中国・四国・九州・
奄美・沖縄）。コードは 9910〜9960 に体系的に収まり、年 1 回の全国一斉訓練報が 14 種すべてを
列挙する。

**続報で増える。** 4 年分（`eew.warning` の全 68 日）で 3 例。**この表がこの 3 例の単一情報源**で、
他の仕様書からは参照するだけにする。

| 日付・地震 | 遷移 | 前の報からの間隔 |
|---|---|---|
| 2024-01-01 能登半島地震（本震） | 北陸 → ＋甲信・東海・関東 → ＋東北・近畿 | +35 秒 / +59 秒（地震発現から） |
| 2024-06-03 石川県能登 | 北陸・甲信・東海・関東 → ＋東北・近畿 | **+0.45 秒** |
| 2025-12-08 青森東方沖 | 東北・北海道 → ＋関東 | +110 秒 |

**減ったときは読み上げない**（画面は最新の顔ぶれへ差し替わる）。4 年分の実配信で縮小の例は
1 件も無く、気象庁は緊急地震速報の警報を地方単位で取り下げない運用と見られる。**観測していない
形に対して「一部の地方が対象から外れました」と言う文を先回りで作らない** —— 実際に起きたときに
どう伝えるべきかは、そのときの電文を見てから決める。

> **予報を受けている人は VXSE43（緊急地震速報（警報））を購読しないが、失うものは無い**（警報だけの人は VXSE43 からこのブロックを読む。→ [`data-sources-spec.md`](data-sources-spec.md) §2「一部の区分だけ受けられる人」）。 同じ見出しブロックが
> VXSE45 の警報報にも入る。4 年分 99 通の VXSE43 と対応する VXSE45 を突き合わせたところ、
> **VXSE43 にあって VXSE45 に無い要素は 1 つも無く**、警報区域・見出し文・`Information` の中身は
> `Item` の分かれ方まで一致した。到着も VXSE45 が先（実測で 8〜148ms）。
> → [`data-sources-spec.md`](data-sources-spec.md) §2「EEW は VXSE45 だけを受ける」

### 固定付加文（`Comments/WarningComment/Text`）

避難行動の呼びかけなどの定型文。`warningComment` として持ち、
**画面にだけ出す**。

**入るのは警報級の報だけ。** 購読分類 `eew.forecast` のアーカイブ全 7,995 通
（2026-05-01〜09-11）を数えると、付加文があったのは警報級の 380 通（VXSE44・VXSE45 各 190）
だけで、**予報級 7,615 通は 1 件も無い**（うち 3,197 通は毎正時の配信試験 VXSE42）。文言も
コード `0201`「強い揺れに警戒してください。」の 1 種類だけ。購読対象外の `eew.warning`
（VXSE43）も同じ期間で 23 通すべてに入っていたが、こちらはアプリへ届かない（→
[`data-sources-spec.md`](data-sources-spec.md) §2）ので上の数には含めていない
（VXSE43 は警報を出した日にしか生成されず、この 133 日のうちアーカイブがあったのは 16 日分）。

**置き場所は予想値のバナー群（予想最大震度・予想長周期地震動）の直後。** 電文が言う唯一の
行動指示なので、カードの末尾に置くと対象地域や到達の一覧の下に埋もれる。震度と長周期の
バナーは対になっているため、その間には割り込ませない。大きさは本文と同じかそれ以上にし、
**色は区分に追随させる**（上の実測から予報級のカードでは出ないが、予報級に別の付加文が
入ったときに警戒色で断定しないため）。

**同じ枠へ対象地方（上記「警報の対象地方」）を入れ、地方を先に・一段大きく置く。** 気象庁も
見出し文で「石川県で地震　北陸　甲信　東海　関東で強い揺れ」と一体で述べており、利用者が最初に
知りたいのは「自分が対象か」。付加文だけを大きく出して対象を小さく添えると、**いちばん先に読む
べきものがいちばん読みにくい**。地方を大きくするのは、行動指示が全報で同じ 1 文（コード 0201）
なのに対し、地方は報ごとに変わるため。

**どちらか片方しか無くても枠は出す。** 実配信では両方そろう（警報級 380 通すべてが付加文を持ち、
地方予報区ブロックも警報級にだけ入る）が、片方を条件にすると欠けたときにもう片方ごと消える。

**コードはあるのに原文が無い電文は記録する**（`readCommentText`。→ [`quake-spec.md`](quake-spec.md)
§8「固定付加文（その他）」）。原文を画面に出す経路で、ここだけ検査を通していなかった。

**読み上げには載せない。** EEW の読み上げは秒を争うため、定型文を挟むと肝心の震度・地域が
遅れる（読み上げの優先順位は [`audio-tts-spec.md`](audio-tts-spec.md) §6）。**気象庁の文を読む設定でも読まない** ——
付加文はコード 0201「強い揺れに警戒してください。」の 1 種類で、読み上げは同じ内容を対象地方と一緒に既に
言っている（「〇〇では強い揺れに警戒してください。」。2026-10-21 ユーザー承認「読まないまま記録する (Recommended)」）。取消電文では出さない
—— そのときの本文は付加文ではなく取消の理由なので、`Comments` の下に限って拾う。

**取消かどうかは `cancelledAt` で見る。** `cancelled` は受け取った電文そのものが取消報かを
表すフラグで、**画面が持つ EEW には伝わらない** —— 状態更新は取消を
`{ ...表示中の EEW, cancelledAt }` の形で当てるため、`cancelled` は取消前の値のまま残る
（上の「帯を出し続ける長さ」と同じ罠）。`!eew.cancelled` で判定していた版があり、
常に真で素通りしていた（実際に隠していたのは取消オーバーレイ）。

### 地震の時刻は発生時刻（`Earthquake/OriginTime`）を出す

画面の日時（`RealtimeTab`。**秒まで出す**）と共有カードの「◯◯ 発生」は**地震発生時刻**から
出している。電文は地震発現時刻（`ArrivalTime`。観測点が地震を検知した時刻）も持つ。

- **カードの出し方。** 発生時刻の下へ発現時刻を並べる。見出しはどちらも気象庁の名前のまま
  「地震発生時刻 2026/10/22 12:34:56」「地震発現時刻 2026/10/22 12:34:57」で、末尾に「ごろ」は
  付けない（2026-10-22 ユーザー承認「2 行とも名前を付ける」）。2 つは数秒しか違わないことが多いので、
  発現時刻の行にだけホバーで「観測点が地震を検知した時刻」と添える（2026-10-22 ユーザー承認
  「ホバーで説明を出す」）
- **standard 版の出どころ。** Yahoo hypoInfo は発現時刻を配信しない（空文字）ので、その報しか届いて
  いない間は発現時刻の行が出ず、P2PQuake（code=556。`services/p2pquake.ts` が `earthquake.arrivalTime` を
  読む）の報が届くと出る。**Yahoo の続報は P2PQuake の報が持ってきた発現時刻を保つ**（`mergeEewReport`）ので、
  そのときの 2 行は発生時刻が Yahoo・発現時刻が P2PQuake と出どころが分かれる
- **計算は発現時刻を読まない。** 経過で決まる値はすべて発生時刻が起点（下記「発生時刻を採る根拠」）
- **読み上げは地震の時刻を語らない** —— 緊急地震速報で時刻を読むのは誤報取消の
  「◯時◯分に発表された」だけで、あれは電文の発表時刻

**地震情報・津波・長周期は発現時刻のほうへ揃えてある**（→ [`tsunami-spec.md`](tsunami-spec.md) §4）。
**緊急地震速報だけ発生時刻なのは、気象庁が種別ごとに違う時刻を「地震の時刻」として示しているから。**
揃えるのは値ではなく、**その種別で気象庁が地震の時刻として示すものに従う**という規則。
規則を一貫して当てると、地震情報は発現時刻・緊急地震速報は発生時刻になる。**2 種別で値が違うのは
規則の破れではなく、規則どおりの結果。**

#### 実測では全報がずれていた

`eew.forecast` / `eew.warning` の 1 日分（2024-11-26）。**数えたのは VXSE45 だけ** —— アプリが
パーサーへ渡すのはこの種別で（§3 冒頭の表・`DISPATCHED_WITHOUT_PARSER`）、同じ内容が VXSE44
としても届く。この日は**93 組すべてが対になり、2 つの時刻は 93/93 で完全に一致**していたので、
両方を数えると母数がちょうど倍になる。**通常報は 93 通**で、その内訳は**地震の時刻を持つ 91 通**と
**取消報 2 通**（`Earthquake` を持たない）。2 つの時刻を比べる行は 91 通、電文の文を数える行は
93 通が母数になる。

| 測ったこと | 結果 |
|---|---|
| 両者が一致した報 | **0 通 / 91** |
| ずれの幅 | **1〜18 秒**（中央値 6 秒。10 秒以上が 12 通） |
| 分の表示が変わる報 | 4 通 / 91（4.4%）。**地震単位では 1 件 / 15** |
| 同じ地震での変動 | **`ArrivalTime` は 15 地震すべてで動かない。`OriginTime` は 11 地震で動く**（石川県西方沖の 27 報では 4 通り） |
| `EventID` と一致する時刻 | **`ArrivalTime` が 91/91。`OriginTime` は 0/91** |
| 気象庁の文へ時刻を書いた報 | **0 通 / 93**（下記） |

**時刻を書いた報の数え方。** `<Text>` の全出現を走査した（走査の落とし穴は →
[`telegram-coverage-audit.md`](telegram-coverage-audit.md) §2「測るときの落とし穴」）。
出どころは見出し文（`Head/Headline`）26 件・
固定付加文（`Comments/WarningComment`）26 件・取消の本文（`Body/Text`）2 件の 3 つだけ。
**文言は見出し文が 2 種類・固定付加文と取消の本文が各 1 種類**で、時・分・秒の表現を含むものは
1 つも無かった（固定付加文が 1 種類なのは §3「固定付加文」の実測と同じ。あちらは 133 日・
警報級 380 通の母集団）。

他の種別はどちらの時刻も**分値まで**で、ずれるのは「発生から観測点が検知するまでが分の境界を
またぐとき」に限られる。緊急地震速報は**両方とも秒値まで有効**（解説資料 Ⅱ.21 1-1 / 1-3）で、
**画面も秒まで出している**（2026-10-22 までは発生時刻だけを「ごろ」付きで出していた）。つまり**2 つの時刻の食い違いは、分単位で
出していたなら 4.4%（上表の 4 通 / 91）でしか見えないが、秒まで出しているぶん全報で見える**。

**ずれが 0 になりにくいのは、発現時刻が発生時刻に走時を足したものだから**（走時は非負）。
ただし**震源が観測点のすぐ近くなら走時が 1 秒未満へ丸まって一致しうる** —— 実測の下限は 1 秒で、
それが 4 通ある。**「全報がずれた」は 1 日分・91 通の実測で、恒常性の保証ではない。**
範囲を広げるなら手順は
[`telegram-coverage-audit.md`](telegram-coverage-audit.md) §2「地震の時刻のずれを測る」
（分類に `eew.forecast,eew.warning` を渡す。**VXSE44 を混ぜないこと**）。

#### 発生時刻を採る根拠

5 つ。**最初の 1 つが決め手**（値を替えると実際に壊れる）で、残りは**選択の妥当性を支える傍証**。
数値は上表が単一情報源なので、ここでは再掲しない。

- **`originTime` は表示専用ではない。** 下記「`originTime` を読む場所」のとおり、**発生時刻からの
  経過で決まる値**（予報円の半径・区域への S 波到達時刻・自動解除・別地点発報の距離閾値）が
  この値を起点にしている。**ここは発生時刻でなければならない** —— 替えれば予報円が 1〜18 秒ぶん
  小さくなる（S 波は 3.5〜4.5km/s の 2 層モデルなので概ね 4〜80km）。**画面の「地震の時刻」を
  発現時刻だけにすると、カードが示す時刻と円の起点が食い違う**（発現時刻は見出しを付けて別の行に出す）
- **地震情報で決め手にした証拠が、緊急地震速報には無い。** あちらを発現時刻へ揃えた根拠は
  「気象庁自身が本文へ書くのは発現時刻」（→ [`tsunami-spec.md`](tsunami-spec.md) §4）。
  緊急地震速報の本文は定型文で、時刻を 1 通も書かない。**同じ物差しが当てられない**
- **気象庁自身の画面も発生時刻を「地震の時刻」の位置に置いている。** 緊急地震速報（警報）
  発表状況ページ（`pub_hist`。ローカル履歴アーカイブが読んでいる。→
  [`settings-pwa-spec.md`](settings-pwa-spec.md) §6）は、震源要素一覧の**先頭列を発生時刻**に
  置き、発現時刻に相当するものは**報の並びの中の 1 行**として置く。その行のラベルが
  **「地震波検知時刻」**であることは原文がリポジトリに残っている
  （`scripts/historicalEewParser.ts` の `ParsedEewReport.reportNum` の説明と、
  `scripts/historicalEewParser.test.ts` のフィクスチャのリテラル）。**一方、震源要素一覧の
  列見出しの原文は残っていない** —— あの表のヘッダ行は `slice(1)` で捨てるため、
  先頭列が発生時刻だと言える根拠は変数名（`originTimeIso`）とフィクスチャの時刻の順序
  （列 0 が検知時刻より早い）に留まる
- **`ArrivalTime` は識別子の素材で、地震の性質ではない。** `EventID` が全通これと一致し、
  地震ごとに 1 通も動かない。「どこかの観測点が最初に検知した時刻」は観測網の配置で決まる値。
  **ただし気象庁が `EventID` をこの値から作ると明言した資料は見ていない** —— 一致の強さから
  導いた推論
- **続報で震源時が更新されたことが画面から読める。** 発現時刻へ揃えるとこれが消える

#### `originTime` を読む場所

**この一覧が単一情報源**（`CLAUDE.md` の該当行・`RealtimeTab` のコメント・
`EEWAlert.earthquake` の doc comment は要約だけを持ち、ここを指している）。

**`grep` だけでは数え直せない。** 省略可能な形で読む場所があり（`ev.earthquake?.originTime`）、
この値を別のオブジェクトへ写して運ぶ経路が将来また現れうる（区域塗りが震源を持っていた頃は
そうしていた。いまは持たない——下記「特定地点への到達予想は気象庁の発表値を伝える」）。
`earthquake.originTime` の字面を探すだけでは下の表の行が揃わない。

| 種類 | 読む場所 | 何に使うか |
|---|---|---|
| 発生時刻からの経過で決まる値 | `usePsWaveCalc` | P 波・S 波予報円の半径（`now - originTime`） |
| 発生時刻からの経過で決まる値 | `utils/eew.ts` の `calcEEWCancelTime` | 自動解除の時刻（規模・深さから決めた猶予秒数を足す）。**発生時刻が無い・読めなければ地震発現時刻を起点にする**（§7） |
| 発生時刻からの経過で決まる値 | `useKyoshinAlerts` | 別地点発報の距離閾値（経過時間から決める） |
| どれを「最新」とみなすか | `CameraFollowsGL` | 複数発報しているときのカメラ追従の対象。`compareEewNewestFirst` で並べる（下記） |
| どれを「最新」とみなすか | `RealtimeTab` | カードの並び順。同上 |
| 取得候補の絞り込み | `dmdataReplayLive` | リプレイで**窓に一報も掛からない地震を落とす**（「報は震源時刻より前には出ない」という意味に依拠する。**`ev.earthquake?.originTime` と書くので字面検索に掛からない**） |
| 表示 | `RealtimeTab` | カードの「地震発生時刻」の行（秒まで。発現時刻は別の行で、計算には使わない） |
| 表示 | `shareCardContent` | 共有カードの「◯◯ 発生」 |

**並べ替えは `utils/eew.ts` の `compareEewNewestFirst`（中で `eewSortTimeMs`）を通す。** 発生時刻が無い・読めない報は
地震発現時刻へ落とす（「非常に強い揺れを検知」の報は発生時刻を持たない。§5）。時刻はエポックミリ秒へ直して
比べる —— 経路ごとに書式が違い（`+09:00` と `Z`）、文字列のまま比べると前後が入れ替わる。
発生時刻の無い報は、表の残りの行ではこう扱われる: カードの日時と共有カードの「発生」は出さない、
揺れ検知の距離閾値と予報円は仮の震源として対象から外す（§5）、リプレイの絞り込みは時刻が読めない地震を落とさない側へ倒す。

## 4. レベル判定（`computeSingleEEWLevel`）

`src/utils/eew.ts` の `computeSingleEEWLevel(eew)` が単一情報源。判定は 3 段階の直列条件で行う:

1. `severity !== 'Warning'` → `0`（予報）で早期 return（P2PQuake の予報電文・Yahoo severity が Forecast のケース）
2. 特別警報判定（下記 OR 条件のいずれか）→ `2`
3. 上記に該当しない（severity === 'Warning' かつ特別警報の条件を満たさない）→ `1`（警報）

**特別警報の判定条件**（OR）:
- `eewMaxScale(eew) >= 55`（震度 6 弱以上。震度が取れないときは `0` になるため自然に対象外になる。
  値の決まり方は下記のフォールバック規則を参照）
- `eewMaxLpgmClass(eew) >= 4`（長周期地震動階級 4 以上）

気象庁の実基準に合わせた OR 条件。長周期地震動階級は DMDATA 電文（VXSE45）にのみ載るため、
standard 版では `eewMaxLpgmClass` が常に 0 になり震度のみでレベルが決まる。

> **「特別警報」は表示に使い、読み上げには使わない。** 位置づけ自体は公式で、気象庁は震度 6 弱以上
> または長周期地震動階級 4 以上を予想した緊急地震速報（警報）を特別警報としている。ただし
> 「これらの特別警報は名称に『特別警報』は用いず、従来どおりの名称で発表します」とも明示している
> （[津波・火山・地震（地震動）に関する特別警報の発表基準](https://www.jma.go.jp/jma/kishou/know/tokubetsu-keiho/kizyun-jikazan.html)）。
> そのためレベル 2 は色分け・ブラウザ通知のタイトル・通知音の選択には使うが、**音声では「警報」と読む**
> （[audio-tts-spec.md](audio-tts-spec.md) §6）。重さは値そのもの（「予想最大震度6弱。」）で伝える。
> **声・地図の震源の吹き出し・ウィンドウタイトル・電文ログでも特別警報と警報を区別しない**
> （§3「電文の名称と表示・読み上げ」の表。2026-10-21 ユーザー承認「今のまま記録する (Recommended)」）。
> 文言で区別するのは EEW カードの見出しとブラウザ通知の見出しで、共有カードの見出しも区分の名前
> （`eewKindLabel`）を使うので区別しない。

### 特別警報の下げ止まり（`computeDisplayEEWLevel`）

**表示（ウィンドウタイトル・EEW カードの見出し・ブラウザ通知の見出し・共有カード）は `computeSingleEEWLevel` の生値ではなく
`computeDisplayEEWLevel(eew)` を使う。** 文言の上で特別警報の表示が維持されるのは EEW カードとブラウザ通知の見出しで、ウィンドウタイトルと
共有カードの見出しは下の段落のとおり文言が変わらない。ブラウザ通知は、受信処理へ届く報が入口で統合済みで印を運ぶので
（`useEarthquakes.ts` の `mergeEewReport`）、その報をそのまま渡す。**下げ止まりが効くのは見出しの文言だけ** —— 通知を
出し直すかどうか（区分の格上げ・予想の引き上げ）は生の区分と予想で決める。一度でも
特別警報相当（震度6弱以上/長周期地震動階級4以上）に達した地震は、続報で震度が下がっても
特別警報の表示を維持する。判定は `EEWAlert.everSpecialWarning` フラグに集約する
（`useEarthquakes.ts` のマージ処理（`mergeEewReport`）・状態更新・起動時復元・リプレイの初期状態復元の
4 経路すべてでこのフラグを引き継ぐ・書き足す）。

**ウィンドウタイトルと共有カードの見出しは、下げ止まりが効いても文言が変わらない。** どちらも
`computeDisplayEEWLevel` を通るが、文言は区分の名前（`eewKindLabel`）で出し、これがレベル 1 と 2 に同じ
「緊急地震速報」を返すため、特別警報と警報の差がもともと出ない（上の注記。2026-10-21 ユーザー承認
「今のまま記録する (Recommended)」）。共有カードでは、複数発表中にどの速報を見出しに選ぶか（`pickMostSevereEew`）にこの値が効く。

**これは気象庁の公式運用ではなく、アプリ独自の判断。** 気象庁は「震度予想が下がっても
（誤報でない限り）警報を取り消さない」と明言しているが（[緊急地震速報（警報）及び（予報）
について](https://www.jma.go.jp/jma/kishou/know/jishin/eew/shikumi/shousai.html)）、これは
**警報という発表行為自体**の話であって、アプリが独自に線引きした特別警報/警報の区分を
「一度上がったら下げない」運用は気象庁側に見当たらない。予報→警報（レベル0→1）の格上げには
この下げ止まりを適用しない——気象庁の運用上、警報級の電文が予報級へ格下げされる続報は
実質的に存在しないため、そちらは生値のままでよい。

**起動時復元（`fetchDmdataActiveEews`）は、本文を読むのが最新報 1 通だけなので、途中の報の
予想は詳細の一覧から読む**（`gdReportsEverSpecialWarning`。§2「起動時に、発表中のものを復元する」）。
全報の電文が揃うのはライブ受信の継続中と、窓内の全電文を持つリプレイの初期状態復元
（`filterPreWindowEvents`）で、この 2 つは `computeEverSpecialWarningEventIds` が共通の畳み込みを担う。
判定の閾値（震度6弱以上/長周期地震動階級4以上）は 3 経路とも `isSpecialWarningForecast` 1 つを通す。

**リプレイ復元は `activeEEWLevelsRef` にも及ぶこと。** `useLiveEventHandler.ts` の
`restorePreWindowTracking` は、ウィンドウタイトルの駆動源を兼ねる `activeEEWLevelsRef` を
`computeSingleEEWLevel`（生値）ではなく `computeDisplayEEWLevel`（表示用）で初期化する。
ここだけ生値のままだと、窓の手前で特別警報だった地震が続報で生の震度が再び上がったとき、
「新規に特別警報へ格上げされた」と誤認して格上げ音を鳴らし直す。読み上げの既読管理
（`spokenEEWLevelsRef` 等）は特別警報の呼称を使わない設計なので、そちらは生値のまま据え置く。

**EEW カードの最大震度バナー（本文）は下げ止まりを反映しない。** カードの見出しは
`computeDisplayEEWLevel` で特別警報の表示を維持するが、予想最大震度の数値・配色は
`eewMaxScaleInfo`/`eewMaxLpgmClassInfo` の**現在値**をそのまま出す——値を誤魔化して固定すると、
実際に下がった震度予想が利用者に伝わらなくなる。**見出しと本文の食い違い（見出しは特別警報の
ままなのに本文の数値は下がっている）を説明する注記は画面に出さない**——アプリ独自の下げ止まりが
生む見た目の副作用として、そのまま許容する。

### 予想最大震度は電文全体の値

`eewMaxScale`・`eewMaxLpgmClass` は**電文全体の `forecastMaxScale` / `forecastMaxLpgmClass`
（`Body/Intensity/Forecast` の `ForecastInt` / `ForecastLgInt`）を先に採り**、それが無いとき
（震度 0・未設定）だけ地域別 `areas[].scaleTo` / `areas[].lgIntTo` の最大を代わりに使う
（大きい方を取るのではない。2026-10-22 ユーザー承認「電文全体の値を使う (Recommended)」）。
気象庁が「最大予測震度」として発表するのは電文全体の値で、区域の最大はそこから導いたものにすぎない。
**同じ階級の区域が「以上」なら、それは残す**（強い側の表現を落とさない）。
電文全体の値は幅（`From`〜`To`）で届くが、**持つのは上限だけ**で下限は出さない（`parseForecastInt`。
`To` が空なら `From`、上限を定めない `over` なら下限を採って「以上」を付ける。2026-10-21 ユーザー承認「今のまま記録する (Recommended)」）。

**画面・音・読み上げは変わらない。** 2026-10-21 に DMDATA アーカイブの控え（`eew.forecast` 1,552 日・
`eew.warning` 69 日）にある通常報 45,079 通（VXSE44 23,578・VXSE45 21,404・VXSE43 97。取消 54 通と訓練報を
除く）を本物のパーサーへ通し、電文全体の値と区域の最大を比べた。**震度・長周期地震動階級とも、「以上」の
有無まで含めて食い違いは 0 件**（区域を持つ報 6,774 通・長周期階級を持つ報 1,185 通）。集計の
スクリプトはリポジトリに残っていない（下記「区域に載る予測震度に下限は無い」の 765 通の突き合わせは
手順つきで、そちらも 0 件）。食い違う報が届いたら、パーサーが記録を残す（電文全体の値のほうが低いとき）。

**DMDATA 以外の報（standard 版・履歴アーカイブ・保存データ・実地震テストシナリオ）は区域を先に見る。**
例外は `maxScaleFromForecast` が立ったときだけ —— standard 版で、区域を運ばない Yahoo hypoInfo の続報が
電文全体の値（`calcintensity`）を新しく運ぶと立ち、区域（前の P2PQuake の報）より新しいとして
電文全体の値を採る（`mergeEewReport`）。テストボタンの報は DMDSS 版では `origin` が `dmdata` なので、
電文全体の値を先に採る。
長周期地震動階級は DMDATA しか運ばないので、経路で分けない。

震度未確定の `-1`（`IntensityScale` のセンチネル）は区域の最大の初期値 0 に丸められる。
**`condition === '仮定震源要素'` を理由に値を捨てない。** 気象庁が最大予測震度を発表しないのは
「観測点 1 点による震度予測」と「深さ 150km 超（PLUM 法による 2 点以上の震度予測がある場合を除く）」の
2 つで、該当すれば電文にそもそも値が入らない。受信側で潰す必要はなく、潰すと発表済みの値を落とす
（詳細は §5）。

> **区域が空でも電文全体の値が載ることがある。** 区域の列挙が始まるのは電文全体の予想が
> 震度 4 以上になってからで、震度 3 以下の予想は区域が空のまま `ForecastInt` だけが載る
> （境目の実測は下記「区域に載る予測震度に下限は無い」）。かつてはそこを `condition` で
> 潰しており、実データで取りこぼしが出ていた（件数は §5）。

`eewMaxScale` は `scaleTo` が震度階級（`IntensityScale`）の値でない地域を最大値の計算から除外する。
そのため P2PQuake の `scaleTo = 99`（「〜程度以上」）は、この判定に届く前に
`convertEvent` が同じ地域の `scaleFrom` へ置き換えている（[`data-sources-spec.md`](data-sources-spec.md) §3）。
置き換えないと「震度 7 程度以上」という最も強い予想が丸ごと無視され、警報止まりになる。

### 上限を定めない予想の扱い（震度・長周期地震動階級）

予想震度は上限が定まらないことがある（DMDATA は `to: "over"`・P2PQuake は `scaleTo: 99`）。
受け口で下限側の階級へ寄せ、上限が定まらないことをフラグで持ち越す。**電文上の表れと寄せ方は
[`data-sources-spec.md`](data-sources-spec.md) §8 が単一情報源。**
ここではその値を EEW 側がどう使うかだけを書く。

**長周期地震動階級も同じ形で来る。** 電文解説資料（Ⅱ.21 2-1-3-2）の値域は
`"0"/"1"/"2"/"3"/"4"/"over"/"不明"` で、事例も「最大予測長周期地震動階級が階級 3 程度以上の
場合」として `<From>3</From><To>over</To>` を示す。**震度側だけ対応して長周期側を忘れると、
`parseInt("over")` が `NaN` になって予測が丸ごと消える**（実際にそうなっていた）。
読み取りは `parseForecastInt`（震度）と `parseForecastLgInt`（長周期）に分けてある。

**長周期の `"0"`（階級1未満の予測）は「予測なし」と分けて持つ。** 階級の欄（`lgIntTo`・`forecastMaxLpgmClass`）は
1〜4 だけを持つので `undefined` のまま、`lgIntBelowClass1`・`forecastMaxLpgmBelowClass1` が立つ。画面と読み上げは
この印を読まない（電文に無いのと同じに見せる。2026-10-19 ユーザー承認「0 を持ち、表示は今のまま (推奨)」
「別の欄で持つ (推奨)」）。手元の控え（DMDATA アーカイブの緊急地震速報 3 日分・62 地震・660 通。2026-10-19 に数えた）では、最大の階級が 0 の報が 256 通あった。

**最大予想震度の `"0"`（震度0）も「予想なし」と分けて持つ。** 階級の欄（`forecastMaxScale`）は震度1〜7 だけを
持つので空のまま、`forecastMaxScaleBelow1` が立つ（`From` が空か `"0"` で、採る値が `"0"` のときだけ）。
変わったのは待ち方だけ。以前は値の付くのを 3 秒待ってから「予想震度なし」と出していたが、気象庁は値を
出し終えているので待たない（`eewNoForecastReason` が `belowScale1` を返す）。出す文言は以前と同じ、理由を
添えない「予想震度なし」（2026-10-20 ユーザー承認「案 1 で進めて」。案 1 は「0 を別の印で持ち、待たずに確定する。
見え方と読み上げの文言は今のまま」）。長周期の 0 と違って印を「読む」のは、震度の欄が空になると何かを出す
しかなく、その経路（予想震度なし）で待つかどうかを決めるのに印が要るため。

手元に控えた DMDATA のアーカイブ（緊急地震速報（予報）の 1,363 日と警報の 69 日。2026-10-20 に数えた）では、
最大予想震度 0 が 24 通・13 地震あった。比べると、1 は 1,210 通・471 地震で、こちらは従来どおり震度1 として読む。
採る値が `"0"`・`"over"`・`"不明"` のどれでもなく読めないときは、読めなかった値を記録に残す（`To` が `"over"` の報の下限の読み取りは、上の「上限を定めない予想」の扱いに従い記録の対象にしていない）。

- **判定は下限で行う。** `computeSingleEEWLevel`（特別警報）・区域塗りの色・地図のカメラ追従は
  すべて階級値だけを見る。フラグを判定に混ぜない
- **語は「程度以上」。気象庁の表現に合わせる。** 電文解説資料は `To` の値域を
  「over:～程度以上」と定め、事例も「震度 5 弱程度以上」「階級 3 程度以上」と書いている。
  付け方は `getIntensityLabelWithApproxAbove()`（震度）と
  `getLpgmClassLabelWithApproxAbove()`（長周期）に集約する
- **「以上」（`getIntensityLabelWithOrAbove`）と混同しない。** そちらは「5弱以上・未入電」専用で、
  電文の値そのものが `震度５弱以上未入電`。**気象庁が「程度」を付けていない**ので付けない。
  以前は 1 つの関数を両方に使い回しており、片方に揃えるともう片方が気象庁の表記から外れる
  状態だった（→ [`quake-spec.md`](quake-spec.md) §4「震度5弱以上未入電」）
- 集約は `src/utils/eew.ts` の `eewMaxScaleInfo()` が `{ scale, orAbove }`、
  `eewMaxLpgmClassInfo()` が `{ cls, over }` で返す。`eewMaxScale()` / `eewMaxLpgmClass()` は
  値だけを返す薄いラッパ
  （**カードのバナーだけは例外**で、語を本体より小さく添えるため自前で組む）
- **比較に「程度以上」を含める。震度と長周期で対称にすること。** 上限が定まらなくなる向き
  （「階級3」→「階級3程度以上」）は**もっと強いかもしれないという安全側の変化**なので、
  数値だけで比べると据え置きと誤判定して**無音で消える**。門は 2 つあり、**両方**に要る。
  - 安定待ちの比較（`EEWLpgmStabilityCycle` が `{ cls, over }` を持つ）
  - 既読との比較（`isForecastLpgmHigher`。震度側の `isForecastScaleHigher` と同じ形）
- **語は確定値と一緒に持ち回る。** 現在の報から引き直さない —— 確定値は安定待ちを経ているため
  現在の報と食い違いうる。引き直すと別の値に語を貼り付ける（`eewIntensityText` の `lpgmOver` 引数）
- 語を出す箇所: EEW カードのバナー・ウィンドウタイトル・ブラウザ通知・読み上げ・区域塗りの
  ポップアップ（ホバー時のバッジを含む）・**震源×印のポップアップ**。
  **新たに予想震度を出す箇所を作ったらここに追記する**
- **読み上げの「上がったか」の比較にも入れる。** 階級値だけで比べると、同じ階級のまま上限が
  定まらなくなった変化（「震度4」→「震度4以上」）を据え置きと見て黙ってしまう。判定は
  `src/utils/eew.ts` の `isForecastScaleHigher()` に集約する
  （[`audio-tts-spec.md`](audio-tts-spec.md) §6）
- 「以上」の集約規則: 最大の階級を与えた区域を基準にする。同じ階級の区域が複数あって片方だけが
  「以上」なら「以上」を採る（強い側の表現を残す）。最大でない区域の「以上」は拾わない

### 区域の種別コード（`areas[].kindCode`）

電文の区域が持つ種別。気象庁「地震火山関連コード表」の表 12（緊急地震速報種別）の値をそのまま使う
（DMDATA の `regions[].kind.code`）。**レベル判定には使わない**（`computeSingleEEWLevel` は
`severity` と予想震度・長周期階級だけを見る）。区域の話なのでこの節に置くが、判定には関与しない。
使うのは「警報域か予報域か」の表示の出し分け。

| コード | 種別 | 主要動 |
|---|---|---|
| `00` / `01` / `09` | 緊急地震速報（**予報**） | 未到達と予測 / 既に到達と予測 / 到達予想なし（PLUM 法。→ §5） |
| `10` / `11` / `19` | 緊急地震速報（**警報**） | 同順 |

- 警報域の判定は `10` / `11` / `19` の 3 値。**判定は `isEewWarningKindCode` の 1 か所に置く**
  （`src/utils/eewKind.ts`）。使う側は 3 つある —— 電文が警報級かどうか（`severity`）、
  `RealtimeTab` の「警報:」「予報:」欄の振り分け、区域塗りの濃さ（`EewRegionFillGL` が
  警報域を `fillOpacity` 0.55・予報域を 0.3 で塗る）。**同じ 3 値を書き分けると、
  片方だけ直したときに静かにずれる**
- **名前を読めない区域も、種別は先に見る**（`dmdataParser.ts` の `parseEEWFromXml`）。名前が空の区域は画面にも地図にも
  出せないので区域の一覧からは外すが、警報級かどうか（`severity`）の判定には数える。種別を見る前に捨てると、名前を
  読めなかった区域が唯一の警報域のとき、警報の電文が予報として扱われる。外した件数は 1 通ごとに 1 行の警告に残す
  （接頭辞を除いて `緊急地震速報の予想区域の名前を読めません（N 件を無視します・うち警報級 M 件）: EventID=… 第N報`。
  警報級が無ければ「うち警報級」は付かない）。警報級を外した電文は、警報なのに「警報:」欄にその区域が出ない
- **判定に使うのはコードで、名前（`Kind/Name`）ではない。** どちらも同じ事実を表すが、名前は
  表記が変われば一致しなくなる。名前を見るのは、**コード表に無い値が来たとき**だけ —— 警報を
  取りこぼさないよう安全側へ倒し、読めなかったコードを記録に残す
- 警報が発表されるのは予想震度 5 弱以上の区域。震度 4 以下の区域は同じ電文の中でも予報域になる
- `kindCode` が空の電文もある（`RealtimeTab` は全区域が空なら「警報/予報」に分けず「対象:」表示へ落ちる）
- **区域に載る予測震度に下限は無い。** **区域の列挙が始まるかどうかは電文全体の値が決め、
  始まったあとは弱い区域も並ぶ**（次項）。

  数えた範囲は 2026-01-02〜2026-09-11 の 253 日。取得元は DMDATA `/v2/archive` の
  `classification=eew.forecast` で、日ごとの目録（`telegrams.json`）から `head.type` が `VXSE45`・
  `format` が `xml`・`head.test` が立っていないものを採った。**VXSE45 4,651 通のうち区域を持つのは
  765 通、区域は 6,268 件**。

  | 区域の最大予測震度（`ForecastInt/To`） | 件数 |
  |---|---|
  | 震度 2 | 88 |
  | 震度 3 | 653 |
  | 震度 4 | 4,280 |
  | 震度 5 弱以上・`over` | 1,247 |

  長周期地震動階級（`ForecastLgInt/To`）も、**階級 0 が 3,103 件**と区域のおよそ半数を占める。
  決め手は組み合わせのほうで、**震度 4 未満の区域 741 件は、すべて長周期階級も 3 未満**
  だった。条件の片方が効いていたのではなく、条件そのものが成り立っていない。予測震度の下限
  （`ForecastInt/From`）が震度 1 の区域も 12 件ある。

  **区域の最大は、区域を持つ 765 通すべてで電文全体の値と一致した**（低い側・高い側とも 0 件）。
  電文全体の値を先に採る順序（上記「予想最大震度は電文全体の値」）に替えても、この範囲では値が変わらない。

  **警報の区域と弱い区域は同じ電文に同居する。** 警報の区域（種別コード 10 / 11 / 19）を含む
  308 通のうち 132 通が震度 4 未満の区域も持っていた。

- **区域の列挙が始まる境目は、電文全体の予測震度の下限が震度 4 以上かどうか。** 同じ 253 日で、
  区域を持たない 3,772 通は全体の `ForecastInt/From` が震度 1〜3、区域を持つ 765 通は震度 4 以上で、
  例外 1 通を除いてきれいに分かれる。
  - **残る 114 通は `Intensity` 要素そのものを持たない**（4,651 = 765 + 3,772 + 114）。深さ 150km 超が
    75 通、単独点で決めた報（`Epicenter@rank` が 1。→ §3）が 38 通で、**どちらも気象庁が最大予測
    震度を発表しない条件**（上記）に当たる。残る 1 通は取消電文だった。両方に当たる報は無く、
    深さ 150km 超の 75 通は全件 `rank` 4（IPF 法 5 点以上）で、震源そのものは精度よく決まっている
    - **この分類に `NumberOfMagnitudeCalculation`（Ｍ計算に使った観測点数）を使わないこと。**
      `rank` 1 の報では確かに 1 以下になるが、`rank` が 1 でない 4,566 通でも 54% が 1 以下で、
      単独点かどうかを見分けられない
  - **長周期地震動階級が単独で区域を生んだ例は 1 通も観測できていない。** 区域を持たない電文の
    全体階級は、要素を欠く 21 通を除いてすべて階級 0 だった。無いと言えるだけの標本ではなく、
    **この範囲では確かめられなかった**ということ
  - 例外の 1 通（2026-05-20 11:46:34 発表）は、全体が「震度 5 弱程度以上」なのに区域を持たない。
    震源を 1 点でしか決められていない報で、規模も「Ｍ不明」だった（→ §5）
- テストボタンが書き換えで作る報もこの節の規則に従う（→ [`settings-pwa-spec.md`](settings-pwa-spec.md) §7「実配信に無い形を作らない」）

#### 「警報:」「予報:」欄の出し方

種別コードは**府県予報区より 1 段細かい細分区域ごと**に付く。そのため 1 つの府県予報区の中に
警報の区域と予報の区域が同居する（能登半島地震の本震では石川・新潟・長野などが該当）。

- **警報の列に出した府県予報区は、予報の列に重ねて出さない。** 両方へ並べると、警報が出ている
  地域が予報の列にも現れて一段軽く見える（2026-10-21 ユーザー承認「今のまま記録する (Recommended)」）
- **件数で打ち切らない。** 電文が載せた府県予報区をすべて出し、行の高さは折り返しに任せる。
  能登半島地震の本震（VXSE45・全 46 報）の最終報は警報 21・予報 14 の府県予報区を載せており、
  先頭 6 件で切っていた頃は警報側の 7 割・予報側の 6 割が「...」の中だった。**対象が広い報ほど
  見えなくなる**という、同じカードの「主要動の到達（予測）」（→ §4「到達予測時刻は種別によって
  意味が変わる」）で直したのと同じ形

  数え方は画面と同じ。取得元は DMDATA `/v2/archive` の `classification=eew.forecast`・
  `date=2024-01-01` で、展開した電文から `VXSE45` の XML を採り、`Pref` ブロックごとに
  `Kind/Code` を警報（10/11/19）と予報（00/01/09）へ振り分けて、警報側に現れた府県予報区を
  予報側から除いて数えた。上の数字は最終報（`Serial` 46・16:14:18 発表）のもの。
- 表示するのは府県予報区の名前で、**「県」を機械的に補わない**（→ `EEWRegion.pref` の説明。
  「熊本」「奄美」「北海道道央」のように県名と一致しない区分がある）

### 主要動が届いたかどうか（`areas[].arrived`）

上の表の「主要動」の列は、**電文がもう 1 つ別の形でも伝えてくる**。区域の `Condition`
（値は「既に主要動到達と推測」の 1 つだけ。電文解説資料 Ⅱ.21 2-1-5-3-7）。

| 伝え方 | DMDATA | P2PQuake |
|---|---|---|
| 種別コードの下 1 桁（`01` / `11`） | 読む | **読む** |
| 区域の `Condition` | 読む（→ `EEWRegion.arrived`） | 配信されない |

**判定は `isEewAreaArrived`（`src/utils/eew.ts`）の 1 か所に置く。** どちらかが立てば到達済みとして
扱う —— 片方しか無い電文が来ても取りこぼさないため。**`arrived` を直接見ないこと**：
`Condition` を配信するのは DMDATA だけなので、そちらだけを見ると standard 版で到達済みの区域が
「時刻も印も持たない区域」に落ちて画面から黙って消える。

**片方しか無いことを異常として記録しない。** 資料が排他だと定めているのは `Condition` と
`ArrivalTime` のあいだ（同 2-1-5-3-6）だけで、**コードと `Condition` が必ず同時に出るとは
書いていない**。実電文では到達済みの区域 358 件すべてが両方を持っていた（`eew.forecast` の
2026-08-02〜09-12 の 42 日分・区域 753 件）が、**資料が保証していない以上、片方だけの
電文が来てもそれは異常ではない**。記録すれば、異常でないものを異常として残すことになる。

記録するのは `Condition` の値が資料の定める 1 つ（「既に主要動到達と推測」）から外れたときだけ
——そちらは値域が定まっているので、外れれば確かに異常。

### 到達予測時刻は種別によって意味が変わる（`areas[].arrivalTime`）

同じ要素に 3 通りの状態が入る。**時刻の有無だけで絞ると、性質の違うものが 1 つの列に並ぶ。**

| 区域の状態 | 電文 | `RealtimeTab` の「主要動の到達（予測）」欄 |
|---|---|---|
| まだ到達していない | `ArrivalTime`（到達予測時刻） | **残り秒数**（「42秒」。0 以下は「まもなく」） |
| 既に到達したと推測 | 時刻は出ず、上記の 2 通りで伝わる | 「到達済み」 |
| PLUM 法（`09` / `19`） | `ArrivalTime`（**その震度を初めて予測した時刻**＝過去） | 「時刻不明」 |

- **PLUM 法の時刻を「到達予想」として出さない。** 周辺の観測点で実際に観測された揺れから震度を
  出す手法で走時を計算しないため、値は到達の予測ではない（同 2-1-5-3-6）。並べると、既に過ぎた
  時刻をこれから来るものとして読ませる。判定は `isEewPlumKindCode`。PLUM 法の区域を「時刻不明」と
  出すことは 2026-10-21 ユーザー承認「今のまま記録する (Recommended)」
- **並びは時間の順** —— 到達済み → 未到達（残り秒数の昇順）→ PLUM 法。**PLUM を末尾へ置く**のは、
  この区域が持つ時刻が時間の軸に乗らないため。乗らないものを途中へ挟むと、前後の行だけが
  時間順という読めない並びになる（実電文では 1 報あたり中央値 0 件・最大 15 件）
- **警報の区域に限らない。** 絞り込みは時刻と到達の有無だけを見ており、`isEewWarningKindCode` を
  通していない（`RealtimeTab`）。**区域に載る予測震度には下限が無い**ので（→ 前節）、震度 2 の区域が
  この欄に並ぶこともある。実測では震度 4 未満の区域 741 件のうち 456 件が `ArrivalTime` を持っていた
  （到達済みと推測される区域は時刻を持たないので、この数には入らない）。
  - **並びは震度順ではない**ため、震源に近い弱い区域が強い区域より先に出る。これは時間順に
    並べるという上の規則どおりで、欄が伝えたいのは「いつ届くか」だから震度で組み替えない。
    **どこが強いかは各行の震度バッジが受け持つ**
- **件数で打ち切らない。電文が載せた区域を全部出す。** かつては上位 6 件で切って残りを
  「他N地域」の数字へ落としていたが、実電文の走査（2025-01-02〜2026-09-11・VXSE45 9,871 通）で
  次が判った。
  - 区域を持つ報 1,461 通のうち **27.7% が 6 件を超える**（中央値 3・p90 18・**最大 56**）。
    最大予想震度が 5 強の報では 85%、**6 弱以上では 97%** が溢れる
  - 旧い並び（到達済みが先頭）と 6 件の打ち切りが重なり、**未到達の区域を持つ報の 24.9% で
    それが 1 件も見えていなかった**（6 弱以上に限れば 65%）。「主要動の到達」の欄なのに、
    これから来る場所が 1 つも出ない状態
  - 高さは**列の折り返し**で吸収する（CSS `columns`。最小幅 `10.5rem`・最大 3 列）。56 件の実電文を
    ブラウザで再生して測った値は次のとおり（1 行 16px）。

    | レイアウト | 画面 | パネルの内幅 | 列数 | **欄の高さ** | パネルの可視高 |
    |---|---|---|---|---|---|
    | 上下分割 | 929×965 | 873px | 3 | **326px** | 434px |
    | 左右分割 | 1280×900 | 359px | 2 | **470px** | 900px |

    パネルの可視高は画面の大きさで決まる（上下分割はつまみの比率、左右分割は画面の高さぶん）ので、
    上の値はこの 2 つの画面での実測。**列数を画面幅で分岐させずブラウザに決めさせている**ので、
    これより狭い端末では 1 列へ落ちる
- **絶対時刻ではなく残り秒数で出す。** 電文は秒の値まで持っており区域ごとの差は数秒だが、
  時刻をそのまま出すと「あと何秒か」を読み手に引き算させることになる。同じカードの
  S 波カウントダウン（`SWaveArrival.etaSec`）が「あと N 秒」で出しているので尺度もそちらへ揃う。
  更新は 1 秒ごと（`useSecondTick`。**欄を出していない間と画面に出ていない間はタイマーを持たない**）
  - 時刻は `serverNow()` から採る。壁時計を使うと、端末の時計がずれている場合とリプレイ中に
    残り秒数が実際と食い違う
  - **0 以下は「まもなく」。** 予測時刻を過ぎても気象庁が `Condition` を出すまでは到達済みに
    ならないので、負の秒数が数秒続く
  - **日時として読めない時刻を「まもなく」へ混ぜない**（`arrivalEtaSec`）。`arrivalTime` は電文の
    生テキストで、パーサーは日時として読めるかを確かめていない。素朴に引き算すると `NaN` になり、
    `NaN > 0` が偽なので**壊れた値が「もうすぐ来る」という確度の高い表示に化ける**。「不明」と
    出して記録する（記録は**報ごとに 1 行へまとめる** —— レンダーの中で出すと毎秒鳴る）
  - **差し迫った区域は秒数の色を変える**（`ARRIVAL_SOON_SEC` = 20 秒以内なら赤系）。境目は実電文の
    分布から決めた —— 未到達の区域 4,004 件で到達までは中央値 17 秒・p90 44 秒なので、20 秒で切ると
    強調される区域は 1 報あたり中央値 6 件・最大 18 件に収まる。広げるほど一覧の大半が赤くなり
    「差し迫っている」の意味が薄れる。**「まもなく」と「不明」も 0 以下・`null` としてこの判定を通る**
    が、前者は差し迫っているので赤でよく、後者は値が無いので白のまま
- **見出しの右肩に内訳を出す**（「到達済み N ／ 未到達 M」）。**PLUM 法の区域は「未到達」に数える** ——
  気象庁は到達したと推測した区域に `Condition` を出すので、それが無い区域を到達済みとして扱えない。
  行の右端には別途「時刻不明」と出るので、内訳と行のあいだで食い違いは起きない
  - 「未到達」は気象庁コード表 12 の「主要動」列にある語幹。**後ろに語を足さない** —— 手元の写しが
    「未到達と予測／予想／推測」に割れており、一次資料で確定できていない
- **見出しに「予測」を残す。** 3 通りとも気象庁の予測・推測で、確定した事実ではない。中立な
  見出し（「主要動の到達」）にすると、秒数の行だけが断り書きを持たないまま確定値の顔をする ——
  他の 2 通りは「推測」「不明」と語の中に断りがある。**意味の違いは `DescriptionTip` で
  ホバーへ逃がす**（同じカードの「精度情報」と同じ流儀）。PLUM 法という手法の名前も
  そちらに置き、行には状態そのもの（「時刻不明」）を書く
- **各行に震度バッジを出す。** 色は地図・震度一覧と同じ気象庁配色（`getIntensityColor`）、
  文字色は背景から選ぶ（`readableTextColor`）。上限が定まらない予想には「程度以上」の語を補う
  （`getIntensityLabelWithApproxAbove`）
  - **バッジの幅は固定しない。** 「6強程度以上」は 6 文字あり、固定幅だと折り返してその行だけ
    高さが崩れる。最小幅だけ与えて伸びる側で受ける（語は気象庁の表現なので縮められない）
  - **震度スケール外の値でも区域を落とさない。** `eewMaxScaleInfo` は最大値を求める関数なので
    `isValidIntensityScale` で弾くが、この欄は「電文が載せた区域を全部出す」のが役目で、弾くと
    区域そのものが画面から消える（到達の情報まで失う）。壊れた値はバッジが「不明」になる形で出る

### 想定外の値に対する実行時ガード

`eewMaxScale` は震度スケール外の値を、`eewMaxLpgmClass` は 1〜4 以外の階級を採用しない
（`isValidIntensityScale()` / `isValidLpgmClass()`）。型（`IntensityScale` / `LpgmClass`）で
宣言してはいるが、実地震シナリオ JSON のように型検査が及ばない経路があるため実行時にも弾く。
これが無いと、壊れた入力の値がそのまま `>= 55` / `>= 4` の比較を通って特別警報へ誤昇格する。
**特別警報は震度と長周期地震動階級の OR 判定なので、片方だけ守っても誤昇格は防げない。**

両関数を経由しない参照経路にも同じガードを通している:

- **地図の区域塗り**（`useEewLayerData`）は `areas[]` を直接集計する（震度区域・長周期区域の両方）。
  とくに長周期側は `getLpgmClassLabel()` がフォールバックを持たなかったため、弾かないと
  「階級99」のような値がそのまま地図ラベルに出ていた（現在は同関数も「階級不明」へ落とす）。

一方、**読み上げ**（`ttsText.ts`）は震度・長周期階級のどちらも両関数を経由する。音声には色の
フォールバックのような逃げ場が無く、不正値がそのまま声に出てしまうため。

> かつては階級だけが `forecastMaxLpgmClass` を直接参照しており、両関数が持つ「地域別予想を優先」の
> ガードが読み上げにだけ効いていなかった。**同種の値を扱う経路は、片方だけ生フィールドを読まないこと。**

**震度を伝えられない報では階級も出さない。** 判定は `eew.ts` の `canPresentLpgmClass` で、
**カードの階級バッジ（`RealtimeTab`）・読み上げ（`eewIntensityText`）・第 2 フェーズの言い直し
（`useLiveEventHandler` の震度据え置き分岐）の 3 経路が同じ述語を共有する**（片方だけに置くと画面と
音声が食い違う）。気象庁の電文では最大予測震度が必須要素で、長周期地震動階級のほうが任意——つまり
**「震度なし・階級あり」という電文は作れない**。到達したら電文の異常なので、読み上げ経路が
`log.warn` で記録を残す。深さ 150km 超では階級のほうが先に落ちる（震度と違い PLUM 法による例外規定を持たないため）。
そのまま読むと「予想震度なし。予想最大階級3。」という矛盾した発話になるので、震度が取れないときは
階級句ごと省く（2026-10-21 ユーザー承認「今のまま記録する (Recommended)」）。

> かつてここには「深発地震で長周期階級だけが載る電文が実在するかは未確認」と書いてあった。
> 電文仕様を確認した結果**仕様上ありえない**と判明し、実データ（2024 年能登 1/1〜1/3）でも深さ 150km 超の
> 13 報すべてが階級を持たなかった。仮定震源要素の 72 報も同様に 0 件で、こちらは PLUM 法が長周期階級を
> 予測しないため。

### 続報で動いた欄を示す（減衰）

**印を持続させず、動いた瞬間に色を付けてそこから 1 秒かけて元の色へ戻す**
（`EEW_HIGHLIGHT_FADE_MS`）。対象は震源名と、規模・深さ・予想最大震度の**値の数字**。

**地震カードと同じ色を使うが、寿命が違う。** 地震カードの印は次の報まで（最大 1 分）残る。
緊急地震速報は秒の単位で続報が届くので、同じ作りにすると印が消える前に次が来て**常時点灯**
になり、「いま動いた」を指せなくなる。

**色で向きを分けるのはこのカードだけ**（赤＝上がった・緑＝下がった・白＝大小が無い。
`EEW_FLASH_COLOR`）。地震・津波のカードは印が持続し、値も画面に残るので**向きは値を見れば
分かる** —— あちらは「緑＝初出・黄＝動いた」の 2 色に留める
（→ [`quake-spec.md`](quake-spec.md) §8「カードの更新の印」）。

**初出の印はここでは出ない** —— 初めて現れた値は「動いた」ではないため。

根拠は実測。控えてあるアーカイブ 8 日分（緊急地震速報 250 件・続報 1,184 通）で、続報が
その欄を動かした割合は次のとおり。

| 欄 | 動いた続報 | |
|---|---|---|
| 規模 | 45.0% | |
| 座標 | 35.9% | **対象外**（カードに座標の欄が無い。地図の震源が示す） |
| 予想最大震度 | 18.7% | |
| 震央地名 | 15.1% | |
| 深さ | 12.9% | |

座標も測ってあるのは、**この仕組みを地震カードと同じ考え方で設計したから**（あちらは座標を出して
いるので印が付く）。ここでは出していないので対象に入らない。

**点滅させない。** 秒ごとに届く続報のたびに点けたり消したりすると目が休まらない。減衰なら、
動いた瞬間がいちばん濃く、見逃しても余韻で気づける。

**色を当てるのは、その欄で色に意味を持たない文字だけ。** 規模・深さ・予想最大震度は値の数字が
白で、色を持つのは隣のラベルと枠（震度階級・段階の色）。地震カードと同じ線引き
（→ [`quake-spec.md`](quake-spec.md) §8「カードの更新の印」）。

**一度も動いていない欄には減衰のクラスを当てない。** CSS アニメーションは要素が現れた時点で
走るので、常に当てているとカードが初めて出たときに全欄が光る。「初めて現れた値は動いていない」
という決まりと食い違う。

**前回値は state で持つ**（`hooks/useFieldFlash.ts`）。レンダー中に ref を書き換えると、
React が捨てたレンダーでも書き込みだけが残り、描き直したときに「変わっていない」と見えて
減衰が出ない。

**はじめの 35% のあいだは色を保ってから戻す**（`EEW_HIGHLIGHT_HOLD_RATIO`）。保たずに落とすと
0.3 秒ほどでほぼ元の色へ抜けてしまい、何色だったのか読めないまま終わる。CSS の `@keyframes` は
オフセットに定数を使えないので、**値は `src/index.css` と手で揃える** ——
揃っていることは `src/hooks/useFieldFlash.test.ts` が機械で確かめる。

**「視差効果を減らす」設定では滑らかに動かさないが、印は消さない。** `animation: none` にすると
色が最初から最後まで元のままになり、手掛かりが丸ごと失われる。保持のあいだ色を出して、
そこから段階を踏まずに戻す（`steps(1, end)`）。

実機で確かめる入口は設定タブ「警報テスト」。**2 通目で規模が上がり、3 通目で深さが浅くなり、
5 通目で規模が下がる**（`EEW_WARNING_MAGNITUDE` / `EEW_WARNING_DEPTH_KM`。動かす回数の比は
上の実測に倣い、**上がる形だけにしない** —— 下がった側の色を実機で確かめられなくなる）。

## 5. 仮定震源要素（震源未確定）の扱い

電文の `condition === '仮定震源要素'` は「**震源要素が推定できず、PLUM 法による震度予測だけが有効**」な
状態を指す。震源が決まらないので、気象庁は PLUM 法でトリガー条件を最初に満たした観測点の**直下 10km・
M1.0** を仮の震源として電文に書く。震央地名もその観測点の所在地であって、震源の推定位置ではない。
（定義と固定値の出典: 気象庁「[緊急地震速報に関する情報のコード電文解説資料](https://www.data.jma.go.jp/suishin/shiyou/pdf/no40202)」・
[配信資料に関する技術情報第 566 号](https://www.data.jma.go.jp/suishin/jyouhou/pdf/566.pdf) 別添資料 1）

（**PLUM 法** = 周辺観測点で実際に観測されたリアルタイム震度から予想震度を算出する手法。震源要素を
使わないため、揺れが観測された瞬間から数秒で予報を出せる。詳細は
[`kyoshin-detection-spec.md`](kyoshin-detection-spec.md) 参照）

> **「単独観測点処理」と同義ではない。** 定義に観測点の数は含まれておらず、PLUM が何点鳴っていても
> 震源要素が推定できなければ仮定震源要素になる。電文の「震央の確からしさ」でも *IPF 法（1 点）* と
> *仮定震源要素* は並列に列挙された別物で、前者は「1 点で震源を決めた」、後者は「決められなかった」。
> 実データ（2024 年能登 1/1〜1/3）では仮定震源要素 72 報のうち **50 報が最大予測震度を持っていた**
> ——気象庁は観測点 1 点による震度予測では値を出さないので、これらは PLUM が 2 点以上鳴っている報。
>
> 呼び方が意味を持つのは**予想震度が付いていない報の理由を述べるとき**だけ。**気象庁のいう
> 「観測点 1 点による震度予測」とは、PLUM 法が 1 地点でしかトリガーしていない状態を指す**——
> 仮定震源要素で値が載っていない報がちょうどそれにあたるので、画面・読み上げとも「単独点処理のため」
> と言える（判定は `eewNoForecastReason`）。PLUM が 2 点以上なら値が載り、`eewMaxScale` が拾うので
> この経路へは来ない。
>
> **震源が決まっていても、震央の確からしさが IPF 法（1 点）なら同じ理由を言う。** ただし**値が付くのを
> 待ち終えてから**に限る（`eewNoForecastReason` の第 2 引数）。確からしさのランク 1 は「P 波／S 波の

### 「非常に強い揺れを検知・最大予測震度のみ」の報も仮の震源として扱う

気象庁は、震源を決める前に強い揺れを検知した観測点だけで第 1 報を出すことがある（解説資料 Ⅱ.21 の
「緊急地震速報（地震動予報）」「同（予報）」にだけ現れる形で、**警報には現れない**）。この報は
**発生時刻（`OriginTime`）を持たず**、`Condition`（仮定震源要素）も持たない。規模は「不明」、
震央は揺れを検知した観測点の位置、深さ 10km は仮の値で、区域も載らない。代わりに本文（`Body/Text`）が
「３日０６時３１分４２秒頃／石川県珠洲市付近　最大震度５弱程度以上と推定」の形で検知した時刻と場所を
伝える（実例: 2024-06-03 06:31 の能登半島の地震。第 2 報は仮定震源要素の報へ移った）。

- **見分け方** — `parseEEWFromXml`（`src/services/dmdataParser.ts`）が、取消でなく `Earthquake` を持つのに
  `OriginTime` が無い報へ `EEWAlert.strongShakingOnly` を立て、本文を `strongShakingText` に持つ。
  取消以外でこの要素が欠けるのはこの形だけ（解説資料 Ⅱ.21 1-1）。本文の有無では見分けない。
  **資料の定義（要素ごと出ない・規模は不明・予報と地震動予報だけ）と食い違う報はこの形と見なさない**
  （発生時刻の要素はあるのに中身が空・規模が数値・警報の報）。確定した震源の報を読み損ねたなら、
  M・深さを消すほうが害が大きいため。その報は記録だけ残す（予報円は描けない）。本文が無いときも記録する
- **下の一覧はこの報にも同じく効く。** 判定は `src/utils/eew.ts` の `isProvisionalHypocenter`
  （仮定震源要素か、この報か）に寄せてあり、一覧の各所はこれを通す
- **予想震度が出ない理由の判定（`eewNoForecastReason`）だけは通さない。** この報は最大予測震度を
  持つので理由を述べる経路へ来ず、巻き込むと「単独点処理のため」と言い出す
- **カードは震源名の下に本文を見出しなしで出す**（改行は電文どおり）。震源名には「（震源未確定）」を
  添え、M・深さは出さない。**本文は読み上げない**。**取り消されたら本文を出さない**（固定付加文と同じ扱い）
  （カードの出し方・読み上げない扱い・取消後に隠す扱いは 2026-10-15 ユーザー承認）
- **地図の震源の吹き出しは「非常に強い揺れを検知（震源未確定）」と「地名は揺れを検知した観測点の
  位置です」**（2026-10-15 ユーザー承認）。仮定震源要素の報とは語を分ける
- **地震カードの P 波・S 波の線の起点にはならない。** この形は発生時刻を持たないので、過去の最終報
  （`src/services/dmdataReplay.ts` の `fetchDmdataEewOrigins`）として読んでも、`eewOriginsFromActive`
  （`src/hooks/useQuakeOriginSeconds.ts`）が時刻なしとして扱い、記録に残さない

以下の**複数箇所で連動して非表示化する**（片方だけ直すと非対称になる）。M・深さを出さず、地図の震源を地表へ置き、
吹き出しに「震源調査中」と出すこと自体は 2026-10-21 ユーザー承認「今のまま記録する (Recommended)」。数を書くと列挙漏れがドリフトしやすいため、

- **予報円を出さない** — `src/hooks/usePsWaveCalc.ts` の `computeEewCircle`（`isProvisionalHypocenter` で早期 return）。
  **発生時刻が読めない報も出さない**（経過秒が数にならない）。

### 震央地名が空なだけの報は、仮の震源として扱わない

**地名が付いていないことは、震源が決まっていないことを意味しない。** 仮の震源かどうかは
`isProvisionalHypocenter`（仮定震源要素・「非常に強い揺れを検知」の報）だけで決め、震央地名の有無は判定に使わない。
座標が判っていれば（`hasKnownEpicenter`。`-200` は位置不明のセンチネル）、地名が空でも次のものを地名のある報と同じに出す。

- **EEW カードの M・深さの欄** —— `RealtimeTab` の欄の条件は「仮の震源でない」かつ「地名がある、または座標が判っている」。
  震源名の欄は「震源調査中」になる
- **予報円** —— `computeEewCircle` は座標・深さ・発生時刻・仮の震源の判定だけを見る（座標が `-200`、深さが `-1`＝§6「震源の深さが判らない報では円を出さない」なら描かない）。
  予報円が出るので、第一報のカメラ追従も地名のある報と同じく、その地震の予報円へ寄る
- **地図の震源の吹き出し** —— 見出しを「震源調査中」にする（`EewEpicentersGL.tsx` の `buildPopupHtml`）
- **共有カードの見出し** —— 名前の位置に「震源調査中」を置き、規模・予想最大震度を続ける（`shareCardContent.ts`。2026-10-22 ユーザー承認「「震源調査中」を入れる」）

> **気象庁の電文には、地名が空の報が見当たらない。** この規則は、地名だけが欠けた報が届いたときの扱いを決めておくもの。
> 2026-10-22 に、DMDATA の日ごとのアーカイブの控え（`eew.forecast` 1,552 本・`eew.warning` 69 本。日付は 2022-07-20〜2026-10-18。
> 置き場所は `.claude/dmdata-archive-cache/`、→ [`telegram-coverage-audit.md`](telegram-coverage-audit.md) §2）から、
> VXSE43・44・45 の XML のうち `Control/Status` が「通常」で震源を持つ 45,079 通を数えた。`Body/Earthquake/Hypocenter/Area/Name` が
> 無い・空の報は 0 通、仮定震源要素の報 457 通もすべて地名を持っていた（すぐ上の注記の「26 通」は `condition` の値を見た別の数え方）。
> Yahoo hypoInfo の `regionName` も、2024-01-01 能登の 3 フレームでは気象庁と同じ地名を持っていた。Yahoo の報は仮定震源要素かどうかを
> 運ばない（§3 の経路の表で `condition` が「常に空」）ので、地名の有無をその代わりに使うことも考えられるが、上の数え方からはその根拠は出てこない。

**地名が空のときの読み上げ・ウィンドウタイトル・ブラウザ通知は、備えとして直してある**（2026-10-24 ユーザー選択「備えとして直す
(Recommended)」。1 回目は問い返し「ちなみにそんな物はあるの？」で、上の数え方と、P2PQuake の公式仕様では `hypocenter.name` が必須の
欄でないこと・この口から緊急地震速報を受けたことが無いことを答えて問い直した）。

  助詞から始まる文になっていた。**震源の言い直しは、名前が空なら読まない**（言い直す地名が無い。`useLiveEventHandler.ts` の第 1 フェーズ）

## 6. 予報円（P 波・S 波）と到達予想

**`src/utils/travelTime.ts`** が走時の単一情報源、**`src/hooks/usePsWaveCalc.ts`** が予報円の計算。
**標準版・DMDSS 版で共通**。

**距離はすべて球で解く。** 地球半径は `src/utils/geo.ts` の `EARTH_RADIUS_KM` に一本化し、震源距離・
地表距離の変換は `hypocentralDistanceKm` / `surfaceDistanceKm` を通す。**平らな直角三角形
（`√(地表距離² + 深さ²)`）では解かない** —— 地表は曲がっているため誤差が生じる。浅い地震では
0.1% 未満だが、深発地震で遠方を見ると効く（地表 800km・深さ 700km で 3.3%）。

### 走時は JMA2001 走時表から引く

**気象庁と同じ表を引く。** 気象庁は緊急地震速報の主要動到達予測時刻を、速度構造 JMA2001 を基に
深さ・震央距離ごとに作った走時表から出している（「緊急地震速報の概要や処理手法に関する技術的
参考資料」令和 6 年 4 月 11 日 p.15）。自前の速度モデルで解くと、同じ地震について電文が名乗る
時刻とアプリが描く波面が別の根拠から出ることになる。

- 表の出どころ・格子の刻み幅・生成コマンドは [`data-sources-spec.md`](data-sources-spec.md) §6
  「JMA2001 走時表」が単一情報源
- 入力: `EEWAlert.earthquake.hypocenter`（lat/lng/depth/magnitude）と `originTime`
- 更新頻度: 100ms（`UPDATE_INTERVAL_MS`）で `setInterval`
- 出力: `PsWaveCircle[]`（各 EEW に対する現時点の P 波・S 波半径）

**距離は震央距離（地表の弧長）で渡す。** 表がその形で作られているので、`utils/geo.ts` の弦への
換算（`hypocentralDistanceKm`）は通さない —— 通すと球の補正が二重に掛かる。地表の曲がりも
地殻・マントルの構造も表が持っている。震央距離そのものは `haversineKm`（大円）で測り、
予報円の頂点・外接矩形・破線の本数は同じ `ringVertex` を通す（`components/Map/gl/psWaveRing.ts`。
別々の近似で出すと、円と矩形・円と破線がわずかにずれる）。

**外接矩形の東西端は「真東・真西へ半径ぶん進んだ点」ではない**（`ringBounds`）。大円は東へ進むと
赤道側へ曲がるので、最も東へ届くのは方位 90 度より少し極寄りの点になる。経度の最大差は解析的に
`asin(sin(Δ) / cos(緯度))`（Δ は角距離）で、総当たりの探索と一致することを確認済み。方位 90 度で
代用すると緯度 40 度・半径 800km で 5.8km、緯度 80 度・半径 300km で 60km 過小になる。南北端の
ほうは方位 0・180 の点で厳密に正しい（そこで緯度の変化率が 0 になる）。

**表の右端（震央距離 2000km）より遠い距離は末端の見かけ速度で外挿する。** 予報円は自動解除まで
伸び、**浅い震源でも M8 で P 円が約 2500km・M9 で約 3900km、深い震源では 5400km に達する**
（実測。`calcEEWAutoCancelSec` の秒数を `reachRadiusKm('P', …)` へ通し、深さ 0–700km を走査した。
**深さで 2 倍以上動く**ので、値を引くときは深さの条件も一緒に読むこと）。表で打ち切ると、そこから
外が描かれないか値が固まる。走時を引く側と半径を逆引きする側で同じ傾きを使う（片方だけ外挿すると往復で値が合わない）。
表より深い震源は表の下端（700km）へ張り付ける。

**半径の逆引きは、走時そのものを二分探索で逆にたどる。** `reachRadiusKm` は
`travelTimeSec` を呼んで探索するので、**定義のうえで逆関数**になる。

**「行ごとに逆引きしてから距離を混ぜる」形にしないこと。** 深さの格子点では同じ値になるが、
格子の間では `travelTimeSec`（走時を深さ方向へ混ぜる）の逆関数にならない —— 2 つは別の演算で、
**深さ 693.5km・震央距離 0km で 43.94km** ずれる。深い震源の震央近傍は距離に対して走時がほぼ
平坦なので、わずかな走時の差が大きな距離差へ化ける。**格子点の深さでは誤差 0 なので、
格子点だけを走査するテストでは見えない** —— 緊急地震速報の深さは整数 km で届き、50km 以深の
格子は 5km・10km 刻みなので実運用では普通に格子から外れる。

いま残る往復の誤差は**走時を 0.01 秒単位へ丸めていること**だけで、深さ 0〜700km を 0.5km 刻み・
震央距離 0〜2000km を 1km 刻みで走査した実測では S 波が最大 6.0km（深さ 470km・距離 6km）・
**震央距離 15km 以上では 0km**、P 波が最大 10.0km（深さ 610km・距離 10km）・距離 30km 以上でも
最大 2.0km。P のほうが大きいのは、速いぶん同じ 0.01 秒が距離へ 1.7 倍ほど出るため。
上限は `src/utils/travelTime.test.ts` が**格子の間の深さを含めて**固定する。

**シェーダー側は単精度**なので、TypeScript 側（倍精度）と完全には一致しない。同じ式を単精度で解いて
突き合わせた実測では、ずれは半径によらず 30〜320m（半径 1km でも 171m 出るので、式の桁落ちではなく
三角関数の実装誤差が支配的）。円の半径に対して 0.04〜0.6% で、zoom 10 でも 3px 程度。

平面（Mercator）投影で表示しているときは、地面の上で正しい円でも画面上では北側が大きくなる
（半径 400km で 4%）。これは図法そのものの性質で、円の作り方では消せない。消すには円が波の到達位置を
表さなくなるのを受け入れるしかないので、消さない（[`map-rendering-spec.md`](map-rendering-spec.md) §6）。

### 震源の深さが判らない報では円を出さない

`Hypocenter.depth` は判らないことをセンチネル **`-1`** で表す（`0` は「ごく浅い」という有効値。
判定は `utils/formatters.ts` の `hasDepth`。単一情報源は [`quake-spec.md`](quake-spec.md) §5
「深さだけが判らない電文」）。この報では**予報円を描かない** —— 仮定震源要素と
同じ層・同じ理由で、描けば根拠のない秒数を見せることになる（2026-10-21 ユーザー承認「今のまま記録する (Recommended)」）。

- **代表値では代えられない。** 深さは事前に判らないので、当てた値が外れれば円も外れる。
  深さ 0 として描いた場合、真の深さとの差は**発報直後ほど大きい**（S 波・実測）

  | 経過 | 深さ 50km | 深さ 70km | 深さ 100km | 深さ 150km | 深さ 300km |
  |---|---|---|---|---|---|
  | 20 秒 | +6km | +26km | **+65km**（実際の半径は 0） | **+65km**（実際の半径は 0） | **+65km**（実際の半径は 0） |
  | 30 秒 | -7km | +1km | +27km | **+100km**（実際の半径は 0） | **+100km**（実際の半径は 0） |
  | 60 秒 | -24km | -23km | -16km | +6km | **+215km**（実際の半径は 0） |

  浅い地震では十数 km に収まるが、**深い地震では「まだ地表へ届いていない」時間帯に円を描く**。
- **判定は `reachRadiusKm` を呼ぶ手前に置く。** あちらは NaN を返さない契約のため内部で
  `Math.max(0, depthKm)` と丸めており、**呼び出し側のクランプを外すだけでは結果が変わらない**。
- **電文の側も「位置は決まっているが深さは不明」を想定している。** 気象庁
  「[緊急地震速報に関する情報のコード電文解説資料](https://www.data.jma.go.jp/suishin/shiyou/pdf/no40202)」
  は震源の深さ `hhh` の値域に「///：不明・未設定時、キャンセル時」を置く一方、緯度経度には
  「キャンセル時」しか無い。XML では高さフィールドを省き `description="…深さ不明"` を添える形で届く。
- **円が消えても、猶予の情報が全部消えるわけではない。** 区域ごとの到達予測時刻は気象庁の
  発表値として電文から出る（下記「特定地点への到達予想は気象庁の発表値を伝える」）。
- **実配信では観測していない。** 手元の控え（緊急地震速報 VXSE45 330 通・2024 年の 3 日分）で 0 件。
  ただしこの 3 日は国内・震源が十分に決定された地震に偏っており、**深さ不明が起きやすい条件
  （遠地・観測点僅少・震源決定前）を含んでいない** —— 起きない証拠ではない。同じ控えの地震情報には
  1 件あった（2026-06-24 の遠地地震）。
- **深さ 700km 以上（下限だけの値）は予報円の扱いを変えていない。** 電文は `-700000/` と
  「深さ　７００ｋｍ以上」で送り、パーサーは印 `depthAtLeast` を立てる（→ [`quake-spec.md`](quake-spec.md) §5
  「深さが下限だけの電文（700km 以上）」）。カードと地図の吹き出しは「700km以上」と出す
  （2026-10-19 ユーザー承認「「700km以上」 (推奨)」）が、予報円は 700 を数として解く（2026-10-20 ユーザー承認「1b 2a 3a」。
  選んだ案は「いまのまま 700km として描く」）。走時表の深さは 700km までなので、それより深くは解けない。地図下端の波形に引く
  P/S の線は深さ不明と同じく引かない（2026-10-19 ユーザー承認「線と距離を出さない (推奨)」）。確かめた範囲で
  700km 以上が届いた例が無いことは [`quake-spec.md`](quake-spec.md) §5 に書いてある

### 特定地点への到達予想は気象庁の発表値を伝える

**自前の走時計算で「その地点へ何秒後」を出す行為は、気象業務法第 17 条の許可を要する地震動の
予報業務に当たりうる。** 気象庁は該当する行為を「気象庁が提供する地震動に係る予報資料を用いて、
自らが作成した装置等により**個別地点の震度や地震動の到達時刻の予想**を行い、その結果を即時的に
利用者に提供する場合」、該当しない行為を「気象庁の行う地震動の予報及び警報…の内容を
**そのまま利用者に伝達する場合**」と定めている（気象庁「地震動の予報業務許可についてよくお寄せ
いただくご質問」 https://www.jma.go.jp/jma/kishou/minkan/q_a_s.html ）。

**このアプリへの当てはまりは確かめていない。** 無償・少数への提供が同条の「業務」に当たるか、
予報円が「個別地点の…到達時刻の予想」に当たるかは、条文にも上記 FAQ にも明示が無く**未確認**で、
外部への照会も済んでいない（裏付けの強さは
[`../forecast-computation-audit.md`](../forecast-computation-audit.md)「確認の度合い」が単一情報源）。
無許可の予報業務には罰則がある（同法第 46 条第 2 号。**条文を読んだもので、上記 FAQ の引用ではない**）。

**アプリが自前で計算している箇所のうち、予想した値を利用者へ出さないもの・発表済みの地震情報から過ぎた時刻を
出すもの・到達時刻を過ぎてから線を引くものは、同じ FAQ の文面に照らして当たらないと整理した**（2026-10-14 ユーザー承認。
その後に足した箇所は 2026-10-15・2026-10-18 ユーザー承認。
文面から読んだもので、照会はしていない。内訳は [`../forecast-computation-audit.md`](../forecast-computation-audit.md)
「予報業務の線引きとの対応」）。次の段落が扱うのは、残る 2 つ —— 登録地点への到達予想と予報円。

**確かめきれていないぶん、許可が要る側だと仮定しても失うものが小さいほうを選んである。**
到達予想は気象庁の発表値の伝達へ移し、自前計算は発行済みトークンを持つ端末だけで有効にした。
**予報円はそのまま出している** —— 気象庁は円を配信しないので載せ替え先が無く、別途の判断が要る。

そのため到達予想は**気象庁が電文で出した区域ごとの到達予測時刻（`Area/ArrivalTime`）を伝える**形に
してある。値の単位は一次細分区域（都道府県を 3〜4 つに分けた広さ）で、地点そのものの値ではない。

| 出す先 | 実装 | 値の出どころ |
|---|---|---|
| 「主要動の到達（予測）」欄（区域の一覧） | `components/RealtimeTab` | 電文の `ArrivalTime` |
| 地図の区域ポップアップ | `components/Map/EewRegionFillGL.tsx` | 電文の `ArrivalTime`（`EewAreaFill.arrival`） |
| ホーム地点のカウントダウン | `hooks/useHomeAreaArrival.ts` | 登録地点が属する区域の電文の `ArrivalTime` |

**区域名を必ず一緒に出す。** どの範囲に対する発表なのかを画面で示さないと、区域の値が地点の値として
読まれる（`SWaveArrival.source` が `'telegram'` のときはカードに区域名、`'own'` のときは
「ホーム地点」と出し、注記も書き分ける。両方の行が混ざった `'mixed'` は行ごとに出す —— 下の「範囲と注記の出し方」）。

**緊急地震速報が同時に複数出ているときは、地震ごとに 1 行を並べる**（2026-10-14 ユーザー決定「地震ごとに並べて出す」。
以下は 2026-10-18 ユーザー承認 —— 見せ方「1 枚に行を並べる (推奨)」・並び順「到達の早い順 (推奨)」・上限「上限なし (推奨)」・
音「いちばん早く届く地震 (推奨)」・枠の色と見出し「先頭の行に合わせる (推奨)」）。この節が決定の正本で、
[`../forecast-computation-audit.md`](../forecast-computation-audit.md) の 1 はここを参照する。

- **どの行も 1 つの速報だけから作る。** 「登録地点の区域」は、登録地点の座標を含む一次細分区域（`useHomeAreaArrival.ts` の
  `useHomeAreaName`）。秒数はその速報がこの区域について出した値（同ファイルの `homeAreaArrivalOf`）、距離は同じ速報の震源から
  測る。理由: 秒数と距離を別々の速報から取ると、別の地震を指す
- **この区域に到達予測時刻を出していない速報は、距離だけの行にする**（`SWaveArrivalRow.noForecast`。2026-10-14 ユーザー承認
  「距離だけのカードを出す」、行の中での見せ方は 2026-10-19 ユーザー承認「行として最後に並べる (推奨)」）。距離は観測事実で予想ではない
  ので、区域が載らない地震でも出す。本文は「ホーム地点の地域には、気象庁の到達予測時刻が出ていません」。区域が電文に載っていても
  到達予測時刻を持たない（PLUM 法の時刻だけ・時刻が読めない）ときも同じ扱い。その区域を「到達済み」と伝える報なら、
  距離だけの行ではなく到達済みの行になる。**震源の決まっていない報・位置の判らない報・取り消された報は
  距離を出せないので、この行も作らない**。自前計算の端末では、自前計算できない地震を戻した行としてだけ出る（下の「自前計算の経路」）

  | 出ている行 | 見出し | 枠 | 下の注記 |
  |---|---|---|---|
  | 距離だけの行が 1 件 | 「震源から N km」（区域名と本文が下に続く） | 灰色 | 出さない |
  | 予測のある行と距離だけの行 | 先頭の行に合わせる（下の表の順で距離だけの行は最後） | 先頭の行に合わせる | 出す |
  | 距離だけの行が 2 件以上 | 「主要動の到達予測なし」 | 灰色 | 出さない |

  複数行のときは、距離だけの行にも震央地名と「震源から N km」を出し、その下に上の本文を添える。注記（「※気象庁が発表した
  地域ごとの到達予測時刻です…」）は予測時刻の性質を説明する文なので、予測を 1 つも出していない枠には当てはまらない
- **自前計算の経路は予報円 1 つ（＝地震 1 つ）ごとに行を作る。** **自前計算できない地震は、気象庁の発表値の行へ戻す** ——
  予報円の無い報（仮の震源・深さ不明・強い揺れの検知だけ）と、解除までに届かない地震。戻した行は公開版の経路と同じ作り
  （区域の値か距離だけの行。`telegramRow`）。キーの無い端末なら同じ報で発表値が出るので、戻さないとキーを入れたほうが
  伝わる情報が減る（2026-10-21 ユーザー承認「直す (Recommended)」）。出どころは行ごと（`SWaveArrivalRow.source`）と枠ごと
  （`SWaveArrival.source`。両方の行があれば `'mixed'`）の 2 段で持つ
- **行が途中で出どころを替えないよう、2 つ揃える。**
  - 予報円を作れる速報で円がまだ届いていない一瞬（円は別の更新で作られる）は、発表値の行を出さずに待つ
  - 解除までに届かない地震は、S 波が地表に出る前から見分けて最初から発表値の行にする（待つと「推定中」の自前計算の行が数秒出てから替わる）
- **カードは 1 枚。** 地震の名前（震央地名）は 2 件以上のときだけ行に添える。1 件のときは以前と同じ見た目。
  枠の色と見出し（「主要動 到達カウントダウン」／「主要動 到達済み」）は先頭の行に合わせる
- **範囲と注記の出し方**（範囲は「ホーム地点」か区域名）。注記はそれが説明する行があるときだけ出す

  | 枠の出どころ | 範囲 | 注記 |
  |---|---|---|
  | `'telegram'` | 区域名を 1 回 | 「※気象庁が発表した…」（予測を 1 つも出していない枠では出さない。上の表） |
  | `'own'` | 「ホーム地点」を 1 回 | 「※推定値。…」 |
  | `'mixed'` | 行ごとに震央地名の下へ（2026-10-22 ユーザー承認「行ごとに範囲を出す (Recommended)」） | 「※推定値。…」と、到達予測時刻を出した発表値の行があれば「※気象庁が発表した…」も（2026-10-22 ユーザー承認「時刻のある行があるときだけ (Recommended)」） |

  混ざった枠で範囲を 1 回だけ出すと、どちらかの行の範囲を偽って伝える
- **並びは 4 つに分ける**（`compareArrivalRows`）。どの行も同じ速さで秒が減るので、続報で時刻が変わらない限り順番は入れ替わらない

  | 順 | 行 | 条件 |
  |---|---|---|
  | 1 | 到達済み | 「主要動が到達しています」と出す行 |
  | 2 | 残り秒数がある | 秒数の短い順 |
  | 3 | 推定中 | まだ届いておらず、秒数が出せない行（「到達時間を推定中…」） |
  | 4 | 到達予測なし | 上の距離だけの行 |

- **件数の上限は置かない。** DMDATA のアーカイブ（分類 `eew.forecast`・`eew.warning`）の 3 日分（2024-01-03・06-03・11-26、
  地震 62 件）で発表の重なりを数えると、同時に出ていたのは最大 2 件だった。標本が少ないので、3 件以上が無いとは言えない
- **秒読みの音は 1 本だけ。** まだ届いていない地震のうち、到達がいちばん早いものの残り秒数で鳴らす（`countdownBeepTarget`）。
  その地震が届いた後は、次の地震の残り秒数へ移る。同じ秒数を二度鳴らさない判定は地震の鍵と組で行う —— 秒数だけで比べると、
  地震が替わった直後に前の地震と同じ秒数だったとき鳴らない。距離だけの行は音の相手にしない（2026-10-19 ユーザー承認。選択「行として最後に並べる (推奨)」の
  説明に含まれる「秒読みの音には加えない」）

**PLUM 法の区域の時刻は採らない。** あの値は到達の予測ではなく「その震度を初めて予測した時刻」
＝過去の時刻（電文解説資料 Ⅱ.21 2-1-5-3-6）。判定は `utils/eew.ts` の `eewAreaArrivalKind` 1 か所で
行い、出す先ごとに書き分けない。

**予報円はこの制限の対象外として残している。** 円が図示するのは「震源から時間経過でここまで波が
届いている」ことで、個別地点への到達時刻の予想ではない。**ただし線引きが明文で示されているのは
上の 2 つの行為についてだけで、予報円について気象庁の判断を確かめたわけではない。**

**自前計算は発行済みトークンを持つ端末でだけ有効になる。** 仕組み・トークンの形・鍵の置き場所は
[`settings-pwa-spec.md`](settings-pwa-spec.md) §4.7「到達予想キー」。

**`useSWaveCountdown` の許可フラグ（`allowOwnCalculation`）に既定値を持たせない。** 呼び出し側に
必ず決めさせる——渡し忘れたときに黙って自前計算へ倒れると、公開版が許可の要る形で動いてしまう。

## 7. 自動解除（`calcEEWCancelTime`）

**明示的な取消電文が来ない限り**、EEW は一定時間経過後に**無音・即消去**される（キャンセルオーバーレイなし）。
自動解除で音もタブ移動も起こさないことは 2026-10-21 ユーザー承認「今のまま記録する (Recommended)」。
計算式は**司・翠川式**（震源からの距離に応じて震度がどれだけ減衰するかを近似する経験式・地震工学で広く使われる）
から**有感半径**（震度 1 以上が届くと推定される距離）を二分探索で逆算し、そこまで S 波が届く時間 + 30 秒を
自動解除時刻とする。最終報から最低
60 秒（`MIN_CANCEL_SEC`）は表示を保つ。詳細は `src/utils/eew.ts` の `calcEEWCancelTime` /
`calcEEWAutoCancelSec` / `calcFeltRadiusKm`（二分探索）参照。

再生（テスト時刻設定 →
[`settings-pwa-spec.md`](settings-pwa-spec.md) §6）中も同じ猶予が効く。解除の予約は再生時計の
時間軸で評価するため、最終報を受けた直後に消えることはない（→ 同 §6「再生中も予約は発火時刻を待つ」）。

### 最終報を名乗らない経路（P2PQuake）

**P2PQuake の 556 は最終報の印を運ばない。** 最終報を起点にする上の予約は、P2PQuake だけが拾った速報
（Yahoo の取得が止まっているときなど）では 1 つも積まれず、取消が来るまで画面に残っていた。

そこで **P2PQuake の報を受けるたびに、その報を最終報とみなした解除を予約する**（見張りの解除・
キューの `eew-watch-expiry`）。計算は上と同じ `calcEEWCancelTime` で、起点は受理した中でいちばん新しい
発表時刻（「最終報から 60 秒」の下限の起点。本体は震源時刻から数える）。

**生きている見張りは 1 地震に 1 本。** 見張りを積むたびに、積んだときの受理回数を印（`eewWatchReceiptsRef`）に
書き、発火した見張りは自分の受理回数が印と合うときだけ働く。前の見張りをキューから探して消すことはしない ——
張り直す側は必ず印も書き直すこと（書かずに積むと 2 本が生きる）。印は取消・失効の報を受けたとき、見張りが
解除したとき、表示から消えた速報の掃除、リプレイ開始のリセットで消える。

**発火した時点で、予約した後にどの経路からでも報を受けていれば、いちばん新しい報から張り直す** ——
Yahoo が続報を出し続けている間に見張りが発火すると、まだ発表中の速報を消し、次の Yahoo の報で
「新規発表」として鳴り直す。捨てずに張り直すのは、Yahoo の続報のあと Yahoo の取得が止まったときに
解除の予約が 1 つも残らなくなるため。新しい報を受けたかは §10 の台帳が数える受理の回数
（`EewAcceptance.receipts`）で見る —— 発表時刻や報番号は、どちらも読めない報がある。取消を受けた速報の
見張りはその場で外す。

DMDATA には置かない。あちらは最終報を名乗る（2026-10-14 ユーザー承認・選んだ選択肢「解除の予約も続報の音・声も直す」。
その選択肢の説明に「見張りの解除は P2PQuake に限る」と書いて諮った）。

### 時刻が読めないとき

解除時刻は**発表時刻と震源時刻の 2 つ**から決まる（「最終報から 60 秒」の下限は前者、S 波の
到達までを見込んだ本体は後者を起点にする）。**震源時刻が無い・読めないときは地震発現時刻を起点にする**
（「非常に強い揺れを検知」の報は震源時刻を持たない。§5）。発現時刻は震源時刻より後なので、解除は
早まらない側へずれる。**規模が「不明」の報は M6.0 として求める**（規模が読めない報に置く固定の仮定値。
読めない値は経路で形が違い、DMDATA と強震モニタは `NaN`、P2PQuake は `-1` —— どちらも `hasMagnitude` で見分ける。
`-1` を M3 相当から M6 相当へ揃えたのは 2026-10-22 ユーザー承認・選んだ選択肢「この形でコミット」）。
S 波カウントダウンが「解除までに届くか」を見るときも同じ仮定値を使う（`calcEEWAutoCancelSec` が 1 か所で持つ）。
予報円の揺れの継続時間の目安（`calcShakingDurationSec`）も、規模が判らなければ表を引かず既定の 20 秒にする。
**片方が読めなければ、読めたほうだけで決める。**

読めない時刻から作った日時は、**それを含む大小比較がどちらの向きでも成り立たない**。素朴に
書くと片側だけが守られ、震源時刻が読めないときは発表時刻基準の値が出るのに、発表時刻が
読めないときだけ解除時刻そのものを決められない、という非対称になる。

**両方読めなければ解除時刻を決めない。** 代わりの値を作ると、決められなかったことが後の
処理へ伝わらない。受け取る側は次のように振る舞う。

| 場所 | 振る舞い |
|---|---|
| ライブ・テスト送信（`hooks/useEarthquakes.ts`） | 自動解除を予約しない。**取消電文が届くまで表示が残る。** 予約できなかったことを記録する |
| 再生の開始時点の復元（`services/dmdataReplay.ts`） | 失効しているかを判定できないので**有効として再現する**（再現する電文を落とすほうが害が大きい）。倒したことを記録する |

発表時刻が読めない電文は実配信で観測できていない（→ [`quake-spec.md`](quake-spec.md) §6.3）。
ここは、届いたときに**例外もログも出さないまま挙動だけが変わる**のを防ぐための構え。

## 8. 誤報取消（明示的な取消電文）

DMDATA・P2PQuake で明示的な取消電文（`cancelled: true`）が来た場合、自動解除と異なり以下を伴う。

**取消は `isFinal` も立つ**（§3。そのイベントの打ち切りだから）。ただし消費側はどこでも
`cancelled` を先に見て分岐するので、`isFinal` の値で取消の扱いが変わることはない。

- `eewCancel` 音の再生（伝える取消のみ。二重鳴り防止）
- ブラウザ通知（どの取消でも発火。tag=`eew-cancel-${key}` なので取消の通知どうしは上書きされ二重にならない。
  発報の通知（tag=`eew-${key}`）は置き換わらず残り、取消の通知と並ぶ）
- VOICEVOX 読み上げ（伝える取消のみ。二重鳴り防止）
- リアルタイムタブへの移動（伝える取消のみ）
- カードに「誤報として取り消されました」表示（10 秒間）

`useLiveEventHandler.ts` の EEW 分岐で「`event.expired` フラグの有無」で自動解除と誤報取消を区別する。
**伝える取消**は次の 2 つ:

- **画面に表示中の EEW を取り消す通常経路**（`hadKey=true`。このセッションで `activeEEWLevelsRef` に登録されていた eventId）
- **取消の前に画面から消えた（自動解除された）EEW へ、消えてから 15 分以内に届いた取消**（2026-10-21 ユーザー承認「直す (Recommended)」）。
  消える直前の報に取消を載せて 10 秒だけ画面へ戻す。標準版の P2PQuake の取消も含む（2026-10-22 ユーザー承認「効かせる (Recommended)」）。
  自動解除と同じ処理の回に並んだ取消も含む（2026-10-22 ユーザー承認「直す (Recommended)」）

**それ以外の取消**（記憶に無い地震の取消・同じ取消の 2 通目）は通知だけを出し、タブは動かさない（2026-10-21 ユーザー承認「直す (Recommended)」）。

**消えた後の取消の仕組み。** 入口（`useEarthquakes`）が消えた地震の記憶（`eewEndedRef`・`utils/eew.ts` の `EndedEew`）と照らして
決める（`isLateEewCancel`）。記憶は消える直前の報と第 1 報の発表時刻を持ち、読み上げ側へは第 1 報の時刻と震央地名を
`LiveEventMeta.eewLateCancel` に載せて渡す（読み上げ側の追跡は自動解除で捨ててあるため）。覚えておく窓は `ACTIVE_EEW_WINDOW_MS`。
伝えたら記憶に取消を載せるので、同じ取消が別の経路から重ねて届いても 2 度は伝えない。自動解除は入口で受けた時点で記憶を書く
—— 状態の反映を待つと、同じ回に続けて届いた取消が、画面に出ている地震の取消にも消えた地震の取消にも当たらない。

**取消しの理由（`Body/Text`）を読む**（`EEWAlert.cancelText`）。取消電文は `Body` に `Text` しか
持たず、そこに気象庁が書いた取り消しの概要が入る。**地震情報・津波情報とまったく同じ構造**なので
3 種別で扱いを揃える —— 片方だけ拾うと、同じ事象なのに種別によって理由が出たり出なかったりする。
**リアルタイムタブの EEW カードの取消オーバーレイ**に定型文の下へ添え、読み上げも定型文の後ろに
続ける。長い本文は読み上げを切って画面へ委ねる（[audio-tts-spec.md](audio-tts-spec.md) §4）。
`activeEEWs` の更新は表示中の EEW を土台にするので、**取消電文だけが持つ項目は名指しで移すこと**
（落とし穴の詳細は [quake-spec.md](quake-spec.md) §8「取消しの理由は電文にしかない」）。

**取消の表示は、カードのうち見えている範囲の真ん中に置く。** 到達予測の区域が多いカードは、スマホのタブの枠
（縦にスクロールする祖先。`App.tsx` の `TAB_SCROLLER_CLASS`）より高くなる。文字をカードの縦の真ん中に固定すると、
カードの頭を見ている間ずっと「取消」が枠の外にある。

- 取消の幕（カード全体を覆う半透明の黒）の中の文字の塊（「取消」・定型文・理由）は、ふだん幕の縦の真ん中にある。
  `useCancelOverlayPlacement`（`components/RealtimeTab/index.tsx`）が枠のスクロールと、枠・カード・塊の寸法の変化を見張り、
  カードと枠の重なり（見えている範囲）の真ん中へ `transform` でずらす。決め方は `utils/cancelBlockOffset.ts`
- 見えている範囲が塊より狭いときは、塊の上端を見えている範囲の上端に合わせる（真ん中に合わせると先頭の「取消」が
  枠の外へ出る）。どの場合も塊はカードの外へは出さないので、カードがほぼ枠の外へ出ると塊も一部が切れる
- カードが枠の外にあって見えている範囲が無いとき、枠の高さが 0（パネルを畳んでいる）のときは位置を変えず、
  見えた・開いた時点で置き直す。見張りを持たない環境では何もせず、塊は幕の縦の真ん中のまま
- 塊の高さには上限を付ける（枠の高さから上下 8px ずつ引いた高さ。`CANCEL_BLOCK_VIEW_MARGIN_PX`）。枠の高さは
  `useCancelOverlayPlacement` が CSS 変数 `--cancel-view-h` で幕へ渡す。超えたぶんは理由の文が縮み、その中でスクロールする
- **取消が届いたら、そのカードを枠へ寄せる**（読み上げが無効でも）。複数のカードがあれば、寄せるのは取消がいちばん
  新しいカードだけ。寄せ方は地震カードと同じ
  （→ [audio-tts-spec.md](audio-tts-spec.md) §6「読み上げに合わせて緊急地震速報のカードを示す」）

理由:

- **ずらすのは `transform` で行う。** レイアウトを変えないので、寸法の見張りが自分の書き込みでまた呼ばれることがない。
  スクロールのたびの計算は 1 コマに 1 回へまとめる（`requestAnimationFrame`）
- **`position: sticky` を使わない。** `sticky` は枠の真ん中か枠の端のどちらかにしか合わせられず、短いカードを枠の外へ
  ずらしたときに見えている範囲の真ん中へ置けない。そのかわり JS で動かすので、スマホでは 1 コマ遅れて揺れて見えることがある

承認（2026-10-23）: 次の 3 つは、Claude の問いへのユーザーの答えで決めた。

- 「見えている範囲の真ん中」に置く —— 原文「取消は表示されている領域の真ん中に置くのは難しいですかね。上に固定しちゃうとスクロールしているときに見えなくなると思います。」
- 取消で寄せるのはいちばん新しいカードだけにすることと、短いカードを枠の外へずらしたときにも「取消」が隠れないようにすること ——
  問い「1. 取消で寄せるのは取消がいちばん新しいカード 1 枚だけでいいか」「2. 枠に収まるカードで、寄せた後にスクロールして
  半分ほど枠の外へ出すと『取消』が隠れることがある。許容でいいか」への答え。原文「1はいいですけど2は対応したいです。これって隠れたら寄せ始めるじゃだめなの」
- `sticky` をやめて JS で見えている範囲の真ん中へずらす —— 原文「それでお願いします」

**取消電文は予想も震源も持たない**: DMDATA の取消電文は `Earthquake` 要素を持たないので、`dmdataParser` は
震央地名を空・震源座標を位置不明のセンチネル（`-200`）・深さを `-1`・規模を `NaN`・発生時刻と発現時刻を空にし、
`forecastMaxScale` / `forecastMaxLpgmClass` を入れない。区域も空。表示側は `activeEEWs` の直前の確定状態を保つため
取消電文の中身を使わない。設定タブの取消・予想震度なしのテストは**実電文の取消をそのまま流す**ので、
この形がそのまま届く（→ [`settings-pwa-spec.md`](settings-pwa-spec.md) §7）。

**ブラウザ通知の本文は、その地震が最後に名乗った震央地名を使う**（`useLiveEventHandler.ts` の
`eewLastHypocenterNameRef`・`utils/eew.ts` の `rememberEewHypocenterName` / `eewCancelNotificationBody`）。
取消電文自身は名前を持たないので、取消でない報を受けるたびに地震ごとの名前を覚えておき、取消のときにそれを引く。
自動解除で地震の記録を捨てた後に遅れて取消が届いても引けるよう、この記憶は解除では捨てない。捨てるのはリプレイの開始・停止
（全部）と、64 件を超えたとき（古いものから）だけ。画面に出ていた地震なのに名前を引けなかったときは警告を 1 行残す
（名前の無い報だけだった地震でも出るが、記憶の鍵がずれた・記憶が消えたときも同じ形になり、名前抜きの文だけでは見分けが付かないため）。
引けなければ名前を抜いて「緊急地震速報は取り消されました」とする（2026-10-14 ユーザー承認、選択
「緊急地震速報は取り消されました」）。

## 9. 音・タブ切替・通知の連動

`useLiveEventHandler.ts` の EEW 分岐が主。以下を発火する:

- **音**: `selectEEWSoundType(isNew, levelUpgraded, currentLevel, isFinal)` で種別決定 →
  `playAlertSound(type)`。種別: `eewSpecial` / `eew` / `eewForecast` / `eewUpdate` / `eewFinal` / `eewCancel`。
  **別の経路から届いた同じ報（§3）では鳴らさず、続報のタブ要求も出さない**（`LiveEventMeta.eewSameReport`）
- **通知**: `showBrowserNotification(...)` で OS 通知。本文は「石川県能登地方 最大震度5弱予想 長周期地震動階級2予想」の形で、
  階級はカード・読み上げと同じ判定（`canPresentLpgmClass`）を通ったときだけ添える（`utils/eew.ts` の `eewNotificationBody`）
  - **出す条件**: 新規発報・区分の格上げ、または**予想最大震度・長周期地震動階級が基準より上がった続報**（同じタグ `eew-${key}` で
    出し直し、ブラウザが前の通知を置き換える）。上がったかは読み上げと同じ物差しで見る —— 「程度以上」が付けば上がった扱い
    （`raisesNotifiedForecast`。2026-10-21 ユーザー承認「直す (Recommended)」）
  - **基準の進め方**: その地震で受けた報の予想の最大。通知を出さなかった報でも進め、下がった続報では下げない。起動時に復元した
    速報（通知しない）は戻した報の値を基準にし、ライブの報で上がったら通知を出す（2026-10-22 ユーザー承認「上がったら出す (Recommended)」）。
    張り直しでライブで見ていた地震の切れていた間の報を戻したときは、基準を上げるだけで通知は出さない。切れていた間に
    特別警報になっていた報なら、震度の基準を 6 弱（特別警報の線）まで引き上げる
- **読み上げ**: `speakWithVoicevox(eewAlertToText(...))`
- **自動タブ切替**: 新規・レベルアップ・誤報取消は最上位の優先度で realtime を確保し、続報は
  それより 1 段低い優先度で要求する。**新規・レベルアップ・誤報取消が確保している 15 秒間は、
  地震情報・長周期地震動情報・津波がタブを奪えない。続報が確保している間は、読み上げが無効な
  端末では電文の受信に越えられる**（優先順位の全体像は [`audio-tts-spec.md`](audio-tts-spec.md)
  §6「自動タブ切替の優先順位」）。続報は手動選択より弱いため、ユーザーが自分で別タブを選んだ
  直後は realtime へ戻らない。ただし新規・レベルアップは手動選択より強く、必ず realtime を
  取り戻す。EEW のレベル（特別警報級か否か）はタブの奪い合いに関与しない
- **カメラフィット**: `FitToEEWGL` が発火。第一報は S 波円（円が無ければ震源）へ寄り、以降は
  予想の区域塗りまで含めた範囲を追う。追従の主な起点は EEW 電文と予報円の更新で、区域塗りの範囲
  （`useEewLayerData` の `eewFitPositions`）は発報中の追従にのみ加わる。kyoshin モード限定。
  詳細・モード限定の理由は [`map-rendering-spec.md`](map-rendering-spec.md) §6（後段「既知の限界（MAP-5）」）参照

**音種別の優先順位**（`selectEEWSoundType` の判定順）:
1. **新規発報またはレベル格上げ**（`isNew || levelUpgraded`）→ `currentLevel` に応じて
   `eewSpecial`（特別警報）／`eew`（警報）／`eewForecast`（予報）。**`isFinal` より優先**するため、
   最終報で震度・長周期階級が上がって levelUpgraded=true になる最重要ケースでも警戒音を鳴らす。
2. **続報の最終報**（`!isNew && !levelUpgraded && isFinal`）→ `eewFinal`（穏やかな終了音）
3. **通常続報**（上記のいずれでもない）→ `eewUpdate`

> **かつてここに「`useLiveEventHandler.ts` 内の 5 箇所の setTimeout が未追跡」と書いていたが、
> 2026-09-20 に数え直して解消を確かめた。** 状態を跨いで生き続ける予約はすべて ref で追跡し、
> アンマウント時とリプレイ切替時の両方で `clearTimeout` している
> （→ [`audio-tts-spec.md`](audio-tts-spec.md) §6「解消済み」）。

## 10. `activeEEWs` の状態遷移

```
[受信]              [handleEvent]                     [状態]
  ├─ 新規 EEW      →  activeEEWs.set(key, eew)      →  active
  ├─ 続報          →  前の報と統合して set          →  active（経路が運ばない欄は保つ）
  ├─ 古い報        →  何もしない（台帳で棄却）      →  active（現状維持）
  │                    ※ 遅れて届いた P2PQuake の報は区域・仮定震源の別（と、読めていない規模）だけを補う（§3）
  ├─ 誤報取消      →  cancelledAt セット・10 秒後 purge
  └─ 自動解除      →  時刻到達で activeEEWs.delete(key)（無音）
```

### 古い報で退行させない

**続報は前の報を土台に上書きするため、順序が入れ替わると内容が古い側へ戻る。** 受理した報より古い報は
適用しない。

**古いかどうかの比べ方は経路で変わる。**

- **同じ経路の中では報番号で比べる。** 同じ秒に複数の報が届くので、秒までの発表時刻だけでは足りない
- **経路をまたぐと発表時刻（秒）で比べる。** 報番号の数え方が経路で違う。2026-10-16 の千島列島の報で
  Yahoo と P2PQuake を突き合わせると、同じ報が P2PQuake では 1・2、Yahoo では 17・19 と番号付けされていた
  （P2PQuake は警報だけの番号、Yahoo は予報も含めた通し番号）。一方で発表時刻は秒まで一致した。
  かつて経路をまたいで報番号を比べていたため、Yahoo が先に出ていると P2PQuake の報を毎回「古い」として
  捨てていた
- P2PQuake と Yahoo の時刻は入口で `+09:00` つきの ISO の形へ直してある（→ [data-sources-spec.md](data-sources-spec.md) §3）。比べるときはミリ秒を落とす（`eewIssueTimeMs`。直せずに時間帯を持たない表記のまま来た値は日本時間として読む）

順序が入れ替わりうるのは、EEW が**同じ秒に複数の報を出す**ため（能登本震の実配信では 46 報中
13 報が同一秒）。キューは電文の時刻でしか並べ替えず（`enqueueEvent`）、その時刻は秒精度しかない。
加えて WebSocket の受信は body の展開（gunzip）を待たずに次へ進むため、同じ秒に届いた報は展開の
完了順で処理されうる。

判定で守ること。

- **入口（`handleEvent` の先頭）で捨てる。** 読み上げ・ウィンドウタイトルへの通知と自動解除の予約は
  状態更新の外で走るため、状態更新の直前で弾いても間に合わない。**地図・カードだけが新しい報を保ち、
  読み上げとタイトルが古い報で上書きされる**——揃って退行するより始末が悪い。**ただし捨てる報が運んできた
  特別警報の印（`everSpecialWarning`）だけは、捨てる前に表示中の速報へ移す**（§2「起動時に、発表中のものを復元する」）
- **入口の判定は「受理した報の台帳」で行う（表示中の状態を見ない）。** 台帳（`EewAcceptance`）は 4 つを持つ。
  経路ごとの最大の報番号（`serialByOrigin`。同じ経路の新旧）、経路をまたいだ最新の発表時刻（`latestIssueMs`。
  経路をまたいだ新旧）、音を出した報の発表時刻（`notifiedIssueMs`。§3 の「同じ報の 2 通目」の判定）、
  受理した回数（`receipts`。§7 の見張りの解除）。キューのディスパッチャは
  1 ティックの中で `handleEvent` を連続で呼び、その間 React の状態はレンダー待ちで進まない。状態を
  見ると直前に受理した報を見落として素通しする。表示が終わった EEW の分は掃除する（残すと伸び続ける）
- **状態更新側にも判定を置く。** ただし比べる相手は違い、こちらは表示中の値（`isOlderEewReport`）。
  状態の整合性を守る二重化で、通知の保護は台帳が担う
- **報番号・発表時刻が読めない報では、その比べ方を使わない。** 読めない側を 0 とみなすと正しい報まで
  捨てる。数値化は `eewSerial`・`eewIssueTimeMs`（`utils/eew.ts`）に委ねる。P2PQuake の公式の
  API 定義では `issue.serial` は必須の欄（欠けた報を見た記録は無いが、数えてはいない）
- **同じ報番号の再送は棄却しない。** 訂正報も同じ番号で届きうるため、内容の異同にかかわらず通す
- **取消・失効・テスト報は判定を通さない。** ここで弾くと誤報を消せなくなる
- **取消は終端として扱う。** 取消済みのエントリ（`cancelledAt` を持つもの）へ非取消の報が届いたら、
  報番号によらず無視する。**報番号では守れない**——取消電文は台帳を進めず（上記のとおり判定を
  通さないため）、状態側も取消前の報番号を保ったまま `cancelledAt` を足すだけなので、**同じ報番号の
  非取消報は「古い報」の判定をすり抜ける**。すり抜けた報は `cancelledAt` を失った状態で上書きし、
  取消の表示が消えるうえに 10 秒後の purge も空振りする（purge は `cancelledAt` の有無で判定する）。
  起動時の復元が取消の直前に発表された報を拾ったとき（一覧 API が取消を反映するまでの遅れ）と、
  ライブで到着順が入れ替わったときに起きる
- **統合の土台は同じティックの写し（`eewLatestRef`）を先に、無ければ表示中の状態を引く。** キューは 1 ティックに
  複数の報を捌き、状態はレンダー待ちで進まないので、状態だけを土台にすると直前に統合した報を見落とす。写しは
  統合のたびに書き、失効・テストの報で消し、表示から消えた速報の掃除とリプレイ開始のリセットで空にする
- **取消の終端は入口でも止める**（同じティックの写し `eewLatestRef` にも取消を載せる）。状態側だけで止めると、
  画面は動かないのに音・通知が鳴り、見張りの解除（§7）も積まれる
- **画面から消えた地震の報も、入口で弾く**（2026-10-21 ユーザー承認「おすすめで」）。台帳と写しは速報が画面から消えた時点で
  捨てるので、消えた後に同じ報・古い報が届くと上の比べ方では「新しい報」に見え、終わった速報が音と読み上げごと戻る。
  例: 標準版の Yahoo は、一覧から 2 回続けて欠けた項目が戻ると同じ報を出し直す（`diffHypoInfoEvents`）。取消の表示（10 秒）が
  消えた後に届いた報も同じ形になる。そこで、台帳にも画面にも無い地震の報は、§2「取り直しの最中に画面から消えた地震は戻さない」の
  記憶（`eewEndedRef`・15 分）と同じ照らし方で弾く（取消で消えた地震の扱いも同じ）。弾いた報は `log.info`（接頭辞 `[eew]`）と
  電文の記録の `notApplied` に残す（上の「捨てたことを記録する」の `log.debug` は、台帳と比べて古い報を捨てたときのもの）
- **自動解除の時刻を過ぎて届いた報も、入口で弾く**（2026-10-21 ユーザー承認「おすすめで」）。ライブの受信の入口（`handleEvent`）で、
  台帳にも画面にも無い地震の報が、その報自身の自動解除の時刻（§7 の `calcEEWCancelTime`。発表時刻から数える）を既に過ぎていれば採らない。
  標準版の Yahoo は、終わった速報の最終報を一覧に 150〜180 秒残す（2026-10-21 に 2 地震で実測）。一覧を前回との差分で見る処理
  （`diffHypoInfoEvents`）は、起動時とリプレイの開始・終了で作り直されて前に見た項目を忘れるので、その直後に残っている最終報が
  新しい項目として届く。上の「画面から消えた地震」の記憶もリセットで捨てるので、ここでは止まらない。最終報の自動解除は発表から 60 秒以上先
  （§7）で、一覧に残る 150〜180 秒より短いことが多く、止めないと音と読み上げが鳴ってから自動解除ですぐ消える。
  - **弾かない場合**:
    - 時計を信じられないとき（リプレイ中でなく、起動から一度もサーバー時刻で較正していない。`isServerClockTrusted`）。ずれた端末の時計で
      本物の報を捨てないため。**このため起動直後の較正前に届いた最終報は、従来どおり鳴ってから消える**
    - 発表時刻が読めない報（解除の時刻が震源時刻だけで決まり、発表から 60 秒の下限が外れるため）
    - `silent` で音を出さずに積まれた報（起動時・張り直しの復元とリプレイの初期状態）。古さは取得側の `selectActiveEews` が判定している。
      ここで落とすと、復元した側は読み上げの記憶とタブ移動を「戻した」つもりで進め、画面だけが空になる
    - 画面に出ている地震の報（最終報か取消で終わる）
  - **規模の大きい地震の出し直しは止まらない。** 自動解除の時刻は規模・深さで延び、最終報から 3 分を超えることがある。そのときは
    一覧に残る 150〜180 秒のあいだ解除の時刻を過ぎていないので、出し直された最終報は採られ、音と読み上げが鳴る（解除の前なので
    表示としては誤りではない）
  - 弾いた報の記録は直前の項と同じ（`log.info` の `[eew]` と電文の記録の `notApplied`）。時計を信じられずに採った報は `log.debug` に残す
- **捨てたことを記録する。** 判定が誤り続けるとその EEW は以降更新されない。痕跡が無いと原因に
  辿り着けないため入口で `log.debug` に残す


**この判定が守らない範囲。**

- ~~取消のあとに来る非取消報~~ は、上記「取消は終端として扱う」で手当てした（報番号を見ずに弾く）
- **同じ秒に別の経路から別の報が届く形**は見分けられない（発表時刻が同じなので「同じ報」として扱う）。
  P2PQuake は警報の報しか運ばないので、起こるのは Yahoo の予報と P2PQuake の警報が同じ秒に出たときに
  限られる。区分か予想の最大震度が上がる場合は音を止めない（§3）
- **報番号を持たない報を挟んだ直後は精度が落ちる。** その報で内容が進んでも台帳は前の値のままなので、
  次に来る報を古い台帳と比べることになる（DMDATA 経路は `serial` が常に埋まるため、起こるとすれば
  P2PQuake 経路に限られる）

キーは `eew.issue?.eventId ?? eew.id` を統一パターンで使う。**地図の震源×印の差分更新キー
（`EewEpicenter.id`）も同じ式を使う。** `eew.id` は報番号込み（DMDATA は
`dmdata-eew-<eventId>-<serial>`・P2PQuake は報ごとに変わるレコード ID）なので、これを直接キーに
すると続報ごとにマーカーを作り直し、点滅が止まってポップアップも閉じる
（理由と対策は [`map-rendering-spec.md`](map-rendering-spec.md) §10）。

`issue.eventId` は DMDATA・P2PQuake のどちらの経路も持つ。Yahoo 強震モニタの hypoInfo 経路
（standard 版の補完）も持ち、`id` 自体にも報番号を含まない。**つまりフォールバックの `?? eew.id` は
防御用で、実データでは通らない。**

# 場面ごとの確かめ方

`CLAUDE.md`「検証」から引く、特定の場面だけで使う確かめ方。いつ開くかは `CLAUDE.md`「場面ごとの確かめ方」に書いてある。文中の「CLAUDE.md「…」」はリポジトリ直下の `CLAUDE.md` の節を指す。

## 常時表示用の端末で性能を確かめる（ユーザーが指示したとき）

**ユーザーが指示したときは、リリースの前に、ビルドしている PC で本番ビルドのサーバーを立て、アプリを常時表示している端末（以下「常時表示用の端末」。2026-10-10 時点では Surface Go 2）から開いて性能を確かめる**（2026-10-10 ユーザー指示。**指示されたときだけ行い、毎回の手順にはしない**）。開発機の Playwright で軽く見えても、常時表示用の端末では違うことがある —— GPU も CPU も開発機よりずっと遅く、自作地震計を繋いでいれば親の描き直しの回数も違う。

**指示の本体は「リリース前にこの PC でサーバーを立て、端末で表示して性能を確かめる」**まで。下の手順 0〜4（修正前との比べ方・ブラウザの再起動・測る指標）は、それを正しく測るために 2026-10-10 の作業で組んだもの。結果をコミットメッセージに残すので、**実装セッションでコミットの前に**行う。

0. **端末のブラウザを丸ごと再起動する。** Edge は起動ブーストで裏に常駐し、アプリのウィンドウを閉じても本体が残る（更新も当たらない）。再起動を挟まないと、修正の前後ではなくブラウザの状態を比べることになる
1. **公開版（端末で普段表示しているもの）の設定の窓で「設定の書き出し」をしておく**（API キーは含まれない）。終わったら公開版は閉じる（負荷が混ざるため）
2. **修正前と修正後を同じ経路で立てる。** 修正前は `main` から計測用のワークツリーを切る（`worktree/chore/<name>`。測り終えたら、[`worktree-operations.md`](worktree-operations.md)「ワークツリーを消す前に、ジャンクションを外す」のコマンドでワークツリーを消してから `git branch -d` で片付ける）。新しく切ったワークツリーには `node_modules` が無いので `npm ci` してから、両方のワークツリーでそれぞれ `npm run build` → `npm run preview -- --host` を `run_in_background: true` で起動する（ポートが重なるので順に立てるか、片方に `--port` を付ける。実際の URL は起動ログの `Network:` 行で確かめる。起動したサーバーを控え、終わったら止めるのは CLAUDE.md「検証」の dev サーバーの規約どおり）。**preview には API キーが自動では入らない**（自動投入は dev サーバーだけの機能）ので、端末側で設定の窓から入れる
3. 端末で `http://<ビルドしている PC の LAN の IP>:<ポート>/` を開き、1 のファイルを「設定の読み込み」で入れ、API キーを入れる（オリジンごとに設定は別に保存される）。修正前と修正後で、開き方（ウィンドウの大きさ・タブ）も揃える
4. **測る指標**: Windows の性能カウンタで、ブラウザのプロセスの `\GPU Engine(*engtype_3D)\Utilization Percentage` をプロセスごとに合計したものと、`\Processor Information(_Total)\% Processor Utility`（端末全体の CPU）。開いて 30 秒ほど落ち着かせてから、5 秒間隔で 60〜120 秒の平均を取る。修正前と修正後で測る長さを揃え、結果（値・平均した長さ・測定を繰り返した回数）はコミットメッセージに残す。1 回きりの値は、ぶれの大きさが分からないことも書き添える

**基準を公開版で代えると、条件が 2 つ混ざる。** 公開版は `https://` で Service Worker が働くが、LAN の `http://` は安全な接続ではないので Service Worker が登録されない。安全な接続でないページでは `crypto.subtle` も使えないので、到達予想キーの検証も働かない。手間を省いて公開版と比べたなら、この違いを結果に書き添えること。

**`scripts/perf/` の計測（dev サーバー ＋ `/__perf-script`）とは用途が違う。** あちらは開発用ビルドで描画負荷の内訳を証跡として残すためのもの（`apply: 'serve'` なので本番ビルドには載らない）。こちらは本番ビルドを常時表示の状態で動かしたときの常駐の負荷を見る。端末への入り方（SSH 等）は端末ごとの事情なので、その端末を扱うセッションのメモリに置く。

> 2026-10-10: 常時表示用の端末の発熱を調べ、津波の海岸線の点滅（毎フレーム描き直していた）を直して、開発機で描き直しが大きく減ったことを確かめてからリリースした（数値は `docs/spec/map-rendering-spec.md` §9「点滅の駆動」）。端末の GPU 使用率は下がらなかったが、このときは朝から常駐していた Edge のままで、全プロセスを止めて開き直すと同じアプリで 58% → 8.5% に下がった —— **点滅の修正の前後ではなく、ブラウザの状態を比べていた**。点滅の修正が端末でどれだけ効いたかは測れていない。その後に端末の上で直接測って見つけたヒートマップの空データの流し込み（→ [`docs/spec/map-rendering-spec.md`](../../docs/spec/map-rendering-spec.md) §9「setData churn 対策」）は、ブラウザを再起動したうえで、同じページの中で流し込みだけを止めて比べた。修正版と公開版の比較もしたが、こちらは上記の 2 条件が混ざっている。

## 自作地震計の「途絶」をブラウザで作る

**押し出しの本文だけを捨て、繋ぎは開いたままにする。** これが**「繋がっているのにその観測点だけが沈黙する」形を再現する唯一の入口**で、実機を止めずに作れる（→ [`data-sources-spec.md`](../../docs/spec/data-sources-spec.md) §4.5「途絶えたら行を残し、値だけ落とす」）。

**効かない手が 2 つある。** どちらも試して外した（2026-10-01）。

- **`setOffline(true)`** —— 効くのは新しいリクエストだけで、**既に開いている押し出しは流れ続ける**（9 秒待っても行は白いまま）
- **`EventSource` の差し替え** —— 押し出しは `fetch` ＋ `ReadableStream` で受けている（`services/seismoStream.ts` が `EventSource` を使わない理由は同節）

**実際に動いたコード**（Playwright の `addInitScript` へ入れる。`window.__cutSeismo` を立てると本文だけが落ち始める）:

```js
window.__cutSeismo = false
const orig = window.fetch
window.fetch = async (input, init) => {
  const url = typeof input === 'string' ? input : input instanceof Request ? input.url : String(input)
  const res = await orig(input, init)
  if (!url.includes('50506') || res.body === null) return res
  const reader = res.body.getReader()
  const gated = new ReadableStream({
    async pull(controller) {
      for (;;) {
        const { done, value } = await reader.read()
        if (done) { controller.close(); return }
        if (window.__cutSeismo) continue   // 中身だけ捨てる。閉じない
        controller.enqueue(value)
        return
      }
    },
    cancel(r) { reader.cancel(r) },
  })
  return new Response(gated, { status: res.status, statusText: res.statusText, headers: res.headers })
}
```

**波形の濃さは画素で測る**（見た目では判らない）。`getImageData` の α の平均 —— 実測で **214.1 → 149.8**。**描いた画素数も併せて見ること**（6229 → 6201 とほぼ同じなら、線の形は保ったまま濃さだけが落ちている）。最大 α が残るのは P/S の到達線が `globalAlpha` の外で描かれるため（線の位置は事実なので薄くしない）。

## 広い範囲の揺れ検知はリプレイで作る

**揺れ検知（`useKyoshinDetectorV2`）が絡む画面・カメラの寄せ・自動タブ切替は、リプレイで大地震の直後を指定して確かめる。** 検知エンジンが実データを処理し、数十秒で数百点規模の検知が自然にできる。合成のテストボタンでは、検知点が広い範囲に散った状態を作れない。

- **API キーが無くても動く**。中継に繋がらないときは電文の取得に失敗した旨が赤字で出るが、強震モニタの再生は続く（→ [`docs/spec/settings-pwa-spec.md`](../../docs/spec/settings-pwa-spec.md) §6「アーカイブの取得に失敗しても強震モニタの再生は続ける」）
- **開始時刻の入力（`datetime-local`）は Playwright の `fill` で入れる。** React が管理しているので、`el.value = x` と `dispatchEvent` では `onChange` が発火しないことがある
- **設定の窓は操作が無いと既定のタブへ戻る**（`idleRevertSec`。既定値は [`src/hooks/useSettings.ts`](../../src/hooks/useSettings.ts) の `DEFAULTS`）。EEW を含む場面では自動タブ切替でリアルタイムタブからも離れるので、カードの DOM を読むたびに戻す
- **検知の中身は `window.__kyoshinV2.detections`** で読める。`memberKeys`（参加した点。一度入った点は外れない）・`confidence`（`likely` か `confirmed`）・`sources`（支えた部分）を見る。地図に描いた点を数えるときは `querySourceFeatures` を使わない —— タイルの境目で重複する（ソースの中身の取り出し方は [`docs/spec/settings-pwa-spec.md`](../../docs/spec/settings-pwa-spec.md) §7「DOM 検証テクニック（動作確認用）」）
- **実データでは出ない稀な分岐**（例: 全メンバーが震度0未満へ落ちたときの文言）は、条件を一時的に反転させて表示だけ確かめる。確かめたら戻し、`git diff` に痕跡が残っていないことを見る

## 津波の観測情報を再生で確かめる

**観測点つきの津波の報は、テストボタンでも流せる。** 大津波警報テストが観測状態の組み合わせを一通り持ち、変化の小さい続報テスト・津波情報の取消テストが続報での更新と取消を流す（どのボタンで何が通るかは [`docs/spec/settings-pwa-spec.md`](../../docs/spec/settings-pwa-spec.md) §7 の表。変化の小さい続報テストは表に無く、同じ §7 の「自動解除・自動確定のタイミング」にある）。**実電文をパーサーへ通した観測情報と、実際に届く間隔は、再生でしか見られない**（CLAUDE.md「収録していない形の読み取りはリプレイで確かめる」）。

- **待ち時間を先に見積もる。** 津波観測情報は地震の電文よりずっと間隔が空き、窓によっては 30 分近く 1 報も来ない（実測は同 §6「再生中の電文の届き方と「更新」の表示」）。見積もりを誤ると 1 時間の待ちを捨てる
- **再生中にソースを編集しない。** dev サーバーがページを丸ごと読み込み直して、再生が消える。コードの変更をすべて終えてから、通しで 1 回だけ再生する（1 時間の再生を捨てた例がある）
- 進み具合は地図左上の「更新」で読まない（再生時計ではない。同 §6）

## 本物の VOICEVOX で確かめるときの話者

**本物の VOICEVOX で確かめるときの話者は、四国めたん（ツンツン）に固定する**（2026-08-21 ユーザー指示）。声が変わると、読み上げの長さや間を回ごとに比べられない。同じ話者でもスタイルごとに ID が違うので、`/speakers` で引いて選ぶ（2026-08-21 時点では 6）。

## VOICEVOX を立てずに読み上げのタイミングを確かめる

**音の鳴り方に関わる不具合は、型チェックとユニットテストが通っても実機で崩れることが多い。** 本物の Web Audio（先読みの予定・`stop()` の効き方・`ended` の発火）を通さないと確認にならない。VOICEVOX が無い環境では、VOICEVOX の API と同じ口に応える偽のサーバー（以下「偽サーバー」）を Node で立てて確かめる。**リポジトリに偽サーバーの実体は無い**ので、その都度スクラッチパッドに書く。

- **応える口と返すもの**（アプリが読むのはこれだけ。呼び出し側は [`src/utils/voicevox.ts`](../../src/utils/voicevox.ts)）。ポートは 50021、CORS はすべて許す

  | 口 | 返すもの |
  |---|---|
  | `GET /version` | 200 なら何でもよい（設定の窓の接続確認は `res.ok` だけを見る） |
  | `GET /speakers` | `[{ name, speaker_uuid, styles: [{ name, id }] }]` の配列 |
  | `POST /audio_query?text&speaker` | `{ accent_phrases: [...] }`。句は `{ moras: [{ vowel: 'a', vowel_length: 0.1 }], pause_mora: null }` の形でよい |
  | `POST /accent_phrases?text&speaker&is_kana=true` | 句の配列（上と同じ形） |
  | `POST /mora_data?speaker` | 受け取った句の配列をそのまま返す |
  | `POST /synthesis?speaker` | 正弦波の WAV（`audio/wav`） |

- **合成の応答の遅れと音の長さを、偽サーバーの環境変数で決められるようにしておく**（名前は自分で決める。アプリ側に対応する設定は無い）。「合成を待っている間」「鳴っている間」を人為的に長くすれば、実地震を待たずに競合を再現できる。たとえば設定の窓の緊急地震速報の行の「誤報取消テスト」（津波の行にも同じ名前のボタンがある）は、最後に押してから 10 秒後に取消を届ける（台本の `EEW_FINAL_SILENCE_MS`。[`src/utils/testTelegramScripts.ts`](../../src/utils/testTelegramScripts.ts)）ので、偽サーバーの音を 4 秒にすれば発話の途中に取消を差し込める。予報から警報への格上げは「地震動予報（単独点処理）」テストで作れる（10 秒以内に押し直す。押さなくても最終報で格上げが起きる）
- **50021 番が埋まっていたら、別のポートで立てる。** 設定の `voicevoxUrl` をそちらへ向ける（`localStorage` の `quake-viewer-settings` を書き換えてリロード）。終わったらポートを空け、本物の VOICEVOX に戻せるようにしておく
- **`soundVolume` は 0 にせず、0.02 程度にする。** 0 でも再生の長さは同じだが、無音と失敗の見分けが付かなくなる
- **偽サーバーには最初からアクセスログを入れる。** `/audio_query` と `/synthesis` に経過秒とテキストを出しておけば、どの読み上げが何秒待たされたかを後から突き合わせられる。ただし待ちの実測は、アプリ側のログ（`[VoiceVox] 読み上げ:` と `[VoiceVox] 先行合成:`）のほうが確か —— 先に合成した分と本番の再生を区別できる

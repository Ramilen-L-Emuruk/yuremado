# 強震モニタ揺れ検知 V3 設計書（近傍一致・PLUM 型）

> **いまの検知器は §43 の組み合わせの検知器**（`kyoshinEnsembleDetector.ts`）。§1〜§42 の検知コア（`kyoshinDetector.ts`・
> `step()`・`PARAMS`・`faint`/`weak` の段など）の記述は入れ替える前のエンジンの経緯で、その識別子はもうコードに無い。
> 音・自動タブ切替・カメラ追従・別地点の発報・地図とカードの表示を扱う節は、組み合わせの検知器の結果を受ける側の話として今も効く
> （仕様書が「設計書§N」で根拠に挙げている節）。

V2（`kyoshinDetector.ts`：波面フィット＋リーキー積分＋逆投影系）を置き換える、**震源非依存の近傍一致検知**の設計。
JMA EEW（PLUM 法・着未着法）と Scratch 前身「リアルタイム地震ビューアー」の検知方式の調査から収束した結論に基づく。

> 関連: V2 設計書 `kyoshin-detection-design.md`。本書は検知コアの全面刷新であり、V2 コアを置換する。
> UI・音・自動タブ切替・自動フィット・地図オーバーレイ（`useKyoshinAlerts` / `deriveKyoshinView` /
> `RealtimeTab` / `KyoshinV2Overlay`）は V2 移行時（commit 3e02a27）のものを**流用**する。

## 1. 背景：なぜ作り替えるか

V2 は「波面フィットで震源を決め、その品質を時間積分して確信度を出す」設計だった。これが次の壁を生んだ:

- **Kanto の壁**: 弱い震度1の実地震（埼玉）と北関東の間欠ノイズが per-cluster 特徴（規模・振幅・連続性）で分離できない。
- **確定レイテンシ**: リーキー積分が S_ON まで登るのに 5〜6 秒。V1 の「2 連続フレーム確定」より遅い。
- **明滅**: クラスタ急成長中に波面フィットが一時破綻（fitOk=false）→ confirmed→weak へ転落→再確定（解除→再検知）。
- **分裂**: 1 地震が震央ジッタ・フィット失敗で複数イベント ID に割れる。
- **warmup**: LTA ベースラインが 60 秒間落ち着かず、コールドスタート直後は confirmed を出せない。

これらに band-aid（fast-confirm・片側拡張・連続性免除・確定ラッチ）を重ねたが、緩めるほど北関東の誤検知が出る堂々巡りになった。

## 2. 調査からの収束（JMA / Scratch 前身）

| | JMA（実物） | Scratch（前身） | V2（旧） |
|---|---|---|---|
| 検知の芯 | **PLUM**＝近傍観測点の実測震度で判定・震源不要 | **最短7点の近傍同時性**・震源不要 | 波面フィット＋積分＋逆投影 |
| ノイズ対策 | 着未着＋振幅分類 | **点別の静的しきい値**（1748点） | オンライン連続性ゲート |
| 震源 | IPF で別立て | EEW から（DM-D.S.S）別立て | 検知と一体化して破綻 |

**結論**: 検知から震源推定を切り離し、「**点別のノイズ床 ＋ 近傍同時性（PLUM 型の面）＋ 地域別の慢性活性ガード**」で検知する。
1 秒・計測震度という入力に最も噛み合い、Kanto の壁（**点別床＋地域活性の二軸**）・分裂（**近傍グラフ連結＋格子 ID**）・warmup（床は静的/長時定数＝LTA 追随不要）を原理から解消する。

## 3. 設計原則

1. **震源非依存**（source-free）: 検知の可否は「面として揺れが在り、近傍が同時に立ち上がったか」で決める。震源・波面フィットは検知に使わない（表示用の任意補助に降格）。
2. **点別の静的しきい値**: 観測点ごとに事前計算したノイズ床を持つ。ノイズの多い点（北関東・都市・火山）は自動的に鈍くなる。オンライン LTA を廃し **warmup を撤廃**。
3. **近傍同時性**: 点の検知は「その点の K 近傍のうち一定数が短時間窓で一緒に立ち上がった」ことを要件にする（PLUM／着未着の思想）。
4. **グループ化は近傍グラフ・格子は ID 専用**: イベントは K 近傍グラフの連結成分で束ねる（セル境界での分裂を避ける）。固定格子は安定 ID の錨としてのみ使う（同一地震が常に同一 ID）。
5. **速い・単純**: 強い per-frame 判別なので長い時間積分は不要。V1 相当（数秒）で確定。可動部を V2 より減らす。
6. **特異度は二軸で守る（単一防御にしない）**: (a) 点別のノイズ床（慢性的に騒がしい点を鈍く）＋ (b) セル別の慢性活性ガード（慢性活性な地域＝北関東等の確定バーを上げる）。北関東ノイズはコヒーレントに多点同時発火し得て近傍同時性(L2)を通過するため、床だけでは守れない。地域軸を独立に持つ（JMA の着未着＋振幅分類に相当する我々版の第2軸）。

## 4. 入力と制約

- 入力: Yahoo リアルタイム震度。約 1725 点・1 Hz・計測震度（`value = -3.0 + index*0.5`。震度0≈0.0）。
- サブ秒精度の到達時刻・P 波は無い。→ 波面フィット／到達時刻総当たりは原理的に不利（V2 で確認済み）。
- 観測点集合は `siteConfigId` で版が変わる。静的メタは**座標キー**（`siteKey(lat,lng)`）で引く。未知点は既定しきいで扱う。
- 純粋関数コア `step(state, frame, meta)` を維持。`meta` は静的（近傍・格子・任意の初期床 JSON）。点別床とセル慢性活性はオンライン学習で `state` 側（永続化対象）。

## 5. アーキテクチャ（層構成）

### L0 静的観測点メタ（オフライン事前計算・`meta`）

`public/data/` に JSON で持ち、初回に一度 fetch（生成データの遅延読込と同方式）。

- **点別しきい値 `siteThreshold[key]`**（計測震度 units）: 各点のノイズ床（ロバストな高分位点。例: 各点 `value` の 99 パーセンタイル）。Scratch の `ten:しきい` に相当。**取得は過剰リクエストを避ける**:
  - Yahoo の 1 リクエスト＝全 ~1725 点の 1 秒ぶん。床推定は点あたり数百〜2千サンプルで足りるので **~1〜2k フレーム（=~1〜2k リクエスト）を疎にサンプルした平常窓**で十分。**密な多日 1Hz 取得（10 万件超）は不要・不可**。この平常窓は検証（§10）で叩く窓と共用できる。
  - **本番はオンライン学習＋永続化が本命**（追加リクエスト 0）: ライブ受信 stream（既に 1 req/s 受信）から**長時定数（時間オーダー）の EWMA**で点別床を推定し localStorage に保存。V2 の LTA（45 秒）は追随が速すぎて慢性ノイズを捉えられなかったが、時間オーダーの時定数なら「その点が慢性的に騒がしい」を捉える。実イベント・群発で床が汚れ鈍化しないよう、床更新は **(i) 検知中の点・(ii) 近傍が同時活性の点で凍結**し、床に上限 `FLOOR_CAP` を設ける（改良4）。
  - コールドスタートは既定床 or 上記の小さな初期 JSON で開始し、稼働中に精緻化（→ warmup とは別。検知自体は初手から可能）。
  - 生成（初期 JSON・任意）: `scripts/build-station-thresholds.mjs`（疎サンプルのみ・スロットル付き）。
- **K 近傍 `neighbors[key]`**: 各点の最近傍 K 点（`R_km` 以内）。Scratch の「最短7点」に相当。
  - **生成は実行時**: `buildStationMeta(sites)` が受信中の実座標（Yahoo `sitelist.json`＝フレーム座標）から
    純粋な幾何計算で組む。近傍はメモリ上の座標から出せるため**追加リクエスト 0**。事前計算 JSON を出荷
    しないことで、`siteConfigId` 版差での `siteKey` ドリフト（JMA `station-coords` と Yahoo sitelist の
    不一致）を構造的に防ぐ。O(点数²) だが観測点集合ごとに一度だけ計算しキャッシュする（フレーム毎ではない）。
- **格子割当 `cellOf[key]`**: 各点が属する固定格子セル（緯度経度の等間隔ビン）。同じく `buildStationMeta` が実行時に算出。
- **セル別慢性活性 `cellActivity[cell]`**（オンライン学習・永続化・追加リクエスト 0）: 各固定格子セルが平常時にどれだけ「確定揺れ点」を出すかの長時定数の率。慢性活性セル（北関東等）で L4 の確定バーを上げる**第2の特異度軸**（§3-6・改良1）。

### L1 点トリガー（per-point, per-frame）

各点 `i` について:
- `level_i = value_i`
- `rate_i` = 直近 `RATE_DT`(2〜3s) での `value` 上昇量（1 フレーム差でなく**窓**で評価し、fetch ジッタ・欠測フレームを吸収。改良6）。
- **トリガー成立**: `level_i ≥ siteThreshold[i] + LEVEL_MARGIN` **かつ** `rate_i ≥ RATE_MIN`
  - level は「その点の床を超えたか」、rate は「今まさに立ち上がったか（オンセット）」。両者で持続ノイズと一過性を分ける。
- 欠測（`missing`）点はトリガー評価から除外し、`value` 履歴は最後の有効値で保持する。
- state: `triggeredAtMs[i]`（最終トリガー時刻）。`now − triggeredAtMs[i] ≤ TRIG_ACTIVE_MS` の間「トリガー継続」とみなす。

### L2 近傍同時性（core discriminator ＝ PLUM／着未着）

各トリガー継続点 `i` について:
- `agree_i` = K 近傍 `neighbors[i]` のうち `now − triggeredAtMs[neighbor] ≤ COINCIDENCE_MS` を満たす数。`avail_i` = `R_km` 以内に実在する近傍数。
- **「確定揺れ点（confirmed-shaking）」**: `agree_i ≥ MIN_NEIGHBORS` **または** `agree_i / max(avail_i,1) ≥ MIN_NEIGHBOR_FRAC`。
  - 実地震は点＋近傍が同時に立ち上がる。孤立・散在ノイズは近傍が揃わず脱落。
  - 疎地域（近傍が R_km 外・少数）は**割合条件**で救済し、離島・過疎網の小地震を取りこぼさない（改良5・§5-A 相当）。
- （Phase 2 任意・着未着精緻化）近傍のうち中心寄りが先に、外側が後にトリガーしている「外向き伝播」の整合を加点。1 秒量子化なので緩い判定に留める。Phase 1 では一致数のみ。

### L3 格子集約とイベント

- **グループ化＝K 近傍グラフの連結成分**（境界の無い方式。セル境界での分裂を避ける・改良3）。確定揺れ点どうしを近傍グラフで連結し、連結成分＝1 イベント。
- **ID 安定化＝固定格子（錨としてのみ）**。各成分に占有格子セル集合／重心セルで**安定 ID** を与え、前フレームとメンバー・セルが重なる成分は ID を継承。→ 分裂・明滅を構造的に防ぐ。
- **セル別慢性活性の更新**: 平常時に各セルが出す確定揺れ点率を長時定数で `cellActivity` に学習（実イベント中の該当セルは凍結）。
- イベント属性: メンバー確定揺れ点、占有セル、`maxIntensity`（メンバー現在 `value` 最大＝PLUM 出力）、初活性時刻、最終活性時刻。

### L4 確信度と発報

- **likely（可能性）**: 確定揺れ点 ≥ `MIN_LIKELY_POINTS`（例 3）**かつ** `maxIntensity ≥ MIN_LIKELY_INTENSITY`（例 震度1）。早期反応（候補音＋タブ）。
- **confirmed（検知）**: 確定揺れ点 ≥ `CONFIRM_POINTS`（例 5〜8・密度正規化＝改良5）**かつ** `maxIntensity ≥ MIN_CONFIRM_INTENSITY`（例 震度1、慢性活性セルは震度2）**かつ** `CONFIRM_FRAMES`（例 2）連続。→ V1 相当の速さで確定（積分待ちなし）。検知音＋タブ＋通知＋観測点フットプリントへ自動フィット。
- **震度ゲート（改良2）**: 低震度（震度0）の同時多発ノイズが点数だけで確定するのを防ぐ。JMA の発報基準（予報=震度3/警報=5弱）に倣った震度しきい。
- **地域活性バー（改良1・第2軸）**: `cellActivity` が高い（慢性活性）セルでは `CONFIRM_POINTS`・`MIN_CONFIRM_INTENSITY` を引き上げる。北関東のコヒーレントノイズが点別床をすり抜けても地域軸で受け止める。地域を名指しせず「慢性活性」で自動的に効く。
- **推定最大震度** = `maxIntensity` を震度階級へ。カード・音レベルに使用（`useKyoshinAlerts` のレベルアップ再鳴に供給）。
- **終了・保持**: セルが非活性化して `HOLD_MS`（例 10 秒）経過で解除（V1 相当の保持）。固定 ID なので明滅しない。
- **特異度＝二軸＋段階ゲート**: (a) 点別床（持続ノイズ）＋(b) セル別慢性活性（地域ノイズ）を独立軸に、L2 近傍同時性（散在排除）・点数集約（単点排除）・震度ゲート（低震度排除）を重ねる。単一防御にしない。

### L5 震源（任意・表示専用）

- 必要なら最早トリガー点近傍の重心を「推定震央（不確実）」として出す。**検知にも自動フィットにも使わない**（自動フィットはメンバー点のフットプリント）。深発・沖合は不確実として明示。

## 6. パラメータ初期値（ハーネスで較正）

| 記号 | 意味 | 初期値 |
|---|---|---|
| `LEVEL_MARGIN` | しきい床への上乗せ（value） | **0.0**（震度0 を含む・§13 参照。旧 0.5） |
| `SUSTAIN_MARGIN` | 継続揺れ判定の床上乗せ（継続点数・保持に使用・§13） | 0.4 |
| `RATE_MIN` | オンセット上昇量（value/RATE_DT） | 0.5 |
| `RATE_DT` | 上昇量の評価間隔 | 2〜3 s |
| `K` | 近傍点数 | **12**（密網での連結の穴を塞ぐ・§17 参照。旧 7） |
| `R_km` | 近傍半径 | 40 km |
| `MIN_CLUSTER` | 揺れクラスタに要する同期 onset 連結成分サイズ（§13。旧 MIN_NEIGHBORS） | 3 |
| `COINCIDENCE_MS` | 同期とみなす時間窓 | 4 s |
| `TRIG_ACTIVE_MS` | トリガー継続窓 | 8 s |
| セル寸法 | 固定格子 | 0.2°（≒ 20 km） |
| `MIN_LIKELY_POINTS` | likely 点数 | 3 |
| `CONFIRM_POINTS` | confirmed 点数（密な網の上限） | 5 |
| `CONFIRM_DENSITY_FRAC` | 確定点数の密度正規化（疎地域救済） | 0.6 |
| `CONFIRM_FRAMES` | confirmed 連続フレーム | 2 |
| `HIGH_CONFIRM_INTENSITY` | 高震度 fast path の震度下限（点数ゲート免除・§20） | 震度3（value 2.5） |
| `HIGH_CONFIRM_POINTS` | 高震度 fast path に要する高震度到達点数（§20） | 2 |
| `CONFIRM_INTENSE_POINTS` | confirmed に要する確定震度到達点数（単点強震ノイズ除去の第3軸・§18） | 2 |
| `EEW_CONFIRM_POINTS` | EEW（震源要素確定）発表中に `CONFIRM_POINTS` の代わりに使う確定点数（§19） | 3 |
| `EEW_CONFIRM_FRAMES` | EEW 発表中に `CONFIRM_FRAMES` の代わりに使う確定連続フレーム数（§19） | 1 |
| `MERGE_EVENT_KM` | イベント重心併合距離（分裂統合） | 100 km |
| `HOLD_MS` | 確定保持（confirmed のイベント存続） | 10 s |
| `LIKELY_HOLD_MS` | likely/faint のティア保持（§16） | 10 s |
| `MIN_LIKELY_INTENSITY` | likely の最大震度下限（未満は faint・§13） | 震度1（value 0.5） |
| `MIN_CONFIRM_INTENSITY` | confirmed の最大震度下限 | 震度1（慢性活性セルは震度2） |
| `FLOOR_CAP` | 点別床の上限（鈍化防止） | 要較正 |
| `cellActivity` 時定数 | セル慢性活性の学習 | 時間オーダー |
| 慢性活性セル閾値 | 確定バー引き上げの発動 | 要較正 |

> パラメータは少数に保ち、可能なら物理から決め打つ（`R_km` は観測点間隔から、`COINCIDENCE_MS` は S 波速度 × `R_km` から）。少数の検証イベントへの過学習を避けるため検証は事件数を増やす。

## 7. 状態・純粋性・永続化

- `state`: 点別の `value` 短時間履歴・`triggeredAtMs`、点別床 `siteThreshold`（オンライン学習ぶん）、`cellActivity`（セル慢性活性）、アクティブイベント（ID・セル・メンバー）、ID 採番。
- `meta`（静的・不変）: `neighbors` / `cellOf` / 任意の初期床 JSON。
- **warmup 撤廃**: 床は静的/長時定数なので LTA の落ち着き待ちが無い。コールドスタート直後から検知可（V2 の 60 秒問題が消える）。
- **永続化対象**: 点別床・`cellActivity`・アクティブイベント（localStorage）。これで再読込・5 時リロード後も学習済みの床/地域活性を保つ（追加リクエスト 0）。

## 8. 出力とUI配線（既存流用）

- コアは既存 `DetectionEvent` 互換の配列を返す（`波面フィット系フィールドは削除`、`maxIntensity` を追加）。
  - 保持: `id` / `confidence` / `memberKeys` / `originTimeMs` / `lastOnsetAtMs` / `maxIntensity`(旧 lastPeak) / `lastSize`。
  - 削除: `epicenter`（→ 任意・null 可）/ `bearingDeg` / `oneSided` / `lastFitOk` / `radialFitOk` / `lastContiguity` / `strongStreak` / `score`。
- `deriveKyoshinView` / `useKyoshinAlerts` / `RealtimeTab` / `KyoshinV2Overlay` は概ね流用。
  - `RealtimeTab` の震度ヒストグラムは memberKeys から集計（現行踏襲）。
  - 片側配置の方位表示・score 表示は削除（震源を出さないため）。オーバーレイは「メンバー点の外周（フットプリント）」＋任意の推定震央に変更。

## 9. 計算量

- L1: O(点数) = 1725/フレーム。L2: O(点数 × K) ≈ 12k/フレーム。L3: 連結成分は活性点のみ（平常時ほぼ 0）。
- V2 の `spatialFill`（メンバー毎に全点走査）より大幅に軽い。1 Hz で余裕。

## 10. 検証計画（ハーネス `window.__fold`）

- **特異度**: 平常窓（北関東 12:00 / 03:00 / 14:30 / 18:00 ほか）で confirmed 0。**特に V2 の band-aid を壊した北関東コヒーレントバースト（[36.1,140.3] 型・震度1・9〜12点同時）を専用テストに据える**（点別床＋地域活性の二軸で 0 を確認）。
- **感度・速度**: 埼玉 M2.0 震度1 / 長野 M3.2 / 大隅 M5.2（沖）/ 福島沖 / 深発 / 疎地域（奄美・離島）などで、ネットワーク到達から数秒以内に confirmed・1 イベント・明滅なし。事件数を増やし過学習を避ける。
- **回帰**: 同時多発（離れた 2 地震）が別 ID に分離。**セル境界をまたぐ地震が 1 イベントに保たれる**（近傍グラフ連結・改良3）。

## 13. spread 型への改訂（2026-07-24・判別軸を「同期 onset の空間的広がり」へ）

**動機**: §10.3 で 紀伊水道 M3.2 震度2 が非検知だった件を精査すると、単点ではなく **3局が時間差で同時反応**していた
（実質2局同時）。旧 L2 の per-point「K 近傍のうち agree≥3」は時間差 onset・密な網（agree≤2）で取りこぼす。
さらにユーザーの着想「**震度0 の広がりを追えば判定できないか**」＝ Scratch 前身の `grid:上昇中割合計算&トリガ`
（グリッド＋周囲9セルの上昇割合で面判定）と一致。実データ実験で「レベルでなく**同期 onset の連結成分**で見れば
震度0 でも実地震と平常ノイズが分離できる」ことを確認したため、判別の芯を作り替える。

**変更点**:
- **L1 床を震度0 へ**: `LEVEL_MARGIN` 0.5→**0.0**（value ≥ floor で levelActive。強震モニタは 0.5 刻み量子化＝
  震度0 は value 0.0。静穏点は floor≈0 なので震度0 を取り込む。慢性ノイズ点は floor 自体が高く据え置き）。
- **L2 を per-point 近傍一致 → 同期 onset の連結成分に置換**: 直近 `COINCIDENCE_MS` に onset した点を K 近傍
  グラフで連結し、成分サイズ ≥ `MIN_CLUSTER`(=3) を「揺れクラスタ」とする。時間差 onset も成分で束ね、
  紀伊水道（成分3）を捕捉。`MIN_NEIGHBORS`/`MIN_NEIGHBOR_FRAC` は廃止（疎地域救済は成分方式に内包）。
- **faint ティア新設**（spread と intensity の分離）: **spread（成分≥3）＝実在性**、**intensity（≥震度1）＝発報の重み**。
  confirmed/likely は震度1以上（音）、**faint は同期 onset の広がりはあるが震度1未満（震度0級）＝無音で控えめに可視化**。
  Confidence は `confirmed | likely | faint | weak`。faint は `deriveKyoshinView` の confirmed/candidate に含めない
  ＝音・自動タブ・自動フィットを駆動しない。`RealtimeTab`（淡青カード「微弱な揺れの兆候」）・`KyoshinV2Overlay`
  （淡色・非脈動マーカー）で控えめ表示。

**保持（HOLD）の不具合修正（同日・spread 改訂に含む）**: 旧実装は継続点数・保持を「最後の onset」基準
（triggeredAt が TRIG_ACTIVE_MS で失効）にしていたため、**値が頭打ちで onset が止まると、まだ揺れている
のに size が減衰しイベントが早期消滅・地図リセット**した（紀伊水道で 3 局が震度1+ 継続中の 7:46:48 に weak
転落を実測）。継続点数・保持を「**いま揺れているメンバー**＝ sustained（value ≥ floor + `SUSTAIN_MARGIN`＝
床を明確に超えて継続）or 直近 onset」で数えるよう修正。`lastOnsetAtMs` は size>0 の間毎フレーム更新し、
**揺れが収まってから HOLD_MS 経過で解除**する。LEVEL_MARGIN=0 では平常の震度0(value 0.0)も levelActive に
なり保持が切れないため、継続判定は一段高い SUSTAIN_MARGIN で行う（faint＝震度0 は sustained にならず
onset ベースの一過性のまま）。→ 紀伊水道は likely が 7:46:38→7:47:38（揺れ継続の約1分間）維持され、
収束後に解除。平常窓は誤持続なし（0/0/0 維持）。

**検証（ハーネス・2026-07-24）**:
- **紀伊水道 M3.2 震度2** → **likely で検知**（従来完全取りこぼし）・揺れ継続中は維持（上記 HOLD 修正）。
- 正コントロール全件 confirmed 維持・**確定が高速化**（長野 5:46:06→5:45:40 等・低い床が初期微動を早く捕捉）。
  福島県沖 5秒短縮・大隅は 06:49:59（狙い通り）・奄美/根室/千葉/宮城/山梨も退行なし。巨大地震7件も即時確定・震度飽和維持。
- **特異度＝平常5窓（03/10/12/14:30/18:00・各300s・全国）で confirmed 0・likely 0・faint 0**。震度0 床でも
  onset連結成分≥3 が平常で発生しないため faint も氾濫しない。faint は実地震の末尾・震度0 フリンジにのみ出現。
- 型 0・vitest 30 件（faint 昇格・揺れ継続中の早期消滅回帰テストを追加）。

## 14. 地域単位の発報（別地点・余震の再検知）

**動機**: 発報が「confirmed が1件でもあるか」の**グローバル真偽**（false→true で1回）だったため、検知中に
(a) 同一地域の余震・(b) 全く別の場所の地震 が来ても鳴らなかった。Scratch 前身はそもそも**グリッド単位・
上昇駆動**（`震度上昇効果音` が各グリッドの上昇で鳴る）で、この問題を持たない。V3 も発報を地域単位へ寄せる。

**実装（`useKyoshinAlerts` のみ・コア/検知は不変）**:
- コアは変更せず、`deriveKyoshinView` が confirmed 各イベント（地域）の代表点＋最大インデックス
  `confirmedShocks` を出す。
- **初検知**（confirmed false→true）＝検知音＋タブ＋通知（従来どおり）。
- **同一地震の揺れ強まり**＝全体最大レベルの再エスカレーション（従来のグローバル判定を維持・安定）。
- **別地点の地震**（新設）＝検知中に、既存の確定地域から `REGION_MATCH_KM`(300km) より離れた新地域が
  `REGION_PERSIST_TICKS`(3f) 持続したら検知音＋タブ＋通知。分裂フラグメントの誤発報を避けるため持続＋
  クールダウン(`NEW_REGION_COOLDOWN_TICKS`=5f)で抑制（この 2 つはフレーム数からデータ時刻へ移した。
  現行名と値は §31）。同一地域の余震（時間差）は、揺れが収まって地域が
  解除された後に来れば「新地域」として、収まる前に来れば全体再エスカレーションとして鳴る。
- 全地域解除で EEW が無ければデフォルトタブへ復帰。

**検証（ハーネス・発報回数シミュレーション）**: 単発中規模は別地点0＝**検知音1回**（福島県沖 M4.2・大隅 M5.2）。
巨大地震は有感域が全国 >300km に割れるため **能登 M7.6 で約10回**（連続する広域大動なので許容）。当初試した
per-point 微小再エスカレーションは能登で168回鳴り過剰だったため廃止し、上記（初＋全体再エスカレーション＋
別地点）に整理。`REGION_MATCH_KM` は 250→300 で単発中規模の分裂フラグメント誤発報（別地点1回）が消えることを確認。

## 19. EEW（震源要素確定）発表中の確定緩和（2026-07-29・Scratch 版との比較から着想）

**動機**: 別実装（Scratch 3.0 版「リアルタイム地震ビューアー」・同じ DM-D.S.S 系データを使用）との比較検証で、
Scratch 版は単点の急峻な立ち上がりや EEW 予想円内の点を優先的に許可する状態機械を持ち、V3 より速く・敏感に
反応することが分かった。ただし Scratch 版の「1点で仮許可」は V3 が意図的に排除してきた誤検知パターン（茨城県
北部の単点強震ノイズ §18・北関東の慢性コヒーレントノイズ §3-6）そのものであり、そのまま輸入すると誤報耐性を
損なう。一方 Scratch 版の「EEW 予想円内の点を優先」は、EEW（気象庁発表）というすでに強いエビデンスがある
局面に限定した緩和であり、震源非依存の面判定という V3 の設計原則を壊さずに速さだけを取り込める。

**変更**: `Frame.eewActive` が true の間、`updateEventMetrics` の確定点数・確定連続フレーム数を
`CONFIRM_POINTS`(5)/`CONFIRM_FRAMES`(2) から `EEW_CONFIRM_POINTS`(3)/`EEW_CONFIRM_FRAMES`(1) に差し替える。
単点ノイズを弾く `MIN_CLUSTER`・`CONFIRM_INTENSE_POINTS`・`MIN_CONFIRM_INTENSITY`・慢性活性の引き上げ幅は
変えない。震源座標・距離は一切見ない（震源非依存を維持）。

**判定条件の試行錯誤（すべてユーザーとの対話で是正）**:
1. 当初案: `hasActiveEEW`（`severity` 不問）→ セルフレビューで「予報級1件だけで全国規模の確定緩和が発動し、
   §18 で塞いだ単点ノイズ誤 confirmed を EEW 経由で再導入しかねない」との指摘を受け、Warning 限定に修正。
2. `severity==='Warning'` 限定（`hasActiveWarningEEW`）→ ユーザー指摘「単独点は低精度だが、通常の予報は
   確度が高いのでは」を受けて `dmdataParser.ts` の `parseEEW` を確認すると、`severity` は DMDATA 電文の
   `isWarning`（推定震度が警報レベルに達したか）で決まる軸であり、震源推定の精度（単独点処理か複数点処理か
   ＝`earthquake.condition==='仮定震源要素'`）とは独立していると判明。複数観測点による確度の高い処理でも
   推定震度が低ければ severity は Forecast のままになりうる。
3. さらにユーザー指摘「予報でも震度3なので結構揺れている」を受け、severity（推定震度の大小）で判定すること
   自体が目的（震源要素の精度が担保された局面でのみ緩和する）とズレていると判明。**最終的に判定軸を
   `severity` から `earthquake.condition !== '仮定震源要素'`（震源要素が確定した EEW か）に変更した
   （`hasActiveNonAssumedEEW`）**。`condition==='仮定震源要素'` は 1 観測点のみのデータで震源を仮決めした
   速報で、震源・マグニチュード・推定震度の誤差が大きい——`eew.ts` の `eewMaxScale`（単独点処理時は
   `forecastMaxScale` を信用せず 0 を返す）・`RealtimeTab`・`ttsText.ts`（単独点処理時はマグニチュード・
   深さ・推定震度を非表示/読み上げない）と同じ判断基準に揃えた。severity=Warning の EEW は通常 areas
   （地域別確定予想）を伴い震源要素も確定していることが多いため、この変更は Warning 級の挙動をほぼ変えず、
   Forecast のまま震源要素が確定した地震（震度3〜4相当を含む）を新たに拾えるようになる。

   > **2026-09-03 追記**: 上の段落が引用している 2 つの前提は、その後の調査で誤りと判明した。
   > ここは当時の判断過程の記録なので本文はそのまま残し、現在との差分だけを注記する。
   > - **`eewMaxScale` は仮定震源要素でも値があれば返す**（当時は 0 を返していた）。気象庁が最大予測震度を
   >   発表しない条件は「観測点 1 点による震度予測」と「深さ 150km 超」で、該当すれば電文に値が入らない
   >   ——受信側で潰す必要がなかった（[`eew-spec.md`](eew-spec.md) §4・§5）
   > - **「仮定震源要素＝1 観測点のみのデータ」ではない**。定義に観測点の数は含まれず、PLUM 法が何点
   >   鳴っていても震源要素が推定できなければ仮定震源要素になる
   >
   > ただし **`hasActiveNonAssumedEEW` の設計判断そのものは維持する。** 拠って立つ理由が
   > 「観測点が 1 点だから低精度」ではなく「**震源要素そのものが固定の仮定値**（観測点直下・深さ 10km・
   > M1.0）で、その震源に基づく緩和は根拠を持たない」に変わっただけで、結論は同じ。

**検証**: 型チェック0・vitest 40件（`kyoshinDetector.test.ts`。EEW 緩和が効くこと・`MIN_CLUSTER` と
`CONFIRM_INTENSE_POINTS` は EEW 中でも緩まないことの回帰テスト +4）。判定条件の変更（severity→condition）は
`App.tsx` 側の派生値のみの変更で、`kyoshinDetector.ts` 側のテスト・ロジックへの影響はない。

**残る限界（受容）**: `hasActiveNonAssumedEEW` は全国一律のフラグで震源距離を見ないため、震源要素が確定した
EEW の震源から遠い無関係な地域でも同じだけ緩和がかかる。ただし L2（近傍同時性・連結成分）の空間コヒーレンス
要求は変えていないため、無関係な地域でこの緩和だけでノイズが confirmed に通ることはない（点数・フレーム数の
バーを下げるだけ）。

## 20. 高震度 fast path（2026-08-09・震度3級の確定を点数待ちから解放する）

**動機**: **2026-08-07 10:02 の福井の地震（最大震度3）で、震度3が現れてから confirmed まで実測で6秒かかった**。
ユーザーからの「震度3が2点並んでいるならノイズである確率は低いはず」という指摘を受けて Yahoo 実データを取得し、
`kyoshinDetector` にそのまま流して原因を特定した。

**実データによる原因の切り分け（Yahoo 強震モニタ・2026-08-07 10:01:50〜10:03:09 の80フレーム）**:

| 時刻 | 出来事 |
|---|---|
| 10:02:34 | 震源から 21km の2点が立ち上がり開始（最至近の 8km 点ではない） |
| 10:02:36 | その2点が value 2.5（震度3相当）に到達＝生データ上の震度3初出 |
| 10:02:37 | イベント生成（`likely`・size=4）。ここから**点数待ちの足踏みが始まる** |
| 10:02:41 | size=5 に到達し `confirmStreak=1` |
| 10:02:42 | `confirmStreak=2` で `CONFIRM_FRAMES` を満たし confirmed |

つまり遅延の主因は **`CONFIRM_POINTS`(5) が揃うまでの4秒の足踏み**であり、震度の大小は確定条件に一切
反映されていなかった。`CONFIRM_INTENSE_POINTS`（§18）は「確定震度（通常 震度1）以上の点が2点」を要求するが、
これは震度1でも震度3でも同じ扱いで、**高震度であることが確定を早める材料になっていない**。

**特異度の裏取り（実データ）**:
- **平常時2時間・全国1725点で value≥2.5 の出現は 0 点**（2026-08-08 13:00 台の日中・2026-08-09 00:00 台の
  深夜。計7200フレーム）。2点連結どころか単点すら現れない。
- 点別ノイズ床の学習上限は `FLOOR_CAP`=1.5（震度2相当）。慢性的に騒がしい点でも学習床はここで頭打ちになる
  ため、2.5 はノイズ床が到達しうる範囲の外側にある。
- 既存の `CELL_FREEZE_INTENSITY`=2.5 が既に「これ以上は明らかに実地震なので地域軸の学習を凍結する」という
  判断を採用している。**新しい閾値を発明したのではなく、既にある境界を確定条件でも使う**という位置づけ。

**変更**: `updateEventMetrics` の `meetsConfirm` に高震度経路を OR で追加する。
`HIGH_CONFIRM_INTENSITY`(2.5) 以上に達した levelActive メンバーが `HIGH_CONFIRM_POINTS`(2) 点以上あれば、
点数ゲート（`effectiveConfirmReq`・慢性活性セルの `CHRONIC_POINT_BUMP` を含む）を免除する。
構造としては §18 の第3ゲートの高震度版——「単点は信じない」思想（要求点数2）はそのままに、震度のバーを
0.5→2.5 に上げる代わりに点数待ちを外す対称的な拡張になっている。

**意図的に免除しないもの**:
- `CONFIRM_FRAMES`(2) の連続フレーム要求。落雷起因の電磁誘導ノイズのような**単フレームの跳ね値を弾く安全弁**
  として残す。これを1にしても短縮は1秒に留まり、得るものより失うものが大きいと判断した。
- `MIN_CLUSTER`(3) の連結成分要求。fast path が数えるのは `e.memberKeys`＝同一イベントのメンバーだけなので、
  遠く離れた2点が偶然同時に高震度でも別イベントとして扱われ発火しない（空間コヒーレンスは構造的に温存）。

**慢性活性セルでも免除する判断（案A採用）**: 当初は慢性セルでのみ要求点数を +1 する案（案B）も検討したが、
平常時2時間の実測で慢性・非慢性を問わず 2.5 の出現が皆無であり、**分岐が効く場面が一度も観測されなかった**
ため見送った（効く場面が無い分岐は複雑さだけを増やす）。慢性セルが育つには長期学習が要るため、実運用の
localStorage 永続化で活性が高いセルが生じた場合の挙動は今後の観測対象として残る。

**`HIGH_CONFIRM_POINTS`=2 の根拠（3 では機能しない）**: 福井の実データでは全国で value≥2.5 に達した点は
**ピークでも2点**（相互距離 13km）しか無かった。3 にすると「震度3が数点だけ」の地震を一切救えず、
パラメータとして死ぬ。実データが 2 以外の選択肢を許さなかった。

**検証**:
- 型チェック0・vitest 46件（`kyoshinDetector.test.ts`。fast path が効くこと／震度2.0 止まりでは効かないこと／
  1点だけでは効かないこと／単フレームの跳ね値では確定しないこと の回帰テスト +4。既存42件は全て維持）。
- **福井の実データ再生**: 初回 confirmed が **10:02:42 → 10:02:38 に4秒短縮**（size=4＝`CONFIRM_POINTS` 未満
  での確定を確認）。震度3初出（10:02:36）からは2秒。
- **平常時2時間**（上記2窓・7200フレーム）で **confirmed=0**（fast path による誤発火なし）。

**残る限界（受容）**: `MIN_CLUSTER`(3) は据え置いたため、**単独点・2点しかない震度3は依然として検知されない**
（イベントが生成されないので fast path 以前の問題）。ユーザーからは「単独点であっても震度3はノイズでは
出づらい」という指摘もあったが、単独点は機器ノイズ・発破の典型パターンでもあり、`MIN_CLUSTER` の緩和は
§18 で塞いだ誤検知経路を再び開くリスクが大きいため今回のスコープ外とした。福井のケースは onset 連結成分が
4点あったため、この制約下でも実用上の短縮効果が得られている。

## 21. 欠測フレームでの学習資産巻き添え消失を修正（2026-08-13・KYO-1）

**問題**: `step()` の欠測分岐は当初 `if (frame.missing?.[i]) continue` で `sites[key]` に何も入れず、
学習資産（`floorMean`/`floorDev`）ごと消失させていた。次フレームで `initSiteState` から再学習に入り
`floorDev=0` にリセットされるため、慢性ノイズ点ほど直後に誤 onset を招くリスクがあった（KYO-1）。

**初回修正の踏み外し**: `sites[key] = prev` で `SiteState` を丸ごと据え置いたところ、`hist` も凍結されて
しまい、`pushHist` は配列長を 2 未満に絞らない仕様（`while (hist.length > 2 && ...) shift()`）のため
「60秒前の値」が復帰1フレーム目の `windowRate` で「`RATE_DT_MS`(2.5秒) 窓の直近サンプル」として採用される
状態が生じた。敵対的レビュアーの検証で 3 点欠測→復帰の合成シナリオを実行したところ、緩やかなドリフト
（value 0.0→0.5、震度0.5相当）でも 3 点同時 onset → `MIN_CLUSTER`(3) 到達 → likely 相当を誤検知することが
再現された。

**確定修正**: `sites[key] = { ...prev, hist: [] }` として学習資産のみ保持し `hist` は空リセット。
復帰1フレーム目の `windowRate` は基準サンプル無しで `null` を返すため `onset=false`。緩やかなドリフトが
偽オンセットに化ける経路を塞ぐ。`triggeredAtMs` は据え置いても `COINCIDENCE_MS`(4秒) の時刻ベース判定で
自然に減衰するため保持で問題無い。

**検証**:
- 型チェック0・vitest 289件（既存 265 → B6 で +23、本節で +1・KYO-1 の回帰テスト）
- 回帰テスト: 学習済み 3 点が 60 秒欠測を挟んで震度 0.5 相当に緩やか復帰しても confirmed/likely を出さないこと

**関連 KYO 修正（同コミット）**:
- KYO-2: `calcintensityToScale` 未知コードで `log.warn`（空文字/null/undefined は震度未確定として抑制）
- KYO-3: `fetchRealtimeIntensity` で `realTimeData.intensity` の欠落・空文字を明示的な失敗として扱い次エッジへ
- KYO-4: `useKyoshinRealtime.processResult` を try/catch で隔離しローカルバグを fetch 失敗と誤集計しない
  （`processResult` は後に取得経路を供給元・キュー・反映の 3 段へ分離した際、反映側の `applyFrame` へ改称）

## 22. 孤立した震度0の検知点を描かない（2026-08-19・大地震後に各地へ点々と残る残骸を消す）

**症状**: 2024-08-08 日向灘 M7.1 のリプレイで、揺れが収まった後も各地に震度0の検知点バッジが単独〜少数で
点々と残り続ける。

**原因**: イベントのメンバー（`memberKeys`）は当時、和集合で単調増加し揺れが収まっても縮まなかった
（現在揺れている数は `lastSize` が別に持つ）。表面波が抜けた後も値が震度0付近をうろつく点はメンバーに
残り続けるため、描画対象（震度0以上）に居座る。**この「縮まない」性質そのものは §30 で改めた**が、
値が震度0付近をうろつく点は下がりきらず刈り取りの対象にならないため、この節の間引きは引き続き必要。

### 計測と条件の決め方

Yahoo 強震モニタの実データを 2024-08-08 16:22〜17:42 の 80 分ぶん取得し、先頭 20 分（平常）で点別ノイズ床を
学習させてから本震以降を流した。孤立した震度0点＝「近傍に震度1以上の検知点が無い震度0点」。
以下「延べ」は秒×点の累積（1点が10秒残れば10と数える）。

**残骸の出どころは confirmed**: 孤立した震度0点の由来は confirmed 96.6%・likely 1.5%・faint 2.0%、連続表示は
中央値13秒・最長121秒。そこで間引きの対象を confirmed のメンバーに限った。likely / faint は
`HOLD_MS` / `LIKELY_HOLD_MS` の範囲で短命なうえ、faint は定義上メンバー全員が震度0なので、対象に含めると
イベントが生きている間に点だけが消え、「微弱な揺れの兆候」カードと地図が食い違う（実測: faint が存在する
52 秒のうち 19 秒で全点が消えた）。

**空間条件だけでは足りない**: 孤立した震度0点のうち「10秒以内に震度1以上へ育つ点」＝到達先端の割合は
時間帯で大きく偏る（本震〜広がり中の 3 分間は 39.3%、ピーク後の減衰期は 0.1%、収束期 0.9%）。空間条件だけで
落とすと広がり中の先端まで消えるため、「直近 `TRIG_ACTIVE_MS`(8秒) に立ち上がっていない」条件を足した
（`step()` の戻り値に `recentOnsetKeys` を追加して表示側へ渡す）。

半径と条件の組み合わせを比べた結果が下表。**間引き量をほぼ保ったまま誤削除が最小になる「30km ＋ 直近の
立ち上がりを除外」を採用した。**

| 条件 | 間引き量（延べ描画比） | 誤って消す「育つ点」（全期間） |
|---|---|---|
| 30km・空間条件のみ | 8.8% | 293点（うち広がり中 245点） |
| **30km ＋ 直近の立ち上がりを除外（採用）** | 7.8% | **54点**（うち広がり中 42点・減衰期と収束期は 0点） |
| 20km ＋ 同上 | 16.3% | 244点 |
| 40km 以上 ＋ 同上 | さらに小 | 29点前後（収束期の残骸がほとんど落ちない） |

20km は間引きが増える代わりに広がり中の先端を大きく削り、40km 以上は本来の目的（収束期の残骸）に効かない。

### カメラ追従との分離（レビュー指摘で判明した退行）

`CameraFollowsGL` の `FitToDetectionGL` は **点列が空になったこと**を「検知終了」の合図として扱い、
日本全体へ戻す（`fitJapan`）。当初は `deriveKyoshinView` が返す全点列に間引きを適用していたため、
confirmed が続いている最中に点列が空になり、カメラが勝手に引く経路が生まれた
（実測: 検知中に点列が空になる区間が **20秒**・空↔非空の往復 2回。間引き前は 0秒）。

対処として点列の役割を分けた:

| 点列 | 間引き | 用途 |
|---|---|---|
| `detectedPoints` | 通さない | カメラフィット・検知の継続判定 |
| `detectedMarkerPoints` | 通す | 検知点マーカーの描画 |
| `candidatePoints` | 通さない | 候補カメラフィット |
| `unconfirmedPoints` | 対象外（confirmed 限定のため） | 検知点マーカーの描画 |

**教訓**: 「表示のフィルタは検知の判定に触れない」という原則を守っただけでは足りなかった。点列の**空判定**が
別の場所で状態のシグナルとして使われていたため、フィルタが間接的に判定を書き換えていた。

### 検証

- 型チェック0・vitest 全通過（本節で `dropIsolatedZeroPoints` と `recentOnsetKeys` のテストを追加）
- 実データ再検証: 退行（カメラ用点列の空・faint の消失）はいずれも 0秒。間引き量 7.7%（上表の 7.8% は
  対象を confirmed に限る前の値。ほぼ変わらない）。収束期 16:52:00 の描画は 10点→3点
  （空間条件だけなら 8点落ちるが、1点は直近の立ち上がりで保護されるため 7点減）、本震ピーク（16:45:30）は
  319点→318点で影響しない
- ブラウザ（standard 版でリプレイ）でも同じ数字を確認（16:48:00=67点／16:49:00=33点／16:50:00=14点）、
  ズームは終始一定でカメラの誤発火なし
- **地図とカードは同一の点列を共有する**（`App` が `detectedMarkerPoints ＋ unconfirmedPoints` を
  `RealtimeTab` へ渡す）。当初は両者が同じ入力から同じ計算を各自で組み立てていたが、それでは片方の実装を
  変えたときに黙って食い違うため、計算を 1 箇所に寄せた

## 23. `recentOnsetKeys` の信頼性を支える 2 つの修正（2026-08-19・§22 と同日）

§22 で `recentOnsetKeys` を表示の判定材料に使い始めたことで、「その値が信頼できるか」が新たに効くように
なった。レビューで挙がった次の 2 点を同時に直した。どちらも**壊れても例外が出ず、静かに劣化する**類。

### 1. 観測点集合の変化を取りこぼす（`siteSignature`）

以前は「点数＋先頭・末尾座標」だけで近傍メタ（`StationMeta`）のキャッシュ有効性を判定していた。配列の
中間だけが差し替わった更新はこれを通り抜けるため、古い `StationMeta.keys`（＝`computeSiteKeys` が座標の
重複点に出現順で付けた `#2`, `#3`）を使い続ける。一方で表示側の `buildSiteIndex` は毎回キーを作り直すため、
両者がずれて `recentOnsetKeys.has(key)` が常に false になり、到達先端の救済が効かなくなる（Yahoo の観測点
リストは全1725点中431点が座標重複に該当する）。

**全点を見るシグネチャに変えた**。走査コストを避けるため二段構えにしている: まず `sites` の**参照**で弾き
（同一 `siteConfigId` なら `fetchSiteList` が同じ配列を返すため通常運用はここで終わる）、参照が変わったときだけ
全点シグネチャを比べる。内容が同じなら近傍メタ（O(点数²)）を再利用し、参照だけ差し替える。

### 2. `step()` 例外時の凍結

例外時は `setResult` を呼ばずに抜けるため、`detections` と `recentOnsetKeys` が前フレームの値で凍結する。
一方で表示側が使う現在震度は生きたまま更新されるので、放置すると「古いメンバーを現在の震度で描き続ける」
状態になる（間引きの判定も古い `recentOnsetKeys` で行われる）。

**`RESULT_STALL_RESET_FRAMES`(5) フレーム連続で失敗したら検知結果を空にする**。数フレームの一過性なら保持した
方が明滅しないため、閾値を設けている。学習資産（点別床・セル慢性活性）は `stateRef` に残すので、復帰時に
学び直しにはならない。

この閾値は後に「観測点数と震度の件数が食い違って `step()` へ入れないフレーム」も数えるようになり、
凍結を解いたことが発報側の鳴り直しへ波及した（定数名を `STEP_FAIL_RESET_FRAMES` から改めたのもその
ときで、経緯は §35）。

## 24. 別地点発報の連発を止める（2026-08-20・能登半島地震リプレイでの利用者報告から）

「能登半島地震のリプレイで検知音が何度も鳴る」という報告を受けて調べた。実データで測ると、揺れ検知の
音のうち**「別地点で揺れ検知」だけが数秒おきに連続**していた（EEW あり条件で 16:21:28〜16:21:43 に
5 秒間隔で 4 連発）。原因は 3 つあり、いずれも「巨大地震で揺れが全国へ伝播する」場面で表に出る。

### 原因

1. **距離判定の起点が地域自身の初検知時刻だった** — 遠くて揺れ始めが遅い地域ほど経過時間が短く
   見積もられ、閾値が下限 300km に張り付く。伝播を吸収するための動的閾値が、いちばん吸収したい遠方で
   こそ育たないという逆転が起きていた。
2. **EEW による吸収が「今この瞬間 EEW があるか」しか見ていなかった** — 吸収した地域を配列から削除する
   実装だったため、次のフレームで新規地域として再登録される。EEW が最終報で解除された後は吸収されず、
   それまで抑えられていた地域が一斉に発報条件を満たした（実測: 解除の 1 秒後に発報）。
3. **距離だけでは表面波を抑えきれない** — 震央から 600〜1350km で震度2以下の揺れが次々確定する。
   これを距離で吸収しようとすると、上限を上げるほど「本当に別の場所で起きた地震」を取りこぼす。

### 対策

| 変更 | 内容 |
|---|---|
| `AlertRegion.absorbedByEew` | EEW の伝播範囲に一度入った地域を記憶し、解除後も発報しない（原因2） |
| `AlertRegionState.outbreakAtMs` | エピソード全体の起点を保持し、EEW が無いときの距離判定の基準にする（原因1）。個々の地域の生存とは切り離す（震源近傍が先に収束して刈られても起点が繰り上がらない） |
| `PROPAGATION_MAX_KM`(800km) | 伝播として吸収する距離の上限。S波半径は起点から4分で約1250kmに達するため、上限が無いと国内のどこで起きた地震も同一地震に見える |
| `NEW_REGION_MIN_INDEX`(11) | 遠さではなく揺れの強さで線を引く。震度3を下回る地域は音を鳴らさない（原因3） |

あわせて、判定を純関数 `stepAlertRegions` に切り出した（副作用はフック側に残す）。実データを流した回帰
検証とユニットテストが同じ経路を通せる。戻り値は発報した地域の座標と震度で、ブラウザ通知の「推定最大
震度」はこの値を使う（従来は検知全体の最大震度を出していた）。

### 実測

Yahoo 強震モニタの当時の実フレーム 960 秒分に、DMDATA archive の実電文（EEW 80 件）を重ねて測定した。

| 条件 | 修正前 | 修正後 |
|---|---|---|
| EEW あり | 5 回（うち 4 回が 5 秒間隔） | **0 回** |
| EEW なし | 7 回（最小間隔 5 秒） | 2 回（最小間隔 30 秒・どちらも震度5強相当） |

修正前の数値はブラウザでの実測と時刻・回数が一致する。EEW なし条件で 0 にならないのは、強震モニタ
だけでは震源も発生時刻も分からないため、揺れ始めから約 1 分間は閾値が下限を超えられない原理的な限界に
よる。この条件は DMDSS 版で API キー未設定のときだけ現れる（standard 版は強震モニタ経由の EEW が入る）。

**寄与は単純な足し算にならない**（EEW なし条件で計測）。`absorbedByEew` とエピソード起点だけなら 3 回まで
落ちるが、そこへ距離の上限を足すと 8 回へ跳ね返る（吸収できる範囲が狭まるため）。その 8 件のうち 6 件は
震度2以下・震央から 600〜1350km で、震度の下限がこれを打ち消す。最後に、下記の照合順序の修正で 2 回に
落ち着いた。

### 判定の順序依存

地域の代表点はマッチのたびに書き換わるため、素直に書くと同じフレームの後続の確定点が「直前の点で
動いた後の位置」と比較され、**確定点の処理順で結果が変わる**（レビュー指摘）。マッチングは
フレーム開始時の座標で行うようにした。同じフレームで新しく生まれた地域も、その場で基準点として
登録する（登録しないと、その地域だけ順序依存が残る）。

### 採らなかった案

どちらも実データで測ったうえで見送った。

- **発報済み地域を照合の対象から外す** — 一度「別地点」を鳴らした地域（`fired`）は二度と鳴らないため、
  その地域の閾値の内側で後から本当に別の地震が起きても無音になる（レビュー指摘）。そこで発報済みを
  エピソード起点による拡張から外してみたが、**発報が 1 回増えた**（2 回 → 3 回）。閾値が狭まったぶん、
  同じ地震の伝播が新規地域として登録し直され、**同じ場所が二度鳴る**方に振れたため。鳴りすぎを直す
  変更で鳴りすぎが増えては本末転倒なので採らなかった。既発報地域が別の地震を吸収しうる限界は、
  修正前から変わらないものとして残っている（音は鳴らないが、地図と検知カードには出る）。
- **クールダウン（`NEW_REGION_COOLDOWN_TICKS`）を 5 → 30 に延ばす** — 発報数が変わらなかった
  （どちらも 2 回。間隔だけが 6 秒から 30 秒に広がる）。延ばすと、クールダウン中に揺れが収まった地域が
  `REGION_PRUNE_TICKS`(3) で破棄されて発報の機会を失う窓が広がる。数を減らせないなら、その代償だけを
  負うことになるため据え置いた。
  （この項の `NEW_REGION_COOLDOWN_TICKS`・`REGION_PRUNE_TICKS` は、後に名前と単位が変わっている。§31 参照）

## 25. 欠測の瞬断で確定済みの検知点が明滅する（2026-08-20・能登半島地震リプレイでの利用者報告から）

**症状**: 2024-01-01 能登半島地震の本震付近を再生すると、確定済み（confirmed）の検知点が一部、**震度6強級を
含めて**一瞬消えて復活する動きを繰り返す。

**原因**: 上流データそのものが単発の欠測を混ぜている。Yahoo の秒データは観測点ごとの値に欠測センチネル
（実測 -1）を含み、**現に強く揺れている観測点でも 1〜2 秒だけ値を落とす**。表示側は欠測を「震度階級なし」
として描かない（`kyoshinIndexToJma` が null）ため、そのまま渡すと 1 秒消えて次の秒で戻る。

### 実測（欠測の継続長）

### 「消す」ではなく「薄く残す」を選んだ理由

直前値で埋めるだけだと、値が生きている点と区別が付かない。欠測は 3% 前後の観測点で常時起きているため、
「表示されている値がいつのものか」を示さないまま補完すると、データの欠落を隠す方向に働く。そこで
保持中は `stale` を立て、震度を読める描画物（検知点バッジ・震度1以上のドット）を不透明度 0.35 で描く。
利用者側の要望でもあった。

### 判定にも効かせた理由

保持値は表示のための補完だが、`deriveKyoshinView` を通るため音・通知・地域単位発報の入力
（`candidateMaxIndex` / `confirmedShocks`）にも入る。**これは意図した設計**。欠測を素通しすると、地域の
最大震度を担う観測点が 1 秒欠測した瞬間に最大値が次点まで落ち、復帰時に `useKyoshinAlerts` の
`postPeakMinLevel` 経路で「再エスカレーション」の更新音が誤って鳴る。検知エンジンが欠測を「揺れ 0」と
扱わない（§21）のと同じ理由で、表示側の最大値も欠測で落とさない。

### 修正後の実測

同じ窓（16:10:11〜16:11:50・100 フレーム）を DMDSS 版のリプレイで地図ソースから毎秒サンプリングした。

| うち震度6強以上 | 18 回 | 0 回 |

残った 9 回は欠測ではなく、震度0未満への低下と孤立震度0点の間引き（§22）による従来どおりの挙動。

## 28. 群発地震で余震検知の感度が徐々に落ちる（2026-07-29・熊本群発リプレイ・FLOOR_FREEZE_MS）

> **本節は後追いの記載**。実装（`PARAMS.FLOOR_FREEZE_MS` の追加）はコミット `1cd75b6`（2026-07-29）で
> 既に main へ入りリリース済みだが、当時この節を書き落としていた。2026-08-21 に実データで再検証した
> うえで経緯を記録し、あわせて境界・副作用のテストを 3 件足した。
> なお `1cd75b6` のコミットメッセージは非検知を「40件→4件」、母数を「M7.1本震+109件の余震」と
> 書いているが、これは**対策前と対策後を別々の突き合わせ条件で測った数字**で、母数の内訳も不正確
> だった。下記の表は `FLOOR_FREEZE_MS` だけを切り替えて同一条件で測り直したもので、こちらを正とする。

**問題**: 点別ノイズ床の学習は「揺れていない静穏点」だけで行い、(i) `levelActive` な点と
(ii) 近傍同時性を満たした確定揺れ点で凍結していた（§5-L0）。しかしこの 2 条件はどちらも
**現フレームの状態**しか見ておらず、`COINCIDENCE_MS`(4秒) を過ぎて揺れが収まったと判定された
瞬間から床学習が再開する。本震・大きめの余震の減衰過程では、値が実効床を割ったり超えたりしながら
緩やかに収まるため、その「割った」瞬間の値が静穏点のノイズとして学習され、
`floorMean + FLOOR_SIGMA_K・floorDev` を `FLOOR_CAP`(震度2相当) まで押し上げてしまう。
一度そこまで上がると震度1程度の後続の余震は `levelActive` にすらならず、検知が完全に消える。

単発の孤立した地震なら `FLOOR_TAU_MS`(15分) の時定数でゆっくり回復する余地があるが、数分おきに
余震が続く群発地震では床が戻る前に次の onset が来るため、**劣化が蓄積して時間とともに悪化する**。

**変更**: `PARAMS.FLOOR_FREEZE_MS`(600,000ms = 10分) を追加し、床学習の凍結条件に 3 つめを足した。
`triggeredAtMs`（最後に onset した時刻）から `FLOOR_FREEZE_MS` 以内の点は、揺れが収まった直後でも
学習をスキップする。対象は **onset した観測点のみ**なので、onset しない慢性ノイズ点を `FLOOR_CAP` まで
鈍くする本来の役目（特異度の第1軸）は妨げない。

**検証（2026-07-28 熊本群発地震のリプレイ）**: M7.1・震度7 の本震（16:27）以降 23:59 まで JMA カタログで
111 件の有感地震が記録された日を、Yahoo 履歴 RealTimeData 27,240 フレーム（7.5 時間・全国）でリプレイした。
111 件の内訳は熊本県熊本地方 79・熊本県天草・芦北地方 28（＝熊本圏 107）と、群発とは無関係な
和歌山県北部 2・鹿児島県薩摩地方 2。
`FLOOR_FREEZE_MS` だけを 0（＝対策前と等価）と 600,000 で切り替え、**同一の突き合わせロジック**で比較:

| | カタログ照合 非検知 | 検知スパン総数 | 広域分裂（既知・§10.4） | 時間的に孤立 |
|---|---|---|---|---|
| 対策前（freeze=0） | **36** / 111 | 136 | 8 | 14（うち confirmed 9） |
| 対策後（freeze=600s） | **4** / 111 | 189 | 9 | 45（うち confirmed 15） |

右 3 列は「検知スパン総数」を分割したものではない。`検知スパン総数` は likely 以上のスパン全件、
`広域分裂` はカタログ地震と時間は重なるが重心が 250km 超離れたもの（巨大地震の有感域が割れる §10.4 の
既知挙動）、`時間的に孤立` はどのカタログ地震とも時間が重ならないもの。残りがカタログと対応した検知。

- 非検知 36→4。残る 4 件は和歌山県北部 2 件（別窓・単点）と熊本 2 件（M2.0/M2.1）で、いずれも
  onset 点数律速の微小地震＝§17 と同じ「K を上げても救えない」型。
- 震度4以上の余震 13 件は対策前後とも 100% confirmed。
- 対策前は本震後 18:13〜18:21 の 8 分間、震度1相当の余震 5 件が完全に無反応だった（劣化の実例）。
- **留意点**: 「時間的に孤立した検知」が 14→45（うち confirmed 9→15）に増えている。感度回復の裏面だが、
  誤検知と断定はできない（M7.1 の余震は JMA が有感として載せる 111 件よりはるかに多く、小さいものは
  カタログに現れない）。ただし **confirmed は検知音とブラウザ通知を伴う階級**なので、仮に誤検知なら
  影響は表示上の残骸より大きい。切り分けには平常時窓での特異度検証が必要で、**本節時点では未実施**。
- 単体テスト: フリーズ機構そのもの（2 件）＋副作用・境界（3 件）。うち 3 件は凍結条件を外すと落ちる
  ことを確認済み（残る 2 件は、フリーズ期間の経過後に学習が再開すること・時刻の巻き戻しで
  `triggeredAtMs` が破棄されることの記録で、凍結条件の有無では変わらない）。

**副作用として確認したこと**:
- onset していない点の床学習は止まらない（`FLOOR_CAP` による慢性ノイズ抑制は健在）。
- 群発中に onset を繰り返すと、そのたびに `triggeredAtMs` が更新されフリーズ起点も延びる。
  つまり余震が続く限り床は守られ続ける。
- データ時刻が巻き戻る（アーカイブ再生など）と `dtMs <= 0` が不連続とみなされ `triggeredAtMs` は
  破棄される。これが無いと `now − triggeredAtMs` が負になりフリーズ条件が永久に真になるため、

## 29. 成分点数を震度に連動させる（2026-08-21・震源最近傍の単点先行を取りこぼさない）

**動機**: 利用者から 2 つの指摘があった。「ノイズで震度3以上まで行ったことがないので、震度3以上なら
即 confirmed でよいのでは」「能登の本震で震度6を観測してもまだ likely にすらならないのが気になる」。
後者は検知エンジンの取りこぼしを指しており、優先して調べた。

### 実データによる原因の切り分け

能登半島地震 本震（2024-01-01 16:10）の Yahoo 実データ 180 フレーム（当時の 1133 点）を
`kyoshinDetector` にそのまま流した。

| データ時刻 | 最大震度(value) | 震度3以上の点 | onset 点 | イベント | 確信度 |
|---|---|---|---|---|---|
| 16:10:13 | 3.0（震度3） | 1 | 1 | 0 | — |
| 16:10:14 | 4.5（震度5弱） | 1 | 1 | 0 | — |
| 16:10:15 | 5.0（震度5強） | 1 | 2 | 0 | — |
| 16:10:16 | 6.0（震度6強） | 2 | 2 | 0 | — |
| 16:10:17 | 6.0 | 3 | 4 | 1 | likely |
| 16:10:18 | 6.0 | 3 | 5 | 1 | confirmed |

**震度3が出てから確定まで5秒、震度6が見えてからでも2秒、イベントが1つも立っていない。** 16:10:16 の
時点で高震度 fast path（§20）の条件（震度3が2点）は既に満たされているが、fast path はイベント内の
メンバーを数える仕組みなので、**イベントが生まれていなければ発火できない**。壁は `MIN_CLUSTER`=3 だった。

`HIGH_CONFIRM_POINTS` を 2→1 に下げる案（利用者の当初の提案）を単独で試すと、初回 confirmed は
**1 秒も動かなかった**。震度3が2点に達する時点では `MIN_CLUSTER` の成分もほぼ同時に成立するため、
点数免除が確定を早める余地が残っていない。§20 で 2 と決めた根拠（福井のケースでピーク2点）は、
「2点あれば効く」ことは示していたが「2点未満では一切効かない」ことの重さを測っていなかった。

### 却下した案

| 案 | 実測・根拠 | 却下理由 |
|---|---|---|
| `MIN_CLUSTER` の全面緩和 | 1 にすると平常時の日中に**誤 confirmed 209 フレーム＝3.5 分**。2 でも likely 誤発火が 10 分に 1 回（1 日 70 回相当）で、confirmed の短縮は 0 秒 | 平常時の誤報が実用に耐えない |
| 散在ガード（同一フレームに高震度の孤立成分が複数あれば例外を適用しない） | — | 故障で 1 点が張り付いている間に別の場所で本物が単点で立ち上がると、孤立成分が 2 つになって**ガードが本物を弾く**。故障は続くのでその間ずっと検知を殺す。安全側に倒したつもりで検知を止める形 |
| 近傍が反応しているかを条件にする | 下表（一次データ） | 単点先行は実地震の初動として正常。故障と区別できない |
| 観測点密度（`avail`）に連動させる | 能登の震源近傍は `avail`=3（全点の中央値 10・下位 25% が 7）なので機能する | 「密網で震度6が 1 点だけでも 2 点揃うまで待たせる」不整合が残る。将来の余地として保留 |

近傍の反応を条件にできない理由は実データが示している。能登本震の震源最近傍の点（`avail`=3）の近傍 value:

| データ時刻 | その点の value | 実在近傍の value |
|---|---|---|
| 16:10:13 | 3.0 | 0, −0.5, −1（ほぼ静穏） |
| 16:10:14 | 4.5 | −0.5, −1（まだ静か） |
| 16:10:15 | 5.0 | 1.5, 1, −0.5 ← ようやく反応 |

**「1 点だけ高震度・周囲は静穏」は機器故障とも実地震の初動とも区別できない。原理的に。** S 波が最初の
1 点に届いた時点で、20〜30km 先の隣の点にはまだ波が来ていない（伝播 3〜4km/s なら 8〜10 秒後）。
能登2023 でも同じ形（震源近傍 `avail`=3・周囲は −2.5〜−3 のまま 4 秒）。**点数では見分けられないので、
震度がノイズ床からどれだけ離れているかで信頼度を決めるしかない**——これが採用案の出発点になった。

### 採用: 成分点数を震度で決める

利用者の提案「震度に合わせて点数を変える」を採った。判定根拠が単一（ノイズ床 `FLOOR_CAP`=1.5 から
どれだけ離れているか）に閉じ、密度という別の軸を持ち込まずに説明できる。

```
requiredClusterSize(成分内の最大 value):
  value >= SOLO_CLUSTER_INTENSITY (3.5・震度4) → 1 点
  value >= HIGH_CONFIRM_INTENSITY (2.5・震度3) → HIGH_CLUSTER_POINTS (2 点)
  それ以外                                    → MIN_CLUSTER (3 点)
```

判定は成分ごとに閉じているため、他所のノイズの有無で本物の判定が変わることはない（散在ガード案の
失敗を構造的に避けている）。

併せて `HIGH_CONFIRM_POINTS` を 2→1 にし、fast path の成立条件を次の形にした（単点イベントを
確定させるには両方が必要。片方だけでは上記のとおり 1 秒も動かない）。

```
meetsHighFastPath =
  高震度(2.5以上)に達したメンバーが HIGH_CONFIRM_POINTS(1) 点以上
  かつ ( ( 今フレームに成分が帰属しており かつ その点数 < MIN_CLUSTER )  または
         intenseCount >= CONFIRM_INTENSE_POINTS )
```

「成分が帰属しており」を省略してはいけない。成分が帰属していないフレームの `compSize` は 0 で、
`0 < MIN_CLUSTER` は真になる——つまり**この一語を落とすと 2 度目の不具合がそのまま戻る**。

後段の括弧の中は**敵対的レビューで 3 度直した**（最後は追加した機構の撤回）。この節の要点なので
経緯を残す。上の擬似コードは最終形——`lastSize` や時間保持を使う中間形は下記のとおり穴を作ったので、
**このブロックだけを引用するときは必ずこの形にすること**。

**1 度目**: 当初は前段だけだった。それでは **`MIN_CLUSTER` で正規に成立した 3 点の面の中で 1 点だけが
震度3・残り 2 点は震度0** という分布が確定してしまう。§18 が塞いだ「単点だけ強く・周囲は震度0」
（2026-07-27 茨城県北部の誤 confirmed）と構造的に同一で、震度のバーを上げただけで再び通していた
（レビュアーが実測で再現）。`EEW_CONFIRM_FRAMES`=1 と重なれば 1 フレームで成立するため実害も小さくない。
そこで「第3ゲートを満たす」か「点数が足りず課せない小さなイベント」のどちらかを要求する形にした。

**2 度目**: その「小さなイベント」の判定に `lastSize` を使ったのが誤りだった。`lastSize` は
**時間で減衰する量**（`TRIG_ACTIVE_MS`=8 秒の onset 途絶で 0 になる）で、成分の出自を表さない。
イベント自体は `HOLD_MS` の間生存し続けるため、**確定に至らず消えていくイベントはすべて
「`lastSize < MIN_CLUSTER` だが生存中」という状態を通過する**。その窓でメンバーの 1 点が震度3へ跳ねると、
周囲が完全に静穏でも confirmed に達した（これもレビュアーが実測で再現）。特殊な条件ではなく通常の
ライフサイクルなので、1 度目より発生確率が高い。

判定を **「今フレームにそのイベントへ帰属した L2 成分の点数」**（`updateEventMetrics` の `compSize` 引数・
成分が帰属していないフレームは 0）に変えて塞いだ。単点の震度3 はそもそも `requiredClusterSize`(2 点) を
満たさず成分にならないため、減衰後のスパイクは免除対象に入らない。一方、震度4 の単点は成分 1 点で
認められるので能登の短縮は残る。両方とも `kyoshinDetector.test.ts` に回帰テストとして残してある。

**3 度目（指摘）**: その `compSize` ベースの判定は、今度は**確定を遅らせる**副作用を持っていた。単点・
2点の成分は毎フレーム `requiredClusterSize` を満たし直さないと成分にならないため、値が 1 フレーム沈むと
免除が切れて `confirmStreak` がリセットされる（実測: 単点に `[3.5, 3.0, 3.5, 4.0]` を流すと確定が
2 フレーム遅れる。実データは 0.5 刻み・1Hz なので震度3〜4 の帯では起こりうる）。速く確定させるための
仕組みが、まさにその帯で自ら遅らせていた。

**4 度目（撤回）**: 免除を `COINCIDENCE_MS`(4 秒) の間保持する実装（`lastSmallClusterAtMs`）を試したが、
**これが 3 つ目の穴を作った**。免除をイベント全体のフラグで持つと、「免除の根拠になった小さな成分の
構成点」と「免除が適用される高震度メンバー」が別人でも通る——4 秒以内に別々のメンバーが 2 回スパイク
すれば確定する（レビュアーが実測で再現）。§18 が塞いだ分布が、また別の形で現れたことになる。

**保持は撤回した。** 決め手は、実データ 34 窓（付録A）で**保持の有無によって結果が一切変わらなかった**
こと（短縮量・特異度・回帰すべて同一）。効く場面が観測されない機構が穴を作っているのだから、外すのが
正しい——§20 で「効く場面が無い分岐は複雑さだけを増やす」と判断したのと同じ理由。免除は
**今フレームに帰属した成分だけで決める**（時間保持を持たせない）形に落ち着いた。

結果として、震度3〜4 の帯で値が沈むと確定が 2 フレーム遅れる挙動は**受容している**。変更前は単点では
永久に確定しなかったので劣化ではない。この遅延も回帰テストで固定してあるので（`単点の震度が閾値付近で
1フレーム沈むと確定が遅れる（受容した挙動）`）、将来また保持で救おうとする人はそのテストとこの節を
読むことになる。

### この節から得た教訓

同じ 1 つの条件式に、実装バグが 3 回連続で見つかった（第3ゲートの迂回／時間で減衰する量を出自の代理に
使う／イベント全体への免除保持）。**3 回とも「どの量で判定するか」の選択ミス**で、パラメータの値ではなく
判定量の意味を取り違えていた。共通していたのは次の 2 点。

- **粒度の不一致**: `requiredClusterSize` は「成分」単位で判定するのに、fast path は「イベント」単位
  （`memberKeys` の累積和集合）で数える。この 2 つを繋ぐ量を選ぶ場所が、3 回とも事故現場になった
- **時間で変わる量を出自の代理に使った**: `lastSize` も保持フラグも「今この瞬間の状態」であって
  「どう成立したか」を表さない。出自を問うなら出自そのものを渡すべきで、それが `compSize` だった

3 回すべて、**穴を再現するテストを書いて修正前に落ちることを確認してから**直している。免除を常時有効に
してテストを走らせると 4 件が落ちる（1 度目・2 度目・4 度目の防御テストと、受容した遅延の記録）ので、
このスイートは免除の緩みを検出できる状態にある。

**この 2 つの条件を足しても実地震の短縮は 1 秒も失われなかった**（実地震では震度3の点が出るとき周囲も
震度1 以上に達しているか、そもそも単点イベントだから）。

**震度4（3.5）を単点の境界にした理由**: 震度3（2.5〜3.4）で単点を許すと、§18 で塞いだ経路が開く。
実際、離れた 5 点が同時に value 3.0 で立つ既存の防御テスト（§18 由来）が落ちる。震度4 は学習床から
2 段階離れており、この段階付けなら**防御テストがそのまま通る**。

**意図的に免除しないもの**:
- `CONFIRM_FRAMES`(2) の連続要求。単点でも免除しない（落雷起因の単フレーム跳ね値を弾く安全弁）
- `CONFIRM_INTENSE_POINTS`(2) の第3ゲート（§18）。上記のとおり、点数が足りて課せる場面では必ず課す
- `MIN_LIKELY_POINTS`(3)。単点イベントは面が足りないので `likely`/`faint` にはならず `weak` に留まる。
  つまり**表示は静かなまま、fast path 経由の `confirmed` だけが早くなる**

### 検証

実データは Yahoo 強震モニタから取得し、同一ワークツリー内で変更を退避して「変更前」を測り直した
（厳密な A/B 比較）。

**短縮（初回 confirmed）**:

| 地震 | 最大震度 | 変更前 | 変更後 |
|---|---|---|---|
| 能登半島地震 2024-01-01 | 震度7 | 16:10:18 | **16:10:15（−3 秒）** |
| 能登 2023-05-05 | 震度6強 | 14:42:13 | **14:42:09（−4 秒）** |
| 根室半島南東沖 2026-07-21 | 震度3 | 11:25:43 | 11:25:41（−2 秒） |
| 福島県沖 2022-03-16 / 2021-02-13・日向灘 2024-08-08 | 震度6弱〜6強 | — | 各 −1 秒 |
| 豊後水道 2024・千葉県北西部 2021・奄美・大隅 | 震度3〜6弱 | — | 変化なし |

単点を無条件に許す案なら能登は −4 秒／−5 秒だったが、防御テストを守るため 1 秒譲っている。

**回帰なし**（窓の一覧は付録A）:
- 正のコントロール 17 件: 全件 confirmed 維持・到達フレームも完全一致
- 非検知カタログ 6 件: 非検知のまま（震度1〜2 なので段階付けが発火しない）
- 特異度 11 窓（平常 35 分＋深夜/日中 20 分＋欠測グリッチ窓＋海外 M7.4）: 誤発火 0・変更前と完全一致
- ユニットテスト 69 件（`kyoshinDetector.test.ts`。§29 の回帰テスト +12・パラメータの不変条件テスト +3・
  既存の意図的な反転 1 件を更新）。不変条件テストは `SOLO_CLUSTER_INTENSITY >= HIGH_CONFIRM_INTENSITY`・
  `HIGH_CLUSTER_POINTS <= MIN_CLUSTER`・`HIGH_CLUSTER_POINTS >= 2` を固定する。`requiredClusterSize` は
  `if` の順序に依存するため、値を 1 つ動かすだけで分岐の意味が静かに反転しうる（型チェックでは捕まらない）

**残る限界（受容）**: 震度3以下の単点は依然として検知しない。機器故障と区別する手立てが無いため
意図的に検知しない選択であり、`avail` による密度連動を将来足す余地は残っている。
震度4以上の単点故障（1 点が高値に張り付く形）は通るが、実データでは平常時に value≥2.5 の出現が
皆無であり、観測されていないリスクに対する分岐は足さない方針を維持した。

## 30. 値が下がりきったメンバーを外す（2026-08-21・能登本震リプレイでの利用者報告から）

**症状**: 2024-01-01 能登半島地震 本震の再生で、本震から数分〜十数分たった後に、揺れが収まった場所で
検知点が単独で立ち直る。利用者の報告は 2 つあった。

1. 石川以外の揺れが収まってカメラが寄らなくなった後、**長崎に震度0の点が 1 つだけ**現れてカメラが
   そこまで引かれた
2. 揺れが収まったはずの場所が単独で「再検知」される

**利用者に確認して分かった、本当に困る挙動**: 「検知が続くこと」ではなく、**一度カメラが寄った後に単独点で
全国へ引き戻されること**だった。1 と 2 はどちらもその形をとる。

**本節が扱うのは、その前提にある「メンバーが縮まないこと」**。これを直さない限り、画が絞られる状態そのものが
作れない。1 と 2 の症状そのものは本節では消えない（後述「残る課題」）。

イベントのメンバー（`memberKeys`）は和集合で単調増加し、揺れが収まっても縮まなかった。表示（検知点
マーカー・検知カード）とカメラフィットはこのメンバーを起点に組み立てられているため、値が下がりきった点が
イベントに残り続ける。実データで測ると、本震から 12 分後（16:22:40）の本震イベントのメンバーは 870 点で、
そのうち **658 点（76%）が震度0未満**——地図に描かれない帯にいる点だった。

長崎の 1 点はここに `dropIsolatedZeroPoints`（§22）の免除条件が重なって現れた。平戸の観測点（33.30/129.70）は
16:16:43 から value −0.5 に沈んでいたが、16:17:01 に量子化 1 段だけ上がって value 0.0 になった。これで
`rate = 0.5 = RATE_MIN` と `levelActive`（床は `FLOOR_MIN`=0.0 に丸められる）が同時に成立して onset 判定になり、
§22 の「直近に立ち上がった点は落とさない」免除が効いて 10 秒間描かれた。近くの震度1（33.30/130.30）とは
約 56km 離れており `ISOLATED_ZERO_RADIUS_KM`(30km) の外なので、免除が無ければ落ちていた点である。
本震イベントのメンバーでなければ、単点・震度0 では `requiredClusterSize`（`MIN_CLUSTER`=3）を満たさず
成分にもならない。

**対策**: メンバーに寿命を持たせた。`levelActive` を最後に満たしてから `MEMBER_DROP_MS` を超えた点を、
帰属の判断より先にメンバーから外す（`pruneFadedMembers`）。

- **今フレームに値が届いていない点（欠測・初出）は外さない。** 1 秒の瞬断でメンバーが落ちると、地図の点と
  カードの点数が明滅する（§25 で直した問題と同型）。欠測の穴埋めは表示側の保持機構の担当
- **占有セル（`cells`）は外さない。** 同じ場所の再 onset を同一イベントへ戻す錨で、これを失うと新規
  イベントが乱立する
- **判定への影響は無い。** 確定ゲートが数える対象はこの猶予より短い窓で絞られている——`lastSize` は
  sustained（`SUSTAIN_MARGIN` は `LEVEL_MARGIN` より高いので levelActive を含意）か直近 `TRIG_ACTIVE_MS` の
  onset、`maxIntensity`・`epicenter`・確定震度到達点数は levelActive のメンバーのみ。外れる点はどれにも
  寄与していない

### 猶予の下限は `TRIG_ACTIVE_MS + HOLD_MS`（敵対的レビューでの指摘）

当初 `MEMBER_DROP_MS` を `HOLD_MS` と揃えて 10 秒にしたが、**イベントが confirmed のまま生存しているのに
メンバーだけ空になる窓**が作れることが敵対的レビューで判明した（2 つのレビューが独立に同じ穴を指摘し、
`step()` を直接叩いて再現した）。

機序はこうである。ある点が onset した直後に値が沈むと、その点は onset から `TRIG_ACTIVE_MS`(8s) の間
`lastSize` に寄与し続ける（`updateEventMetrics` 内の `recentOnset`。現在の値を見ない。同名の変数が `step()` の
L2 にもあるが、あちらは `COINCIDENCE_MS`(4s) 窓で成分を作るための別物）。一方 `lastLevelActiveAtMs` は onset の
瞬間で止まる。イベントは `lastOnsetAtMs`（最後に size が 1 以上だった時刻）から `HOLD_MS`(10s) で解除される
ので、猶予が **8 + 10 = 18 秒**を下回ると、メンバーの刈り取りがイベントの解除より先に完了してしまう。

この窓は表示に響く。`deriveKyoshinView` の `detectedPoints` が空になり、地図側の `hasDetection` が false へ
落ちて、`FitToDetectionGL` がカメラを全国表示へ戻す。**この節が直そうとしている「画が全国に張り付く」の
裏返し（検知中に画が戻る）**を作ってしまう——`CameraFollowsGL` が「描ける点が無いこと」と「検知が終わった
こと」を別の入力に分けている理由そのものを崩す形だった。

`MEMBER_DROP_MS` を 20 秒（下限 18 秒＋余裕 2 秒）に改め、不変条件をテストで固定した。刈り取りが遅れる
ぶん「下がりきった点」は長く残るが、狙いは分オーダーで居残る点を消すことなので影響しない。

**この穴は型チェック・実データ回帰（付録A の 41 窓）のどちらでも検出されなかった**。回帰が比較するのは
初 likely・初 confirmed・継続フレーム数で、`memberKeys` の時系列は見ていない。ユニットテストも当初の
`fade()` ヘルパーが 1 点を揺らし続ける形だったため、sustained 経路しか通っておらず recentOnset だけで
size を維持するケースを踏んでいなかった。**「メトリクスが変わらないこと」を確かめても、その配列そのものが
別の意味（検知が続いているかの代理）で使われていれば意味が違う**——同じ量を別の目的で読む場所を数え
落とすと、こうなる。

### 併せて直したこと

- **`memberOverlapFrac` の分母を成分側に固定した**（`min(|a|,|b|)` → `|a|`）。メンバーが縮むようになると、
  痩せた古いイベントが大きな成分を飲み込む向き（メンバー2点のイベントに30点の成分が1点だけ共通していれば
  `1/2 = 0.5` で `MERGE_MEMBER_FRAC`(0.34) を超える）が現実的になる。そうなると新しい地震が古いイベントの
  続きとして扱われ、`everConfirmed` のラッチで初検知の発報が鳴らない。分母を成分側にすれば「小さな成分が
  大きなイベントへ帰属する」向き（分子＝分母で 1.0）は保たれたまま、この向きだけが締まる
- **刈り取りの件数を観測できるようにした**。`step()` が今フレームで外した延べ点数を返し、
  `window.__kyoshinV2.prunedMembers` に載せる。点を静かに消す処理は失敗しても例外が出ないため、
  `dropIsolatedZeroPoints` を `recentOnsetKeys` の件数で追っているのと同じ趣旨
- **「メンバーは縮まない」と述べていたコメント・仕様書を直した**（コード 5 箇所・ドキュメント 3 冊＝
  仕様書 2 冊と本設計書 §22）。これらは
  単なる説明ではなく「だから `hasDetection` を素のメンバー和集合にしておける」という設計判断の根拠として
  書かれていたので、前提が崩れたまま残すと同じ穴を再生産する

### 検証

- ユニットテスト: 正（猶予を超えた点が外れる）・対照（猶予の手前では外れない）・安全弁 4 種
  （点数と最大震度が変わらない／欠測では刈らない／イベント生存中はメンバーが空にならない／
  `MEMBER_DROP_MS >= TRIG_ACTIVE_MS + HOLD_MS`）・平戸の再現（刈られた点が単独で震度0まで立ち上がり
  直しても成分にならない）。穴の再現テストは修正前に落ちることを確認してから直している
- 実データ回帰: 付録A の 41 窓すべてで、初 likely・初 confirmed・confirmed 継続フレーム数が変更前と
  完全一致。唯一の差は `big-fukushima2022` の「confirmed 最大 size」711→710
  - これは `mergeAdjacentEvents` が `lastSize` を**合算**しつつ `memberKeys` は**和集合**にしている既存の
    非対称性による（ピークのフレームで size=710 に対しメンバーは 477 点・他イベントとの共有 107 点）。
    刈り取りが合算相手のメンバーを 1 点削ったぶんが出た。`lastSize` の消費先はデバッグログ 1 箇所だけなので
    利用者への影響は無い。この非対称性自体は本節の範囲外
- 実機（DMDSS 版・能登本震を 16:06 から再生）: 本震から 12 分後（16:22:33）の時点で、地図に描かれる
  検知点は 123 点・範囲は経135.4〜140.7／緯34.7〜38.9（中部〜東北南部）に収まっていた。本震イベントの
  メンバーも 180 点で頭打ちになる（変更前は 870 点まで増え続けた）。揺れ検知のエラー・`step()` の失敗は 0

**この節は「長崎に震度0 が 1 点だけ立つ」症状そのものは解消していない。** 平戸の点は震度1（value 0.5）と
震度0（value 0.0）の間を往復していて、床（`FLOOR_MIN` で 0.0 に丸められる）を割ったのは 16:16:43〜16:17:00 の
**17 秒だけ**だった。20 分の窓で levelActive に達した回数は 284 回である。つまりこれは「値が下がりきった点」
ではなく「境界を跨ぎ続ける点」で、20 秒の猶予では刈れない（10 秒なら刈れるが、上記のとおり 10 秒は使えない）。
16:17:01 に量子化 1 段だけ上がって onset 判定になり、§22 の免除で 10 フレーム描かれることは変更後も同じ。

**1 つの定数に 2 つの要求を負わせようとしたのが誤り**だった。「メンバーが無限に増えるのを止める」ことと
「境界を跨ぎ続ける単点を描かない・カメラに追わせない」ことは別の機構が担うべきで、後者はフィット目標に
震度の下限を入れる（実データでは震度1以上にすると 16:17:01〜16:17:10 の西端が 130.3 に留まる）か、§22 の
免除に賞味期限を持たせるのが候補。**本節の狙いは「一度絞られた画が引き戻されない前提を作ること」**に
あり、フットプリントが実際に収縮するようになった点でそれは達成している。

### 残る課題（本節では直していない）

**利用者報告の 1（長崎の震度0 単点）**: 上記のとおり、境界を跨ぎ続ける点は刈り取りでは消えない。カメラに
追わせないだけなら、フィット目標（`JapanMapGL` の `detectedFitPoints`）に震度の下限を入れるのが最短で、
実データでは震度1以上にすると 16:17:01〜16:17:10 の西端が経130.3 に留まる（フィット目標の点数は 291→228）。
描画そのものを消すなら §22 の免除に賞味期限が要る。**利用者の判断で本節には含めていない**——困るのは
「寄った画が引き戻されること」であって、既に広い画に小さな点が 1 つ増えること自体ではないため。

**利用者報告の 2（揺れが収まった場所の単独「再検知」）**は別経路で、刈り取りでは止まらない。実データでは
16:11:25 に富山の 1 点が震度5強相当で新規イベントとして生まれ、2 フレームで confirmed に達している
（`SOLO_CLUSTER_INTENSITY` による単点成分＋高震度 fast path。§29）。値が高い点は刈られないため、
帰属側（1 フレームに 1 イベントは 1 成分しか受け取れない `updated` ガード・重心が全国平均へ流れることで
`MERGE_EVENT_KM` の併合が効かなくなること）と fast path の初動限定を検討する必要がある。

## 31. 別地点発報の 3 判定をデータ時刻で測る（2026-08-22・ライブとリプレイで長さが変わる問題）

**きっかけ**: v4.20.0 のリリース後レビュー。観測された誤動作ではなく、**同じ定数がライブとリプレイで
違う長さを意味していた**という整合性の問題。

`stepAlertRegions`（`useKyoshinAlerts.ts`）の 3 判定は、フレームの到来回数を数える通し番号（`tick`）で
測っていた。フレームの供給側を見ると:

| 供給元 | 次のデータ時刻 | 帰結 |
|---|---|---|
| ライブ（`kyoshinSource.ts`） | `max(前回 + POLL_MS, serverNow() - FETCH_OFFSET_MS)` | 取得が遅れると最新へジャンプし、**コマを飛ばす** |
| リプレイ（同） | 常に `前回 + POLL_MS` | 必ず 1 秒ずつ這う |

> この表は当時の実装。リプレイはその後**再生時刻より先の秒を取ってキューへ積む**形へ変わったが
> （`data-sources-spec.md` §4「リプレイは先に取って積む」）、**1 フレーム = 1 データ秒は保たれる**
> ので下の整理の前提は変わらない。

`POLL_MS` は 1000。つまりリプレイでは「1 フレーム = 1 データ秒」が常に成り立ち、ライブでだけ崩れる。
**この不一致はリプレイでも `npm run bench-kyoshin` でも原理的に再現できない**（どちらもリプレイ経路）。
検知エンジン本体（`kyoshinDetector.ts`）は時刻をすべて `frame.dataTimeMs` から供給する方針なので、
そちらへ揃える整理でもある。

### 置き換えた 3 つ

| 旧 | 新 | 1 秒フレームでの等価性 |
|---|---|---|
| `reg.seen >= REGION_PERSIST_TICKS`(3) | `nowMs - reg.firstSeenAtMs >= REGION_PERSIST_MS`(2 秒) | 登録フレームは経過 0 なので 3 フレーム目でちょうど成立 |
| `tick - lastNewRegionTick >= NEW_REGION_COOLDOWN_TICKS`(5) | `nowMs - lastNewRegionAtMs >= NEW_REGION_COOLDOWN_MS`(5 秒) | 一致 |
| `tick - r.lastTick <= REGION_PRUNE_TICKS`(3) | `nowMs - r.lastSeenAtMs <= REGION_PRUNE_MS`(3 秒) | 一致 |

併せて `AlertRegionState.tick` と `AlertRegion.seen` を落とし、`lastTick` → `lastSeenAtMs`、
`lastNewRegionTick`（番兵 `-999`）→ `lastNewRegionAtMs: number | null` にした。

### 破棄はフレームの末尾に残した

破棄を末尾で行うため、照合の対象として残る時間は猶予より長い。1 秒フレームなら 1 フレーム分（旧実装と
同じ）だが、**コマ飛びのときはその飛び幅ぶん伸びる**。猶予を超えた古い地域が、飛びの直後の 1 フレーム
だけ照合されうる。

冒頭で破棄する案を検討して**採らなかった**。冒頭に移すと、飛びが猶予を超えた瞬間に現存する地域が
まとめて捨てられ、同じフレームの確定点が**新規地域として登録し直される**。新規地域の `fired` は
「進行中の検知なら false」なので、発報済みの地域や震源近傍の地域が持続到達後に別地点として鳴り直す。
古い地域が 1 度だけ照合されることより重い誤発報になる。

### 持続判定は「回数」ではなく「幅」になった（承知の上の緩み）

旧 `seen` はマッチのたびに増える累積カウンタで、**3 回の実観測**を要求していた。新実装は初検知からの
経過時間だけを見るため、途中の観測が欠けても幅が足りれば満たす。**最短は登録＋再観測の 2 回**で、
1 観測分ぶん緩い。欠落の長さに上限を与えているのは `REGION_PRUNE_MS` だけで、この判定自身は連続性を
検証しない。

回数の下限を別途置く案もあったが、回数で数えることがそもそも今回消した不一致の正体なので採らなかった。
**緩みは代償として引き受け、テストで固定してある**（下記）。他のゲート——`NEW_REGION_MIN_INDEX`（震度3）・
`absorbedByEew`・距離の上限・クールダウン——は変えていない。

### 回帰テスト

`useKyoshinAlerts.test.ts` に 8 件（正 5・対照 2・安全弁 1）。いずれも合成フレームで、ライブのコマ飛びと
観測の欠測を人工的に作る。**旧実装（tick 方式）で通るのは 2 件だけ**で、残る 6 件は落ちる。

通る 2 件は、この変更で動かしていないものを押さえている——1 秒刻みではクールダウンの境界（4 秒で鳴らず
5 秒で鳴る）が変わらないこと、コマ飛びを挟んでも `fired` が保たれて同じ地域が二度鳴らないこと。

落ちる 6 件が、フレーム数で数えていたために起きていた差そのもの。何を突いているかで分かれる。

| 突いている判定 | 件数 | 旧実装での落ち方 |
|---|---|---|
| 持続 | 2 | 発報すべきところで `null` が返る |
| クールダウン | 1 | 同上 |
| 破棄猶予 | 3 | 刈られるべき地域が残り、地域数が合わない |

個々の内容はテスト名（`[正・…]` / `[対照]` / `[安全弁]` のタグ付き）に書いてあるので、ここには写さない。

**破棄猶予もフレーム数依存だった**点は見落としやすい。tick 方式では大きなデータ時刻のジャンプでも tick は
1 しか進まないため、**現れなくなった地域が猶予を過ぎても刈られず、`fired=false` のまま居座る**。上の表で
破棄猶予が 3 件あるうち 1 件は `[対照]` タグのテストで、名前に「破棄猶予」が入っていない——**冒頭の
アサーションが刈り取り漏れで落ちる**ため、数えるときに落としやすい。

実データ回帰ベンチは回していない。`scripts/bench-kyoshin.ts` は `useKyoshinAlerts` を参照せず
`stepAlertRegions` を通らないため、回帰の証拠にならない。

## 32. 周囲の同時上昇を likely の条件にする（2026-08-23・利用者が記録した誤検知 30 件から）

利用者から「揺れ検知の音が鳴ったのに地震情報が出なかった」時刻が 30 件報告された。1 日 4〜6 回の頻度。

### 何が起きていたか

30 件のうち 18 件を Yahoo のアーカイブから秒単位で再現できた。判で押したように同じ形をしている。

```
size=3  最大=0.5(震度1)  震度1に達した点=1  上位=[0.5, 0.0, 0.0]  → likely
```

3 点が 4 秒以内に立ち上がり、**うち 1 点だけが震度1 の下端、残り 2 点は震度0**。これで likely になり、
候補音が鳴ってリアルタイムタブへ自動で切り替わる。

`confirmed` には §18 で `CONFIRM_INTENSE_POINTS`（確定震度に達した点が 2 点以上）を置いてあるが、
`likely` には課していない。弱い実地震（福岡 M2.4・§17）を取りこぼさないための判断だった。

気象庁の発表と突き合わせると、18 件のうち本物は 1 件（熊本県天草・芦北 M2.7 震度1）だけで、残りは
誤検知。地点は東京江東区亀戸・荒川・墨田、茨城坂東市役所・守谷、千葉旭市・香取、北海道釧路——
**都市部の常習点に集中**していた。

### 瞬間の値の並びでは分けられない

`pc-fukuoka`（福岡県筑後 M2.4 震度1・付録Aの正のコントロール）の likely も `size=3 上位=[0.5,0.0,0.0]` で、
誤検知と**完全に同一**。その瞬間の値だけを見るかぎり、どんな閾値を置いても両者は分けられない。

そこで「`likely` にも確定震度到達点数を課す」案を実データで測った。誤検知は 18→8 件に減るが、
福岡型（1 点だけ震度1 の弱い実地震）を丸ごと失う。取りこぼしを増やさずに誤検知だけを減らす軸が要る。

### 捨てていた情報 — 床下の一斉上昇

L1 の `levelActive` は絶対レベル（点別床）で切るため、**床（震度0）に届かない点の立ち上がりを丸ごと
捨てていた**。実地震は震度0 未満の点まで一斉に持ち上げるのに対し、局所ノイズは周囲を動かさない。

イベント重心から半径 50km の観測点について、同じ 2.5 秒窓で `RATE_MIN` 以上上がった点の割合を測ると
こう分かれた（`likely` に達した瞬間のフレーム）。

| | 割合 |
|---|---|
| 気象庁が発表した地震で likely 止まりだったもの（福岡型・5 件） | 22〜26% |
| `pc-fukuoka`（福岡 M2.4） | 22% |
| 都市部の常習点による誤検知 | 2〜12% |

閾値 15% で分かれる。

### 試して駄目だった軸

| 案 | 結果 |
|---|---|
| 地中（ボアホール）観測値との比較 | Yahoo の配信は地表の計測震度のみ（`realTimeData.intensity`）。使えない |
| 常習点の長期学習 | 「よく誤検知する点」は「よく本物を捉える点」でもある（熊本美里町馬場: 誤 32 回／本物 122 回）。回数で罰すると微小地震の多い地域を鈍らせる |
| 揺れが減衰するか | 分離しない。リアルタイム計測震度は 30 秒経ってもピーク値を保つ（誤検知 13 件・本物 12 件で減衰 0.0） |
| 伝播の整合性（距離と立ち上がり時刻の順位相関） | M2 級は 40km 圏の立ち上がりが 2〜3 秒に収まり、1 Hz では順序が付かない。弱い地震ほど不利で守りたいものと逆を向く |

### ラッチが要る理由

`rising` は上昇量で判定するため、**周囲が持ち上がるのは波が通り過ぎる 1〜2 秒だけ**で、その後は横ばいに
なって偽に戻る。毎フレーム評価にすると揺れの最中に条件を割り、`faint` へ落ちる。実際、ラッチを外して
ユニットテストを回すと 6 件落ちる（§18・§16 が置いた既存テストを含む）。

問うべきは「いま周囲が上がっているか」ではなく「**周囲が一度でも裏付けたか**」。一斉に動いた事実は
後から消えない。副次的に、確信度が `likely` と `faint` を往復して候補音が鳴り直すのも防げる。

### 疎地域の救済を置かなかった理由

当初は「圏内の点が 3 未満なら判定を見送る」保護を入れたが、実データ 793 窓で**一度も働かなかった**。
`likely` はそれ自体が 3 点の広がり（`MIN_LIKELY_POINTS`）を要求するため、圏内が 3 点未満になる状況が
そもそも起きない。

むしろ穴になる。**大量欠測の瞬間だけ分母が縮んで判定を素通しし、ラッチで `likely` が開きっぱなしに
なる。** 欠測グリッチ（§付録Aの `glitch-0724`）はまさに守りたい相手なので、そこへ向けて緩む分岐は
置かない。圏内に点が 1 つも無ければ偽を返す。

### 検証

`npm run bench-kyoshin` の全 793 窓で測った（変更前との差分）。

| | 変更前 | 変更後 |
|---|---|---|
| 正のコントロール 17 件 | 17/17 | **17/17** |
| 大地震 7 件 | 7/7 | **7/7** |
| 非検知 6 件 | 6/6 | **6/6** |
| 気象庁発表 711 件の confirmed | 477 | **477（初 confirmed が動いた窓は 0）** |
| 気象庁発表 711 件の likely | 67 | 66 |
| 無関係な検知（全分類） | 64 件 | **22 件** |
| 報告された誤検知 30 窓の合格 | 11/30 | **21/30** |

段階が下がった実地震は **1 件だけ**（熊本県熊本地方 M2.1 震度1・2026-08-01 06:25）。生データを追うと
益城・山都で 3〜4 点が同時に持ち上がる本物だが、圏内 23 点に対して 13〜17% で閾値をわずかに下回る。
これ以上ないほど弱い信号で、判別の限界に置かれた 1 件。

初 likely は 34 窓で遅れたが、**32 窓が 1 秒・1 窓が 2 秒・1 窓が 3 秒**。いずれも `confirmed` は同じ秒に
到達する（＝検知音の時刻は変わらない）。

### 測る道具のほうを 2 度直した

この検証の途中で、ベンチの「その地震を検知したか」の判定を 2 度直している。**どちらも、直す前は
検知エンジンの評価そのものを誤らせていた。**

1 度目は距離が一律に広すぎた。M2.4 の地震の窓で 185km 離れた常習点のノイズを「その地震を検知できた」と
数えており、対策で誤検知が消えたときに「取りこぼしが増えた」ように見えた。規模で距離を変えて直した。

2 度目はその規模依存が**深さを見ていなかった**。深発地震は震央の周りではなく、スラブに沿った先
（太平洋側）が強く揺れる——異常震域。日本海北部 M5.6 深さ350km の窓で岩手・宮古市の検知（641km）を、
渡島地方東部 M3.9 深さ130km の窓で十勝・豊頃町の検知（246km）を、それぞれ「無関係」に数えていた。
「M3.9 が 246km 先を揺らすはずがない」という規模だけの見立てが誤りで、どちらも起こって当然の姿だった。

**評価の道具が間違っていると、対策の良し悪しの判断ごと間違える。** 深さを入れたことで
「無関係な検知」は 38→11 件（気象庁発表の窓）に減り、確定検知の総数も 476→477 に戻った。

### 残る誤検知

ゲートを通り抜ける誤検知が 9 件残る（珠洲・勝山・王滝・小野町・本別・三原・氷川・宮崎ほか）。いずれも
能登・飛騨・熊本群発・十勝・日向灘といった地震活動域で、周囲の同時上昇も 13〜46% ある。**手持ちのどの
軸で測っても本物の地震と区別が付かず、発表基準（震度1）に届かない本物の微小地震である可能性が高い。**

## 33. 単点のまま居座る確定を降ろす（2026-08-24・診断ログが捉えた実例から）

**症状**: 2026-08-24 04:04:37、茨城の観測点 1 点だけで確定検知が立ち、記録の最後（33 秒後）まで降りなかった。
気象庁の発表は無い。同じ時刻に熊本で M3.9 震度3 があったが、900km 離れている。

**診断ログ**（[`settings-pwa-spec.md`](settings-pwa-spec.md) §12・`utils/detectionDiagnostics.ts`）が残した生の値で正体が判った。

```
index: 0 0 0 ...(28個)... 0 20 20 20 20 ...(33個)... 20
                            ↑ 04:04:35
```

`0` は取りうる最小値（value −3.0）、`20` は最大値（value 7.0＝震度7）。**40 段の階段を 1 フレームで
駆け上がり、そのまま 30 秒以上まったく動かない。** 近傍 50km の 30 点は −1.5 のまま一切反応しなかった。
震度7 の揺れで周囲 30 点が無反応というのは物理的にありえず、センサーかデータの異常である。

### なぜ降りられなかったか

2 つが独立に効いていた。

1. **イベントが期限切れにならない。** `updateEventMetrics` 末尾の `if (size > 0) e.lastOnsetAtMs = now` は、
   `sustained`（床を明確に超えて継続中）なメンバーがいる限り毎フレーム走る。上限に張り付いた点は永久に
   `sustained` なので `HOLD_MS`(10s) の砂時計が一度もひっくり返らない
2. **確信度が降りない。** `everConfirmed` は期限のないラッチ。実測では `confirmStreak` が 6 秒後に 0 へ
   落ちている（成分が帰属しなくなり高震度 fast path の免除が切れるため）のに、ラッチが `confirmed` を
   維持し続ける

### 鳴らすこと自体は正しい（利用者の判断）

当初は「周囲の同時上昇（§32）を高震度 fast path にも課す」案を検討したが、**利用者の指摘で取り下げた**。

> この場合音を鳴らすのはしょうがないかなと思います。大地震の場合端点のみ立ち上がって遅れて周囲に
> 伝播することもある（能登地震等）ので。ただそれをずっと保持し続けてしまうのが問題かなと思いました。

震源最近傍の 1 点が先行する初動は実地震の正常な姿で、§29 はまさにそれを拾うために fast path を入れた。
発報を遅らせる方向の対策は、守りたいものと逆を向く。**直すべきは「周囲が続かなかったときに降りられない」
ほう**である。

### 判定材料の選定（実データ 793 窓）

「周囲が続いたか」をどう測るかで 2 案を比較した。

| 案 | 結果 |
|---|---|
| `everNeighborRise`（§32 のラッチ） | **使えない。** 確定検知 148 件のうち 16 件で最後まで立たなかった。能登・福島の大地震で `lastSize` が 46 に達しているものを含む |
| `lastSize` が 2 以上になったか | **分かれる。** 823 件すべてがいずれ到達し、最後まで単点だったものは 0 件 |

母数が違うのは測った範囲が違うため。前者は正のコントロール・大地震・非検知・平常時の 52 窓で当たりを付けた
段階（148 件）、後者は全 793 窓へ広げた本測（823 件）。

`lastSize >= 2` に達するまでの時間（気象庁発表の地震に紐づく確定検知 823 件）:

| | 件数 |
|---|---|
| 確定した時点で既に単点でなかった | 817 |
| 確定より後で 2 点目が続いた | 6（2 / 2 / 4 / 5 / 9 / 55 秒） |
| 最後まで単点のままだった | **0** |

55 秒の 1 件は §30「残る課題」の富山の単独再検知そのもので、降ろしたい側にあたる。それを除けば
**最長 9 秒**。`SOLO_CONFIRM_GRACE_MS` を 20 秒に置けば 2 倍以上の余裕がある。

`SOLO_DECAY_SIZE` を `MIN_CLUSTER`(3) ではなく 2 にしたのは、`size >= 3` を要求すると size 2 で終わる本物
（能登・福島の大地震の成分）を 4 件巻き込むため。

### 実装で 3 度直した

**1 度目: 点数だけを見ていた（敵対的レビューの指摘）。** メンバーは `mergeAdjacentEvents` で和集合になり、
併合は重心が `MERGE_EVENT_KM`(100km) 以内なら成立する。**離れた場所で別々に張り付いた 2 点が併合されると
点数だけは 2 になり、この対策が丸ごと素通しになる。** 複数局が同時におかしくなる事象は実在する
（付録A の `glitch-0724` は全国の半数近くが急落・復帰し 34 局が同時に立ち上がる窓）。
数えるのを「隣り合う対があるか」（`hasAdjacentPair`・L2 が成分を作るときと同じ `R_KM`）へ改めた。

**2 度目: 状態を書き換えていた。** 当初は `everConfirmed = false` と書き戻す実装だった。これだと確定条件を
満たし直した瞬間に再確定し、**猶予の周期で `confirmed` と `weak` を往復する**（実測: 離れた 2 点が張り付く
合成フレームで 21 秒 confirmed → 2 秒 weak → 再確定）。`useKyoshinAlerts` は確定の立ち上がりで検知音を
鳴らすため、**明滅は居座りより悪い**。状態は触らず、確信度を決めるときの述語（`isSoloConfirmStale`）に
改めた。

**その過程でもう 1 つ見つかった。** 確信度を書く箇所は `updateEventMetrics` と `mergeAdjacentEvents` の
**2 つある**。述語を前者にしか置かなかったため、併合が走ったフレームだけ `everConfirmed` から
`confirmed` が付け直され、能登の富山イベントが復帰の瞬間に 1 フレームだけ跳ねた。**1 フレームでも
立ち上がれば音が鳴る。** 判定を `isSoloConfirmStale` に集約して塞いだ。

**3 度目: 降ろした先が `weak` とは限らなかった。** 併合は「重心間 `MERGE_EVENT_KM`」で greedy に連なるため、
互いに `R_KM` を超えて離れた 3 点でも 1 本化しうる（重心が動くので配置は選ぶ。実測では 55km 間隔の 3 群で
成立した）。このとき `lastSize` は併合で**合算される**ため `MIN_LIKELY_POINTS` に届き、`spreadHeld` が立って
降格後に `faint` へ、条件が揃えば `likely` にまで上がる。**`likely` は候補音を鳴らす。** 「本物ではない」と
判断して降ろしたものが下から出てくるのでは意味が無いので、述語が真の間は `weak` に固定した。

### この節から得た教訓

**「一度きり」を意味するラッチに、期限と降り方を用意しておくこと。** `everConfirmed` は §18 以来
「明滅防止」の役割で置かれてきたが、降りる契機が `HOLD_MS` の満了しか無く、その満了自体が別の条件
（`size > 0`）に握られていた。**2 つの機構が互いの前提になっていると、片方が壊れたときにもう片方も
効かなくなる。**

**降ろし方は「状態を戻す」より「述語で覆う」ほうが安全。** 状態を戻すと、その状態を作る経路が全部
復活の経路になる。述語なら覆う条件だけを見ればよい。

### 検証

- ユニットテスト 10 件（正 1・対照 2・安全弁 7）。**いずれも該当の処理を外すと落ちることを確認してから入れた**

`lastOnsetAtMs` が毎フレーム更新されてイベントは生き続ける（確信度が `weak` なので表示からは外れる）。
寿命に踏み込むと本物の余韻まで切りかねないため、ここでは確信度だけを扱った。

イベント単位の挙動ではない。

### 「その地震を検知した」と数えてよい条件（なぜこの形か）

検知イベントの重心が震央から一定距離以内にあり、かつ発生時刻より後であること。**しきい値と実装は
`scripts/bench-kyoshin.ts` の `relatedQuake` / `relatedKmFor` が持つ**（ここに数値を写すと必ず食い違う）。
設計上の要点は 3 つ。

- **距離は規模で広げ、深発地震はさらに広く採る。** 大きな地震ほど遠くまで揺らす。加えて深発地震は
  震央の周りより**スラブに沿った先（太平洋側）が強く揺れる**（異常震域）ため、震央からの距離という
  尺度がそもそも当てはまらない。規模だけで決めていたときは、遠地の本当の揺れを「無関係な検知」に
  数えていた（設計書§32「測る道具のほうを 2 度直した」）
- **判定はイベント単位で、窓を流し終えてから行う。** イベントの重心は揺れの広がりに合わせて動くため、
  立ち上がり直後は震央から離れていて後から寄ってくることがある。フレームごとにその場で数えると、
  同じ揺れを「無関係な検知」と「その地震の検知」の両方に計上してしまう
- **時刻の条件は素直に効く。** 発生時刻より前の検知はその地震のものとみなさない（気象庁の発生時刻は
  分単位なので、分の頭から遡れる幅だけ許す）

**この区別が無いと集計が静かに嘘をつく。** 2026-08-23 の調査では、トカラ列島近海の地震の窓で東京の観測点が鳴って
いたのを「その地震を検知できた」と数えていた。対策を入れて誤検知が消えたとき、集計上は「取りこぼしが増えた」に
見えてしまう。

## 34. 判定の根拠を外へ出す（2026-08-30・実装計画 59 番の実装から）

### 何が足りなかったか

検知カードは確信度を 4 段（`confirmed` / `likely` / `faint` / `weak`）のチップで示していたが、
**なぜその段なのかは画面から一切読めなかった**。誤検知を議論するときも、パラメータを調整するときも、
「この検知は何を根拠に確定したのか」を知るにはコードを読むしかない。

### 数値の確信度は作らない

「確信度 82%」のような値は作らなかった。エンジンは確率モデルではなく、**決定的なゲートの通過判定**で
段を決めている（§4 L4）。中間の連続量を持っていないので、割合へ均すと実装が持っていない精度を装う
ことになる。出せるのは「どの条件をいくつ満たしたか」「あと何が足りないか」だけ。

### 判定は変えず、判定した値を持ち帰る

`updateEventMetrics` が確信度を決めるのに使った要求値と中間集計を、**決め終わった後に 1 箇所だけで**
`DetectionEvent.gates` へ書く。分岐の入力にはしない——表示用の構造体が判定の一部になると、片方を
変えたときにもう片方が黙って変わる。

イベント自身が既に持っている値（`lastSize`・`maxIntensity`・`confirmStreak`・`everNeighborRise`）は
複製しない。`mergeAdjacentEvents` が本体だけを書き換えたときに二重管理が食い違うため、`gates` に
置くのは**要求値とイベントに残らない中間集計だけ**にした。

実データ回帰（`npm run bench-kyoshin`・793 窓）でベースラインとの差分が 0 であることを、実装の前後で
確認している。

### 現フレームの内訳だけでは「なぜ確定したか」が残らない

確定後は震度が減衰して点数も減り、`everConfirmed` のラッチだけが確信度を支える局面が普通に来る。
その状態で現フレームの内訳を見せると「確定しているのに、確定の条件をどれも満たしていない」表になる。

そこで**確定した瞬間の判定材料を凍結する**（`ConfirmSnapshot`）。書くのは
`firstConfirmedAtMs === now` のフレーム、つまり確定した当のフレームだけ。

### 併合で内訳がずれる 3 つの箇所

`mergeAdjacentEvents` は本体の値を書き換える（点数は合算・最大震度は max・確定時刻は早いほうへ）。
内訳を追従させないと、点数だけ倍になって内訳が古いままの表ができる。追従で判断が要ったのは 3 つ。

| 項目 | どうしたか | 理由 |
|---|---|---|
| `confirmedBy` | **先に確定したほう**を採る | `firstConfirmedAtMs` を早いほうへ揃えるのと対の操作。揃える**前**の値で選ぶ |
| `intenseCount` | バーが揃っているときだけ合算する | 数える閾値（`confirmIntensityReq`）は慢性活性セルかどうかでイベントごとに変わる。違うバーで数えた点を混ぜた数を出すより、片側だけの数を出すほうがまし |
| 要求値（`sizeReq`・`streakReq`） | host のものを残す | 引き直すには `avail`・`cellActivity` が要るが `mergeAdjacentEvents` には渡っていない。ずれるのは併合フレームの 1 秒だけで、次フレームには引き直される |

**`intensityReq` だけは例外で、host に据え置かず両者の max を採る。** `intenseCount` を上の規則で
選ぶ以上、表示する閾値も選んだ側に合わせないと数と単位が食い違うため。要求値だからといって
一律に host 据え置きではない。

`highIntenseCount` は `HIGH_CONFIRM_INTENSITY` という**全イベント共通の定数**で数えるため、この問題を
持たない（そのまま合算してよい）。

### `DetectionGates` にフィールドを足すとき

併合の扱いは、そのフィールドが**イベント間で同じ基準になるか**で決まる。足す前にどちらかを決めること。

| 性質 | 例 | 併合での扱い |
|---|---|---|
| 全イベント共通の定数から来る | `highIntenseReq`・`highIntensityReq`・`likelyIntensityReq` | 据え置き。数え上げなら合算してよい |
| イベントごとに変わりうる | `intensityReq`（慢性活性で変わる）・`sizeReq`（慢性活性・密度・EEW で変わる） | **合算しない。** 基準が揃うときだけ足すか、片側を選んで基準も揃える |

判定を誤ると、違う基準で数えた値を混ぜた数が「根拠」として画面に出る。例外は出ない。

### 敵対的レビューが見つけたもの

**「一度入ったら上書きしない」と書いたコメントが実装と食い違っていた。** `confirmedBy` は
`mergeAdjacentEvents` が正当に差し替える。この誤った前提のまま診断ログ側を「到着順で先勝ち」に
していたため、併合が起きると**画面が出している根拠と記録に残る根拠が食い違ったまま固定される**穴が
できていた。例外は出ないので、書き出した記録を読むまで誰も気づかない。

直し方は、`ConfirmSnapshot` に確定時刻（`atMs`）を持たせ、記録側もエンジンと同じ基準
（確定時刻の早いほう）で選ぶこと。両者が同じ基準を見ていれば必ず一致する。

**確信度より先に「秒読み中か」を見る。** 確定の条件（`meetsConfirm`）は周囲の裏付け
（`everNeighborRise`）を見ないが、`likely` へ上げる条件は見る（§32）。そのため「確定へ向けて
`CONFIRM_FRAMES` の秒読みに入っているのに確信度は faint」が普通に起こる——震源最近傍の単点が先行する
高震度 fast path（§29）の典型がこれ。確信度で先に分岐すると、この状態で「周囲の裏付け待ち」という
**確定には要らない条件**を残り条件として示してしまう。

### 利用者に見せる言葉

内訳の表は開発者だけのものではない——検知カードは一般利用者の画面なので、**折りたたみの中も
利用者が読む文字列**として扱う。エンジンの内部用語（「フレーム」「spread」「近傍一致」）は仕様書に
しか定義が無く、表を開いた人には手がかりが無い。

連続して条件を満たした回数は、内部では 1 秒ごとの処理単位（フレーム）で数えているが、画面では
「あと約N秒」と時間で言う。「約」を付けているのは、観測値が届かなかった秒は判定が進まないため。
判定が 1 秒ごとであることは表の下の注記で伝える。

### 前提が正しかったもの

実装計画（`docs/implementation-plan.md`）はこの項目を「基盤B（onset 時刻の外部公開）が要る」と
していたが、**要らなかった**。判定の根拠はイベント単位のゲート値で完結しており、点単位で要るもの
（onset した点・確定揺れ点）は `step()` が既に `triggers` / `recentOnsetKeys` で返していた。
onset 時刻そのものを外へ出す必要があるのは、揺れの進行方向を描く項目のほう。

## 35. 検知が止まったまま凍結する状態を解く（2026-08-31・震度0ドットの床フィルタ修正のレビューから）

震度0ドットの慢性ノイズ床フィルタを直す作業のレビューで、検知エンジンの早期 return に安全弁が
片方しか無いことが見つかった。`step()` が例外を投げる経路には「連続したら結果を空にする」がある
（§23）のに、**観測点数と震度の件数が食い違って `step()` へ入れない経路には無い**。後者に落ちると
`setResult` を呼ばずに抜けるため、その瞬間に出ていた検知イベントが**異常が続く限り凍結**し、音・
自動タブ切替・自動フィット・地図・検知カードへ流れ続ける。

### カウンタを理由ごとに分けない

理由（例外／件数の食い違い）は違っても、表示から見た帰結は同じ「結果が凍結している」。1 本のカウンタで
「結果を出せないフレーム」を数える形にし、定数名も `STEP_FAIL_RESET_FRAMES` から
`RESULT_STALL_RESET_FRAMES` へ改めた（分けたときに何が起きるかは仕様書「検知結果を出せないフレームが
続いたとき」）。

### 凍結を解くと、今度は発報が鳴り直す

結果を空にすると `confirmed` が落ちるので、復帰したときに発報のエッジ検出がもう一度立つ。つまり
「凍結を固定したまま古い検知を描き続ける」か「凍結を解いて誤った鳴り直しを招く」かのトレードオフに
なる。解く側を採り、鳴り直しは発報側で抑えた（何をどう抑えるかは仕様書「発報ロジック」）。

### 抑止の判定に経過時間を持ち込まない

最初は「`confirmed` が落ちた時刻から `MAX_DT_GAP_MS` 以内の復帰なら抑止する」と書いた。これは
**「鳴るべきときに鳴らない」側へ倒れる**——穴が 3 つあった。

- **起点がずれる。** 記録できるのは「`confirmed` が落ちたのを観測した時刻」で、これは検知エンジンが
  数えている「最後に結果を出せた時刻」より `RESULT_STALL_RESET_FRAMES` 分だけ遅い
- **時計が違う。** エンジンの `MAX_DT_GAP_MS` はデータ時刻の差で測るが、発報側はアプリ時計しか
  持たない（結果が空のときデータ時刻も空になるため）。リプレイでは両者の進む速さが違い、時計の
  切り替わりで値が飛ぶ
- **窓を閉じ忘れる。** 「検知が戻らないまま異常だけ解消した」場合に印が残り続ける

3 つとも、時刻の比較をやめれば消える。時刻の逆行（`dtMs <= 0`。リプレイ開始で起こる）は検知エンジン側の
不連続分岐が吸収する。

### 印だけでは足りない——場所の照合を足した

時刻を捨てた最初の版は「結果が戻った最初のフレームで検知が立っていれば続き」とだけ判定していた。根拠は
「途絶が長ければエンジンが状態を組み直して検知を空にする」だったが、**それが成り立つのは途絶が
`MAX_DT_GAP_MS` を超えたときだけ**。短い途絶では通常の経路を通るうえ、`EEW_CONFIRM_FRAMES`(1) と高震度の
fast path があるため、強い地震ほど 1 フレームで確定してこの穴に嵌まる。そこで、途絶に入る直前の検知地点を
控えて突き合わせるようにした（判定の中身と要件は仕様書「発報ロジック」）。

物差しには最初 `REGION_MATCH_KM`(300km) を借りたが、あれは「1 つの地震が継続監視の中でどこまで広がるか」を
測る値で、途絶をまたいだ同一性の判定には広すぎた——能登から 289km、東京〜仙台ほど離れた別の地震まで
「同じ揺れ」になる。イベント重心どうしを 1 地震とみなす `MERGE_EVENT_KM`(100km) に改めた。照合しているのが
まさに重心どうしであり、`MAX_DT_GAP_MS` の途絶で重心が動くのは S 波が進む数十 km ぶんなので足りる。

**この抑止の判定は 3 度書き直しており（時刻窓／印だけ／印＋場所の照合。上の物差しの選び直しのような
数値の調整は数えない）、そのすべてが「抑えすぎ」の穴だった。** 次に触るときも、緩める方向の変更には
同じ疑いを向けること。

## 36. 張り付いた点の隣が「2 点目」に数えられていた（2026-09-03・利用者が見つけた 5 時間居座る震度7 から）

### 何が起きたか

利用者の画面に「リアルタイム震度7・強い揺れを観測しています」の行動チェックリストが 5 時間居座った。
診断ログ（[`settings-pwa-spec.md`](settings-pwa-spec.md) §12・`utils/detectionDiagnostics.ts`）に残っていた記録がこれ。
**1 レコードが持つのは前後合わせて約 60 秒ぶん**なので、5 時間のうち検知した瞬間の断面にあたる。

| | |
|---|---|
| 検知 | 2026-09-03 08:36:47 JST・愛知県東部（35.0N 137.4E） |
| メンバー | 2 点。値は **7.0 と 0.5** |
| 値の推移 | 直前まで最低値 → 2 秒で 7.0 → **31 秒間 1 度も動かない** |
| 隣接点（約 25km） | その間ずっと 0〜0.5 |
| 判定 | `fastPath: true`・`intenseCount: 2`（`intensityReq` が 0.5 なので隣も数に入った） |

地震波ではない。自然の揺れなら立ち上がって、ピークを打って、減衰する。31 秒間まったく同じ値で
固定されるのは観測点の値が固着した姿で、震度7 の揺れが 25km 先で 0.5 ということも起こらない。

### なぜ降ろされなかったか

§33 が置いた「単点のまま居座る確定を降ろす」は、`everMultiPoint`（一度でも単点でなくなったか）が
立たないまま `SOLO_CONFIRM_GRACE_MS` を過ぎた確定を降ろす。ところが `everMultiPoint` を立てる条件は
**「隣り合う対があるか」だけ**で、その相手が実際に揺れているかを見ていなかった。

張り付いた点の隣で微動しているだけの点も `sustained`／直近 onset には該当するため成分になり、対が
成立してしまう。一度立った `everMultiPoint` は降りないので、**降ろす契機が永久に消える**。

### 直し方を 2 度取り違えた

**1 度目**——「高い点と裏付け点の値の差が大きすぎたら弾く」を考えた。利用者の指摘で崩れた。

> 裏付け点だけで見ると能登の地震（余震含む）などで見られる最初に単点だけ立ち上がる地震に対応できますか？

値の差はその瞬間のスナップショットでしかなく、**震源最近傍の 1 点が先に立ち上がる本物の初動と
見分けが付かない**。仕様書自身が「実地震の正常な姿なので、鳴らすまでの経路には手を入れない」と
書いているとおり。差で弾けば第一報を殺す。

**2 度目**——境界を測ろうとして、実装と別のものを測った。`size` に数えられるのは `sustained` か
直近 onset のメンバーだけで、その判定はエンジンが持つ床・onset 履歴に依存する。それをメンバーの
座標と現フレームの値だけで外から真似たため、**能登本震のイベントが降ろされている**という誤った
結論を出した。利用者の指摘で測り直した。

> 能登の地震なんて周りの点も立ち上がってると思いますが。ちゃんと確認していますか？

実装そのもの（`everMultiPoint` の立つ時刻）を測ると、能登窓の確定検知 24 件のうち**本震（最大震度 7）は
確定と同時に複数点**で、60 秒かかっていたのは本震ではない別の 1 件だった。

**外から内部状態を再現しない。** エンジンが持つ状態に依存する判定を測るときは、エンジン自身が
公開している値（ここでは `DetectionEvent.everMultiPoint`）を読む。

### 決めた形

`everMultiPoint` を立てる条件に、**イベントの最大震度が `SOLO_PAIR_HIGH_INTENSITY`(4.5) 以上のときだけ**
`SOLO_PAIR_MIN_INTENSITY`(2.0) 以上を対の相手へ要求する。**発報の経路には触れていない**——鳴らすこと
自体は正しく、問題は取り下げられないことなので、直すのは降ろす側だけでよい。

あわせて、**併合（`mergeAdjacentEvents`）で `everMultiPoint` を引き継ぐのをやめた。** 和集合になるの
だから引き継いでよさそうに見えるが、この印は一度立つと降りない。引き継ぐと**併合相手が消えて根拠が
無くなった後も残り、降ろす契機が永久に消える**。`MERGE_EVENT_KM` は 100km なので、固着した点の
周りで無関係な小さい地震が 1 度起きるだけで成立してしまう（実測では 84km 先の震度1 が 6 秒で足りた）。
引き継がなくても、併合後の姿は次のフレームで評価し直されるので、対が実在すればそこで立つ。

**この 2 つは両方要る。** 震度の下限だけでは併合経由で印が立ち、併合の継承を外すだけでは併合後の
再評価で無関係な点が対になる。片方だけでは塞がらない。

低い震度で要求しないのは、実データが理由。一律に 1.0 を課すと、確定検知 167 件のうち **26 件**が
猶予内に間に合わなくなる（`pc-sanriku` M4.9、`pc-shimane` M2.9 など、隣が 1.0 に届かない小さな地震）。
最大震度 4 以上に絞っても、福島県沖 M7.3（最大震度6強）が新たに降ろされる。

**4.5 にしたのは、行動チェックリストが出る下限に合わせるため。** リアルタイム震度 4.5 が震度5弱の
下端で（`kyoshinIndexToJma`）、その設定の既定値が震度5弱（`actionChecklistMinScale` = 45）。ここを
5.0 にすると、震度5弱の帯（4.5〜5.0）で固着した点が帯を出したまま降りない。

### 測った結果

| | 実装前 | 実装後 |
|---|---|---|
| その地震に紐づく確定検知（positive + major の 24 窓） | 146 件 | 146 件 |
| 確定した時点で既に複数点 | 141 件 | 140 件 |
| 猶予を超えて降ろされる | 1 件 | **1 件**（変化なし） |
| 能登本震（最大震度 7）が複数点になるまで | 0 秒 | **1 秒** |

全 793 窓のベンチの差分は **1 窓**（`oq7-0502-0435` 宗谷地方南部 M3.6 震度1 で確定の継続が 52 → 48
フレーム）。検知そのものは維持され、検知率・無関係な検知 22 件は変わらない。**閾値を 5.0 に置けば
差分はゼロ**だが、上記の理由で 4.5 を採った。

### 残っている穴

**この対策は「値が動いていない」ことを直接見ていない。** 見ているのは「震度が高いなら固着を疑う」
という代理で、`SOLO_PAIR_HIGH_INTENSITY` を下回る値で固着した観測点は、今回と同じ形で居座る
（固着値を 4.0 にすると、猶予を 24 秒過ぎても確定が降りないことを実測で確かめた）。

**併合の穴は震度に依らず開いていた。** 上の 2 つ目（継承をやめた件）はレビューで実測されて初めて
見つかったもので、震度の下限をどう調整しても塞がらなかった。代理指標で判定している限り、この種の
「印が別の経路から立つ」穴は残りうる。実際、レビューで次の 2 つが**疑いとして**挙がっている。
どちらも再現には至っていないので塞いでいない。

- **併合の場で `firstConfirmedAtMs` は即座に巻き戻るのに、`everMultiPoint` の見直しは次のフレーム。**
  この非対称のため、確定の計時が古いほうへ揃った 1 フレームだけ `isSoloConfirmStale` が真になり、
  確信度が `weak` へ落ちて次のフレームで戻る——という筋道が実装の並びから読める。落ちて戻ると
  検知音が鳴り直す（`useKyoshinAlerts`）。ただし合成フレームでの再現は 2 度試して届いていない
  （近づけると併合の前に成分が直接つながり、離すと震央が動いて 100km の境目を跨げない）。
  塞ぐなら併合関数へメンバーの値を渡す必要があり、影響が広がるので見送った
- **`everNeighborRise` は同じ形のまま**（一度立つと降りない印を、併合で無条件に論理和する）。
  こちらが効くのは `likely` への昇格だけで `confirmed` には関わらないため、深刻度は下がる。
  `everMultiPoint` 系を次に見直すときに、同じ構造として一緒に見ること

4.5 という値は「行動チェックリストの既定の下限」に合わせたもので、**利用者がその設定を震度4 以下へ
下げていれば、その帯は塞げていない**。恒久的に塞ぐなら、震度に依らず「一定時間、値が変化していない」
ことを直接見る軸が要る。ただし強震モニタの値は 0.5 刻みで、弱い揺れでは同じ値が続くのが普通なので、
「何秒なら異常か」を実データで測るところから始まる。

### テスト

| 種別 | 内容 |
|---|---|
| **正** | 2 点目がほぼ平常（0.5）なら降ろす。**実装前に落ちることを確認済み** |
| **対照** | 猶予内に 2 点目が続けば降ろさない（既存。1 点目・2 点目とも 3.5 で `SOLO_PAIR_HIGH_INTENSITY` 未満のため、**対の下限そのものは発動しない**経路） |

## 37. 途絶明けで検知を残し、孤立点の確定を値で降ろす（2026-10-15）

次の不具合 3 つを同じ経路で直した。

### 何が起きていたか

1. **10 秒を超える途絶で、検知が全部消えていた。** `step()` は `MAX_DT_GAP_MS`（10 秒）を超える間隔を
   すべて「不連続」として作り直していた。通信の途絶でも時間軸の切替でも同じ扱いで、途絶をまたいで揺れが
   続いていても検知は消える。減衰期の揺れは立ち上がりが無いので二度と検知されず、立ち上がりの途中なら
   別の地震として検知音が鳴り直す。時間軸の切替はフックが別の合図（データ時刻が空になる）で知っているのに、
   エンジンを明示的には作り直していなかった（数秒だけ先へ飛ぶ切替は普通の続きとして引き継がれていた）
2. **孤立点の確定が 20 秒で降りていた。** §33 の「単点のまま居座る確定を降ろす」は、隣り合う対ができたかで
   見る。`R_KM` 以内に他の観測点が無い孤立点はそもそも対を作れないので、本物の揺れでも
   `SOLO_CONFIRM_GRACE_MS` で降りる。§33 の集計は孤立点を分けていなかった
3. **作り直しの瞬間に欠測だった点が、学習済みの床を失っていた。** `ingest()` が欠測点のキーを落として
   いたため（通常のフレームの欠測は KYO-1 で床を残すので、扱いが食い違っていた）。平常窓 15 本で
   857 点中 16 点

### 途絶明け

間隔が `MAX_DT_GAP_MS` を超えて `MAX_RESUME_GAP_MS` 以内なら、点ごとの履歴だけを空にしてイベントを残す。
このフレームでは立ち上がりを判定できない（履歴の起点が無い）ので新しい検知は生まれず、残したイベントは
メンバーがまだ揺れているか（`size`）で生き残りが決まる。学習（点別床・セル慢性活性）もこのフレームでは
進めない。時間軸の切替はフックで `resetTransientState` を呼んで落とす。助走の連続区間
（`firstContinuousIndex`）も、穴の判定を `MAX_RESUME_GAP_MS` へ揃えた（途絶明けで済む穴より前も効くため）。

**値の決め方。** 控えにある 811 窓（ベンチのカタログ 793 窓と、カタログに載っていない 18 窓）・16 万フレームには 10 秒を超える飛びが 1 つも無かったので、実地震の窓
（positive・major の 24 窓）で、確定した検知の途中（確定から 0〜120 秒後）へ G 秒の途絶を差し込んで
1,700 回再生した。「揺れが続いていた」は、元の再生で途絶明けの時刻に同じ ID の検知が残っていたもの。
「揺れが終わっていた」は、途絶前のメンバーが元の再生でどの検知にも含まれていないもの（同じ ID が消えても、
併合で別の ID へ移って揺れが続いている例が多いので、ID ではなくメンバーで見る）。表の列は次のとおり。

- 「続いていた」「終わっていた」: 上の 2 つに当たった件数
- 「新：残せた」: 「続いていた」のうち、新しい実装で途絶明けに同じ検知が残った件数（差は取りこぼし。60 秒で 6 件）
- 「新：誤って残した」: 「終わっていた」のうち、新しい実装で残してしまった件数
- 「旧：30 秒内に鳴り直し」: 「続いていた」のうち、旧い実装（作り直し）で途絶明けから 30 秒以内に別の検知として確定し直した件数（検知音が鳴り直す）
- 「旧：30 秒内に戻らず」: 「続いていた」のうち、旧い実装で 30 秒以内に確定へ戻らなかった件数（揺れの最中に検知が消えたまま）

| G | 続いていた | 新：残せた | 終わっていた | 新：誤って残した | 旧：30 秒内に鳴り直し | 旧：30 秒内に戻らず |

### 孤立点を値で降ろす

最初に考えた案は「値が `SOLO_ISOLATED_FLAT_MS`（15 秒）動かなければ降ろす・`SOLO_CONFIRM_GRACE_MS` 以下に
置く」だった。**実測すると成り立たなかった。**

- カタログの 793 窓に、孤立したまま確定した検知は 0 件（孤立点は今の観測点リストで 4 点）。孤立点では直接測れない
- 揺れの物理は観測点を選ばないので、全観測点で測った。実地震の窓で値 3.5 以上に達した 1,902 区間の
  「同じ値が続いた最長」は中央値 13 秒・上位 1 割 62 秒・上位 1% 73 秒・最長 88 秒（能登本震）。値 2.5 以上
  の 3,914 区間でもほぼ同じ（中央値 12 秒・最長 88 秒）。強震モニタの値は 0.5 刻みで、ピークの後しばらく
  同じ段に留まる。**15 秒なら 906 区間（約半分）を揺れの最中に降ろす**
- キャッシュに固着の見本は無い（地震の無い窓で 10 秒以上動かなかった例も、上位はすべてカタログの地震の窓）。
  手元の記録は §36 の 1 件（31 秒不変・5 時間居座り）だけ

そこで値の判定は残し、時間を実測の最長の外側（120 秒）に置いた（2026-10-15 ユーザー承認「値の判定のまま
120 秒（推奨）」）。`FLAT ≤ GRACE` の条件は外し、代わりに「実測の最長 88 秒より長い」をテストで固定した。
そのぶん固着した孤立点は 20 秒ではなく 120 秒で降りる。

**印はイベント単位ではなく観測点ごとに持つ。** 最初はイベント単位の一方向の印（降ろしたら戻らない）で
作ったが、回帰テストで穴が出た。固着して降りた孤立点の近く（併合の距離の内）で本物の揺れが確定すると、
本物の揺れの立ち上がりは既存の固着イベントへ帰属するので、イベント単位の印では本物まで二度と確定へ
戻らない。値が動かないまま続いた観測点を一方向で覚え（`isolatedStuckKeys`）、メンバー全員がそうなった
ときだけ降ろす形にした。動いている点が加わればその時点で降ろさず、その点が抜ければまた降りる。併合では
和集合にする（印は観測点ごとの事実なので、相手の動いている点まで降ろすことはない）。

降ろしたときの説明は「値が動かないまま続いたため、確定を取り下げました」（2026-10-14 ユーザー承認。選んだ選択肢
「孤立点用の文を足す (Recommended)」、その説明「『値が動かないまま続いたため、確定を取り下げました』」）、
1 行の要約は「値が動かないまま続いたため取り下げ」（2026-10-15 ユーザー承認。選んだ選択肢「値が動かないまま
続いたため取り下げ」）。

**観測していない時間は数えない。** 敵対的レビューで、欠測や途絶をまたいで同じ値に戻ると、観測していない
区間まで「動かなかった時間」に数えていたことが分かった（欠測のフレームは前の値を据え置くため）。本物の
揺れで 88 秒同じ値が続いた最中に 50 秒の途絶が入れば、それだけで 120 秒を超えて降りる。直し方は 2 通り
あった。

- 空白のたびに時計を始め直す
- 空白の長さだけ時計を後ろへずらす

孤立点の値を数えると、同じ値が 60 秒以上続いた 3,320 区間のうち欠測を挟むものは 203 区間（6%）で、欠測が
9% に及ぶ点もある。始め直すと、そういう点は固着しても降りない。そこで最後に値を見た時刻
（`lastObservedAtMs`）を持たせ、空白の分だけずらす形にした。

**長く値が届かないメンバーも固着と同じく数える。** 値の届かないメンバーは `pruneFadedMembers` が外さない
（届いていないことは揺れが収まった証拠にならないため）。そのため、孤立点 2 つのイベントで片方が欠測のまま
居続けると「全員が固着」にならず、残りの点が固着しても降りなかった。`SOLO_ISOLATED_FLAT_MS` を超えて
値が届かないメンバーも、降ろす判定では固着と同じく数える。ただし印は固着（一方向）とは別の欄
（`isolatedSilentKeys`）に置き、値が戻れば外せるようにした。最初は固着と同じ一方向の印にしたが、レビューで、長く欠測してから値が戻って動き出した点まで「支えていない」と数え続け、固着した相手と
合わせて本物の揺れを降ろすことが分かった。一方向がちらつき対策として要るのは固着の印だけで、
届かないことは値が戻れば終わる一時の事実だから。

ただし印を外すのは、値が戻った瞬間ではなく**戻って実際に変わったフレーム**にした。続くレビューで、
同じ値で戻った点を戻った瞬間に支え直すと、降格→確定→降格を往復することが分かった。確定の立ち上がりの
たびに検知音と通知が鳴り直す（`useKyoshinAlerts` の鳴り直しの抑止 `isSameShakeAsBefore` が効くのは
途絶からの復帰だけで、この経路には効かない）。同じ値で戻っただけでは動いている証拠にならない。

最初は「変わったか」を固着の時計（`lastChangeAtMs`）が今の時刻と等しいかで見ていた。次のレビューで、
欠測の後に途絶明けで戻る形では、空白の分だけずらした時計がちょうど今の時刻と重なり、変わっていないのに
「変わった」と読めることが分かった。届かない印の扱いを続けて 3 度書き換えていたので、継ぎ足しをやめて形を変えた。
代理の値から推し量るのをやめ、観測点ごとに「最後に値が届いたフレームで前の値から変わったか」
（`changedOnLastObservation`）を事実として持つ。

それまでの実装は、孤立のフレームのたびに印を集合として作り直していた（値が届いていないメンバーは最後に
届いてから `SOLO_ISOLATED_FLAT_MS` を超えていれば入れ、届いたメンバーは前から印があって値が変わって
いなければ残す）。その次のレビューで、この作り直す形そのものに穴が 2 つ残っていると分かった。

1. 同じ値で戻った直後に 1 フレームだけ欠けると、そのフレームでは最後に届いてから 1 秒しか経っていないので
   入れられず、印が落ちる
2. 孤立でないフレームでは作り直さずに持ち越すため、その間に値が動いても印が外れない

どちらも、作り直す条件にフレームの種類（欠測か・孤立か）が絡むことから来ていた。そこで印を状態として持ち、付ける・外すを
それぞれ 1 つの事実で決め、孤立かどうかによらず毎フレーム当てる形へ改めた。付けるのは
`SOLO_ISOLATED_FLAT_MS` を超えて値が届いていないとき、外すのは今フレームに値が届いて前の値から変わった
ときと、メンバーから外れたときだけ。

メンバー全員の値が届かない形は降格まで至らない。点数が 0 になり、イベントは `HOLD_MS` で消えるため。
したがって降ろすときは値が届いて動いていないメンバーが必ずいて、説明の「値が動かないまま続いた」は
事実と合う。

## 39. 疎な地域だけ点数の要件を 2 点へ下げる（2026-10-24）

離島・南西諸島の地震の検知率は、ベンチ 795 窓の 81 件で 14% しかなかった（本土は 630 件で 84%）。効いていたのは
3 点の要件 —— 成分の `MIN_CLUSTER`・広がりの `MIN_LIKELY_POINTS`・確定点数の下限 —— で、離島ではそもそも
3 点の面を作れる観測点が無い（2026-10-22 ユーザー選択「疎な地域向けに設計する (Recommended)」）。

震央の近くの観測点を数えると、81 件のうち 37 件は震央の 50km 以内に観測点が 1 点も無かった（トカラ・与那国・
硫黄島など。最寄りが 60〜950km）。これはどう要件を下げても拾えない。西表島付近の 8 件は 15km 先に観測点が
あるが、その点の `R_KM`（40km）以内に隣が居ない。

**測った案**（ベンチ・通信なし。`SPARSE_AVAIL_MAX` は「疎な点」とみなす近傍数の上限）:

| 案 | 中身 | 離島 | 本土 | 地震と無関係な検知 |
|---|---|---|---|---|
| 今まで | 3 点 | 14% | 84% | 24 件 |
| A | 近傍 2 点以下の点だけの成分・イベントは 2 点でよい | 41% | 85% | 24 件 |
| B | A ＋ 疎な点だけ隣とみなす半径を 80km へ | 42% | 85% | 24 件 |
| C | A の上限を近傍 1 点以下にする | 33% | 84% | 24 件 |

どの案も平常の窓（54 本・14.3 時間・全国の観測点を含む）で無関係な検知は 0 件のまま、悪くなった窓は 0。
A は 31 窓が変わり、うち 22 窓が「検知無し → 確定」、残りは likely・確定が早まった。B は A より離島で 1 窓
多いだけで仕組みが 1 つ増えるので採らなかった（2026-10-24 ユーザー選択「案 A を入れる (Recommended)」）。

- **疎かどうかは点ごとの近傍数（`avail`）で決める。** 成分は全員が疎な点のとき、イベントは確定点数の
  密度正規化と同じ「局所実在近傍数」（`availLocal`）が上限以下のときに下げる
- **1 点には下げない**（`SPARSE_MIN_POINTS` = 2）。単点の揺れは機器の故障と区別が付かない（§29 と同じ理由）
- 第3軸（`CONFIRM_INTENSE_POINTS`）・周囲の同時上昇（§32）・連続フレームの要求は変えていない
- 回帰テストは `kyoshinDetector.test.ts` の「疎な地域の点数の要件」。正（疎な 2 点で確定）は、上限を無効に
  戻すと落ちることを確かめた
- **高震度の免除（§29 の `smallCluster`）の根拠を守った。** 変更前は、3 点未満の成分は高震度でしか存在できなかった
  ので「小さな成分が帰属した」が「高震度の成分が帰属した」と同じ意味だった。疎な 2 点の低震度の成分ができる
  ようになったので、免除に渡す成分の点数は**成分の最大が `HIGH_CONFIRM_INTENSITY` 以上のときだけ**にした
  （`exemptCompSize`）。ベンチの結果は変わらない
- **成分とイベントで「疎」の基準が違う。** 成分は全員が疎な点のとき、イベントは揺れているメンバーの近傍数の
  最大（`availLocal`）が上限以下のとき。イベント側のほうが狭い（1 点でも密な点がいれば 3 点に戻る）ので、
  疎な 2 点の成分が密なメンバーを持つイベントへ帰属したときは 3 点が要る。保守側なのでこのままにした
- **EEW 発表中・慢性活性セルとも重なる。** EEW 中は確定点数の基礎が `EEW_CONFIRM_POINTS`(3) に下がり、疎な
  地域ではさらに 2 点・`EEW_CONFIRM_FRAMES`(1) フレームで確定する。慢性活性セルの引き上げ（+4）は、疎な地域では
  変更前から密度の項に負けて効かない（変更前は 3 点まで、今は 2 点まで下がる）
- **既知の限界: 隣り合う疎な 2 点が同時に張り付くと、§33 の降格に掛からない。** 隣り合う 2 点は確定した

## 42. EEW の範囲を P 波と有感半径で測り、範囲の外の揺れも同じ場所はまとめる（2026-10-25）

### 起きたこと

2026-10-25 11:09:21 の小笠原諸島西方沖（緊急地震速報の最終報で M7.5・深さ 530km。地震情報では M7.0・深さ 470km・
最大震度3）で、揺れたのは震源から 900km 以上離れた関東〜東北だった（異常震域。震度を観測した 412 地点は東北・関東・
甲信越・静岡の 16 都県だけ）。
EEW（予報・19 報）の自動解除の瞬間（11:16:47）から、「別地点で揺れ検知」の検知音が 5 秒おき（別地点の
最小間隔 `NEW_REGION_COOLDOWN_MS`）に 4 回鳴った。DMDSS 版の再生で同じ時刻に同じ回数を再現した。

### 原因

1. EEW がある間、`isSameEarthquake` はどの EEW の範囲にも入らない確定点を常に「別の地域」と答えていた。
   同じ場所の揺れでもまとまらないので、フレームごとに新しい地域が登録され、どれも一致しない（＝鳴らない）
   まま `REGION_PRUNE_MS` の間だけ溜まり続けた
2. EEW が消えた瞬間に通常の距離判定へ切り替わり、溜まっていた未発報の地域が一致して、別地点として鳴った
3. 関東・東北が EEW の範囲の外だったのは 2 つの理由が重なったため
   - **上限**: 範囲は `PROPAGATION_MAX_KM`(800km) で打ち止めだった。東京は 901km、仙台は 1192km（震源 27.6°N
     140.1°E から）
   - **測る波**: 範囲は S 波の到達半径×1.2 だった。深い地震では P 波と S 波の到着が大きくずれ、強震モニタは
     P 波の揺れで確定していた。最初に確定した 11:11:29（発生 128 秒後）の S 波×1.2 は 348km、P 波の到達は 996km

判定関数へ同じ形（東京・仙台の 2 点だけが揺れ続け、11:16:47 に EEW が消える）を流すと、解除の時点で地域が
8 つ溜まり、解除から 2 回鳴った。実機の 4 回より少ないのは、入力を 2 点に絞ったため。EEW が無ければ 0 回。

### 直したこと

- **範囲は P 波の到達半径×1.2 で測る**（EEW があるとき）。P 波がまだ届いていない場所の揺れはその地震のもの
  ではありえないので、境目は P 波の前面が正しい（2026-10-25 ユーザー承認。原文「それで。」）
- **上限はその EEW の有感半径**（`eewFeltRadiusKm`。EEW の自動解除と同じ式・同じ M6.0 の仮定）。小笠原の
  地震では 2146km で、自動解除の時刻（発生 446 秒後＝11:16:47）もこの値から決まっていた。EEW は「まだ揺れが
  届く」と見て残っているのに、揺れた場所を別の地震と扱うという食い違いが無くなる（2026-10-25 ユーザー承認。
  原文「それでいいよ」。規模が判らないときは選択肢「自動解除と同じ M6.0 (Recommended)」）
- **どの EEW の範囲にも入らない点どうしは、`REGION_MATCH_KM`(300km) 以内なら同じ地域にする**（2026-10-25
  ユーザー選択「①も直す (Recommended)」）。溜まらなくなるので、解除の瞬間にまとめて鳴る形が無くなる。
  EEW の最中に範囲の外で本当に別の地震が起きたときは、解除を待たずにその場で 1 回鳴る

EEW が無いときの判定（仮の深さ 15km・S 波・800km）は変えていない。

### 効き方

この表の半径は、当時の境（震度1）で引いた値。§48 で境を計測震度 0 へ広げたので、今の値はこれより大きい（M6.0・深さ 10km で 761km）。

| 地震 | 有感半径（上限） | 旧来の上限 |
|---|---|---|
| M7.5・深さ 530km | 2146km | 800km |
| M6.0・深さ 530km | 1412km | 800km |
| M7.5・深さ 10km | 992km | 800km |
| M7.0・深さ 50km | 876km | 800km |
| M6.0・深さ 10km | 479km | 800km |
| M5.0・深さ 10km | 245km → 下限 300km | 800km |

浅く小さい地震では範囲が狭まり、EEW の最中に起きた離れた別の地震を見分けやすくなる。

- ベンチ（795 窓）は EEW なしで流しているので、今回の変更では数が変わらない（直した 3 点はどれも EEW がある
  ときだけ効く）
- 小笠原の地震を DMDSS 版の再生（11:09:00 から）で流し直すと、別地点の検知音は EEW の最中も解除の瞬間も
  0 回だった（修正前は解除から 5 秒おきに 4 回）

### 残っていること

EEW が無いとき（標準版で予報が届かない、強震モニタだけで検知した）の深い地震は、仮の深さ 15km・S 波・800km で
測るので、同じ形の異常震域は別地点として鳴りうる。

### 見たうえで残したこと

- **深く大きい地震では、範囲がほぼ日本全体になる**（M6.0・深さ 530km で 1412km、M7.5 なら 2146km）。その EEW が
  出ている数分の間に範囲の中で起きた別の地震は、別地点として鳴らない。吸収の印（`absorbedByEew`）は下ろさない
  ので、EEW が消えた後も鳴らない。有感半径は EEW 自身が揺れが届くとみている距離なので、そのまま使う
  （2026-10-25 ユーザー選択「このまま・記録する (Recommended)」）
- **範囲の上限は最新報の規模で決める**（自動解除と同じ）。初報の規模が小さく出て、続報で上がる前に 300km より
  遠くで確定した揺れは、別地点として先に鳴りうる（2026-10-25 ユーザー選択「最新報の規模のまま」）
- 深さが判らない報は、有感半径を自動解除と同じ 30km の仮定で求める（P 波の到達半径は従来どおり仮の深さ 15km）。
  発生時刻が読めない報は範囲を測れないので、EEW として数えず、EEW が無いときの判定へ落とす

## 43. 揺れ検知エンジンを組み合わせの検知器へ入れ替える（2026-10-29）

### 検知器の動かし方

仕組みは仕様書§7「検知器の動かし方」。ここには理由だけを残す。

- **画面へ出さないフレーム（`silent`）を持つ。** 助走は最大 900 フレームを一度に流すので、その途中の結果をそのまま出すと、
  何分も前の時刻の検知で音が鳴り、タブが移り、地図が寄る。検知器・学び直しの係・「今揺れ始めた点」の掃除には通し、
  出すのは最後の 1 枚とふだんのフレームの結果だけにした
- **Worker の返事を 30 秒見張る。** Worker は落ちれば `error` が届くが、止まっただけでは何も届かない。返事を待っている
  フレームがあるのに黙ったままなら、落ちたときと同じく主スレッドの係へ切り替える。前の世代の返事でも見張りを延ばすのは、
  作り直しの直後に古い返事が続いているだけの Worker を止まったと取り違えないため
- **作れなかった・例外を投げた検知器は次のフレームで作り直す。** 1 度の失敗で検知を止めると、その起動の間ずっと鳴らなくなる
- **学び直した表を効かせるのはライブの間だけ。** 端末が学んだ数は「いまの時期のこの端末で見た普段」なので、リプレイや
  ローカル履歴アーカイブで別の時期を流すときは配る表で検知する（再生の結果が、端末が何を学んだかで変わらないように）。
  端末が学んだ数は日々変わるので、混ぜた表で再生すると、同じ窓の結果が端末や再生した日によって変わることにもなる。
  観測点の違いは理由にならない。2026-10-29 に評価台の観測点リスト 4 版（2019・2022・2024・2026 年版）の座標と配る表を突き合わせたところ、
  配る表は各版の観測点の 98〜99% を持っていた（2019 年版 1,043 点中 1,029・2022 年版 1,043 点中 1,033・2024 年版 1,371 点中 1,360・
  2026 年版 1,501 点中 1,482）。`blendQuietTables`（`kyoshinQuietTables.ts`）は配る表と端末の数の両方の点を合わせて混ぜる。古い版にしか無い点は、
  端末も数えない（端末が数えるのはライブのフレームだけ）ので、混ぜた表にも載らず、配る表と同じく「表に無い点」になる。
  いまの観測点のうち配る表に無いもの（2026 年版で 19 点）は、端末が数えれば混ぜた表にだけ載る。ただしそれはライブでの差で、
  再生中は混ぜた表を使わないので、この決定には効かない。
  初めは実装で置いた扱いだった。2026-10-29 に「再生中も混ぜた表を効かせるか」を諮り、ユーザーは選択肢「効かせないと決める (Recommended)」を選んだ。
  リプレイ・ローカル履歴アーカイブの再生中は配る表で検知する（仕様書§4「端末での学び直し」）

### 同じ場所の 2 つ目の地震の合図（§40 の続き）

組み合わせの検知器は、同じ場所の 2 つ目の揺れを別の束として出すことがある。現れたばかりの束は §40 の見分け方
（現れてから 60 秒は鳴らさない）では鳴らないので、近く（300 km の内）の確かな束が 60 秒以上続く最中に別の束が
確かな段になったら、それも 2 つ目とみなす。余震の多い 3 窓（福島県沖 2022・トカラ列島 2025・能登 2024）で、最中に
新しい束が確かな段になった 11 回のうち 7 回は音が無く、能登の 5 回は M3.9〜M5.0 の余震だった。

この規則を 795 窓へ流すと、地震が 1 つの窓でも 15 回鳴った。うち約 11 回は、150〜260 km 離れた所で同じ地震の揺れが
届いて別の束になったもので、先の束の揺れ始めからの見かけの速さは 3.4〜3.6 km/s に集まっていた（地震の波の速さ）。
そこで、見かけの速さが 2.5〜5 km/s の束は同じ地震の波とみなして鳴らさないことにした（`REONSET_WAVE_KMPS_MIN`・
`REONSET_WAVE_KMPS_MAX`）。

- 795 窓と余震の 3 窓で、2 つ目の合図は 31 回から 18 回に減った
- 外れた 13 回は見かけの速さが 2.5〜4.7 km/s で、うち 12 回は新しい束の揺れ始めの前後（30 秒前〜10 秒後）に 150 km
  以内の気象庁の震源が無かった
- 1 回（2026-08-14 17:31・M3.1）は本物の別の地震だった見込みがあるが、3.0 km/s で外れた。速さだけでは見分けられない
- 残った本物（福島県沖 2022 の本震・能登 2024 の余震）は 0.2〜1.5 km/s だった

テストは `kyoshinReonset.test.ts` の「同じ地震の波」（正: 1.2 km/s で鳴る・対照: 3.9 km/s で鳴らない・安全弁:
11.6 km/s で鳴る）。

### 助走の最低の長さ

助走（仕様書§7「助走」）の最低の長さは、旧エンジンで測って 3 分にしていた（2026-10-28「3 分のまま残し、理由を書き直す」）。
組み合わせの検知器で測り直すと、遡って打ち切る方式（最低 3 分）は 157/164 で、固定 600 秒（164/164）を下回った。
最低の長さだけを変えて測ると、1・3・5・7・10 ブロックで 148・157・159・161・164/164（遡る長さの平均は 289・369・435・468・490 秒）。
最低 10 分にした（平常時の取得は固定 600 秒と同じ 600 件で、揺れが続けば 15 分まで遡る）。

ここまでの測り方には穴があった。窓の始まりより前を取っていなかったので、遡った先が窓の始まりで頭打ちになると、
そこから流した結果と「ずっと再生し続けた場合」（これも窓の始まりから流す）が同じものになり、一致が水増しされていた。
窓の手前に 15 分（遡りの上限と同じ長さ）を足して測り直すと、最低 1・3・5・7・10・12・15 ブロックで
144・153・154・156・157・158・159/164 だった。最低 10 分で遡った長さは平均 631 秒・最大 900 秒（上限に当たったのは 1 点）。
10 分を超えると 2〜3 分ごとに 1 点しか増えず、15 分にすると静穏で打ち切る仕組みが無くなり毎回 900 件を取る。
10 分のままにした。手前の窓の取得と最低の長さの比較は `scripts/measure-kyoshin-warmup.ts` へ入れた
（`--fetch` で手前も取り、`--min-blocks=` で比べる）。

## 44. 平常のゆらぎの表の窓を波面の発火の窓へ揃え、無くなった 3 つの仕組みの扱いを決める（2026-10-29）

### 表の窓を 3〜59 秒前へ揃えた

波面は、いまの値を 3〜59 秒前の最大と比べて発火を決める（`kyoshinClusterDetector.ts` の `LAG`・`L`）。
平常のゆらぎの表の `fire` は、同じ上がりを 4〜60 秒前の最大と比べて数えていた。表が答えるのは
「この点で、この段数の上がりが普段どれだけ起きるか」なので、比べる窓が 1 秒ずれると、波面が実際に
見ている上がりとは少し違うものを数えた表で発火のしきい値を決めることになる。
2026-10-29 ユーザー選択「揃える (Recommended)」で、表の側を波面へ揃えた
（`kyoshinQuietTables.ts` の `FIRE_LAG` = 3・`FIRE_L` = 60。窓は `FIRE_LAG`〜`FIRE_L`−1 秒前）。

- 配る表（`public/data/kyoshin-quiet-tables.json`）は、同じ日を同じスクリプトで焼き直した。雑音の表を持つ 1,487 点のうち、しきい値は 251 点で下がり、上がった点は無い
- 端末で数えた分（`QuietCounts`）の版を 1 から 2 へ上げた（`QUIET_COUNTS_VERSION`）。v5.74.0 で既に端末に溜まった
  版 1 の数は、読み込みで捨てて数え直す。混ぜると、新しい数え方の表へ古い数え方の回数が足し込まれる
  捨てると時間帯ごとの秒も 0 から数え直すので、そうした端末ではどの時間帯も 30 分ずつ数え終えるまで配る表で検知する（仕様書§4）。
  捨てたことは崩れの警告ではなく情報として記録に残る（`kyoshinQuietLearnerDb.ts`）
- 評価台（795 窓）では、確かな段が早まった窓が 85（早まった秒の合計は 140 秒）、遅れた窓が 2（どちらも 1 秒）。新たに確かな段まで捉えた窓が 2。
  地震と結び付かない確かな段は 60 → 67 件、震源カタログに当てはまらない確かな段は 18 → 20 件（浦河沖・根室地方南部の窓）。
  分類ごとの合否（平常時 20/22・報告された誤検知 30/32）は変わらず、合わない 4 窓は揃える前から合わなかった窓

## 46. 統計の部分の顔ぶれを、波で届く点に絞る（2026-10-29）

### 何が起きていたか

2026-10-29 の昼、v5.74.0 で確かな段の検知が続けて出た（以下、1 つの検知にまとめられた点の集まりを「束」と呼ぶ）。
取得の秒飛びで出た全国に広がる束は、ライブで飛ばした秒を取り直す変更（コミット「強震モニタのライブで飛ばした秒を取り直して検知へ流す」）で扱った。
残りは欠けの無いデータでも出る小さな束で、地図には震源から 200〜600 km 離れた震度1 前後の点が一緒に光っていた。

統計の部分（`kyoshinStatDetector.ts`）は、走査で最も強かった半径（最大 400 km）の内で珍しさ 1.5 以上の点を、まとめて事象の顔ぶれに入れていた。
半径 400 km が選ばれると、その秒にたまたま 1〜2 段上がった遠い点まで顔ぶれに入る。顔ぶれは報告する点（地図・カード）と、確かな段を延ばす判定に使う。

### 決めたこと

| 項目 | 決めたこと | ユーザーの選択（原文） |
|---|---|---|
| 直し方 | 顔ぶれを、距離と上がった時刻が波の広がり方に合う点だけにする | 「顏ぶれを波の届く範囲に絞る (Recommended)」 |
| 合流の判定 | 絞らない。届かない点も事象が引き取り、別の事象を立てさせない（合流の判定は引き取った点で行う） | 「合流は全点のまま (Recommended)」 |
| 離れた所で同時に始まった別の揺れが遅れて出る限界（下の「試して採らなかった形」） | 今のまま残し、仕様書§9 に限界として書く | 「今のまま残す (Recommended)」（2026-10-29） |

絞りの式は、すでに顔ぶれにいるどれかの点 m について、m からの距離 ≤ `REACH_V`（8 km/s）×（その点の今回の立ち上がり − m の立ち上がり）＋ `REACH_SLACK`（40 km）。
顔ぶれは種 1 点から始まり、波が近い点から近い点へ伝わるのに沿って広がる。m の立ち上がりは m が顔ぶれに入った秒の値を覚えて使う。同じ秒に入った点からも届くので、その秒の候補の点は入る点が無くなるまで繰り返し見る（敵対的レビューで、候補の点を見る順で入る秒が遅れうると指摘されたため）。
平常の数え（点ごとの直近の数え）から外す点は、引き取った点で決める。顔ぶれから外れた点が揺れの間に平常の数えへ混ざると、その点の上がりが珍しく見えなくなるためで、利用者に見える差は無い技術判断。
S の計算（どれだけ偶然でないか）は変えていない。確かな段に上がる秒は変わらないか、早まるだけ。

### 種から測る形をやめた理由

はじめは種（と事象の始まり）からの距離と時刻だけで測っていた。敵対的レビューで、種より先に上がった点が永久に顔ぶれへ入らない穴を指摘された。
種は「25 km 以内の珍しさの和が最大の点」で、震源に近い点とは限らない。震源側の点が疎らで、離れた所の密な点が先に揃うと種はそちら側になり、
震源側の点は種から遠いうえに上がった時刻が始まりより前なので、差を 0 秒として 40 km の余裕しか残らない。回帰テストの 2 つ目（下）はこの形で、種から測ると震源側の 4 点が入らない。
顔ぶれのどれかの点から測る形（連鎖）にすると、隣り合う点どうしで届くので入る。

しかもこの灰は震度0 のバッジ（#9ca3af）より明るく、震度0 より弱い点のほうが明るく見えていた。

### 採った形

- 塗りは #363b44 から #828a96 までの 6 色（`KYOSHIN_SUB_ZERO_STEP_COLORS`）。弱い→強いが「暗い灰 → 明るい灰 → 震度0 の灰 → 震度1 の水色」と一続きになる

### 混同しやすい点

検知に入っていない点の層（`subThresholdLayer.ts`）も濃さで段を付けているが、数え方が違う。検知に入っていない点の層は index 1〜6（震度0 以下）、検知に入った点の層は index 0〜5（計測震度 −3.0〜−0.5）。

### index 0 の扱い（2026-10-30 に確かめた）

強震モニタの index 0 は値なしではなく目盛りの底（計測震度 −3.0）。値なし（欠測）は負の index（実測は −1）が表し、検知エンジンも負の値だけを欠測として外す（`MISSING_INDEX_THRESHOLD`）。確かめたことは次の 2 つ。

- Yahoo 強震モニタの公式の CSS（`https://s.yimg.jp/images/weather/pc/v2/css/kyoshin-1.0.1.css`）は index 0 に色（`#97b7cc`）を付けて描き、隠しているのは −1 だけ
- 評価台の控え（`.cache/kyoshin-bench`。窓は `scripts/kyoshin-bench/windows.json`）を数えると、静かな窓 `calm22-03`（300 フレーム・1725 点）では欠測を含む全点・全フレームのうち 85% が index 0 だった。能登の窓 `big-noto2023`（180 フレーム・1133 点）で 180 フレームすべて index 0 だった点は 20 点（欠測が混じった点も含めて一度も 0 を超えなかった点は 42 点）

検知に入った点の層は、受け取った index 0 を底としてそのまま描く。検知に入っていない点の層へは、慢性ノイズ床＋0.4 を超えた点だけが値のまま届き、それ以外は 0 に書き換えて届く（`kyoshinSubThresholdFilter.ts`）。つまりこちらの層の 0 は「描かない」の印で、底の 0 もここに入る（床は −3.0 以上の値から学ぶので、底は床＋0.4 を超えられない）。

### 採らなかった案（同じ問いの選択肢）

- 強震モニタ風の色相（紺→青→水色）: 震度1（#7bb4c8）・震度2（#0070c8）と見分けにくくなる
- 大きさだけで段を付ける: 重なると差が読み取りにくく、震度0 より明るく見える逆転が残る
- 点の代わりに範囲の輪郭を描く: 段（強さ）の違いは見えないまま

| EEW の自動解除も同じ半径を使う | 「揃える」 |

### 測ったこと

評価台の窓のうち、主な地震が M3.5 以上の 267 窓に、その地震を震源にした合成の EEW を当てた（発生時刻は長期震源カタログの
秒つきの値、第 1 報は発生 8 秒後、窓の終わりまで発表中のまま）。検知器を助走つきで流し、`stepAlertRegions` が「別の地点」と
返した発報を、境の計測震度ごとに数えた。窓は多くが 120 秒なので、長く続く揺れの終わり際は測れていない。

| 境の計測震度 | M5・深さ 10km の半径 | M6・深さ 10km の半径 | 別の地点の発報 |
|---|---|---|---|
| 1.0（これまで） | 245 km | 479 km | 11 |
| 0.5 | 348 km | 614 km | 10 |
| 0 | 468 km | 761 km | 6 |
| −0.5 | 603 km | 917 km | 6 |
| −1.0 | 750 km | 1081 km | 6 |

- 1.0 から 0 で消えた 5 件は、どれも近くに別の地震が無く、震源から 305〜913 km・予測計測震度 −0.5〜0.2 の点だった
  （同じ地震の外縁が割れていた）
- 本当に別の地震だった発報 2 件（福島県沖 M7.3 の前震 M6.1・M3.4 の別の地震）は、どの境でも残った（吸い込んでいない）
- 残る 4 件は、P 波がまだ届いていない時刻・距離の発報や、震源から 1,500 km 離れた点で、上限を広げても消えない（§42 の P 波の前面で切れる）
- −0.5・−1.0 にしても、この 267 窓では消える件数は増えなかった。広げるほど、同時に起きた別の地震を吸い込む範囲が広がる

### 自動解除への影響

自動解除（`calcEEWAutoCancelSec`）も同じ半径へ S 波が届く時刻で決めるので、解除までが延びる（深さ 10km）。

| 規模 | これまで | 計測震度 0 |
|---|---|---|
| M4 | 59 秒 | 94 秒 |
| M5 | 95 秒 | 145 秒 |
| M6 | 148 秒 | 211 秒 |
| M7 | 219 秒 | 291 秒 |

揃えるのは、片方だけ広げると「EEW が消えた後に、外縁の揺れが別の地点と鳴る」食い違いが戻るため（§42 の 2026-10-25 の事例）。
S 波カウントダウンの「解除までに届くか」と、検知の束が広がっている間の待ち（§7 の `eewSpreadHold`）も同じ半径を使う。

半径には前からの上限 `MAX_FELT_RADIUS_KM`（2500 km）があり、境を下げたので張り付く規模も下がった。張り付くのは
おおよそ、深さ 10km で M9.2 以上、100km で M9.0 以上、400km で M8.0 以上、700km では M6.9 でも。張り付いたときの自動解除は
浅い震源で 581 秒・深さ 700km で 489 秒で、起動時に発表中の速報を探す窓（15 分）には収まる。上限の値は変えていない。

吸収した地域は「別の地点」として鳴らないので、吸収の印が立った 1 回だけ記録に残す（`[kyoshin] 揺れ検知の地域を
緊急地震速報の揺れに含めた`）。範囲が広がった分、別の地震を取り込んで黙ったときに後から追えるようにするため。

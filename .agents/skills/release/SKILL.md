# リリース

利用者がリリース・統合・タグ・push をはっきり頼んだときだけ使う。実装を終えたことは、リリースしてよいという許しではない。

1. 対象のリポジトリのリリースのコマンド・既定ブランチ・版の付け方・公開の動き・要る確かめを読む。決まっていなければ止めて確かめる。
2. Git の状態を変える前に、いまのブランチ・作業ツリーがきれいか・リモートの追跡の状態・出す候補・リモートの既定ブランチの最新を確かめる。Codex はリリースのロックを作らず消さない。リリースの前に `.claude/release.lock` があれば、Claude Code 側がリリース中なので止めて報告する。古いロックに見えても Codex は消さず、持ち主の確認をユーザーに頼む（持ち主を見分ける手段が Codex に無いため）。
3. 頼まれた内容から統合・確かめ・版の更新・タグ・push の手順が一通りに決まらないときは、予定を示す。共有の履歴を変える操作・成果物の公開・本番への配布の前には確認を取る。
4. 履歴を書き換えずに統合し、要る統合後の確かめを走らせ、通ったときだけ版の更新とタグ付けをする。
5. push の直前にもう一度 fetch する。このリポジトリは公開されているので、push の前に、出す差分・コミットメッセージ・作者とコミッターの欄（名前とメールアドレスの両方）に個人情報が無いことを読んで確かめる。push の前には pre-push フック（`check-personal-info`）が走る。`--no-verify` で飛ばさない。止まっても照合ファイルの中身は読まず、見つかったものと場所をユーザーへ伝える（AGENTS.md「公開する前に個人情報が無いことを確かめる」）。push や CI が失敗したら、force push・版のタグの作り直し・できた状態の破棄をしない。そのままの状態を報告して指示を待つ。
6. 消すのは、確かめた・統合済みのワークツリーとブランチだけ。確かめていないパスに対して、強制のブランチ削除や再帰の削除を決して使わない。ワークツリーは素の `git worktree remove` で消さず、AGENTS.md「ワークツリーを消す前に、ジャンクションを外す」のコマンドで消す（`node_modules` のジャンクションが残っていると、git が向け先の中身まで消す）。

着手前の確かめと取りまとめには `release-manager` を使う。

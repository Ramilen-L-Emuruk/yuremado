# 電文の中継サーバー（設計）

いまの標準版と DMDSS 版を 1 つのアプリにまとめるため、DMDATA.JP の電文を中継するサーバーを
Cloudflare に置く。鍵を持たない利用者も、地震・津波などの電文と緊急地震速報（警報）を受け取れるようにする。
**この資料は中継の設計で、アプリとの約束（配る形・取得の口）の正はここに置く。** 中継のコードと、回数の上限の具体的な値・中継の内部の口の名前は非公開のリポジトリ `yuremado-relay` に置く。実装が進んだら、アプリ側の振る舞いはこのリポジトリの `docs/spec/` の該当箇所へ移す。

**読者は、中継サーバー（非公開のリポジトリ `yuremado-relay`）か、アプリがそこへ繋ぐ経路を触る開発者。**

一本化の前に、いまの PWA の制約・使っている外部サービス・機能・サーバーで新たにできることを洗い出した表は
[`relay-migration-inventory.md`](relay-migration-inventory.md) にある。

## 用語

| 語 | 意味 |
|---|---|
| DMDATA.JP（DMDATA） | 気象庁の電文を配信する民間のサービス。DMDSS 版は利用者が自分の契約の API キーで繋ぐ |
| 標準版・DMDSS 版 | いまのアプリの 2 つの作り（[`architecture-spec.md`](spec/architecture-spec.md)）。標準版は鍵なしで使え、P2PQuake から情報を取る。DMDSS 版は利用者が自分の DMDATA の鍵を入れる。**中継を入れた後は 1 つのアプリにまとめる**（§0）。この資料で「標準版」「DMDSS 版」と書くのは、いまの 2 つの版のこと。まとめた後の話は「鍵の無い利用者」「鍵を入れた人」と書く |
| P2PQuake | P2P地震情報の API。標準版のいまの情報源 |
| EEW | 緊急地震速報 |
| 束 | 1 日ぶんの電文をまとめたファイル（§5.3）。DMDATA の「アーカイブ」と同じ形 |
| 区分 | DMDATA の契約の単位。この資料で扱うのは「地震・津波関連」（`telegram.earthquake`）と、緊急地震速報の「予報」（`eew.forecast`）・「警報」（`eew.warning`） |
| Durable Object（DO） | Cloudflare の、状態（メモリと小さな SQLite）を持てる実行単位。1 つの名前に対して世界で 1 つだけ動く |
| Alarm | DO が自分を起こす予約。1 つの DO に 1 本 |
| Hibernation API | DO が受けた WebSocket を、繋いだまま DO を休ませる仕組み。休んでいる間は時間の課金が掛からない |
| R2 | Cloudflare のファイル置き場（オブジェクトストレージ）。取り出しの転送料が掛からない |
| Cron | Worker を決まった時刻に動かす仕組み（Cron Triggers） |
| Cache API | Worker が応答を Cloudflare の控えへ明示して置き、取り出す仕組み |
| Workers Paid | Cloudflare Workers の有料プラン（月 5 ドル）。DO・R2 の一定量を含む |
| GB-s | DO の時間の課金単位。使ったメモリ（128MB で数える）× 起きていた秒数 |
| VOICEVOX CORE | 音声合成ソフト VOICEVOX のうち、合成を担うライブラリ（`VOICEVOX/voicevox_core`）。アプリへ組み込んで使える |

**A1・B1・E4 のような記号**は [`data-sources-spec.md`](spec/data-sources-spec.md) §2「配信元が定める要件」の表の行番号（A＝レート制限、B＝電文本体の作法、C＝一覧、D＝アーカイブ、E＝WebSocket、F＝認証、H＝利用規約、I＝エンドポイントごとの想定用途）。

Cloudflare の挙動は、公式の資料（developers.cloudflare.com）を 2026-10-14 に読んだ範囲のもの。
主に Durable Objects の「Lifecycle」「WebSockets」「Limits」「Pricing」、Workers の「Limits」「Pricing」「Response」、R2 の「Limits」「Pricing」の各ページと、Workers の「Workers Logs」（ログの料金の切り替え）。
**読んで分からなかったことは §9 に集めた。**

## 1. 何をして、何をしないか

**する**

- DMDATA の WebSocket を 1 本だけ張り、届いた電文を控え、利用者へ配る
- 過去の電文を日ごとの束にして返す（リプレイ・起動時の履歴・「もっと見る」が使う）
- DMDATA が保存し始めた時点（B4。地震津波関連は 2020-11-18、緊急地震速報は 2022-07-20）からの過去分を、ゆっくり取って控える
- 利用者が繋いだとき、いま発表中の警報を送る（§6.1）

**しない**

- 緊急地震速報の予報（VXSE44・VXSE45）を配らない（§0）。鍵を入れた人は自分の鍵で足す

- 推計震度分布図と DMDATA の加工データ（震源カタログ・EEW の一覧）も配る（§0）

プッシュ通知の購読より先の利用者ごとの状態（設定の同期など）をどうするかは決まっていない（§12）。
読み上げは、ネイティブアプリに VOICEVOX CORE を組み込む方向（§0）。PWA の読み上げをどうするかと、中継が受け持つものがあるかは §12。

## 2. 規約との関係

**以下は開発側の読み方で、配信元の見解を得たものではない**（[`data-sources-spec.md`](spec/data-sources-spec.md) §2 の H と同じ立場）。
配信元へは確かめない（§0 の推計震度分布図と加工データを配る行）。条文は [DMDATA の利用規約](https://dmdata.jp/terms) を 2026-10-14 に読んだもの（第 14 条 4 項は 2026-10-30 に読み直した）。

|---|---|---|
| 第 14 条 | 「気象庁が発表する情報において、本サービスを通して得られた場合、特別に定める条項がないものについては二次利用（第三者へ無加工電文配信を含む）ができます。」二次利用で生じた責任はユーザーが負う | 電文は**加工せずに**配る。責任を負うのは中継を運営する開発者 |
| 第 15 条 | 法人契約以外では EEW の二次配信に制限がある。「当配信サービスで配信する緊急地震速報（予報）の内容を、広く公開するAPI等へ使用することはできません。」第三者への表示・鳴動には許可が要り、許可は製作者が取る | 予報の区分 `eew.forecast` は申し込まず、鍵にも権限を付けない（§4.7）。**警報については、DMDATA のサポートから「緊急地震速報（警報）につきましては、現在のところ二次配信（利用）について制限等は行っておりません。」と返事を得た**（2026-10-14 に受け取った返事）ので、区分 `eew.warning` を申し込んで中継する |
| 第 7 条 3 項 | アカウント停止の事由として「他人・他社等へアカウント・その他アカウントに付随した権限等の譲渡・共有。」 | **中継の鍵は利用者に渡さない。** 鍵を入れた人が使うのは自分の契約の鍵（§0） |

**読み方の要点**

- **配るものは 3 種類。** 電文そのもの（無加工）・電文から機械的に引いた値（種別・発表時刻・EventID）・DMDATA が付けた値（電文の `id` と受信時刻）。最後の 2 つは、アプリが電文を取り出し・並べるのに使う（§5.2）
- **加工データ（`/v2/gd/*`。I5）も第 14 条で二次利用できると読む。** 第 14 条 4 項は「本サービスが加工・作成した（エンコーディングや送信過程で必要な変換は加工としない）データについて、特に断りがない限り二次利用を行う場合についても同様とします。」（2026-10-30 に読んだ条文）。`/v2/gd/eew` の資料にある「事後参照としてお使いください」（I1）は使い方の案内と読み、この「断り」には当たらないと扱う。配る（§0）
- **`telegram.earthquake` に EEW の電文は含まれない。** EEW は区分 `eew.*` で配信され、DMDATA の電文一覧（`/v2/telegram`）にも出ない（C2）。中継が切れていた間の警報を一覧で取り戻せないのはこのため。代わりに `/v2/gd/eew` で電文の id を引く（§4.4）
- **推計震度分布図（IXAC41）は配る**（§0）。電文は区分 `telegram.earthquake` で配信される、地震の後の観測にもとづく情報で、作り方に緊急地震速報の震度予測の技術が使われている（[`data-sources-spec.md`](spec/data-sources-spec.md) §2「扱うことにした 4 種」）。第 15 条の制限は「緊急地震速報（予報）」だけを対象にしているので、当たらないと読む
- **束（§5.3）の作り直しと中継の `ping` は、電文の加工ではない。** 電文本体のバイト列には触れない

**2 つの版は 1 つにまとめる**（§0）。予報だけは中継せず、鍵を入れた人が自分の契約で受ける。まとめ方は §12。

## 3. 全体の形

```
DMDATA.JP
  │  WebSocket 1 本（区分は telegram.earthquake と eew.warning）
  │  REST（切れていた間の取り戻し・日が終わった後の突き合わせ・過去分の控え）
  ▼
Cloudflare
  ├─ DO「中継」1 つ
  │    ・DMDATA の WebSocket を張り続ける（毎分の Alarm で繋がっているか確かめる）
  │    ・届いた電文を R2 へ置き、索引を自分の SQLite へ書く
  │    ・利用者の WebSocket を受け、届いた電文をそのまま配る
  │    ・DMDATA と繋がっているかを利用者へ知らせる（§6.1）
  │    ・利用者が繋いだとき、いま発表中の警報を送る（§6.1）
  ├─ R2 … 電文 1 通につき 1 つ、日ごとの束 1 つ
  └─ Worker … 利用者への REST の口。閉じた日の束と電文本体は R2 から直接返す
  ▼
アプリ（1 つにまとめた後）
  ・誰でも中継の WebSocket 1 本（地震・津波などと警報）
  ・鍵を入れた人だけ、予報を自分の鍵で DMDATA から受ける（§7）
  ・読み取りは DMDSS 版と同じパーサーを通す
```

**中継の口は DMDATA と同じ形にする**（§6）。アプリの DMDATA の経路は、繋ぐ先と認証を
差し替えるだけで中継にも使える。**読み取りの経路を 2 本持たないため** —— 標準版と DMDSS 版で
同じ電文から違う画面が出る形を作らない（1 つにまとめた後も、中継と自分の鍵の両方を同じパーサーで読む）。

## 4. 上流（DMDATA との繋ぎ）

### 4.1 申し込む内容

`POST /v2/socket` の本文はアプリと同じ形にする（[`src/services/dmdata.ts`](../src/services/dmdata.ts) の `tryFetchTicket`）。

| 項目 | 値 | 理由 |
|---|---|---|
| `classifications` | `['telegram.earthquake', 'eew.warning']` | §2。予報が無く警報だけを受ける形は、DMDSS 版の「一部の区分だけ受けられる人」と同じ（[`data-sources-spec.md`](spec/data-sources-spec.md) §2。EEW は VXSE43 だけが届く） |
| `test` | `'including'` | 試験報を配るかは受け手が決める。**アプリは受け取った後に `head.test` で振り分けている** —— WebSocket（`dmdata.ts` の `handleMessage`）・電文一覧（`dmdataReplayLive.ts` の `classifyTelegram`）・アーカイブ（`dmdataReplay.ts`）の 3 経路とも。非 XML の推計震度分布図は本文で判定している（`isFilteredBinaryTelegram`） |
| `formatMode` | `'raw'` | アプリが気象庁の XML だけを読むため（[`data-sources-spec.md`](spec/data-sources-spec.md) §2「受信する電文種別」） |
| `appName` | 中継だけの名前 | DMDATA の管理画面で、アプリの接続と見分けるため |

### 4.2 張り続ける

| 事実（Cloudflare の資料） | 設計 |
|---|---|
| DO は外へ WebSocket を張れる。張っている間は休まない | 中継の DO は常に起きている。時間の課金が掛かり続ける（§10） |
| 外へ張った接続が DO を退避から守るのは**最長 15 分**。その後も接続は残りうるが、保証は無い | **毎分の Alarm で「繋がっているか」を確かめ、切れていれば張り直す。** 発火のたびに次の 1 分後を予約する |
| **デプロイのたびにすべての DO が再起動し、接続が切れる** | デプロイは切断と同じに扱う。§4.4 の取り戻しで埋まるが、**デプロイの頻度がそのまま取り戻しの回数になる**ので、地震が続いている間はデプロイしない |
| 停止のフックは無い | 状態（最後に受けた電文の受信時刻・`socketId`）は受けるたびに SQLite へ書く。見ていた区間の終わりは、毎分の Alarm が書く心拍で決める（§4.6） |
| Alarm は 1 つの DO に 1 本 | **毎分の Alarm が、SQLite に控えた「次の仕事の時刻」を読んで振り分ける**（接続の確認・日を閉じる・突き合わせの取り直し）。過去分の控え（§5.4）は Cron から Worker 経由で DO を呼ぶ |

**DMDATA の作法もアプリと同じに守る**（E1〜E4）。

- `ping` を受けたら `pong` を返す（E1）
- 最後に何かを受けてから 90 秒で、自分から閉じて張り直す（アプリの `PING_WATCHDOG_MS` と同じ。半開きの接続への備え）
- 張り直しの間隔は指数で伸ばす（3 秒から 30 秒まで。アプリの `RECONNECT_BASE_MS`・`RECONNECT_MAX_MS` と同じ）

### 4.3 同時接続の枠

**中継は DMDATA の同時接続の枠を 1 本使う。** 枠はアカウントごとに数える（DMDATA の資料「Socket Start v2」の 409 の説明による。2026-10-14 の点検で読んだもの。数え方の細部は資料に無い）ので、開発者の dev サーバー・実機・
検証用のブラウザと取り合いになる。**開発者の端末が枠を埋めると、中継が繋がらない。** P2PQuake は控えにしない（§0）ので、ほかの控えを持たなければ、鍵の無い利用者全員の受信が警報も含めて止まる。
ほかの経路を控えに持つかと、枠の分け方は §12。

409（枠が埋まっている）を受けたら、**SQLite に控えた自分の前の `socketId` を閉じてから**張り直す（E4）。
アプリは「このセッションで掴んだ id だけを閉じる」と決めている（他の端末の接続を閉じうるため）が、
**中継は専用の鍵を使う**（§4.7）ので、その鍵の接続は中継自身のものしかない。だから控えた id を閉じてよい。
それでも 409 が続くなら、ほかの端末が枠を埋めている。待つ上限はアプリと同じく 5 分まで伸ばし、その間は §6.1 の知らせを出し続ける。

### 4.4 切れていた間の取り戻し

**張り直したら、前の回の見ていた区間の終わり（§4.6 の心拍）から今までを一覧で引き、受けていない電文の本体だけを取る。**
起点を最後に電文を受けた時刻にしないのは、電文の来ない静かな夜のあとにデプロイしただけで、長く切れていたように見えるため。

1. `GET /v2/telegram?datetime=<前の回の区間の終わりの 5 分前>~<新しい回の始まり＋1 分>&test=including&limit=100`
   - 終わりを新しい回の始まりから 1 分先まで延ばすのは、新しい回が覆いの判定で頭を 1 分削られるため（§4.6）。その時刻が DMDATA にとって来てから引けるよう、新しい回の始まりから 2 分待って引く
   - 区分は鍵の権限で決まるので `classification` は付けない
   - `test=including` を付けないと試験報が返らず、WebSocket とアーカイブとで中身が食い違う
   - **`datetime` に日時を渡せるかは確かめていない**（アプリは日付だけを渡している。§9）
2. 索引に無い `id` だけ `GET /v1/:id` で本体を取る（本体の上限 50req/5min を守る。A3）
3. 取った本体は gzip し直して R2 へ置き（§5.1）、WebSocket で受けたものと同じ `data` メッセージの形に組み直して利用者へ配る。`head` と受信時刻は一覧の項目から取る

**WebSocket で受けた電文の本体を REST で取り直すことはしない**（B1）。取るのは受けていない分だけ。
ページを辿るループには上限を置く（[`data-sources-spec.md`](spec/data-sources-spec.md) §2「ページを辿るループには上限を置く」）。

- **取り戻せた範囲は記録する**（§4.6 の「見ていた区間」）。記録してよいのは、一覧を最後のページまで辿り、欠けた本体を取り終えた回の範囲だけ。一覧の途中で失敗した回は記録しない（取れたところまでを記録すると、取り損ねた時間が見ていた区間に数えられる）
- **一覧で、索引に無い電文が上限（既定 40 件・設定で変える）を超えたら取り戻さない**（§0）。その区間は見ていなかったものとして、DMDATA のアーカイブとの突き合わせ（§4.5）に任せる。本体を 1 通ずつ取ると、50req/5min（A3）を突き合わせ・過去分の控えと食い合ううえ、同じ日はアーカイブ 1 本で確定できる。40 件は、その上限を過去分の控えと突き合わせに少し残して 1 回の 5 分に収める数。一覧を最後のページまで辿れなかったとき（失敗・ページの上限での打ち切り）も、件数によらず任せる
- **初めて繋がったときは取り戻さない。** 繋がる前の分は、その日の突き合わせが埋める
- **警報は電文一覧では取り戻せないので、`/v2/gd/eew` で電文の id を引く**（§0）。DMDATA の電文一覧に EEW は載らない（C2）。代わりに `/v2/gd/eew` の一覧で切れていた間に警報を出した地震を探し、地震ごとの詳細（`/v2/gd/eew/{eventId}`）の `telegrams[].id` から VXSE43 の id を取る。本体は `/v1/:id` から生の電文として取り、上の手順 2・3 と同じに扱う。加工データの応答は id を探すのに使うだけで、索引・束・利用者への配信には入れない
  - **この一覧は最終報の後にしか更新されない**（I1「このAPIでは、緊急地震速報の最終報を受信したのちデータが更新されますので、リアルタイム処理に用いるのではなく事後参照としてお使いください」）。続報が出ている最中に切れていた分は、その地震の最終報が出るまで取り戻せない。最終報の後に引いて欠けを埋める使い方は、I1 の「事後参照」に収まると読んでいる（配信元には確かめていない）
  - 詳細の `telegrams[]` が JSON 版を指すときは、XML 版の id が `originalId` に入る（アプリの `dmdata.ts` の `fetchLatestEewReport` が同じ扱いをしている）。`/v1/:id` には XML 版の id を渡す
  - 一覧を引く間隔・ページの上限・門は、ほかの取り戻しと同じ規約に従う（A3・ページを辿るループの上限）。地震ごとに区間に入る報を全部取るか最新報だけかは §4.6 の「まだ決めていないこと」
  - **こうして取り戻した区間は「見ていた区間」（§4.6）に数えない**（§0）。区分 `eew.warning` の日は切れていた区間があれば `gapped` になり、警報が無ければ日が終わって 48 時間後に `confirmed-empty` へ進む（§4.6）
  - 取り戻した警報は利用者へ WebSocket で流し、アプリは初めて受けた警報として鳴らす（§0）

### 4.5 DMDATA のアーカイブと突き合わせる

**運用開始の日（§4.6）以降の日は、日が終わった後に DMDATA のアーカイブと突き合わせる。** 目録に載るまで見続け、載ったら本体を取り込む（取り込めなければ取り直す。§4.6）。
WebSocket と取り戻し（§4.4）で落とした電文を拾い、見ていなかった区間を埋めるため。結果は索引と日の状態（§4.6）へ書くだけで、束は §5.3 の規則で作る。
**区分ごとに突き合わせる**（DMDATA のアーカイブは区分ごとに分かれている。`telegram.earthquake` と `eew.warning`）。`eew.warning` のアーカイブは警報の出た日にしか作られないので、ほとんどの日は目録に現れず、手順 4 の待ちを経て決まる。

1. **1 時間おきに引くのは目録（`/v2/archive`）だけ。** DMDATA は前日分を 00:30 ごろまでに作るが（D1）、遅れることもある（D3）
2. **目録にその日が現れたら、本体を取る**（同じ id を短い間に繰り返し取らない。A4・I3）。日が終わった後のアーカイブは増えないので、取れれば 1 回で確定する。取れなかったときの取り直しも、同じ id を短い間に繰り返さない間隔で行う
3. 本体の中の電文のうち、索引に無いものを足す。受信時刻はファイル名の 17 桁、日はそこから決める。索引にあって受信時刻が中継の時計のもの（§5.2）は、アーカイブの値で書き換える
4. **目録に現れないまま日が終わってから 48 時間たったら、目録を引くのを 1 日 1 回へ落とす。** 打ち切らないのは、「DMDATA 側に 1 通も無かった」（D2）と「まだ作られていない」（D3）を目録だけでは見分けられないため。どちらと扱うかは日の状態（§4.6）で決める

### 4.6 日の状態

**日と区分の組ごとに「その日を中継がどこまで見ていたか」を SQLite に持ち、束を出してよいかをそこから決める。** 区分で分けるのは、取り戻し（§4.4）が区分で違い（`eew.warning` は `/v2/gd/eew` を通し、その地震の最終報の後にしか効かない）、同じ日でも見ていた区間が区分で違うため。
「1 通も無かった」と「見ていなかった」を見分けるのはこの状態だけで、索引が空かどうかでは見分けられない。

**見ていた区間** —— DMDATA の WebSocket に繋がっていた区間と、取り戻し（§4.4）で埋められた区間の和。繋いだ時刻・切れた時刻・取り戻せた範囲を、起きるたびに書く。

| 状態 | 意味 | 束 |
|---|---|---|
| `open` | 日が終わっていない（今日）、または終わってから 11 分たっていない（遅い配信の 10 分＋区間を削る 1 分） | 出さない。アプリは電文一覧の経路で読む |
| `observed` | 日が終わり、見ていた区間がその日を隙間なく覆っている | **出す**（電文が無ければ空の束） |
| `gapped` | 日が終わったが、見ていない区間がある（中継の停止・409 が続いた・長い切断・運用開始の日の繋がる前） | **出さない**。突き合わせ（§4.5）を待つ |
| `reconciled` | DMDATA のアーカイブと突き合わせ済み | 出す |
| `confirmed-empty` | 1 通も無かったと確かめた日。索引が空のまま、日が終わってから 48 時間たっても目録に現れない日（見ていない時間があってもよい）と、過去分の控え（§5.4）で同じく 48 時間を過ぎても範囲の目録に現れなかった日 | 出す（空の束） |
| `unfetched` | 運用開始の日より前で、過去分の控え（§5.4）がまだ取っていない | 出さない |
| `failed` | 過去分の控えで取れなかった | 出さない。次の周回で取り直す |

- **日の状態は、受け持ちの区切りも兼ねる。** 運用開始の日（中継が初めて DMDATA の WebSocket に繋がった日。JST）より前の日は `unfetched` から始まり、過去分の控え（§5.4）だけが動かす。それ以降の日は `open` から始まり、WebSocket・取り戻し・突き合わせだけが動かす。2 つの処理が同じ日を取りに行くことはない
- **`gapped` のまま突き合わせが済まない日は、束を出さないので、窓の上端から 2 日より古ければアプリが「取り込めていません」と示す。** これを許すかは §12（直近 2 日のうちはアプリが電文一覧で読むので、欠けが見えない。§12）。見ていない日を空の束で埋めると、アプリは「その日は電文が無かった」と読み、端末に永続的に控えてしまう
- 遅い配信（発表から最大 59 秒。[`data-sources-spec.md`](spec/data-sources-spec.md) §2）を拾うため、見ていた区間は日が終わってから 10 分後まで覆っている必要がある。`open` を抜けるのはそこからさらに 1 分後（WebSocket の区間は末尾も 1 分削るので、10 分の時点ではまだ覆いきれない）
- **DMDATA と繋がっているかは、日を閉じる条件に入れない。** 日が終わった時点の見ていた区間だけで決まる。繋がらない状態が長く続いても、突き合わせは REST だけで進む
- **空の束の根拠は 2 種類ある。** `observed` は「中継が自分で隙間なく見ていて、1 通も届かなかった」、`confirmed-empty` は「それに加えて、DMDATA 側にも無いと確かめた」。どちらも空の束を出すが、根拠が違う

**状態の決め方**（2026-10-26 に決めた。§0）

- **状態は保存しない。保存するのは事実だけで、状態は事実から毎分計算し直す**（純関数は非公開のリポジトリ `yuremado-relay` の `src/dayState.ts`）。出来事ごとに状態を書き換える形だと、出来事を起こす処理（WebSocket・取り戻し・突き合わせ・過去分の控え）のどれか 1 つが書き換えを呼び忘れただけで、その日の状態が止まる。取り戻しが日が終わって 10 分より後に済んだ日も、次の 1 分で `gapped` を抜ける
- **事実が無い日は見ていない日。** 中継が丸 1 日止まっていた日も、日ごとの記録を作る処理を別に置かなくても `gapped` になる
- 保存する事実は、WebSocket の繋がり（繋いだ時刻・最後の心拍・自分で知った切れた時刻）、一覧で取り戻せた区間（§4.4 の条件を満たした回だけ）、日と区分ごとの索引の件数、目録に載ったのを初めて見た時刻・取り込んだ時刻・48 時間たって載らないのを見た時刻・取り込みに失敗した時刻、運用開始の日
- **見ていた区間の終わりは最後の心拍。** 毎分の Alarm が「いま繋がっている」と確かめた時刻を書き、止められた回は最後の心拍で切る（最後の心拍から実際に切れるまでの最長 1 分は見ていない側に倒す）。閉じる合図を受けて閉じた回はその時刻、90 秒の見張りやエラーで閉じた回は最後に何かを受けた時刻で切る（半開きで届いていなかったかもしれないため）。区間の終わりは今の時刻で頭打ちにする
- **覆いの判定では、WebSocket の区間を両端 1 分ずつ削る。** 区間は中継の時計、電文の受信時刻は DMDATA の時計で測るので、ずれのぶん受け損ねた電文を見ていたと数えないため。一覧で取り戻した区間は DMDATA の時計なので削らない。数秒で繋ぎ直しても 2 分あまりの穴ができ、取り戻しが埋める（§4.4）。1 分は段 1a で §9 の 3（WebSocket の電文に DMDATA の受信時刻が載るか）を確かめてから見直す
- **警報の区分（`eew.warning`）では、一覧で取り戻した区間を数えない。** 電文一覧に緊急地震速報は載らない（C2）。`/v2/gd/eew` で警報を取り戻した時間帯も数えない（§4.4）
- **壊れた入力は投げる。** 存在しない日・有限でない時刻・負の件数のほか、設定値も確かめる（余裕が負・「無い」と読む待ちが 24 時間より短い、など）。値を甘くする方向の誤りは、全部の日の状態を黙って甘くするため

**遷移**（上の行ほど先に見る）

| 日 | 事実 | 状態 |
|---|---|---|
| どの日も | アーカイブを取り込んだ | `reconciled` |
| 運用開始より前 | 目録に載ったが、取り込みに失敗した | `failed`（周回ごとに取り直す） |
| 運用開始より前 | 日が終わって 48 時間たった後に最後まで辿れた目録を見て、その日が載っていなかった（その後も載っていない） | `confirmed-empty` |
| 運用開始より前 | それ以外 | `unfetched` |
| 運用開始以降 | 日が終わって 11 分たっていない | `open` |
| 運用開始以降 | 索引が空で、上と同じく 48 時間後に載っていなかった（その後も載っていない） | `confirmed-empty`（見ていない時間があってもよい） |
| 運用開始以降 | 索引が空なのに目録に載っている（まだ取り込めていない） | `gapped`（見ていたつもりでも空の束は出さない） |
| 運用開始以降 | 見ていた区間の和が [日の始まり, 日の終わり＋10 分] を隙間なく含む（索引に電文があって 48 時間後も目録に載らない日も、ここで判定し印を付ける） | `observed` |
| 運用開始以降 | それ以外 | `gapped` |

- **一度立てた印は戻さない。** 一度目録に載ったのを見た日は、後で載っていなくても「無い」と読まない
- **`confirmed-empty` の日が後で目録に載ったら、取り込むまで空の束を引っ込める**（§0）。目録に載った時点で、その日に電文があったと分かるため。取り込めば `reconciled` で版の違う束を出す
- **目録の結果を「載っていなかった」として記録してよいのは、応答が成功し、最後のページまで辿れ、引いた範囲がその日を両側に余裕を持って含むときだけ。** 取得の失敗・打ち切りは何も記録しない（一度の取り違えでその日が空と確定するため）
- **起きないはずの組み合わせは、状態を変えずに印を付けて記録する。** 索引に電文があるのに 48 時間たっても目録に載らない日、隙間なく見ていたのに目録に載った日の索引が空の日、目録に載ったのに取り込みに失敗している運用開始以降の日。いずれも目録を見続け、取り込みを取り直す
- **目録は、日が終わってから 48 時間までは 1 時間おき、その後は 1 日 1 回見る。** `reconciled` になるまで見続ける（`confirmed-empty` の後も見る。アーカイブが待ちより遅れて作られた日を偽の空のまま固めないため）。目録は期間で引くので、1 回で全部の日を見られる
- **警報の区分（`eew.warning`）はアーカイブが警報の出た日にしか作られない**ので、切れていた時間のある日のほとんどは、日が終わって 48 時間後に `confirmed-empty` へ進む

**まだ決めていないこと**（日の状態の純関数の外。その部分を作るときに諮る）

| 決めること | 何が問題になるか |
|---|---|
| 電文 1 通の R2 と索引の書く順 | 索引だけ入って R2 に無い電文は、束の作り直しで本体が読めない。R2 を先に書き、成功してから索引へ入れる案 |
| `confirmed-empty` の日の目録をいつまで見続けるか | いまは `reconciled` になるまで 1 日 1 回見続ける（§0）。警報の区分は大半の日が `confirmed-empty` になるので、見る日数が運用の長さに比例して増え、目録のページ数も増える。ページの上限で打ち切られた応答は「載っていなかった」の根拠にならない |
| `/v2/gd/eew` での取り戻しで、地震ごとに区間に入る報を全部取るか、最新報だけを取るか（§4.4） | 全部取れば 1 地震あたりの本体の取得が報の数だけ増え、50req/5min（A3）を突き合わせ・過去分の控えと食い合う。最新報だけなら途中の報は束に入らない |

### 4.7 鍵

- **中継には専用の API キーを作る。** アプリや開発者の端末の鍵と分けておけば、漏れたときにその鍵だけ止められる。§4.3 の 409 の扱いもこれが前提
- 付ける権限は `socket.start`・`socket.close`・`telegram.list`・`telegram.data`・`archive.list`・`archive.data` と `telegram.get.earthquake`・`eew.get.warning`、それに `gd.eew`（§4.4 の警報の取り戻しに使う。§0）。**`eew.get.forecast` は付けない**（予報は中継しない。§0）。加工データ（震源カタログ）を配るので `gd.earthquake` も付ける（§0）。鍵の契約には「緊急地震（警報）」の区分が要る（2026-10-14 に契約済みと確認）
- 置き場所は Worker の secret。リポジトリにも会話にも出さない
- **鍵に IP の制限（F5）を付けられるかは確かめていない**（§9）。Workers から外へ出る通信の送信元 IP が固定されないなら付けられず、IP ごとの上限（A1）も同じ IP を使う他人の通信と合わせて数えられうる

## 5. 控え

### 5.1 置き方

| 何を | どこへ | 鍵・形 |
|---|---|---|
| 電文 1 通 | R2 | `t/<id>`。中身は**常に gzip**（WebSocket で受けた分は `body` を base64 から戻したもの、REST で取った分は中継が gzip したもの）。`customMetadata` に種別・発表時刻・受信時刻 |
| 日ごとの束 | R2 | `a/<区分>/<YYYYMMDD>-<版>.tar.gz`（JST の日・区分ごとに 1 つ）。§5.3 |
| 索引 | 中継の DO の SQLite | 下表 |

**電文の鍵を `id` だけにするのは、本体を返すとき DO を通らずに済むため。** 本体の口（§6）は R2 を直接読む。

| 索引の列 | 中身 |
|---|---|
| `id` | DMDATA の電文 id（主キー） |
| `classification` | `telegram.earthquake` か `eew.warning`。束と日の状態の単位になる |
| `head_type` / `head_time` / `head_test` / `author` / `designation` | 電文の `head` そのまま。`author`・`time`・`designation` は分割された二進電文の断片を束ねる鍵になる |
| `event_id` | XML の `Head/EventID`（二進は空） |
| `received_ms` | DMDATA の受信時刻（ミリ秒）。出どころは §5.2 |
| `jst_day` | 受信時刻の JST の日。束の単位（[`data-sources-spec.md`](spec/data-sources-spec.md) §2「落とすアーカイブは JST 日で決める」と同じ決め方） |
| `source` | `live`（WebSocket）／`gapfill`（§4.4）／`archive`（§4.5・§5.4） |

**R2 の同じ鍵への書き込みは毎秒 1 回まで**（超えると 429）。「最新の一覧」のような 1 つの鍵を電文のたびに
書き換える形にはしない。一覧は SQLite から作る。

### 5.2 受信時刻の出どころ

**受信時刻は DMDATA が付けた値を使い、中継の時計では付けない。** 束の日（`jst_day`）が DMDATA のアーカイブの日と
日付の境目でずれると、アプリのアーカイブの経路が電文を前後の日に取り違える（アプリは窓の終わりに 10 分の余裕しか持たず、
前日分は足さない。`dmdataReplayLive.ts` の `DELIVERY_LAG_MARGIN_MS`）。

| 経路 | 受信時刻の出どころ |
|---|---|
| 取り戻し（§4.4） | 一覧の `receivedTime` |
| アーカイブ（§4.5・§5.4） | 目録のファイル名の 17 桁 |
| WebSocket | **確かめていない**（§9）。`data` メッセージに DMDATA の受信時刻が載っていればそれを使う。載っていなければ中継の時計で仮に付けて印を残し、突き合わせ（§4.5）でアーカイブの値に書き換える。書き換えで日が変われば、前後の日の束が §5.3 の規則で作り直される |

### 5.3 日ごとの束

**束は、索引と日の状態（§4.6）から機械的に作る。** 束を出してよい状態の日と区分の組について、その日（`jst_day`）・その区分の索引の電文を全部入れたものが、その組の束になる。DMDATA のアーカイブと同じく、区分ごとに別の束にする。

- **その日の索引か状態が変われば、変えたのがどの経路でも（取り戻し・突き合わせ・過去分の控え・受信時刻の書き換え）、その日に「作り直し待ち」の印を付ける。** 毎分の Alarm が、印の付いた日を 1 日につき 1 回だけ作り直す。経路ごとに「出し直すか」を判定しないのは、判定を経路ごとに持つと、どれかの経路で必ず書き漏らすため。印でまとめるのは、1 回の突き合わせで電文が何百通足されても、作り直しを 1 回で済ませるため
- **同じ中身からは同じ束ができるように作る**（電文の並びを受信時刻と id で固定し、tar の時刻欄は 0 にする）。中身が変わらなければ版も変わらない
- **DMDATA のアーカイブを待たずに出せるのは `observed` の日だけ。** 待つと、アーカイブが遅れたり作られなかったりする日にアプリの履歴が欠ける ——
  アプリの起動時の履歴と「もっと見る」は、束の無い日を電文一覧で埋めるのが**窓の上端から 2 日まで**で
  （`dmdataReplay.ts` の `LIVE_FALLBACK_DAYS`）、それより古い日は「取り込めていません」と記録して飛ばすため
- **電文が無かった日の束は空にする。** 目録は文字どおり `[]` の JSON にする（目録が無い・空の文字列・0 バイトの tar は、アプリが「取れなかった」と数える。`dmdataReplay.ts` の目録の読み取り）。束を出さないと、アプリはその日を取りこぼしと数え、「もっと見る」もそこで止まる。**空の束を出してよいのは `observed`・`confirmed-empty`・空のアーカイブで確かめた日だけ**（§4.6）

**中身と形**

DMDATA のアーカイブと同じ形（tar.gz の中に目録 `telegrams.json` と電文ファイル）にする。アプリのアーカイブの経路
（[`src/services/dmdataReplay.ts`](../src/services/dmdataReplay.ts)）がそのまま読めるため。

- 束の中の電文ファイルは、R2 の gzip を展開した平文の XML。アプリは中身をそのまま文字として読む（推計震度分布図は二進のまま入れる。§0）
- **DMDATA のアーカイブをそのまま置かない。** あちらには中継が配らない JSON 変換版の電文も入っている（区分ごとに XML と JSON の 2 版。アプリは JSON 版を捨てている）。目録の項目もアプリが読むものだけに絞れる
- 突き合わせ（§4.5）・過去分の控え（§5.4）で取ったアーカイブからも、索引へ入れるのは XML 版だけ

**束の目録に書く項目**は、アプリが読むもの（`dmdataReplay.ts` の `ManifestEntry`）だけ。

| 項目 | 中身 |
|---|---|
| `id` | 電文 id |
| `classification` | その束の区分（`telegram.earthquake` か `eew.warning`） |
| `filename` | 束の中の電文ファイル名。**`_<受信時刻 17 桁>_` を含める**（アプリは `parseMsFromFileName` が `/_(\d{17})_/` で読み、**UTC の年月日時分秒ミリ秒**として解釈する） |
| `head` | `type`・`time`・`test`・`designation` |
| `xmlReport.head.eventId` | XML の `Head/EventID` |

**アプリがこれ以外の項目を読み始めたら、中継の束にも足す必要がある**（§6.0 のテストが受け持つ）。

**版**

- **束の URL に版を入れる。** アプリは今日以外の日のアーカイブを端末に永続的に控える（`dmdataReplay.ts` の `isArchiveCacheable`）。束を作り直したら URL を変えないと、一度取った端末は古いまま残る
- 版は中身の要約（ハッシュ）から作り、**URL の最後のパス要素に入れる**（`/v1/archive/<YYYYMMDD>-<区分>-<版>`。区分は `earthquake`・`warning` の短い名）。アプリはこの要素を束の id として、取り直しの間隔の帳面（`archiveIdFromUrl`）にも使うので、クエリに入れると版の違う束が同じ id に見える。区分を入れないと、同じ日の 2 つの束が同じ id に見える
- 日と区分の組ごとの今の版は SQLite に持つ（日・区分・状態・版・作った時刻・電文の数）。**束の一覧は日と区分の組ごとに今の版を 1 件だけ返す**（同じ組が 2 件並ぶと、アプリは両方を落として二重に読む）
- **R2 へ新しい版を置いてから、SQLite の今の版を書き換える。** 逆の順で途中に落ちると、一覧が存在しない URL を返す
- 古い版の束は 30 日 R2 に残してから消す。作り直しの直前に一覧を引いた端末が、古い版の URL で 404 にならないため

### 5.4 過去分の控え

**中継の運用開始の日（§4.6）より前の日ごとのアーカイブを、区分ごとに DMDATA が保存し始めた時点（B4）まで遡って、Cron で 2 分に 1 本ずつ取る。** `telegram.earthquake` は 2020-11-18、`eew.warning` は 2022-07-20 から。
運用開始の日以降は §4.5 が受け持つので、同じ日を 2 つの処理が取りに行くことはない。

| | 値 |
|---|---|
| 日数 | `telegram.earthquake` は 2020-11-18 から 2026-10 までの暦日で約 2,150 日。`eew.warning` は 2022-07-20 からの約 1,550 日のうち、アーカイブがあるのは警報の出た日だけ（2022-08-11〜2026-08-23 で 68 日。[`data-sources-spec.md`](spec/data-sources-spec.md) §2 の突き合わせ） |
| 本体の取得 | 1 日 1 本。2 分に 1 本なら約 75 時間で終わる（`eew.warning` の分は 70 本前後） |
| 本体の上限との比 | 5 分に 2.5 本。上限（50req/5min・A3）の 1/20 |
| 目録の取得 | 1 ページ 100 件（C1）で 1 日 1 件なので、`telegram.earthquake` で 22 ページ前後、`eew.warning` で 1 ページ |
| 置く量 | 1 日分の gzip を約 10KB（[`src/services/dmdata.ts`](../src/services/dmdata.ts) のコメントにある 1 日の実測）とすると、全期間で約 21MB。推計震度分布図がある日はそれより重く、どれだけ重いかは測っていないが、含まれる量（10GB）より 2 桁以上小さい |

- **2026-09-14 に、調査スクリプトの走査で DMDATA から利用量の指摘を受けている**（[`data-sources-spec.md`](spec/data-sources-spec.md) §11 改訂履歴）。上限の内側でも負荷が高ければ制限されうる（A5）。2 分に 1 本はそれを踏まえた間隔で、縮めない
- 取れた日・取れなかった日を SQLite に記録し、取れなかった日は次の周回で取り直す。**「その日は電文が無かった」（D2。範囲を引いた目録にその日が現れない）と「取れなかった」を分けて記録する**
- 取った分は索引へ入れ、日の状態（§4.6）を `unfetched` から `reconciled` へ進める。束は §5.3 の規則で作る。**範囲を引いた目録にその日が現れなかった日（D2）は、電文が無かったと確かめた日として `confirmed-empty` にし、空の束を出す**（過去の日のアーカイブは作り終わっているので、現れないことが不在の根拠になる）。ただし日が終わってから 48 時間たつまでは「無い」と読まない（運用開始の日の前日は、アーカイブの遅れ D3 でまだ作られていないことがある。§0）。**取れなかった日（`failed`）には出さない** —— アプリはその日を取りこぼしとして示す（許すかは §12）
- 進み具合は §6 の `/health` に出す

## 6. 利用者への口

**DMDATA と同じ道（パス）・同じ形で返す。** 違うのは次の点だけ。

- 利用者の鍵を受け取らない。代わりに、中継が端末へ出す短い期限の札を付けて呼ぶ（§6.4 の C）。札をどこに載せるか（ブラウザの WebSocket はヘッダを付けられないので、URL かサブプロトコル）は段 1b で決める
- 束と本体は、Worker とは別のオリジン（R2 の公開バケット）から返す（§6.4 の A）。どちらの URL も一覧の `url` に載せるので、アプリは道を組み立てない
- WebSocket は DMDATA のチケット（`POST /v2/socket`）を経ずに繋ぐ
- 区分は `telegram.earthquake` と `eew.warning` に固定
- 繋いだとき、いま発表中の警報を送る（§6.1）。DMDATA の WebSocket には無い、中継だけの知らせ
- 中継が `ping` と、DMDATA と繋がっているかの知らせを出す（§6.1）

| 口 | 返すもの |
|---|---|
| `wss://<中継>/v2/websocket` | 繋いだら `start`、以後は DMDATA から届いた `data` メッセージをそのまま（§6.1） |
| `GET /v2/telegram?datetime=A~B&test=&limit=&cursorToken=` | 索引から作る電文一覧 |
| `GET /v1/:id` | 電文本体（XML の平文として届く。§6.3） |
| `GET /v2/archive?datetime=A~B&classification=&limit=&cursorToken=` | 束の一覧。`classification` はアプリが付けて送る。`telegram.earthquake`・`eew.warning` のどちらでもなければ空の一覧を返す |
| `GET /v1/archive/:id` | 日ごとの束（§5.3）。tar.gz のまま |
| `GET /health` | 上流に繋がっているか・最後に受けた時刻・過去分の控えの進み具合 |

**時刻の範囲の扱いも DMDATA に揃える**（電文一覧は UTC の半開区間、アーカイブ一覧は左端が排他・右端が包含）。
アプリ側はこれに合わせた補正を既に持っている（[`data-sources-spec.md`](spec/data-sources-spec.md) §2「目録の `datetime` は左端が排他・右端が包含」）ので、
中継が「直した」形にすると、そこで 1 日ずれる。

### 6.0 応答の最小形

**アプリが読む項目は、欠けると型では捕まらずに全件が読めない扱いになる。** 中継の応答（一覧 3 つと日ごとの束）を
アプリの取得関数へ通すテストで、次の項目と §5.3 の束の目録の項目を固定する。アプリの取得関数はこのリポジトリ、中継の応答は非公開のリポジトリにある。**応答の見本はこのリポジトリに置き**、アプリ側のテストで固定する。中継のリポジトリのテストは、その見本を取ってきて同じ形を返すかを確かめる（§0）。見本には中継の内部の口の名前や上限の値を入れない

| 口 | アプリが読む項目 | 欠けたとき |
|---|---|---|
| 一覧 3 つ共通 | `status: 'ok'`、続きの `nextToken`（続きを取るときは `cursorToken` に入れ、同じ `limit` を渡し続ける。C4） | `status` が無いと例外（`dmdataReplayLive.ts`・`dmdataReplay.ts`） |
| 電文一覧 | `items[]` の `id`・`head`（`type`・`time`・`test`・`designation`）・`receivedTime`・`url`（中継の本体の口を指す） | `receivedTime` が無いと、その電文は窓に置けず取りこぼしに数えられる（`classifyTelegram` の `malformed`） |
| 束の一覧 | `items[]` の `classification`・`date`（JST の日）・`url` | — |

### 6.1 WebSocket

**繋いだとき**

- アプリは `new WebSocket(url, 'dmdata.v2')` で繋ぐ。**中継はサブプロトコル `dmdata.v2` を返す**（返さないとブラウザが接続を失敗させる）
- 繋いだらすぐ、**状態の知らせ（下記）を送ってから** `start` を送る。アプリは `start` を受けて「接続中」にする（`dmdata.ts` の `handleMessage`）ので、DMDATA と切れている間に繋いだ利用者に、一瞬でも「接続中」と見せないため。いまのアプリは `data` 以外の知らない種類を読み捨てる（同じ関数）ので、知らせを先に送っても壊れない
- 利用者の接続は Hibernation API（`acceptWebSocket`）で受ける。1 つの DO で 32,768 本まで

**いま発表中の警報を送る**（§0）

- 状態の知らせの後に、いま発表中の警報（VXSE43）を送る。DMDATA の WebSocket には無い、中継だけの知らせ
- 張り直したアプリにも同じものを送る（§0）。DMDATA の電文一覧に EEW は載らない（C2）ので、張り直し後の取り戻し（§6.2）では警報を拾えないため
- **何が「いま発表中」かは中継が決める**（§0）。中継は保存した電文から、地震ごとに有効なものだけを選んで送る。有効かの判定（取消・最終報・自動解除の時刻）の細かい形は段 1b で決める
- **受けたアプリは音・読み上げを鳴らさない**（§0）。起動時も張り直しも、画面だけを作る（いまの DMDSS 版の起動時の復元と同じ）

**DMDATA と繋がっているかを知らせる**

- **中継の `ping` だけでは足りない。** 中継は自分で `ping` を出すので、DMDATA との接続が切れていても、アプリの見張り（90 秒届かなければ閉じる）は働かない。知らせが無いと、アプリは「接続中」のまま電文を受け取れない
- 中継は、DMDATA との接続の状態が変わるたびと、利用者が繋いだ直後に、状態の知らせ（`type: 'relay-status'`・繋がっているか・切れた時刻）を送る。アプリはこれを接続の状態へ反映する（§7.3）
- DMDATA と繋がり直したら、§4.4 で取り戻した電文を配ってから「繋がった」を知らせる（`/v2/gd/eew` で取り戻した警報も流す。§0）

**ping**

- **中継は 30 秒ごとに `ping` を出す**（アプリは 90 秒何も届かないと閉じるため）
- `ping` の中身を毎回同じ文字列にし、アプリが返す `pong` を `setWebSocketAutoResponse` で受ける。受けた分は DO を起こさず、課金もされない（§9）
- 送る分（`ws.send`）は課金されない。届いた電文を全員へ配る費用はほぼ掛からない

### 6.2 張り直したアプリの取り戻し

アプリが中継へ張り直したら、**切れていた間の分を `/v2/telegram` で取り戻す。** いまの標準版が P2PQuake でやっていること
（`fetchHistorySince`）と同じ考え方にする（[`data-sources-spec.md`](spec/data-sources-spec.md) §3「張り直したら、切れていた間の分を取り戻す」）。

- 起点は最後に受けた電文の**中継の受信時刻**から 5 分前（P2PQuake の経路の `P2P_RECONNECT_BACKFILL_MARGIN_MS` と同じ幅）
- **取り戻しの要求は控えを通さない**（`cache: 'no-store'`）。P2PQuake の取り戻しも同じ理由で控えから外している（`vite.config.ts` の `runtimeCaching` の注記）

### 6.3 控えと寿命

| 口 | `Cache-Control` | 理由 |
|---|---|---|
| `/v1/:id` | `public, max-age=31536000, immutable` | 電文は変わらない |
| `/v1/archive/:id` | 同上 | 版が URL に入る（§5.3） |
| `/v2/telegram` | `no-store` | 今日の分は育ち、閉じた日の分も突き合わせ（§4.5）で足されうる。控えると、取り戻しや当日の経路が古い一覧を見る。閉じた日はアプリが束で読むので、控えなくても量は増えない |
| `/v2/archive` | `no-store` | 束が足される |
| `/health` | `no-store` | — |

**Worker から返す形では、下の 2 つが成り立つと §9.1 の 5 で確かめた。** 実際には §6.4 の A で R2 の公開バケットから gzip のまま返す（§0）ので、そちらでの返り方は §9 の 11 で確かめる。

- 電文本体は R2 の gzip を `Content-Encoding: gzip` で返し、ブラウザに展開させる。Workers は既定で `Content-Encoding` を見て圧縮し直すので、`encodeBody: "manual"` を付ける見込み
- 束は tar.gz を**`Content-Encoding` を付けずに** `application/gzip` で返す。付けるとブラウザが先に展開し、アプリの展開（`expandArchive`）が失敗する

### 6.4 濫用への備え

アプリはソースを公開しているので、「アプリ以外からは繋げない」形は作れない。**守るのは、費用が膨らむことと、正規の利用者が繋げなくなること**（§0）。中継から送る分は課金されない（§6.1）。利用者から届く分は、`pong` が毎回同じ文字列なら DO を起こさず課金されない見込みで、§9 の 7 で確かめる（成り立たなければ 30 秒ごと × 接続数が DO の要求に乗る。§10）。費用になるのは HTTP の口を繰り返し叩くことと、繋いでは切るを繰り返すこと。1 つの DO が受けられる WebSocket は 32,768 本までなので、埋められると正規の利用者が繋げない。

- **A. 変わらないものは Worker を通さずに返す。** 束と電文本体は R2 の公開バケットを独自ドメインで出し、Cloudflare の控えから返す。叩かれても Worker の要求に数えない見込み。R2 の公開バケットの課金と、`Content-Encoding` の返り方（§6.3）は確かめていない（§9 の 11）
- **B. 回数の上限は IP ごとに置く。** WebSocket は IP ごとの本数も絞る。**上限の値はコードに書かず設定へ置く**（§0）。同じ IP の後ろに多くの人がいる回線（学校・携帯の一部）で当たりうる
- **C. 端末ごとの短い期限の札。** 初めて開いたとき中継から署名つきの札（期限は数時間）を受け、以後の口（一覧・WebSocket・Web Push の購読）はその札を付けて呼ぶ。札の発行にも B の上限を掛ける。正規の利用者は初回に 1 往復増える。オフラインで札を取り直せなくても、控えで動く分には要らない。守るのは Worker の口（一覧・WebSocket・札の発行・Web Push の購読）だけで、A の公開バケットの口は札も B の上限も見ない。そちらの費用は Cloudflare の控えと公開バケットの課金で抑える（§9 の 11）。公開バケットの中身の一覧が外から引けないことも §9 の 11 で確かめる
- 中継（Worker）の CORS は、公開しているアプリのオリジンと開発用のオリジン（localhost の dev サーバー・preview）に開く（§0。R2 の公開バケットの側も同じオリジンへ開く。§0 の公開バケットの CORS の行）。フォークしたアプリからは、ブラウザでは繋げない。**ただし CORS はブラウザの外からの呼び出しを止めない**ので、守りは B と C が担う
- 配り直しを止める備え（札の発行に Turnstile・端末認証を挟む、利用規約で禁じる）は入れない（§0）

### 6.5 不正アクセスへの備え

中継の利用者の口は読み取りだけにする。守るものと手当ては次の 6 件（§0）。

| 守るもの | 手当て |
|---|---|
| DMDATA の鍵 | Worker の secret に置き、コード・リポジトリ・ログに出さない。鍵の権限は中継に要る区分（`telegram.earthquake`・`eew.warning`・`gd.eew`）だけにする（§4.7） |
| Cloudflare のアカウント | 二要素認証。配備に使う API トークンは、その Worker と R2 だけを触れる最小の権限で作り、期限を付ける |
| 中継の口 | 利用者の口は読み取りだけにする。入力（`datetime`・`limit`・`id`）は形を検証し、R2 のキーへそのまま渡さない。管理の口は作らない（作るなら Cloudflare Access の後ろへ置く） |
| Web Push の購読と送り口 | 購読の登録・解除は C の札がある端末だけ。通知を送る処理は中継の中からだけ呼び、外の口を作らない。購読は通知のためだけに持ち、購読と一緒に IP を保存しない（Cloudflare のログに残る分は §12 の「中継が何を記録し、どれだけ残すか」） |
| 依存 | 非公開のリポジトリ `yuremado-relay` にも `npm audit` を掛ける。依存は少なく保つ |
| 気づく | 要求数・WebSocket の本数・DMDATA との接続の状態を見張り、閾値を超えたら知らせる（Cloudflare の通知）。費用の上限の通知も置く |

## 7. アプリ側の差し替え

### 7.1 繋ぐ先と認証を外から渡す

DMDATA の経路は、繋ぐ先（`API_BASE`・`TELEGRAM_DATA_BASE` ほか）と認証（`authHeader(apiKey)`）を定数で持っている。
これを「どこへ・どう繋ぐか」を表す 1 つの値にまとめ、呼び出し側から渡す。下の表は §0 の決めごとから導いた見込みで、まとめ方（§12）が決まってから確かめる。

| 経路 | 中継（誰でも） | 自分の鍵（鍵を入れた人だけ。予報を足す。§0） |
|---|---|---|
| WebSocket | 中継へ直接繋ぐ。区分の交渉（`dmdataClassifications.ts`）・409 の枠返し（`releaseSocket`）は通らない | `POST /v2/socket` でチケット → `new WebSocket(url, 'dmdata.v2')`。申し込む区分は予報（`eew.forecast`）だけ |
| 受けている区分 | **`['telegram.earthquake', 'eew.warning']` を初めから渡し、待たせない** | チケットの応答から決まる（`classificationsReady`） |
| EEW の電文種別（`eewHeadType`） | `'VXSE43'`（予報が無く警報だけを受ける人の既存の経路。[`data-sources-spec.md`](spec/data-sources-spec.md) §2「一部の区分だけ受けられる人」） | `'VXSE45'`（VXSE44 は取り込まない。いまの `eewHeadTypeFor` と同じ） |
| 一覧・本体・アーカイブ | 鍵なし | 鍵つき（予報の分だけ） |
| 門（`dmdataRequestGates.ts`） | **中継の上限に合わせた別の門。** 「もっと見る」の残り時間の表示（`useFetchThrottled`）はこの門に依存している | DMDATA の上限（50req/5min ほか）を守る |

**鍵を入れた人では、警報が中継の VXSE43 と自分の鍵の VXSE45 の 2 経路から届く。** いまの DMDSS 版は、予報を受けているなら VXSE43 を取り込まないと決めている（同 §2「EEW は VXSE45 だけを受ける」。遅れて届く VXSE43 が新しい予想を上書きするため）。予報を受けている人は VXSE45 だけを採り、VXSE43 は取り込まない（§0）。鍵の接続が切れている間の扱いは段 3a で詰める。

**中継のための差し替えでは、パーサー（`buildXmlPayload`・`buildBinaryPayload`）から下には手を入れない。** 中継に繋いでも自分の鍵で繋いでも、読み取りの経路を 2 本持たないため（§3）。

**ライブの受信も、一覧・リプレイ・取り戻しと同じ `buildXmlPayload` を通る。**

- **共通のもの**: 電文の読み取り（`buildXmlPayload`）と、電文種別から何の電文かを決める表（`dmdataTelegramPayload.ts` の
  `TELEGRAM_KIND_OF_HEAD_TYPE`。電文ログもこれを引く）
- **`handleMessage` にだけあるもの**: 受信の手前の処理（試験報の破棄・本文の復号・二進電文の結合・受け取り済みの印）と、
  ライブだけの振り分け（VXSE42・購読していない EEW の警告・VXSE44・設定「試験報を受信（検証用）」のときに試験報の
  EEW を `test: false` にして画面へ流す扱い）

### 7.2 `isDmdss` を外す

いまは `isDmdss`（[`src/utils/env.ts`](../src/utils/env.ts)）1 つが「電文をどこから取るか」「EEW をどこから取るか」「どの機能を出すか」を決め、ビルドも配信の URL（`/yuremado/`・`/yuremado/dmdss/`）も 2 つに分かれている。
1 つにまとめると（§0）、この判定は「鍵が入っているか」と「中継に繋がっているか」に置き換わる。

**`isDmdss` の参照を、すべてどちらかに割り当て直す**（2026-10-29 時点で、`src/` のテスト以外の 11 ファイルに 122 行。`grep -rc isDmdss src` から名前に `.test.` を含むファイルと `src/test-utils` を除いた合計で、コメントの中の言及も含む。2026-10-14 には 105 行だった）。
割り当ての一覧表は段 3a の成果物にする。迷う例が既にある —— 地震カードの発生時刻の秒（`useQuakeOriginSeconds.ts`）は、
`isDmdss` でカードの識別子の取り出し方（XML 由来か P2PQuake 由来か）と、秒の材料（`/v2/gd/eew` か気象庁の一覧か）を分けている。まとめた後のカードは XML 由来になるが、秒の材料は中継が配る `/v2/gd/eew` になる（§0）。

**2 つの版をどうまとめるか**は §0（2026-10-30）。アプリは独自ドメイン（`yuremado.com`・Cloudflare Pages）へ移り、github.io の 2 つの URL に残す橋渡しのページが、`quake-viewer-settings-dmdss` を先に、無ければ `quake-viewer-settings` を読んで新しいドメインへ渡す。
同じに動くかは、決まった窓を両方でリプレイして録画用の記録（`drainEvents`）の差を比べて確かめる（§0）。段 3a では繋ぐ先が DMDATA のままなので、差は出ない見込み（確かめていない）。

### 7.3 WebSocket の本数

いまの標準版の受信（[`src/hooks/useEarthquakes.ts`](../src/hooks/useEarthquakes.ts) の P2PQuake の分岐）は、P2PQuake の WebSocket 1 本・
起動時の履歴・張り直し後の取り戻しを一体で書いている。P2PQuake は使わなくなる（§0）ので、まとめた後は

- **中継** —— 誰でも 1 本。地震・津波・南海トラフ・長周期・地震回数・お知らせ・警報・推計震度分布図・加工データ
- **自分の鍵** —— 鍵を入れた人だけもう 1 本。予報

になる。いまの標準版が P2PQuake の 556 と Yahoo の EEW を 1 つにまとめている役（`mergeEewReport`）を、何が引き継ぐかは §12。
接続の状態は、中継の接続・中継が知らせる DMDATA との状態（§6.1）・自分の鍵の接続から決まる。
中継の接続は、状態の知らせを受けるまで「接続中」と確定させない。**画面へどう畳んで出すかは未決**（§12）。

### 7.4 鍵の無い利用者に増えるもの（見込み）

いまの DMDSS 版にしかなかった次の情報が、鍵が無くても届くようになる。**画面に出すかどうか・出し方は §12 で決める。**

- 緊急地震速報（警報）の電文（警報の対象地方・予想される長周期地震動の階級・固定付加文など、P2PQuake の 556 に無い項目を含む）
- 南海トラフ地震臨時情報・関連解説情報・後発地震注意情報
- 長周期地震動観測情報・地震回数に関する情報・地震・津波に関するお知らせ・推計震度分布図（§0）
- 地震情報の取消と訂正の区別・遠地地震・震源要素更新・区域の震度
- 津波の観測点・観測波高・到達確認・失効時刻・解除と取消の区別

テストボタン（設定の窓で `isDmdss &&` に包まれているもの。2026-10-14 時点で `SettingsTab/index.tsx` に 24 箇所）・
テストボタンの台本がバリアントを分けている箇所（`testTelegramScripts.ts` の `onlyIn`）・仕様書の「標準版は〜」の記述も、§7.2 の割り当てに合わせて直す。

### 7.5 中継と関係しないもの

| もの | 扱い |
|---|---|
| 強震モニタ（Yahoo） | どちらの版も同じで、中継と関係しない。いまの標準版は予報の段階の緊急地震速報も Yahoo（hypoInfo）から取っている。鍵の無い人にそれを続けるかは §12 |
| ヒートマップ（いまの標準版は P2PQuake の `/jma/quake`、DMDSS 版は DMDATA の震源カタログ） | P2PQuake は使わなくなる（§0）。代わりは長期震源カタログに、末尾の空きを中継が配る震源カタログ（`/v2/gd/earthquake`）で足す（§0。いまの DMDSS 版と同じ） |

### 7.6 Service Worker と控え

中継の口は別のオリジンになる。寿命は中継が付ける（§6.2・§6.3）ので、Service Worker の `runtimeCaching` には足さない。
アプリ側の控え（電文本体の IndexedDB・アーカイブ本体の IndexedDB）は DMDSS 版と同じものを使う。

中継を利用者に出す段（§11 の段 3b）で、次を同じコミットで直す。

## 9. 作る前に実機で確かめること

| # | 確かめること | 確かめないと |
|---|---|---|
| 1 | **DO から DMDATA の WebSocket に、サブプロトコル `dmdata.v2` を付けて繋げるか。** アプリは `new WebSocket(url, 'dmdata.v2')` で繋いでいる。Cloudflare の資料にはサブプロトコルの指定についての記述が無い | 中継そのものが成り立たない |

| 4 | `/v2/telegram` の `datetime` に日時（時分秒）を渡せるか（§4.4） | 取り戻しを日付単位に広げることになる（その日の一覧を全部引き、索引と比べる） |

| 6 | Workers の回数の上限の仕組み（Rate Limiting の束縛）が、この用途に使えるか | §6.4 を自前で作ることになる |
| 7 | アプリの `pong` が毎回同じ文字列になるか（§6.1） | `pong` のたびに DO が起き、受信の課金（20 通で 1 リクエスト）が掛かる。30 秒ごと × 接続数が DO の要求に乗る（§10） |

### 9.1 段 1a で確かめた結果

使い捨ての測定用 Worker を workers.dev に立てて測った（2026-10-30）。叩き方と判定の基準は、中継のリポジトリの測定用 README にある。

| # | 判定 | 出たもの |
|---|---|---|
| 1 | 成り立つ | 繋ぐための払い出しは 200、接続の切り替えは 101 で、返ったサブプロトコルは `dmdata.v2`。申し込んだ区分（`telegram.earthquake`・`eew.warning`）がそのまま通った。枠は `DELETE /v2/socket/:id` の 204 で返せた |
| 2 | 成り立たない | `ping` は 20 秒おき（中央値 20.005 秒・45 回）に届いたが、毎分の Alarm を止めた形では、張ってから約 15 分で `ping` が途絶えた。次に叩いたときは DO が起き直していて（起動の印が変わった）、上流は閉じていた。閉じた記録は残っていない。**測った 1 回（毎分の Alarm なし・約 15 分）では、外から `ping` が届いていても、外へ張った接続だけでは DO は起き続けなかった**。閉じた記録が無いので、落ちた仕組みは確かめていない。**毎分の Alarm を張った形では、約 1 時間 48 分（02:31〜04:19 JST）上流が開いたまま `ping` が届き続けた。** その後 DO が起き直し（起動の印が変わった）、上流は閉じていた。このときも閉じた記録は残っていない。測ったのは 1 回だけで、起き直した理由は確かめていない |
| 3 | 保留（資料にはあるが、実物は見ていない） | 2 の 15 分と、Alarm を張った約 1 時間 48 分のどちらでも、電文は 1 通も届かなかった。DMDATA の公開の資料（WebSocket v2 の `data` の欄）には、通過した場所ごとの時刻 `passing[].time`（説明は「通過した時間」）と、基点時刻 `head.time` がある。受信時刻と書いた欄は無く、`passing` のどの要素が DMDATA の受信にあたるかも書かれていない。実物は段 1b 以降の中継で電文を受けたときに確かめる |
| 4 | 成り立つ | 日時は日本時間として読まれ、受信時刻（`receivedTime`）で絞られて秒まで効く。00:10:00〜00:12:00 を渡すと、受信が 00:10:30 と 00:11:05 の 2 通だけが返り、00:09:30 と 00:12:22 は入らなかった。発表時刻（`head.time`）が範囲の外でも、受信が範囲の中なら返る |
| 5 | 成り立つ（条件つき） | gzip を受け付ける要求（`Accept-Encoding: gzip`）には、置いたバイト列のまま `Content-Encoding: gzip` で届き、二重には圧縮されなかった。**gzip を受け付けない要求には、Cloudflare が展開して `Content-Encoding` なしの元の XML で返す。** 束（`Content-Encoding` なし）は置いたバイト列のまま届いた |
| 6 | 成り立つ | 上限を超えた分は断られた。数え方は場所ごとなので、上限ちょうどではなく 1 回多く通った |
| 7 | 成り立つ | 利用者役の接続から 30 秒ごとに `pong` を 10 分（20 回）送り、20 回とも自動応答が返った。その間 DO が起きた記録は増えず（増えたのは状態を読んだ 1 回だけ）、接続は 1 本のまま保たれた。測ったのは接続 1 本・10 分の 1 回 |
| 8 | 当たるが、gzip のままでは成り立たない | workers.dev でも 2 回目は控えから返った。ただ控えから読んだ本体は `Content-Encoding` なしで、展開された大きさだった。gzip のまま控えに置いて返す形にはならない |
| 9 | 保留 | 約 1 時間半・さらに約 2 時間あけて 3 回測り、Worker と DO のどちらからも、3 回とも同じ IPv6 の 1 つ（各 3 回とも同じ）。DMDATA へ IPv4 で繋いでいるかは分からないので、固定かは決められない |
| 11 | 成り立つ（控えの規則が要る。課金の見積もりは保留） | 独自ドメイン（`yuremado.com` の下の測定用の名前）で公開バケットを出して測った。gzip を受け付ける要求には `Content-Encoding: gzip` のまま、受け付けない要求には展開して返り、束はそのまま届いた（5 と同じ）。**拡張子の無い本体は、既定では控えに入らなかった**（`DYNAMIC`）。その名前を拡張子によらず控える規則（Cache Rules）を足すと、2 回目から控えに当たり、当たったときも gzip の扱いは同じだった。控えに当たる 30 回の間に数えられた R2 の読み取りは 1 件。規則を足す前の 10 分間の読み取りは 49 件で、叩いた 8 回より多い理由は確かめていない。§10 の見積もりに使う前に確かめる |

5 と 8 を受けて、束と本体は公開バケットから gzip のまま返し、Worker の Cache API は使わないと決めた（§0）。11 から、本番の公開バケットの名前にも同じ控えの規則が要る。2 から、上流の接続を保つには DO を Alarm などで起こし続ける必要がある。Alarm を張っても DO が起き直すことはあったので、起き直したときに上流を張り直す処理も要る。

## 10. 費用の見積もり

Workers Paid（月 5 ドル）に含まれる量と比べた。料金は 2026-10-14 に Cloudflare の資料で読んだもの。

**利用者数によらず掛かるもの**

| 項目 | 見込み | 含まれる量 |
|---|---|---|
| DO の時間 | 常に起きている 1 つで月 324,000 GB-s（0.125GB × 30 日） | 月 400,000 GB-s |
| DO の要求（Alarm） | 月 43,200 回（毎分） | 月 100 万 |
| R2 の書き込み | 電文 1 通につき 1 回・束 1 日 1 回（作り直しを除く）。1 日あたりの電文の件数は数えていない | 月 100 万 |
| R2 の量 | 見積もっていない（§5.4） | 10 GB |

**利用者数で増えるもの**（起動 1 回あたり）

| 項目 | 起動 1 回あたり | 含まれる量 |
|---|---|---|
| Worker の要求 | 2 回目以降で 15 件前後（束の一覧 1・束 7・当日の一覧 1・本体数件）。**端末の控えが空の初回は 100 件前後**（DMDSS 版の初回の実測で電文本体が 85 件。2 回目以降は端末の控えで 0 件。[`data-sources-spec.md`](spec/data-sources-spec.md) §2「大量に取るならアーカイブを使う」と CLAUDE.md「検証」） | 月 1,000 万 |
| DO の要求 | 接続 1・当日の一覧 1 | 月 100 万 |
| R2 の読み取り | 控え（§9 の 8）に当たらなかった分だけ（束と本体） | 月 1,000 万 |

- **利用者数の想定はまだ置いていない。** 含まれる量から逆算すると、2 回目以降の起動だけなら Worker の要求（15 件）が月 67 万回、DO の要求（2 件）が月 50 万回で上限に届く。DO の側が先に効くが、初回の起動が混ざると Worker の側が先に効く（初回 1 回で 2 回目以降の 7 回ぶん）
- **デプロイと DO の再起動のたびに、全員が繋ぎ直す。** そのぶんの接続も DO の要求に乗る
- §9 の 7 が成り立たなければ、`pong` の受信が 30 秒ごと × 接続数で DO の要求に乗る（受けた分は 20 通で 1 リクエストに数えるので、100 接続で月 43 万回）
- 1 つの DO が受けられる WebSocket は 32,768 本まで。超えるときの分け方は §12
- **ログの料金は 2026-12-01 に切り替わる**（Cloudflare Observability の料金へ）。ログの量は切り替わった後の料金で見積もり直す

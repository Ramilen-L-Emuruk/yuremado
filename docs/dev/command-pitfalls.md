# コマンドの実行と結果の読み方

> [`CLAUDE.md`](../../CLAUDE.md) の同名の節から案内される詳細。いつ開くかは `CLAUDE.md` 側に書いてある。

コマンドやツールを走らせるときの落とし穴。中心は**成功したかどうかを何で判断するか**で、「エラーが出なかったから通った」で進めると、通っていない結果を材料にして先へ進むことになる。あわせて、Windows と Excel で**成否が見た目から分からない**ケースを扱う。

> 「日本語を含むパスが渡らないことがある」「Git Bash（Windows）で引数が書き換わる」「Windows PowerShell 5.1 から外部コマンドを呼ぶとき」は Windows 固有、「リモートの Windows へ SSH で命令を渡すとき」は接続先が Windows の場合、「既存の Excel ブックを書き換えるとき」は Excel を扱う場合の話。当てはまらない環境では読み飛ばしてよい。

## 終了コード 0 を成功と決めつけない

**終了コードは、コマンドが「自分の仕事を終えた」ことしか表さない。** 目的を果たしたかは別。

実例（Subversion 1.14.5 で実測）: **作業コピーの中の存在しないパス**を `svn status` に渡すと、**出力は空、終了コードは 0、警告も出ない**。「対象が無い」と「対象を見に行けていない」が同じ見た目になる。

**成功とみなす条件を、コマンドごとに 3 つ揃えてから使う。**

1. **終了コードが 0**
2. **出力にエラーの印が無い** —— そのコマンドがエラー・警告を出すときの形（`svn:` や `svn: warning:` で始まる行、`error:` など）が 1 行も無い。PowerShell から外部コマンドを呼ぶ場合は `NativeCommandError`（外部コマンドが標準エラーへ出した内容を PowerShell がエラーとして包んだときの型名）も印になる
3. **目的を果たしたときにだけ出る印がある** —— 処理した件数、作成・更新されたパスの表示、取得した値そのもの

**3 に使えるのは「対象が実在したこと」を示す出力だけ。** 対象の有無にかかわらず必ず出る見出しや決まり文句は印にならない（上の `svn status -u` は、存在しないパスでも「何リビジョンに対しての状態か」を示す行を出し、終了コードも 0 になる。実測で確認した）。

**3 が無いコマンドは、3 で判定できない。** その場合は、結果を別のコマンドで確かめる。同じ対象に対して**失敗を終了コードで返すコマンド**があれば、それを使う（`svn` なら `status` ではなく `info` が、存在しないパスに対して終了コード 1 を返す）。

**1 つでも欠けたら失敗として扱い、その結果を後続の材料にしない**（3 が無いコマンドは、上記のとおり別の確認で代える）。

**パイプの後ろの終了コードを、前のコマンドのものと読まない。** `cmd | tail -n 20; echo $?` が出すのは `tail` の終了コードで、`cmd` が失敗していても 0 になる（型チェックの失敗をこれで「通過」と誤報しかけた例がある）。終了コードを見たいコマンドはパイプせずに実行し、次の行で `echo $?` を出す。

### 「0 件」「見つからない」は、見に行けていない可能性を先に消す

**何も無いという答えは、失敗が最も無害な顔で現れる形。** 「無かった」と「探せていない」が同じ見た目になる。

- **検索の 0 件は、当たると分かっているファイルで検算してから結論に使う。** 同じパターンを、その文字列が実在する 1 ファイルへ当てて 1 件以上出ることを確かめる（Git Bash の `grep` が黙って 0 件を返す例は下記「Git Bash（Windows）で引数が書き換わる」）
- **`which` / `where` の「見つからない」は「入っていない」ではない。** 答えているのは PATH に無いことだけ。インストール先へ PATH を通していない道具は、入っていても見つからないと答える。**入れ直しを提案する前に、インストール先の絶対パスにその実行ファイルがあるかを確かめる**（ある道具の入れ直しを提案し、入れ直しに 1〜2 GB の取得が要るところで、実は入っていたと指摘された例がある）
- **「この端末に無い」と結論する前に、メモリと会話の記録も読む。** 道具の在処や接続先は、以前に教わっていることがある。教わった在処をメモリへ書かずにいて、後で「無い」と言い、その誤りの上に要らない提案まで積んだ例がある（教わった端末の事情をその場でメモリへ書く決まりは[`CLAUDE.md`](../../CLAUDE.md)「「記録した」と言えるのは、消えない場所へ書いたとき」。記録の読み方は[`CLAUDE.md`](../../CLAUDE.md)「会話の内容を思い出せないときはトランスクリプトを読む」）。誤りに気づいたら、そこから派生した提案も一緒に取り下げる

## ツールの出力に想定外の文が混じったら、判断に使う前に報告する

**ツールの結果に、そのツールが出すはずのない文が混じることがある。** 空の `git status --short` の結果の後ろに、本来ハーネスが出さない英語の解説文（「空の出力はコマンドが成功したことを示す」の類）が付いていた例がある。これを黙って受け入れたことが、ありもしないコミットのハッシュを報告する虚報へ繋がった。

- **想定と食い違う出力・余計な説明文・不自然な語りが混じっていたら、どんなに些末でも、判断の材料にする前に「予期しない出力があった」とユーザーへ伝える。** 黙って処理しない
- **信じるのは確かめられる事実だけ**（上の例なら、出力が空だったことそのもの）。混じった文は根拠にしない
- **結果が返る前に結果らしきものを先回りして書かない・返った後は必ず文で報告する**、の扱いは[`CLAUDE.md`](../../CLAUDE.md)「ツールの結果が返ったら、文で報告する」が持つ。先回りが、混線や捏造の入口になる
- 虚報が続くなら、コンテキストの圧縮（`/compact`）を提案する。圧縮を挟むと解消した例がある（なぜ効くかは確かめていない）

**モデルを問わず起きる。** 最上位モデルで観測した「実行していないツールの結果を捏造する」現象への手当ては[`CLAUDE.md`](../../CLAUDE.md)「モデルの昇格・降格を提案する」の「最上位モデルで動いている間は、ツールの結果を検算する」にあり、混じった文を見つけたときの扱いはこの節が持つ。

## 日本語を含むパスが渡らないことがある（Windows）

非 ASCII を含むパスを外部コマンドへ渡すと、「ファイルが見つからない」という形で失敗したり、返ってくる出力が化けたりすることがある。**コマンドの書き方ではなく、文字コードの食い違いが原因**なので、引数の書き方を変えても直らない。

**まず、入力側（引数が渡っていない）か出力側（返りが読めない）かを切り分ける。** 対処が違う。

| 症状 | どちら | 見分け方 |
|---|---|---|
| 「見つからない」と言われるが、そのパスは確かに存在する | 入力側 | ASCII だけのパスに置いて同じコマンドを試す。通れば入力側 |
| 処理は動いたが、返ってきた文字が化けている | 出力側 | 出力をファイルへ書いて、そのファイルを読む。正しく読めれば出力側 |

**出力側なら、結果をファイルへ書いて読む。** エラー出力も含めて UTF-8 で書き、そのファイルを読む。置き場所は**作業対象の外**（一時作業用のディレクトリ）——作業対象の中に置くと、バージョン管理の差分や成果物に混ざる。

**入力側なら、コンソールの文字コードを切り替える手がある。** ただし**切り替え先の値も、何を切り替えれば効くかも環境による。** 自分の環境で 1 度試して効くことを確かめてから使うこと。

**切り替える前に、いまの値を控える。** 切り替えたら**必ず元へ戻す**——設定はコンソールに残り、後続の呼び出しへ影響する。**次の呼び出しの最初に、戻っているかを確かめる**（途中で止まると戻らないため）。

> **引数の `$` が消えるのは、文字コードとは別の原因。** パスを `"` で囲むと `$` から始まる部分が変数として解釈されて消えるので、`'` で囲む（Excel が開いている間に作られる `~$<ブック名>` のようなファイル名で実害が出る）。

## Git Bash（Windows）で引数が書き換わる

Windows の Git Bash（MSYS2）は、コマンドへ渡す前に引数を書き換えることがある。**どれもエラーを出さず、別の結果として返ってくる**ので、書き換えを疑わないと原因を取り違える。

| 症状 | 原因 | 代わりにすること |
|---|---|---|
| `grep` のパターンに、バックスラッシュそのものの直後に `/` が続く形（`'https:\\/'`）を含めると、当たるはずのものが **0 件**になる。`/` だけ・`\/`・`\|` は当たる（2026-10-21 に Git Bash で実測） | MSYS2 の引数変換 | 固定文字列なら **`grep -F`**（複数は `-e` を並べる）。正規表現が要るなら `Grep` ツール（ripgrep。この変換を受けない） |
| `/` で始まる引数（`/api/items` のような API のパス）が `C:/Program Files/Git/api/items` に化け、URL が壊れて `getaddrinfo failed` のような**名前解決の失敗**に見える | MSYS2 のパス変換 | そのコマンドの前に **`MSYS_NO_PATHCONV=1`** を付ける |
| `curl -o /tmp/x.json` で書いたファイルを、Windows のプログラム（`node` など）が `ENOENT` で読めない | Git Bash の `/tmp` は Git Bash の中だけの場所で、Windows のプログラムは `C:\tmp` を探す | Windows のプログラムにも渡すファイルは、Windows 形の絶対パス（`C:/Users/...`）へ書く |

実例（固定文字列 `https:\/\/` が 2 箇所あるファイルで実測）:

```bash
grep -c 'https:\\/\\/' <ファイル>        # → 0（誤り）
grep -cF 'https:\/\/' <ファイル>         # → 2（正しい）
MSYS_NO_PATHCONV=1 python <スクリプト>.py /api/items out.json   # / で始まる引数がそのまま渡る
```

`curl` に `http://...` で始まる URL を丸ごと渡す形は書き換えられない。**IP を直に書いているのに名前解決で落ちたら、まずパスの書き換えを疑う**（プロキシや DNS のせいと誤診して時間を失った例がある）。

## Windows PowerShell 5.1 から外部コマンドを呼ぶとき

Windows PowerShell 5.1（`powershell.exe`。`$PSVersionTable.PSVersion` が 5.1 のもの。PowerShell 7 の `pwsh` とは別物で、7 での挙動は確かめていない）から外部コマンド（`ssh`・`git`・`python`、別の `powershell.exe -Command` など）を呼ぶとき、次の 3 つの場面で食い違いが起きる（2026-10-22 に Windows PowerShell 5.1.26100 で実測）。**どれもエラーにならず、違うものが向こうへ届くか、違うものとして読まれる。** 当てはまる場面が無い呼び出しでは、何もしなくてよい。

| 場面 | 起きること | 代わりにすること |
|---|---|---|
| 引数に `"` を含めるとき | **引数に埋め込んだ `"` が消える。** 空白を含む引数では、その位置で引数も割れる。`'{"a":1}'` は `{a:1}` として届き、`'bash -lc "echo hi there"'` は `bash -lc echo`・`hi`・`there` の 3 つとして届いて別のコマンドとして動く | 外側を `'` で包んだまま、中の `"` を `\"` と書く（`'{\"a\":1}'` も `'bash -lc \"echo hi there\"'` も、書いたとおりの 1 つの引数で届いた。`\"` を解するのは、引数を標準のやり方で解釈する相手だけで、`cmd.exe /c` などには当てはまらない）。込み入った引用は、ファイルに書いて渡す（コミットメッセージなら `git commit -F <ファイル>`、リモートなら下記「リモートの Windows へ SSH で命令を渡すとき」の `-EncodedCommand`） |
| 外部コマンドの出力を文字列として受け取るとき | **出力が、コンソールの文字コードで読まれる。** 日本語版の Windows の既定（cp932）のコンソールでは、UTF-8 の出力（JSON など）が化けて解釈に失敗する | 相手が UTF-8 で出すと分かっているなら、呼ぶ間だけ `[Console]::OutputEncoding` を UTF-8 にし、終わったら戻す（下の例）。**決め打ちで切り替えない** —— 相手がコンソールの文字コードで出す道具なら、UTF-8 にすると逆に化ける |
| 文字列をパイプで外部コマンドの標準入力へ渡すとき | **渡す文字列は `$OutputEncoding` で符号化される。** 5.1 の既定は US-ASCII なので、非 ASCII は `?` になる。末尾には必ず CRLF が付く。さらに `[Console]::InputEncoding` が BOM 付きの UTF-8 のコンソールでは、頭に BOM（`EF BB BF`）が付く | 非 ASCII を渡すとき、または BOM を許さない相手へ渡すときは、呼ぶ間だけ `$OutputEncoding` と `[Console]::InputEncoding` の両方を BOM 無しの UTF-8 にする（下の例） |

**名前の似た 2 つの設定は、向きが逆。** `[Console]::OutputEncoding` は相手の出力を読む向き、`$OutputEncoding` は相手の標準入力へ送る向き（送るときの頭の BOM の有無は `[Console]::InputEncoding` が決める）。

出力と標準入力の対処を、相手が UTF-8 で入出力する場合についてまとめると次の形になる。この例を、Claude Code の PowerShell のツールのコンソールと、cp932 に切り替えたコンソールの 2 つで走らせて確かめた。どちらでも、標準入力は BOM 無しの UTF-8 で届き、UTF-8 の出力は正しく読め、終わった後に 3 つの設定とも元の値へ戻った。相手の出力が UTF-8 でないなら `output` の行を、標準入力へ何も渡さないなら `input` の行と `<渡す文字列> |` を外す（注釈が英語なのは、下記のとおり `.ps1` を ASCII だけで書くため）。

```powershell
$prevOut = [Console]::OutputEncoding; $prevIn = [Console]::InputEncoding; $prevOE = $OutputEncoding
try {
  $utf8 = New-Object System.Text.UTF8Encoding $false
  [Console]::OutputEncoding = $utf8                          # output: read the tool's output as UTF-8
  [Console]::InputEncoding = $utf8; $OutputEncoding = $utf8  # input: send stdin as UTF-8 without BOM
  $result = <渡す文字列> | & <外部コマンド> <引数>
} finally {
  [Console]::OutputEncoding = $prevOut; [Console]::InputEncoding = $prevIn; $OutputEncoding = $prevOE
}
```

**Claude Code の PowerShell のツールで確かめた結果は、ユーザーのコンソールと食い違う。** 上の実測の時点で、ツールのコンソールは入出力とも BOM 付きの UTF-8 で始まっていた（Claude Code の版で変わりうる）。日本語版の Windows のコンソールの既定は cp932。**食い違う向きは場面によって違う** —— 出力の文字化けはユーザーの側でだけ起き、標準入力の頭の BOM はツールの側でだけ付く（`?` と末尾の CRLF は両方で起きる）。ツールで確かめて直ったとした修正が、ユーザーのコンソールでは壊れたままだった例がある。

- **ユーザーと同じ条件で確かめるときは、スクリプトをファイルに書き**（下記「スクリプトはファイルに書いてから実行する」）、上の例と同じく値を控えてから、コンソールの入出力をユーザーと同じ文字コードにする（日本語版の既定なら `[Console]::OutputEncoding` と `[Console]::InputEncoding` の両方を `[Text.Encoding]::GetEncoding(932)`）。終わったら `finally` で戻す。それを `powershell.exe -NoProfile -ExecutionPolicy Bypass -File <ファイル>` で走らせる
- **`.ps1` は ASCII だけで書く**（コメントも）。5.1 は BOM の無いスクリプトを ANSI のコードページで読む。日本語の文字列が要るなら文字コードから組み立てる（`[string][char]0x65E5` のように）

## スクリプトはファイルに書いてから実行する

**シェルのコマンドラインに、別の言語のスクリプトを埋め込まない。** 引用符・バックスラッシュ・バッククォートがシェルに解釈され、意図と違う中身が渡る。しかもスクリプトは動くので、壊れたことに気づきにくい。

- **Bash ツールのヒアドキュメントは、引用符付き（`<<'PY'`）でもバックスラッシュを半分に潰す。** Python からソースを書き換えるつもりで `"\\n"` と書くと、Python には `"\n"` が渡って本物の改行になり、文字列リテラルが壊れる。`[\\s\\S]` のような正規表現は `SyntaxWarning: invalid escape sequence` として現れる
- `python -c "..."` に**バッククォートを含む文字列を入れると、シェルがコマンド置換として解釈して消える**
- 引用符が入れ子になるものも同じ。外側と内側の引用符の扱いを読み違える

**守り方を「気づいたら避ける」にしない。** 書く瞬間に頭にあるのは「改行を入れる」であって「バックスラッシュを 1 文字置く」ではないので、注意深さでは防げない（この注意を知っている状態で、1 日に 2 回踏んだ例がある）。判断の分かれ目を、気づけない「特殊な文字を含むか」ではなく、毎回必ず選ぶ**「どのツールで書くか」**へ移す。

- **ソースの編集は `Edit` / `Write` で行う。** 引数は JSON で渡るので、エスケープがそのまま通る
- **スクリプトは `Write` で一時作業用のディレクトリへファイルとして書き、`python <ファイル>` のようにファイルを指定して実行する**（`Write` は潰さない）
- それでも Python の一括置換をコマンドラインで書くなら、特殊な文字の有無を問わず、冒頭に `BS = chr(92)` を置いてバックスラッシュはそこから組み立てる（使わなくても害は無い。**要ることに気づけないのが問題**なので、無条件に置く）

**作業ツリーのファイルは LF と CRLF が混ざりうる**（`git checkout --` で戻したファイルが CRLF になることがある）。Python で複数行を照合するときは、読み込んだ後に `s.replace('\r\n', '\n')` で揃えてから置換する。揃えないと、複数行のパターンが黙って 0 件になる。

## 作業ディレクトリはコマンドの中で固定する

**Bash の作業ディレクトリは、ワークツリーへ `cd` した後でも共有の checkout へ戻っていることがある**（別のツールやバックグラウンドの起動を挟んだ後に観測した）。気づかないまま検証を走らせると、**未変更のコードに対する「型エラー 0・テスト通過」を報告する**ことになる（テストの件数が前回より減っていたことで気づいた例がある）。成功して見えるので、宛先の誤りは結果からは分からない。

**宛先は、前の呼び出しで `cd` したことに頼らず、そのコマンドの中で指す。**

| やること | 効く書き方 |
|---|---|
| git | `git -C <パス> <サブコマンド>` |
| 依存のインストール | `npm --prefix <パス> ci` |
| 型チェック | `<パス>/node_modules/.bin/tsc -b <パス>` |
| ユニットテスト | `<パス>/node_modules/.bin/vitest run --root <パス>` |
| dev サーバー・本番ビルド | PowerShell ツールで `Set-Location <パス>; npm run ...` |

- **`npm --prefix` は作業ディレクトリを変えない。** `package.json` は `<パス>` のものを読むが、そこから起動されるビルドツールやスクリプトは**呼び出し元の作業ディレクトリ**を基準に動く。dev サーバー・ビルドは `Set-Location` を使う（`vite --root <パス>` も通らなかった。vite 6 はルートを位置引数で取る）
- **`cd <パス> && git ...` のように `cd` を前に付けた複合コマンドは、許可設定に当たらない。** 許可パターンはコマンド文字列全体に対して照合されるので、`Bash(git push)` を許可していても `cd ... && git push` は確認待ちになる。`git -C <パス>` で指す（ワークツリー隔離セッションでは、`&&` で繋いだ複合コマンドがそもそも止められる。[`CLAUDE.md`](../../CLAUDE.md)「ワークツリーに入れないとき・入ったまま他を触れないとき」）
- どうしても宛先を固定できない形で走らせるなら、直前に `pwd` と `git rev-parse --abbrev-ref HEAD` を出して確かめる。**テストの件数が前回と違ったら、宛先を疑う**

## 応答が返らないコマンドは、呼ぶ前に打ち切り方を決める

ネットワーク越しのコマンド（リモートのバージョン管理・外部サービスの取得）は、**相手へ届かないとエラーも返さずに止まる**ことがある。

**止まってから手は打てない。** 同期実行中のコマンドは途中で止められないので、**呼ぶ前に決めておく**。

- **短いタイムアウトを付けて呼ぶ**（応答が無いことを、待ち続けずに失敗として受け取れる）
- または**バックグラウンドで起動して、後から結果を見に行く**

打ち切られたら、何を実行して止まったかをユーザーへ伝える。**黙ってもう一度叩かない**——届かない原因（接続・資格情報）はたいてい再実行では変わらない。

## リモートの Windows へ SSH で命令を渡すとき

**Windows の OpenSSH サーバーは、ログインシェルが Windows PowerShell 5.1 のことがある。** 手元の Bash の書き方のまま渡すと、向こうで構文の誤りになる。**構文の誤りは何も実行せずに終わる**ので、止めたつもりのサービスが動いたまま、ということが起きる。結果は必ず向こうに訊いて確かめる。

- **`&&` は PowerShell 5.1 では使えない**（「有効なステートメント区切りではありません」で落ちる）。`cmd.exe` で繋ぎたいなら、中身全体をシングルクォートで包んで `cmd.exe /c '...'` に渡す
- **`cmd.exe` の `set` は行末までを値に取る。** `set VAR=値 && 次` と書くと値の末尾に空白が混ざるので、`set VAR=値&& 次` と詰める
- **`cmd.exe` の中で終了コードを `& echo %ERRORLEVEL%` で受けない。** 行を読んだ時点で展開されるので常に 0 を出す。`&& echo RESULT-OK || echo RESULT-FAILED` で受ける
- **1 回の ssh に 1 つの命令なら、`-Command` で素直に通る。** `ssh <ホスト> "powershell -NoProfile -Command \"Stop-Service -Name <サービス名>; (Get-Service <サービス名>).Status\""` の形は通った。ここへ `Start-Sleep` や `-Filter \"…\"` を足すと引用が崩れ、構文の誤りで**何も実行されなかった**
- **`$_` や `"` を含む PowerShell は、ssh の引数に直接書かない。** 手元のシェルが `$_` を展開して消す

**複数行の PowerShell は、UTF-16LE を base64 にして `-EncodedCommand` で渡す**（`&&` も改行も素では通らない）。スクリプトは上記「スクリプトはファイルに書いてから実行する」のとおりファイルに書いてから符号化する。実際に通した形:

```bash
B64=$(python -c "import base64;print(base64.b64encode(open(r'<一時作業用のディレクトリ>/x.ps1',encoding='utf-8').read().encode('utf-16-le')).decode())")
timeout 500 ssh -o BatchMode=yes -o ConnectTimeout=8 <ホスト> "powershell -NoProfile -EncodedCommand $B64" 2>&1 | tr -d '\r' | grep -av "^\*\*\|CLIXML\|^<Objs\|_x000D_"
```

- `iconv -f UTF-8 -t UTF-16LE x.ps1 | base64 -w0` でも同じものが作れる
- `timeout` と `-o BatchMode=yes -o ConnectTimeout=8` は、届かないときに待ち続けないため（上記「応答が返らないコマンドは、呼ぶ前に打ち切り方を決める」）
- `grep -av` で捨てているのは、ssh が出す警告の行と PowerShell が混ぜる CLIXML。**`-a` が無いと「binary file matches」とだけ出て、中身が出ない**
- 別の形として、`.ps1` を scp で向こうへ送り、`powershell -NoProfile -ExecutionPolicy Bypass -File <向こうの絶対パス>.ps1` で走らせて、結果は向こうで `Out-File -Encoding utf8` に書いて scp で持ち帰る方法も通った

**手元で受け取った結果を Windows のプログラムで読むなら、Windows 形の絶対パスへ書く**（上記「Git Bash（Windows）で引数が書き換わる」の `/tmp`）。scp の宛先に空白を含むパスを書くときは、`"<ホスト>:/D:/<空白を含むパス>/<ファイル>"` のように全体を `"` で包む。

## PDF の原典を読むとき

**`WebFetch` が PDF を読めないと答えても、取得したファイルはツールの結果の保存先に残っている。**そこから `pdftotext`（poppler-utils。Git Bash から `/mingw64/bin/pdftotext` で呼べた Windows 環境がある）で全文を取り出せる。`Read` ツールの PDF 対応は、画像化の道具（`pdftoppm`）が無い環境では使えない。

```bash
pdftotext -enc UTF-8 "<保存された .pdf>" out.txt          # 読み順
pdftotext -layout -enc UTF-8 "<保存された .pdf>" out.txt   # 見た目のレイアウトを保つ
```

**2 つとも取る。** 読み順の抽出では表の列が分かれて整って見え、印字の上で行がずれているといった原典そのものの問題が再現できない（読み順では整合していた表が、レイアウト保持では行の位置がずれていた例がある）。引用の裏取り（鉤括弧で引いた文が原典に本当にあるか）にも使える。出力の置き場所は作業対象の外にする。

## 既存の Excel ブックを書き換えるとき

**ライブラリで保存すると、ライブラリが解釈できない要素が落ちる。** Python の `openpyxl` で開いて保存し直すと、**条件付き書式の一部が消える**ことがある（ブックによる）。**崩れは保存した時点では分からず、後で人が開いたときに気づく。**

- **書き込みは Excel 本体を操作して行う**（Windows なら COM 経由。Excel が入っていない環境ではこの方針が取れないので、壊れる可能性を承知で進めるかをユーザーに確認する）
- **`openpyxl` は読み取りだけに使う。** 読み取りでも、開いて保存し直さないこと
- 書き込む前に、**元のブックの写しを取る**。置き場所は作業対象の外
- **合計を計算するセルは、見た目が入力欄と同じことがある。** 色や枠では見分けられないので、どのセルが数式かを確かめてから書く
- **数式を別の行へ写すときは、相対参照が行に合わせてずれる方法を使う**（コピー貼り付け、オートフィル、範囲への一括代入など）。**セルごとに元の行の数式文字列（`=B5*C5`）をそのまま代入すると、参照は元の行を指したまま**になり、値は入っているように見える。**1 行試して、写した行が自分の行を参照しているかを確かめてから**本番に掛ける
- **保存したら開き直して確かめる。** 書き込みの成否は、書いた直後の戻り値では分からない

# コミットメッセージ・履歴を書き換える

`CLAUDE.md`「公開する前に個人情報が無いことを確かめる」から引く手順。

## まだ push していないコミットメッセージで止められたら

止められたのが**まだ push していない**コミットのメッセージなら、メッセージだけを書き換えて出し直せる（マージの形も木も変わらない）。どちらの形も、**main を戻す・履歴を書き換える前にユーザーの承認を取る**。`<元の語>` と `<置き換える語>` は実際の語に置き換える（`sed` の区切りの `/` や正規表現の記号を含むなら逃がす）。

**マージと版上げを済ませた後なら、main を戻さずにその場で書き換える**（衝突の解消も木もそのまま残るので、検証をやり直さずに済む。2026-10-13 に 21 コミットで約 3 分）。

```bash
# 書き換える前に、該当する行を洗い出す
for c in $(git rev-list origin/main..main); do git log -1 --format=%B $c | grep -n "<元の語>"; done
git rev-parse HEAD^{tree}   # main にいる状態で、書き換え前の木を控える
FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch -f --msg-filter 'sed -e "s/<元の語>/<置き換える語>/g"' --tag-name-filter cat -- origin/main..main
```

置き換える語が複数あるなら `-e "s/…/…/g"` を並べる。push の前に次の 3 つを確かめる。

- `git rev-parse HEAD^{tree}` が書き換え前と一致する
- 版のタグが注釈付きのまま残っている（`git cat-file -t v<版>` が `tag`）
- `npm run check-personal-info -- --range origin/main..main` が 0 件

**ブランチの段で直すなら**、main を版上げ前へ戻し（`git reset --hard origin/main`・`git tag -d v<版>`）、ブランチの範囲だけを書き換えてから、マージ・版上げをやり直す（2026-10-07 に 9 コミットで約 70 秒）。

```bash
FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch -f --msg-filter 'sed "s/<元の語>/<置き換える語>/g"' -- origin/main..ready/<type>/<name>
```

ここでも `git rev-parse <ブランチ>^{tree}` が書き換え前と一致することと、`npm run check-personal-info -- --range origin/main..<ブランチ>` が 0 件であることを確かめる。

**後始末**: `git update-ref -d refs/original/refs/heads/<ブランチ>` で書き換え前の控えを消す。書き換え前のコミットを指したまま残る `ready/*` などのブランチは、木が同じ書き換え後のコミットへ `git branch -f` で合わせてから `-d` で消す（消さないと、書き換え前のメッセージが ref として残る）。

**`--msg-filter` が直すのはコミットのメッセージだけ。** 注釈付きタグの本文は書き換わらないので、そこに入っていたら `git tag -a -f` で付け直す。ファイルの中身に入っていたら、ファイルを直すだけでは古いコミットに残る —— 範囲の各コミットから消すには `--index-filter` などでの書き換えが要るので、手を止めてユーザーへ諮る。そうならないよう、足したファイルはコミットの前に `npm run check-personal-info -- --text <ファイル>` に掛けておく。

## 履歴を書き換えて force push するとき

ユーザーが履歴の書き換え（`git filter-repo` 等）を決めたら、**手元の作業コピーではなく、新しく取った bare clone を起点にする。**

- **理由**: `git log @{u}..` が 0 件でも、手元がリモートより古くないことは保証されない。fetch していない作業コピーでは `@{u}` 自体が古いままなので、リモートが先行していても気づけない。手元を起点に書き換えて force push し、リモートにだけあったコミットを複数のリポジトリで巻き戻した例がある。手元に無い ref（取っていないタグ・他の端末で作ったブランチ）も取りこぼす
- 手順（実際にこの順で通した）:
  1. **作業の前に、対象の全リポジトリの bare clone をバックアップとして取る。** 巻き戻したときの唯一の復旧手段になる
  2. 書き換えは、新しく取った bare clone（`git clone --bare <リモートの URL>`）に対して行う。**取った時点の各 ref の SHA を控える。** `git filter-repo` は書き換えの後に `origin` を外すので、push 先の URL は明示する。push する ref はその clone の ref を列挙して明示し、`git push --force-with-lease=<ref>:<控えた SHA> <リモートの URL> <ref>...` の形で、取った後にリモートへ入ったコミットを巻き戻さないようにする（`--mirror` は手元専用のブランチまで公開するので使わない）。**force push の前に、push する ref の一覧をユーザーへ提示して承認を得る**
  3. push の後、各作業コピーを追従させる。**先に、未コミットの変更・リモートに無いコミット（手元の `git log` を、書き換え前に取ったバックアップと比べる）・stash・手元専用のブランチが無いかを確かめる。** 付け替えは下の箇条のとおり `git reset --keep` で行う（未コミットの変更とぶつかれば止まる）。**`--keep` も `--hard` も、付け替える前の手元のコミットは黙って外す** —— 手元にしか無いコミットを守るのは、この確認だけ
  4. 最後に**新しく clone し直して**、消したい値が消えたことを確かめる（作者とコミッターの欄も `git log --all --format='%an <%ae> / %cn <%ce>'` で、名前とアドレスの両方を見る）
- 手元専用のブランチも書き換えるなら、bare clone へ `git fetch <手元のリポジトリ> 'refs/heads/*:refs/heads/*' 'refs/tags/*:refs/tags/*'`（強制なし）で取り込み、`git filter-repo` を `--force` で走らせる
- 手元の付け替えは、作業ツリーのあるものは `git reset --keep <新>`、無いものは `git update-ref <ref> <新> <旧>`。**付け替える対象は `git for-each-ref` で `refs/heads` 以外も全部数える** —— 手で作った追跡用の ref が古い履歴を握ったまま残り、最後の検査で初めて気づいた例がある
- `--replace-text` は、表に書いた順ではなく**文字どおりの置き換えを全部当ててから正規表現を当てる**（別のリポジトリで踏んだ挙動。版によって変わりうるので、この節の手順 4 の確認で消し残しを見る）。片方がもう片方の部分文字列になる置き換え（長い番号とその一部の短い番号など）は、両方を正規表現にして順序を保つ
- 同じ入力の履歴に同じ mailmap を当てれば、出てくるコミットの SHA は再現する（作業コピー側を別に書き換えても、リモートと SHA が一致する）
- 長いパスを含むリポジトリは、作業ツリーへ取り出すとき（手順 4 で clone し直すときなど）に `git -c core.longpaths=true clone` でないと取り出せないことがある（Windows）
- 置き換えの表には消したい実際の値が入るので、表や実際に通したコマンドの控えはリポジトリの外（スクラッチの領域）に置く

# 開発の進め方

何段にも分かれる機能・不具合・作り直し・設定の変更に使う。1 行で答えられる事実の質問や、ほかに響かない小さな編集には使わない。

1. やり方を選ぶ前にリポジトリを調べる。既にある書き方を使い回し、消す・差し替える案のときは呼び出し元と設定を辿り、ライブラリの振る舞いが効くときは一次資料で確かめる。
2. 何段にも分かれる作業や設計に響く作業では、触るファイル・危険・確かめ方・利用者の判断が要る決めごとを書いた短い計画を作る。確かめた範囲と終わりの条件は守るものとして扱い、狭めるときは根拠を示して確認を取る。独立して調べられる作業には `code-explorer`・`implementation-planner`・`architect` を使う。
   - 案や選択肢に載せる数字・影響には、実測の値か `file:line` の根拠を添える。添えられないものは「未確認」と書き、確かめていない前提の上に選択肢を組まない。
   - 機能を落とす・制限する・取る範囲を狭める案（リクエストを減らすためのものも含む）は、落とさずに済む方法を調べてから出す。設計として正しい直し方を必ず含めて推し、触る範囲・競合・工数は推す理由にしない。
   - 課題を立てる前・判断を訊く前に、資材と会話の記録で既に決まっていないかを探す。決定を覆すなら、引用して「覆すか」として訊く。
   - 問い返しや答えの無い問いを了承として扱わない。利用者に見える判断を「意図的に外している」と書くなら承認した日付を添え、無ければ未決として残す。外す・狭める・後回しにする書き方も諮る。返事が決めるのは訊いた問いの範囲だけで、そこからリリース・配布・実機への書き込みといった別の段の承認を読まない。
   - 利用者に届く文言（画面・通知・エラー表示・読み上げ）を足す・変えるなら、実装の前に `docs/ui-wording-procedure.md` の手順で文面の実物を用意して諮る。文言を変えない選択肢も入れる。レビューの指摘から足す場合に限らない。
3. 確かめた要件を満たす最も小さい変更を実装する。狙った振る舞いと、関係する失敗の場合を示すテストを足すか直す。
4. 見合ったビルド・テスト・lint・静的検査・絞った再現を走らせる。利用者に見える動きが変わるときは、振る舞いの段でも安全な確かめをする。何を走らせ、何を走らせなかったか、その理由を書く。
   - 終了コード 0 だけで成功と決めない。成功は、終了コードが 0・エラーの印が無い・仕事をした印（件数・パス・値）がある、の 3 つが揃ったとき。「0 件」「見つからない」は、当たると分かっている対象へ同じ確かめを当ててから結論にする。パイプの後ろの終了コードを、前のコマンドのものと読まない。
5. 影響の大きい変更は、読むだけの `code-reviewer` にレビューを頼む。`adversarial-reviewer`・`documentation-reviewer`・`java-reviewer`・`verifier` は、その視点が当てはまるときだけ使う。直すべき指摘を直し、影響する道筋を確かめ直す。見合ったレビューが済んだら止め、終わりの無いレビューを始めずに残る危険を報告する。並べて走らせるのは、互いに独立した読むだけの作業に限る。
   - 指摘や不具合を直す前に、同じ誤り・同じ原因の箇所を対象全体で洗い（対になる関数、往復の逆向き、同じ前提を持つ経路）、まとめて直す。指摘された 1 行だけを直すと、残りは次の巡か、誰にも見つからないまま残る。
   - 1 つの作業が複数の段に分かれるなら、段ごとではなく、続けて実装したあと全段の変更へ 1 回レビューを掛ける（2026-10-21 ユーザー承認）。レビューは省かない。コミットは中身ごとに分け、分け方の確認は 1 回で取る。段の途中で止まるのは、利用者向けの文言を諮るときと、ユーザーの手が要る実測のときなど、他の決まりが求めるときだけ。
   - レビューの指摘に応えるために利用者向けの文言を足す・変えるときも、実装の前に文面の実物を示して諮る。「足さない」が選ばれたら既知の制約として扱い、その判断をコミットメッセージに残す。ただし CRITICAL の指摘は、文言以外の直し方で解消するか、範囲の拡大をユーザーへ諮る。表示の誤り・誤字・事実と違う固定の文言を正すのはバグの修正で、この確認は要らない。
6. 振る舞いや使い方が変わったら、利用者向けの文書・設定の説明・コメントを直す。

利用者が許していない限り、コミット・push・統合・公開・本番の依存の追加・外部への変更はしない。
